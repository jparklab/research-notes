# Interim report: control-plane-convergence-or-proliferation

**Locus question:** Are llm-d, AIBrix, NVIDIA Dynamo and KServe four competing choices or one converging design with four sponsors — and is its governance consolidating or forking?
**Flavor:** dialectical

## What the corpus already said

The width sweep's `engine-monoculture` cluster established that all four control planes sit *above* vLLM/SGLang rather than replacing them — "none of the control planes discussed below replace the engine... llm-d, AIBrix and Dynamo all launch vLLM or SGLang processes in pods and orchestrate around them" ([[llm-serving-on-kubernetes-llm-d-aibrix-dynamo-compared]]). The `gateway-governance-neutrality` cluster in the contradiction graph already identified the core tension precisely: side A treats the Gateway API Inference Extension (GIE) as a settled, SIG-governed standard; side B shows the reference EPP implementation was moved out of neutral `kubernetes-sigs` governance into the llm-d repo over an Istio maintainer's on-record objection, that Dynamo forked its own EPP, and that KAITO's migration PR to llm-d stalled and auto-closed. The consensus-claims file independently supports both "Kubernetes is the assumed substrate" (all four are K8s-native) and "the OSS layer originates as released internal systems" (AIBrix is ByteDance's internal system released outward). This locus's job is to resolve what the contradiction graph left open: whether this is genuine proliferation or whether the underlying engineering is one design wearing four logos.

## What the new sources say

I spent zero of the 9-source fetch budget: the pre-existing vault corpus (reached via `hyperresearch search`, not the `internal-llm-inference-stacks-7f0c90` tag alone, which undercounts it — confirmed per the run's caveat) already contains the primary documents this locus needs, including several that were not obviously indexed under the run's own tag. All sources below are primary (project docs, white papers, GitHub issues/PRs) rather than secondary commentary.

**llm-d's founding proposal** ([[llm-d-kubernetes-native-distributed-inference-at-scale-llm-d]], docs v0.7, `llm-d.ai/docs/0.7/proposals/llm-d`) is the single most load-bearing document for the layer-map question because it states, in llm-d's own words, how it differs from each of the other three:
- *Vs Dynamo*: "llm-d... Prefers to make the prefill/decode disaggregation decision within the scheduler to more precisely control placement... Uses RPC for disaggregation rather than an async queue in the Distributed Runtime... Prioritizes a strong operational boundary between in-memory prefix cache tiers and local or remote storage tiers rather than a unified memory API like the KV Block Manager."
- *Vs AIBrix*: "llm-d... Prefers to adapt serving to existing user infrastructure vs. providing an opinionated serving platform [and] Prioritizes standardizing Kubernetes upstream APIs in the Gateway ecosystem to drive alignment across many deployments."
- *Vs KServe*: "llm-d... Does not orchestrate inference workloads directly [and] Does not attempt to solve problems related to traditional ML serving or models that consume less than 1 accelerator" — llm-d supplies capabilities *into* KServe's CRD rather than competing with it.
- Non-Goals explicitly disclaim forking upstreams or controlling vLLM deployment configuration — llm-d defines itself as a thin, composable layer by design.

**KServe's own documentation confirms direct subsumption, not mere compatibility.** [[understanding-llminferenceservice-kserve]] states: "Built on the foundation of llm-d — a production-ready framework for scalable LLM serving — LLMInferenceService delivers enterprise-grade capabilities." This is not an integration claim; [[announcing-kserve-v017-production-ready-llm-serving-with-llminferenceservice-kse]] shows the LLMInferenceService controller "auto-creates" an InferencePool, InferenceModel, and literal "EPP (Endpoint Picker Pod)" citing the llm-d-inference-scheduler repo's plugin architecture directly, down to the exact `EndpointPickerConfig` plugin weights (`prefix-cache-scorer` weight 2.0, `load-aware-scorer` weight 1.0). [[best-of-both-worlds-cloud-native-ai-inference-at-scale-using-kserve-and-llm-d-ks]] gives KServe's own layer table: KServe owns lifecycle/scaling/governance and the OpenAI-compatible API surface; llm-d owns "cross-runtime routing and cache awareness"; vLLM executes. KServe is CNCF Incubating (joined Nov 2025); llm-d is CNCF Sandbox (accepted 12 March 2026, announced at KubeCon EU).

**AIBrix's own white paper** ([[aibrix-towards-scalable-cost-effective-large-2]], arXiv:2504.03648) confirms governance concentration directly from its author list: of 25 named authors, 24 are ByteDance-affiliated (two explicitly flagged as ByteDance interns), one is from DaoCloud. Its Related Works section makes the same "gap" argument llm-d makes about pre-2024 platforms — Knative/Istio are "not designed for GPU-based inference workloads" and KServe/RayServe "lack deep integration with LLM inference engines" — but AIBrix's own response is the opposite of llm-d's: it builds an integrated, opinionated platform (LoRA management, its own autoscaler, its own gateway/routing, and critically its own **Distributed KV Cache**) rather than a thin plug-in layer. The live repo ([[github-vllm-projectaibrix-cost-efficient-and-pluggable-infrastructure-components]]) confirms AIBrix lives under the `vllm-project` GitHub org — not CNCF, not its own foundation — though KubeCon talks (including a joint KubeCon EU 2025 keynote with Google's Clayton Coleman) show external validation beyond ByteDance alone.

**Dynamo's documentation confirms a genuinely distinct KV-routing design**, not a wrapper. [[router-design-nvidia-dynamo-documentation]] describes a from-scratch cost-function router (`cost = prefill_load_scale * adjusted_prefill_blocks + potential_decode_blocks + active_request_blocks`) with its own prefix-tree indexer and its own event transport (NATS Core or ZMQ) — architecturally parallel to, but not derived from, llm-d's EPP scorer/filter plugins or AIBrix's distributed cache. [[gateway-api-inference-extension-gaie-nvidia-dynamo-documentation]] confirms Dynamo also *optionally* plugs into the shared GIE/EPP pattern via its own forked EPP, verified against two gateways (agentgateway, Istio) — so Dynamo runs two parallel routing paths: its native Frontend router (no gateway) and a GIE-compliant forked EPP (with a gateway). [[scale-and-serve-generative-ai-nvidia-dynamo]] and the live repo README confirm Dynamo's "KV Cache Manager" integrates LMCache specifically for the storage/offload tier (CPU/SSD/network), while its headline performance numbers ("7x MoE throughput... measured only on NVIDIA GB200 NVL72 vs B200," also "750x on GB300 via InferenceX," "2x faster TTFT via Baseten blog") are sourced from vendor/third-party blogs on NVIDIA's own newest hardware, not Dynamo's own controlled benchmark harness — consistent with the scope constraint that these claims are hardware-tied and their *provenance*, not their hardware merit, is the relevant fact here.

**The LMCache paper's shared-subsystem claim is real but narrower than it first appears.** The paper states directly: "where LMCACHE is used in vLLM production stack, Dynamo, llm-d, and KServe" ([[lmcache-an-efficient-kv-cache-layer-for-enterprise-scale-llm-inference]]) — and AIBrix is conspicuously absent from that sentence, consistent with AIBrix's whitepaper describing its own, separate Distributed KV Cache rather than adopting LMCache. But a live GitHub RFC ([[rfc-lmcache-mp-server-nvidia-dynamo-integration-issue-4352-lmcachelmcache]], opened 30 Jul 2026, unresolved as of early Aug 2026) shows the LMCache-Dynamo integration is incomplete specifically at the *routing-credit* layer: LMCache's offloaded blocks are not yet correctly attributed to the right worker in Dynamo's KV-aware routing decision, because "the indexer registry currently rejects a second registration for an existing worker_id." Two proposals are under live debate; proposal 2 (register LMCache as a pull-queried "shared cache") is endorsed by an LMCache maintainer but not confirmed merged. This means: LMCache is shared as a *storage/offload substrate* across three of the four (not AIBrix), but the *routing decision logic that reads that cache* is not shared — it is re-implemented per stack (llm-d's EPP scorer, Dynamo's cost-function router, AIBrix's own cache-aware scheduler).

**The governance-neutrality fight is documented with named participants and a real outcome, not a hypothetical risk.** [[proposal-to-move-epp-and-bbr-to-the-llm-d-repo-issue-2430-kubernetes-sigsgateway]] (GitHub issue #2430, opened 26 Feb 2026 by Google's `ahg-g`, closed completed 13 May 2026) documents Istio maintainer `keithmattix` (Microsoft) objecting on the record: "What LLM-D doesn't provide that GAIE did is neutral governance. Other inference frameworks that want to create an EPP would be faced with starting from scratch or importing a competitor's (i.e. llm-d's) EPP" — naming Dynamo and Ray/KubeRay explicitly as frameworks with a stake. A third commenter flags, mid-thread, that Dynamo had already vendored its own EPP fork rather than wait. llm-d maintainer `kfswain` counters that llm-d itself is "soon to be in the same foundation as K8s" (anticipating the CNCF Sandbox donation) and that a lightweight reference EPP remains for conformance. The move happened anyway; a late comment flags an unresolved Envoy Gateway regression. Separately, [[docs-add-design-proposal-for-migrating-epp-to-llm-d-inference-scheduler-by-andyz]] (KAITO PR #1979, Microsoft engineer `andyzhangx`, opened 21 Apr 2026) shows the practical consequence: Microsoft tried to migrate its own KAITO project's default EPP to llm-d's as a "drop-in replacement," a llm-d maintainer warned mid-thread that the merged EPP "may remove the plugin extensibility model" other vendors rely on, and the PR went stale and auto-closed unmerged 15 Sept 2026 — the consolidation that issue #2430 authorized did not actually land in KAITO.

**One governance data point cuts the other way, and is worth naming precisely so the picture isn't one-sided.** The inference-adjacent gateway layer immediately above EPP — Envoy AI Gateway, renamed "Agent Router" (Sept 2026) — moved *into* a neutral multi-vendor foundation (AAIF) rather than being captured by one vendor: "same code, same maintainers, same APIs" ([[blog-agent-router]]), with maintainers from Bloomberg, Tetrate, Tencent, Nutanix and Google and "no single-company control" ([[project-proposal-agent-router-previously-envoy-ai-gateway-issue-18-aaifproject-p]]). So in the same 2026 window, one adjacent layer (EPP reference implementation) moved *out* of neutral governance into a project repo, while another adjacent layer (the gateway product around it) moved *into* a neutral multi-vendor foundation. Governance trajectory is not monotonic across this stack; it has to be assessed layer by layer.

## Evidence synthesis

The four projects are not four independent inventions of the same thing, and they are not one thing wearing four badges either. The accurate description is layered: there is real, deep convergence at two specific layers, and real, documented divergence at two other specific layers, and the dialectic in the prompt collapses once those layers are separated.

**Where convergence is real and structural:** (1) The substrate — Kubernetes, vLLM/SGLang as the engine, the vLLM KV-connector API as the plumbing — is identical across all four; none of them touches the engine. (2) The upward-facing API contract — Gateway API, InferencePool/InferenceModel CRDs, the EPP protocol itself (filter→score→pick, with a config of weighted scorer plugins) — is shared infrastructure that KServe adopts wholesale from llm-d, that Dynamo voluntarily implements a second, parallel path for, and that the comparison literature calls "the routing contract... becoming portable even though the control planes are not" ([[llm-serving-on-kubernetes-llm-d-aibrix-dynamo-compared]]). (3) The KV-cache *storage/offload substrate* — LMCache — is shared by three of four (vLLM production stack, Dynamo, llm-d, and via llm-d, KServe), per the LMCache paper's own direct claim.

**Where divergence is real and persistent:** (1) The KV-cache *routing decision* — the algorithm that decides which replica a request lands on given cache state — is not shared. llm-d's EPP runs a weighted scorer/filter pipeline; Dynamo runs an independently-derived cost function over its own NATS/ZMQ event plane; AIBrix runs its own distributed-cache-aware scheduler that the LMCache paper does not even list as an adopter. Sharing LMCache as a cache does not mean sharing a router — the live, unresolved RFC #4352 is direct proof this seam is still being engineered, not finished. (2) Governance is explicitly and verifiably not consolidating at the layer that matters most for lock-in — the EPP reference implementation. It moved from neutral `kubernetes-sigs` ownership into llm-d's own repo over a named, on-the-record objection from a competing maintainer, Dynamo responded by forking rather than depending on the shared code, and the one documented attempt by a non-Red-Hat-aligned project (Microsoft's KAITO) to adopt llm-d's EPP as the shared implementation stalled and died unmerged. (3) Sponsorship and foundation status differ in ways that are not cosmetic: llm-d is CNCF Sandbox (multi-vendor, Red Hat/Google/IBM/CoreWeave/NVIDIA-founded), KServe is CNCF Incubating (older, broader, multi-vendor), AIBrix is ByteDance's internal system in a vendor-controlled GitHub org with 24-of-25 paper authors from one company, and Dynamo is NVIDIA's own open-core project bundled with paid NIM/Enterprise tiers and benchmarked only on NVIDIA's newest hardware.

**What this means for a platform team choosing today.** A team adopting KServe's LLMInferenceService is, by KServe's own documentation, adopting llm-d's EPP and scheduler verbatim — this is not really four choices, it is one design (llm-d's) with a second, more opinionated front door (KServe) bolted on top, and llm-d's own founding Alternatives section says this explicitly. A team adopting AIBrix is choosing ByteDance's internally-built, internally-dominated opinionated platform, with its own cache implementation that the shared storage substrate (LMCache) does not cover and that the CNCF-neutral EPP ecosystem does not integrate with by design — the strongest claim that AIBrix is a genuine fourth design rather than a wrapper. A team adopting Dynamo is choosing NVIDIA's own routing algorithm and its own benchmark-hardware story, with an EPP compatibility path that exists but is forked, not shared, and whose newest cache-attribution feature is still mid-RFC. Only llm-d itself is "the design" in the sense that the others either subsume it (KServe), fork its API surface while keeping their own routing brain (Dynamo), or decline to depend on it at all (AIBrix).

### Position A: convergence

The strongest version of this case: every serious new entrant in 2025-2026 standardized on the same substrate (K8s + vLLM/SGLang + vLLM KV-connector API) and the same upward API contract (Gateway API Inference Extension, InferencePool/EPP). KServe's wholesale adoption of llm-d's EPP is not a loose integration — it is literally the same controller, the same CRD shapes, the same plugin config syntax. Three of the four share the identical KV-cache storage substrate (LMCache). Even Dynamo, the most NVIDIA-proprietary of the four, chose to implement a second, standards-compliant EPP path rather than ignore GIE entirely, and even the layer above EPP (the gateway itself, Agent Router) just consolidated into a neutral multi-vendor foundation rather than fragmenting. On this reading, "four choices" is a surface-level illusion; underneath, there is one converging stack and the only real decision is how opinionated a front door you want on top of it.

### Position B: proliferation

The strongest version of the opposing case: the layer that actually determines lock-in — who decides how a request is routed, and whose governance controls that logic — is not converging, it is forking in real time, with primary-source documentation of each fork. The reference EPP was moved out of neutral Kubernetes governance into a single vendor-coalition's repo over the explicit, on-record objection of a competing maintainer who named the exact risk (a competitor's framework now has to "start from scratch or import a competitor's EPP"). NVIDIA Dynamo did exactly that — forked rather than imported. Microsoft tried the alternative (importing) through KAITO and it died unmerged after a llm-d maintainer warned the merge might remove the very extensibility point other vendors depend on. AIBrix never even entered this negotiation — it lives in a different GitHub org, under different governance, with its own cache implementation that none of the others' papers list as shared. Four different CNCF/foundation statuses (Sandbox, Incubating, vendor-org, vendor-owned-open-core) are not an accident of paperwork; they are four different answers to "who can veto a roadmap decision," and that is the actual question a platform team is answering when it picks one of these.

## Committed position

This is convergence at the substrate and API-contract layers and proliferation at the routing-logic and governance layers, and the second fact is the one that should actually drive a platform team's decision, because it is the layer where switching cost and vendor leverage live. The shared substrate (K8s, vLLM, LMCache, the InferencePool/EPP CRD shape) means a team can move its *model-serving* workload between these four with moderate friction — the APIs genuinely rhyme. But the shared substrate does not mean a team is routing-logic-neutral or governance-neutral: choosing KServe is choosing to depend on llm-d's EPP and Red-Hat-coalition roadmap decisions (documented: the EPP's plugin extensibility itself may be stripped as llm-d's own implementation consolidates, per the KAITO-PR maintainer's own warning); choosing Dynamo is choosing NVIDIA's roadmap, NVIDIA's benchmark hardware, and a forked EPP that will drift from upstream GIE releases at NVIDIA's pace, not the community's; choosing AIBrix is choosing ByteDance's roadmap and a cache implementation with no path into the shared LMCache ecosystem documented anywhere in this corpus. "Four sponsors, one converging design" is the wrong frame because it implies the sponsor choice is nearly costless; the GitHub-issue record (#2430, the KAITO PR, the Dynamo fork) shows sponsor choice determines who can change the routing algorithm under you, and that has already happened once (the EPP governance move) with a documented regression (the unresolved Envoy Gateway issue) and one failed attempt to reverse it (KAITO).

- **Position:** A platform team choosing among llm-d/KServe, AIBrix, and Dynamo today is choosing a sponsor and its governance/roadmap control more than it is choosing a technically distinct design, because the engine, the storage substrate, and the API contract are already shared or convergent — but it should weight that choice heavily, because the one layer that still forks (KV-routing logic and its governance) is exactly the layer most expensive to migrate off later, and the record shows the Red Hat-led coalition (llm-d) has both the leverage to move that layer's governance (the #2430 move) and a maintainer-acknowledged willingness to reduce pluggability as it consolidates (the KAITO-PR warning).
- **Confidence:** medium-high. The convergence claims (shared substrate, shared API contract, KServe-on-llm-d) rest on unambiguous first-party documentation from both sides (KServe's own docs, llm-d's own founding proposal) — high confidence there. The "proliferation at the routing layer is the one that matters for lock-in" interpretive claim is my synthesis across primary sources that don't themselves state this framing explicitly — medium confidence, because it depends on how much weight a given adopter places on routing-algorithm portability versus overall operational cost, which this evidence doesn't quantify.
- **Boundary conditions:** This holds for platform teams choosing a Kubernetes-native control plane specifically (i.e., teams already committed to K8s as substrate, which the consensus-claims file says is near-universal for this population). It does not speak to teams running a single vLLM instance behind a plain K8s Service with no control plane at all — the adoption heuristic in [[llm-serving-on-kubernetes-llm-d-aibrix-dynamo-compared]] suggests that is still the default for teams without multiple SLO tiers or multi-model pools, and the convergence/proliferation question is moot for them.
- **What would change this position:** (a) If the LMCache-Dynamo RFC #4352 resolves and ships, and if a later source shows Dynamo's own cost-function router is deprecated in favor of a shared scoring library, that would push the picture further toward convergence even at the routing layer. (b) If a future snapshot shows the llm-d EPP's plugin extensibility was NOT stripped (contradicting the KAITO-PR maintainer's warning) and multiple non-Red-Hat-aligned projects (KAITO retry, Ray/KubeRay, others) successfully adopted llm-d's EPP without maintainer friction, that would weaken the "sponsor risk" framing substantially. (c) If AIBrix is confirmed to have adopted LMCache or joined CNCF in a later snapshot, the "AIBrix is the one genuinely divergent design" claim would need softening.
- **Evidence weight:** Convergence claims: 4 first-party primary sources (llm-d founding proposal, KServe docs x2, LMCache paper) agree without contradiction. Proliferation claims: 3 first-party primary sources with named individuals and dated, resolved outcomes (GitHub issue #2430, KAITO PR #1979, AIBrix's own author list and GitHub org) — no source in the corpus disputes these facts; the only counter-evidence is the Agent Router/AAIF governance consolidation, which is a different layer (gateway product, not EPP reference implementation) and does not contradict the EPP-specific finding.

## Open questions

- Whether the LMCache-Dynamo routing-credit RFC (#4352) has resolved since early August 2026 — this would sharpen or soften the "shared substrate but not shared routing logic" claim. Worth a follow-up GitHub check closer to report finalization.
- Whether AIBrix has any roadmap statement about CNCF submission or governance broadening beyond ByteDance — none found in this corpus; absence noted rather than inferred.
- Whether llm-d's EPP plugin-extensibility removal (flagged as a risk by a llm-d maintainer in the KAITO PR thread) has actually happened in a subsequent llm-d release — this is the single most decision-relevant unresolved fact for the lock-in argument and I could not find a later primary source confirming or denying it within budget.
- No new sources were fetched for this locus (0 of 9 used) because the existing vault corpus, found via broad `hyperresearch search` rather than tag-filtering, already contained primary-source coverage sufficient to resolve the dialectic. If the orchestrator wants independent verification of the "EPP plugin extensibility" open question above, that is the highest-value remaining fetch.
