# Interim report: approximate-vs-precise-index

**Locus question:** Is the EPP's self-tracked approximate prefix index good enough for production routing, or is the event-driven precise KV index (with real engine eviction state) required, and which is llm-d's actual default today? Also: does the precise path work with SGLang/TensorRT-LLM KV events in practice, and what must match between router tokenization/block keys and the engine (block size, hash algorithm/seed, render endpoint)?

**Flavor:** dialectical

## What the corpus already said

The width sweep had already flagged this as unresolved: the contradiction graph's `approximate-vs-precise-index` cluster frames Side A ("approximate is lightweight, needs no engine integration, and is the default") against Side B ("approximate diverges from real state on eviction; precise gives exact state and measurably better results"), noting "the only head-to-head number (~9.97% precise+P2P vs calibrated approximate) bundles P2P" and that neither side has a routing-only benchmark isolating the two index types ([[prefix-cache-aware-routing-llm-d]], [[prefix-cache-aware-routing-llm-d-2]], [[kv-cache-indexer-llm-d]], [[precise-prefix-cache-routing-llm-d]], [[configuring-the-endpoint-picker-via-configuration-yaml-file-kubernetes-gateway-a]]). [[request-scheduler-llm-d]] establishes that both implementations are wired into the *same* `prefix-cache-scorer` scoring plugin, selectable via which DataProducer feeds it (`approx-prefix-cache-producer` vs `precise-prefix-cache-producer`) — this is a config choice, not a fork of the scoring logic.

## What the new sources say

**[[llm-d-kv-cachedocsarchitecturemd-at-main-llm-dllm-d-kv-cache-github]]** (llm-d-kv-cache `docs/architecture.md`, commit 1d8e62e, May 2026) is the single most load-bearing new source. It resolves the "hash algorithm/seed parity" half of the locus, and the headline answer overturns the plausible-sounding assumption that the router must replicate vLLM's own hash function bit-for-bit. The doc describes a **dual-key design**: "the indexer cannot derive a 'request key' ... from an 'engine key' ... or vice versa — the two hash spaces are independent." The router computes its own **request key** as a chained **FNV-64a hash over CBOR(parentHash, tokenChunk, extra)**, default block size 16, seeded by a configurable `hashSeed` + model name — independent of whatever hash algorithm the engine itself uses internally (the **engine key**, e.g. vLLM's `sha256`/`sha256_cbor`/`xxhash`, configured via `--prefix-caching-hash-algo`). The bridge between the two hash spaces is built at ingestion time: `BlockStored` events carry *both* the engine key and the raw token chunk, so the router computes its own request key from those tokens and records an `engine_key → request_key` mapping; `BlockRemoved` events carry only the engine key and use that map to find and evict the corresponding request-key entry.

There is a genuine internal-documentation tension worth flagging, though: the `kvblock.TokenProcessorConfig.HashSeed` godoc (found via the `kvblock` package page) says verbatim that `HashSeed` "is used to prefix initial hash chunks, similarly to vLLM's NONE_HASH. This should be aligned with vLLM's `PYTHONHASHSEED` environment variable. The system's deployer is responsible for aligning the vLLM deployments with the same seed value." That reads as a partial contradiction of architecture.md's "does not require alignment with any engine-side hash seed" framing — my best read is that only the *placeholder* value used for a block's absent parent hash (the analogue of vLLM's `NONE_HASH` sentinel) has any cross-system significance, not the router's full chained-hash computation, but the corpus does not resolve this cleanly. Treat "no hash-algorithm parity needed" as correct for the bulk of the mechanism (block content hashing) but flag the `HashSeed`/`NONE_HASH` sentinel specifically as an unresolved edge case an operator should verify against current code, not just docs.

**[[kvblock-package-githubcomllm-dllm-d-routerpkgkvcachekvblock-go-packages]]** (pkg.go.dev, v0.10.0) confirms the dual-key split at the type-signature level: `Index.Add(ctx, engineKeys, requestKeys []BlockHash, entries []PodEntry)` and `GetRequestKey(ctx, engineKey) (BlockHash, error)` both take engine keys and request keys as distinct parameters — the bridge is a first-class part of the index API, not an implementation detail.

What **does** have to match, per the same architecture doc and the deployment guide (**[[llm-dguidesprecise-prefix-cache-routingreadmemd-at-main-llm-dllm-d-github]]**): (1) **block size** — the producer's `tokenProcessorConfig.blockSizeTokens` must equal the engine's chunking boundary (vLLM `--block-size`, SGLang `--page-size`; the reference guide sets both to 64), because block chaining only aligns if the two sides cut the same token sequence into the same-sized pieces; and (2) **tokenizer/model identity** — the `token-producer`'s `modelName` must match what the render endpoint tokenizes with, and the guide notes a mismatch "is rejected outright rather than silently scoring against the wrong tokenizer," because the router's request key is computed from token IDs that must be byte-identical to what the engine itself tokenized.

**[[vllmvllmdistributedkv_eventspy-at-main-vllm-projectvllm-github]]** (vLLM `kv_events.py`, main, Sep 2026) is the vLLM-side ground truth for the event/replay mechanics: `BlockStored`/`BlockRemoved` batched into `KVEventBatch`, msgpack-encoded, published over a ZMQ PUB socket with a bind-vs-connect heuristic (binds on wildcard/`ipc://`/`inproc://` addresses, else connects out as a client) — directly relevant for non-Kubernetes topologies where a pod can't accept inbound connections. A `replay_endpoint` (ZMQ ROUTER, llm-d default port 5559) replays up to 10,000 past `(seq, payload)` pairs on request, letting a reconnecting router backfill its index without waiting on live traffic. Publish is documented as "at-least-once delivery and monotonic ordering," fire-and-forget from a background thread.

**[[automatic-prefix-caching-vllm]]** adds a wrinkle worth flagging even though the dual-key design defuses it as a strict blocking requirement: vLLM's *default* hash algorithm (`sha256`) "uses Python's pickle for serialization. Hashes may not be reproducible across different Python or vLLM versions" — only `sha256_cbor` is documented as "reproducible, cross-language compatible." Since the router never needs to reproduce the engine's hash (dual-key design), this doesn't block precise routing today, but it does mean the *engine key* itself is not guaranteed stable across a vLLM version bump — relevant to index-recovery correctness, which another investigator's locus covers in more depth.

**Engine compatibility.** **[[kvevents-package-githubcomllm-dllm-d-routerpkgkvevents-go-packages]]** shows the router's `EngineType` config field accepts exactly two values today: `"vllm"` or `"sglang"` (default vllm) — i.e., there are only two shipped `EngineAdapter` implementations, confirmed again in architecture.md, which names only `VLLMAdapter` and `SGLangAdapter` and never mentions TensorRT-LLM. This matters because **[[precise-prefix-cache-routing-llm-d]]** (llm-d.ai architecture docs) asserts "vLLM, SGLang and NVIDIA TensorRT-LLM publish every cache change as an event," implying three-way support. I fetched primary sources for the other two engines, plus a second SGLang file and a TensorRT-LLM PR, to check this claim directly:

- **SGLang**: **[[sglangpythonsglangsrtmem_cacheeventspy-at-main-sgl-projectsglang-github]]** (`sglang/srt/mem_cache/events.py`, commit 0b415fa, Sep 12 2026) and **[[sglangpythonsglangsrtdisaggregationkv_eventspy-at-main-sgl-projectsglang-github]]** (`sglang/srt/disaggregation/kv_events.py`, the wire-format module the first file imports from) together confirm SGLang natively emits the *same* event vocabulary — `BlockStored`/`BlockRemoved`/`AllBlocksCleared` msgspec structs, `ZmqEventPublisher` with PUB/ROUTER replay, driven by a `--kv-events-config` CLI flag and discoverable via `/server_info`'s `kv_events` block. Its own docstring names Dynamo, not llm-d, as the example consumer: "consumed by KV-aware routers (**e.g. dynamo**)." Critically, `BlockStored` has **no `extra_keys` field at all** — the base struct is `block_hashes`, `parent_block_hash`, `token_ids`, `block_size`, `lora_id`, `medium`. Multimodal/salt differentiation instead goes through a *separate* subtype, `BlockStoredWithMetadata` (carrying `BlockStoredMetadata.cache_salt`), which is **deliberately excluded from the tagged union** specifically so that legacy typed consumers decoding the base `BlockStored` tag silently ignore the trailing metadata rather than erroring. That is a *protocol design choice for backward compatibility*, not a temporary omission that will "resolve itself" as SGLang code ages — an llm-d `SGLangAdapter` needs an explicit code path for the `WithMetadata` variant to ever see `cache_salt`, and nothing in the corpus shows llm-d has added one. This directly confirms and sharpens the corpus's known claim (from **[[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcachere]]**) that "SGLang KV-events currently omit `extra_keys`, so salted SGLang requests are precise-cache misses" — the failure mode remains a safe miss (fewer cache hits, not wrong-pod routing), but it is a standing, structurally-motivated gap rather than a closing one.
- **TensorRT-LLM**: this is where new evidence materially changed my read from an earlier pass over just the disagg-serving.md doc. **[[trtllm-15331feat-improve-kv-event-publish-performance-via-streamingevent-by-tanm]]** — NVIDIA/TensorRT-LLM PR #17023, **merged into main Sep 10, 2026** (commit `05293ce`) — adds a `StreamingKVCacheEventManager` + `ZmqEventPublisher` that publishes `BlockStored`/`BlockRemoved`/`AllBlocksCleared` msgspec structs over a ZMQ PUB socket, msgpack-encoded, 3-frame (topic/seq/payload), with an optional ROUTER replay socket — structurally the same event vocabulary and transport as vLLM and SGLang. The PR's own motivation names Dynamo, not llm-d, as the target consumer: "External KV-cache-aware routers (e.g. Dynamo) subscribe to a stream of block stored/removed events to route requests to the engine that already holds a prefix." So the llm-d.ai claim that TensorRT-LLM "publishes every cache change as an event" is **technically accurate about TensorRT-LLM's own capability** as of Sep 10, 2026 — but the feature is explicitly flagged `prototype`, off by default, restricted to the KV-cache-manager V2 (PyTorch) backend, excluded for draft models and KV-size estimation, and incompatible with pipeline/context parallelism; the older buffered/pull path (`LLM.get_kv_cache_events()`) remains the default. Block hashes reuse "the low 64 bits of the radix block key" — a third, independent hashing scheme from both vLLM's and SGLang's, which is fine under the dual-key design but underscores that all three engines hash differently. **The gap for llm-d is entirely on the consumption side**: no `TRTLLMAdapter` exists in `kvevents`, architecture.md lists only `VLLMAdapter`/`SGLangAdapter`, and the deployment guide's backend directories still cover only `vllm`/`sglang`. TensorRT-LLM readiness should now be read as "engine-side plumbing exists (prototype-grade) but llm-d has not built a consumer for it" rather than "TensorRT-LLM doesn't support this at all," which is a meaningfully different — and more optimistic about near-term feasibility — claim than I could support from the architecture doc alone.

**Untangling the 9.97% number.** **[[pull-dont-recompute-peer-to-peer-kv-cache-sharing-in-llm-d-llm-d]]** is the actual source behind the contradiction graph's "9.97%" figure, and reading it directly shows the figure does *not* isolate precise vs. approximate routing. The exact quote: "P2P improved successful throughput by 4.6% with approximate routing and 9.7–11.1% with precise routing (average +9.6% successful throughput ... across 3 repeats)" on GLM-5.2-FP8, 32×H200, P/D-disaggregated, concurrency 64. This measures **P2P's incremental lift on top of each routing mode** (P2P-on vs. P2P-off, holding the index type fixed) — not precise-alone vs. approximate-alone throughput. The corpus's framing ("Precise routing plus P2P improved successful throughput 9.97%... over calibrated approximate routing") conflates a within-mode P2P ablation with a cross-mode index comparison. The only indirect signal here is that P2P's lift is roughly twice as large under precise routing (9.7–11.1%) as under approximate (4.6%) on the identical workload — plausibly because the precise index gives P2P's source-selection logic exact fleet-wide block residency to work from, so it finds better P2P-sharing opportunities. That's a real, if second-order, data point favoring precise, but it is not the "precise beats approximate by ~10%" headline the graph implies. Separately, the guide's own official benchmark reports (`vllm-qwen3-32b-h100.md`, `sglang-qwen3-32b-h100.md`, referenced from **[[llm-dguidesprecise-prefix-cache-routingreadmemd-at-main-llm-dllm-d-github]]**) compare precise routing against **plain round-robin Kubernetes Service** load balancing, not against approximate routing. No source in the corpus (old or new) contains a controlled, apples-to-apples precise-vs-approximate routing benchmark.

**Default status.** **[[configuring-the-endpoint-picker-via-configuration-yaml-file-kubernetes-gateway-a]]**, the upstream Gateway API Inference Extension config reference that the llm-d Router's EPP is built on, ships a `prefix-cache-scorer` with defaults (`blockSize: 64`, `maxPrefixBlocksToMatch: 256`, `lruCapacityPerServer: 31250`) that require zero extra infrastructure to run — this is the approximate-style, self-computed-hash scorer baked into the reference EPP. Precise routing, by contrast, is documented across the corpus as its own separate "well-lit path" (**[[precise-prefix-cache-routing-llm-d]]**, **[[llm-dguidesprecise-prefix-cache-routingreadmemd-at-main-llm-dllm-d-github]]**) with a dedicated deployment guide, a render Service, and (in the reference topology) 8×2-GPU replicas — i.e., it is opt-in additional infrastructure layered on top of the baseline, not what ships by default. I could not independently verify the contradiction graph's claim that "precise... is intended to become the default in a future release" against primary text in any note I read; treat that specific claim as unconfirmed roadmap chatter, not documented fact.

## Evidence synthesis

Mechanically, the two paths differ exactly as the llm-d.ai comparison table states, and the new sources let me be precise about *why* each pro/con holds. Approximate routing is genuinely infrastructure-free: no tokenizer, no ZMQ, no render endpoint — it is the built-in scorer that ships with the upstream Gateway API Inference Extension EPP, hashing an *approximated* token stream (character-to-token ratio) into fixed blocks and tracking an EPP-local, self-reported "I think I routed this prefix here" index that is never confirmed against reality. Its documented failure mode — divergence under real eviction — is not hypothetical; it follows directly from the design, since nothing in the approximate path ever hears from the engine about what actually got evicted.

Precise routing closes exactly that gap via the event-driven KVEvents pipeline, and the dual-key design is the single most important mechanical fact this investigation surfaced: the router's block-key computation does **not** need to bit-match the engine's own internal hashing scheme (a plausible but wrong worry, given vLLM's own hash algorithm is configurable and its default is not even reproducible across vLLM/Python versions) — with the caveat that a `HashSeed`/`PYTHONHASHSEED` alignment note in the router's own godoc creates some internal-documentation tension around the parent-hash sentinel value specifically. What actually needs to match across router and engine, unambiguously, is block size and tokenizer/model identity, both enforced by config validation. This substantially lowers the deployment-fragility bar for precise routing relative to what "hash algorithm parity" would suggest — the real risk surface is event-schema coverage gaps (SGLang's deliberately-separate salt/metadata tag, TensorRT-LLM's missing consumer) rather than cryptographic hash mismatches.

On engine coverage, the marketing framing of "three engines supported" does not survive contact with the router's own code, though the picture is more nuanced than a simple "vLLM only." vLLM is the reference implementation with full support (render endpoint, replay buffer, configurable hash algo). SGLang is genuinely wired in — same event vocabulary, dedicated render-pool workaround for the missing vLLM-style render endpoint — but carries a structurally-motivated (not merely transitional) gap: cache-salted/multimodal blocks travel in a wire tag (`BlockStoredWithMetadata`) that a naive consumer silently ignores, and SGLang's own code names Dynamo, not llm-d, as its primary consumer. TensorRT-LLM's situation flipped materially between my first and second reads: NVIDIA merged a real, schema-compatible streaming KV-event publisher on Sep 10, 2026 (prototype-flagged, off by default, PyTorch-backend-only) — so the engine-side capability the llm-d.ai doc claims now genuinely exists — but llm-d has built no `TRTLLMAdapter` to consume it, so end-to-end interoperability remains unevidenced in the corpus. The honest framing is: vLLM works today; SGLang works with a known correctness caveat; TensorRT-LLM's engine-side building block exists but llm-d's router-side integration does not, as of this corpus snapshot.

On the empirical question of whether precise routing is worth its cost, the corpus genuinely does not contain the benchmark that would settle it. The only number offered as head-to-head evidence is confounded with P2P cache sharing and measures a different comparison than the one advertised. The strongest *indirect* argument for precise is architectural convergence rather than a benchmark: NVIDIA Dynamo's engineering team went through six iterations of indexer design specifically to reach an event-driven, engine-eviction-aware index (**[[flash-indexer-a-story-of-inter-galactic-kv-routing-nvidia-dynamo-documentation]]**) and explicitly rejected inference-based approaches because "eviction policies are opaque and cannot be inferred from request/response cycles alone" — the same argument llm-d's own docs make for precise over approximate. Two independently-engineered, architecturally similar systems converging on the same design for the same stated reason is meaningful evidence, even without a shared benchmark. It is also notable that both SGLang and (now) TensorRT-LLM built their KV-event publishers with Dynamo named as the reference consumer, not llm-d — precise/event-driven KV-cache eventing is becoming a genuine cross-project standard, and llm-d's own KVEvents schema is closely aligned with it, but llm-d is currently behind the engine side of that ecosystem on the consumption/adapter side for two of three engines.

## Committed position

Precise (event-driven) indexing is the mechanically correct design and the direction the whole ecosystem is converging on — the dual-key bridge, replay-buffer recovery, speculative indexing, native P/D block identification, and now independent TensorRT-LLM and SGLang engine-side investment in the same event vocabulary all point the same direction — but it is not llm-d's default today, is not uniformly production-ready across engines, and the corpus's single quantitative "precise beats approximate" number does not actually show that: it shows P2P's benefit is larger under precise routing, not that precise beats approximate head-to-head. The practical recommendation splits by engine and by failure mode: for vLLM fleets under real memory pressure, multimodal/LoRA workloads, or P/D disaggregation, precise routing's benefit is a design-level near-certainty even without a controlled benchmark, because the approximate path's blind spot (unconfirmed eviction state) is exactly the failure mode those workloads trigger; for homogeneous, low-eviction-pressure, single-tenant text-only fleets, approximate routing's zero-infrastructure cost makes it a reasonable default and the corpus gives no evidence that switching to precise would measurably help. On engines: treat precise routing as production-viable only for vLLM today; SGLang works mechanically but has a structurally-motivated (not transitional) correctness gap on salted/multimodal requests that must be checked against whether llm-d's `SGLangAdapter` parses `BlockStoredWithMetadata` before trusting cache isolation; treat TensorRT-LLM as "engine-side capability now exists (prototype, Sep 10 2026) but llm-d has built no consumer" — closer to feasible-soon than to not-supported, but not yet usable, and distinct from the SGLang case in that the blocker is entirely on llm-d's side rather than split between both sides.

- **Position:** Precise/event-driven indexing is architecturally necessary for eviction-heavy, multimodal, or P/D-disaggregated production workloads on vLLM, and the corpus's own engineering trajectory (plus independent convergence from NVIDIA Dynamo, SGLang, and now TensorRT-LLM on the same KVEvents vocabulary) supports it as the ecosystem end-state — but llm-d ships approximate as the infrastructure-free default, has real benchmark support only for precise-vs-round-robin (not precise-vs-approximate), and today only vLLM has full, gap-free precise-path support; SGLang has a structural (not merely transitional) cache-salt/multimodal gap on llm-d's consumption side, and TensorRT-LLM's engine-side event publisher is real but has no llm-d-side adapter yet.
- **Confidence:** medium-high on the mechanics (dual-key design, block-size/tokenizer-match requirements, engine coverage) — these are drawn from primary source code/docs with direct quotes and are not in dispute across sources, though the `HashSeed`/`PYTHONHASHSEED` godoc creates one unresolved internal tension I could not fully close. Medium-low on the "precise is worth it" cost-benefit claim specifically, because the corpus has no controlled benchmark isolating the two index types; my position there rests on design-level reasoning and cross-project convergence (Dynamo, SGLang, TensorRT-LLM), which is suggestive but not dispositive.
- **Boundary conditions:** The "precise is necessary" claim applies specifically to (a) fleets experiencing real KV eviction under memory pressure, (b) multimodal/LoRA workloads where content-scoped cache correctness matters, and (c) P/D-disaggregated deployments needing exact block identification for transfer. Outside those conditions — small, homogeneous, low-contention text-only fleets — the evidence does not support paying precise routing's operational cost (render endpoint, ZMQ subscriptions, index memory, an extra deployable service). The engine-support claims are scoped strictly to the corpus snapshot (commits through Sep 12, 2026 for SGLang, Sep 10, 2026 for TensorRT-LLM); both are explicitly moving targets and should be re-verified against current code before being asserted as settled facts in the final report.
- **What would change this position:** A controlled A/B benchmark holding P2P, workload, and hardware fixed while switching only the index type (approximate vs. precise) would directly resolve the cost-benefit question either way. Evidence that llm-d's `SGLangAdapter` now parses `BlockStoredWithMetadata`/`cache_salt` (a code diff or changelog entry) would close the SGLang gap. Evidence of a `TRTLLMAdapter` (or an `EngineType` value other than `vllm`/`sglang`) landing in `llm-d-router`'s `kvevents` package, or a TensorRT-LLM backend directory appearing in the `precise-prefix-cache-routing` guide, would confirm TensorRT-LLM has moved from "engine-side capability exists" to "actually integrated." I did not search llm-d-router's issue tracker directly for `trtllm`/`sglang cache_salt` — that would be the fastest way to check both open gaps before the final report ships.
- **Evidence weight:** Mechanics (dual-key design, block-size/tokenizer matching, engine coverage): 6 primary-source code/doc quotes support directly (architecture.md, kvblock package, kvevents package, vLLM kv_events.py, SGLang events.py + kv_events.py, TensorRT-LLM PR #17023), 1 internal tension unresolved (HashSeed godoc). Cost-benefit of precise vs. approximate: 1 benchmark exists but is confounded (P2P bundled) and 0 clean comparisons exist; 3 independent architectural-convergence data points (Dynamo, SGLang, TensorRT-LLM all building the same event vocabulary) support precise indirectly. Default status: 1 doc (upstream GAIE config) supports approximate-as-shipped-default; 1 unverified secondary claim (in the contradiction graph, source not independently located) claims precise is becoming the default — I weight the latter as unconfirmed.
