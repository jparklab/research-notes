# Interim report: offload-connector-routing-visibility

**Locus question:** When KV blocks live outside GPU memory — vLLM native OffloadingConnector tiers (CPU, llm-d FS backend, P2P) versus out-of-tree connectors (LMCache, Mooncake Store, NVIDIA KVBM) that own their own indexing — are those blocks visible to llm-d's KV-cache indexer and scored by the router, and how does tier information (medium/locality in KV events, per-tier weights) change routing decisions?
**Flavor:** convergent

## What the corpus already said

[[kv-cache-offloading-llm-d]] draws the two-pattern distinction explicitly: the **native** path (vLLM `OffloadingConnector` targeting CPU RAM, and the llm-d FS backend targeting shared storage) is "complementary to (not a substitute for) prefix-cache-aware routing" and pairs directly with it. **Out-of-tree connectors** (LMCache, Mooncake, NVIDIA KVBM) "own their own indexing, memory management, and storage." The same page's newest (dev/0.9) revision adds a load-bearing claim not present in earlier fetches of this doc: "Scheduling side — connectors integrate with llm-d through **KV-Events**: cache mutation notifications that the KV-Cache Indexer consumes to maintain a global view of cache distribution, enabling prefix-aware routing regardless of which backend is in use." That is llm-d's own documented position: visibility is asserted to be backend-agnostic.

[[kv-cache-indexer-llm-d]] (v0.7) independently confirms the mechanism the indexer actually runs on: it subscribes to `BlockStored`/`BlockRemoved`/`AllBlocksCleared` events "published over ZMQ by vLLM/SGLang" — i.e., published by the **model-serving engine**, not by any connector directly — and states tier weighting defaults of `gpu = 1.0`, `cpu = 0.8`, with "When blocks are stored across memory tiers, each matching block's contribution is weighted by tier." [[kv-cache-management-llm-d]] (dev) reinforces that the indexer's "observability" layer tracks "the movement and eviction of individual token blocks" "including offloaded tiers," and that P2P sharing works by having "the index know[] which peer holds a request's prefix, the router stamp[s] the request with that source, and the model server pulls the blocks directly from the peer's CPU offload tier."

The loci-analyst's rationale correctly flagged that none of these three sources states whether LMCache/Mooncake/KVBM concretely *emit* engine-compatible KV-Events, nor whether an out-of-tree connector's tier identity survives into the router's scoring weights, nor whether Mooncake's separately documented global-scheduler ambitions ([[rfc-mooncake-conductor-design-and-implementation-of-a-global-scheduler-module-fo]]) compete with or feed llm-d's own indexer.

## What the new sources say

**vLLM's own KV-event schema, ground truth (`vllm/distributed/kv_events.py`, commit d9e2b52, Sep 4 2026 — [[vllmvllmdistributedkv_eventspy-at-main-vllm-projectvllm-github]]).** `BlockStored`/`BlockRemoved` carry a `medium: str | None` field with three named constants (`MEDIUM_GPU`, `MEDIUM_CPU`, `MEDIUM_STORAGE`), plus two additional fields added since the Jul 2026 RFC negotiation: `locality: str | None` ("LOCAL or REMOTE relative to the publisher; None means unspecified") and `ownership: str | None` ("Secondary offloading tier identifier, if generated by one"). The `ownership` field is precisely the slot a connector like LMCache or Mooncake would use to stamp its own identity onto an event distinct from the coarse GPU/CPU/STORAGE medium bucket — but it is brand new (this commit is 10 days before this research run) and its consumption is untested in the corpus.

**llm-d-router's read-side event struct, ground truth (`pkg/kvevents`, v0.10.0 — [[kvevents-package-githubcomllm-dllm-d-routerpkgkvevents-go-packages]]).** `BlockStoredEvent` and `BlockRemovedEvent`, as decoded by llm-d's own `EngineAdapter`, carry: `BlockHashes`, `Tokens`, `ParentHash`, `BlockSize`, **`DeviceTier string`**, `LoraID`/`LoraName`, `ExtraKeys`, `GroupIdx`, `KVCacheSpecKind`, `KVCacheSpecSlidingWindowSize`. **There is no `locality` field and no `ownership` field in this struct.** `EngineType` in the event-pool config is `"vllm"` or `"sglang"` only ([[llm-d-kv-cachedocsconfigurationmd-at-main-llm-dllm-d-kv-cache-github]], [[kvcache-package-githubcomllm-dllm-d-routerpkgkvcache-go-packages]]) — there is no LMCache/Mooncake/KVBM-specific `EngineAdapter`. [[llm-d-kv-cachedocsarchitecturemd-at-main-llm-dllm-d-kv-cache-github]] confirms only a `VLLMAdapter` exists in the fetched documentation.

**The scorer, ground truth (`pkg/kvcache`, v0.10.0).** `KVCacheBackendConfig{Name string; Weight float64}` is a flat name→weight map (default example pairs `"gpu": 1.0`, `"cpu": 0.8`, or `"disk"` in the general schema) that `LongestPrefixScorer` looks up by whatever string arrives as the event's device-tier/medium. This is a generic string match, not a connector-aware mechanism — a block reported with `medium="CPU"` scores identically whether it was placed there by vLLM's native `OffloadingConnector`, by `MooncakeStoreConnector`, or by LMCache, because the scorer only ever sees the three-way (or operator-configured) medium bucket, never a connector identity.

**Source-analysis of vLLM RFC #38260 ([[source-analysis-rfc-multi-tier-kv-offloading-vllm-issue-38260]]), covering the Mar–Jul 2026 negotiation that produced the fields above.** This is the single most load-bearing source for *why* the picture is unsettled. Direct quotes: Change72 (vLLM maintainer/contributor), Jun 23 2026 — "llm-d can mostly treat this as an opaque string, but Dynamo maps `medium` into fixed tiers like `HostPinned`, `Disk`, and `External`" — an explicit, named statement that llm-d is a *looser*, not stricter, consumer of tier metadata than a peer router (NVIDIA Dynamo). Same Change72, Jun 23: "[#43468] intentionally rejects `self_describing_kv_events` under `TieringOffloadingSpec` ... tier promotions can create primary-tier store events that do not correspond to a live GPU store job" — richer self-describing events exist only for the single-tier CPU offload path, not for multi-tier/secondary-tier stores, as of mid-2026. Most consequentially: Change72, Jun 24 2026 claimed `MEDIUM_FS`/`MEDIUM_OBJ` constants and secondary-tier event emission had landed in PR #46544 — then self-corrected on Jul 7: "It does not yet emit actual secondary-tier events or add `MEDIUM_FS` / `MEDIUM_OBJ`; my earlier comments above described an earlier revision." And on eviction correctness: Change72, Jun 23 — "whoever owns eviction should also provide invalidation. Otherwise, routers may score or route based on stale placement state" — a maintainer-stated hazard that applies directly to any out-of-tree connector whose eviction policy is not coordinated with llm-d's indexer.

**LMCache's documented KV-event mechanism ([[kv-cache-events-lmcache]], `docs.lmcache.ai/production/kv_cache_events.html`).** LMCache does not run a separate transport for KV events. Verbatim: "LMCache supports KV cache events as follows: Generates storage KV cache events... The events format is defined as per the `BlockStored` class in vLLM... LMCache passes the events to SGLang or vLLM to publish them using their messaging system." This is an explicit, documented design choice to piggyback on the exact ZMQ `kv-events` topic llm-d's indexer already subscribes to, with `medium` populated (worked example uses `medium='cpu'`). Requires opt-in on both sides: LMCache's `enable_kv_events: true` plus vLLM's `--kv-events-config '{"enable_kv_cache_events": "True", "publisher": "zmq", "topic": "kv-events"}'`; multi-worker vLLM deployments additionally need a non-default `pre_caching_hash_algorithm` (e.g. `sha256_cbor_64bit`) or hash collisions cause duplicate events per worker. The page carries a deprecation banner: this is "LMCache's in-process mode (deprecated)... consider using LMCache MP mode."

**A live bug specifically in the CPU-tier path ([[lmcache-vllm-kv-events-missing-cpu-blockstored-event-only-gpu-event-emitted-issu]], LMCache/LMCache issue #3532, filed Jun 2026).** The reporter shows LMCache's `LMCacheConnectorV1Dynamic` internally *generates* the CPU-medium event (visible in DEBUG logs: `Added kv cache event 'CacheStoreEvent(... medium='cpu' ...)' to kv cache events queue`) but it never reaches the ZMQ subscriber — only the GPU-tier event is actually published. The reporter cross-checked with vLLM's own built-in `OffloadingConnector` (no LMCache in the loop), which correctly published a `medium='CPU'` `BlockStored` event, isolating the defect to LMCache's connector rather than vLLM. GitHub auto-closed the issue "not planned" (stale-bot) on Sep 4, 2026 with no fix landed against the reported (deprecated) connector — but a commit referencing the issue landed against LMCache's newer MP-mode architecture on Aug 27, 2026: `[MP] Add ZmqKVEventSink: re-emit cache events in vLLM KV-event format`, i.e. the fix is arriving as new infrastructure in the mode LMCache is migrating to, not a patch to the mode the bug was filed against.

**Mooncake's event-publishing status, corrected ([[storefeature-update-kv-event-publish-system-by-asher-xunzhang-pull-request-1251]], [[cibuild-enable-kv-events-in-release-wheels-by-ishandhanani-pull-request-4039-kvc]]).** PR #1251 ("[Store][Feature] Update KV event publish system," opened Dec 22 2025, explicitly motivated by the Mooncake-Conductor RFC) was never merged: a maintainer asked for it to be split into smaller PRs (Jan 7 2026), the author split off PR #1306 as "the first PR for the interface declaration" and deferred implementation PRs pending its merge, and #1251 itself went stale and was auto-closed for inactivity on Jul 18, 2026 — superseded, not merged. But the underlying feature appears to have shipped via that follow-on chain: PR #4039 ("[CI/Build] Enable KV events in release wheels," opened Sep 11 2026) treats `ENABLE_KV_EVENTS` as a real, already-working build flag and tries to wire it into official release-wheel CI; it was closed Sep 14, 2026 in favor of its direct successor, PR #4060 ("Enable KV events in wheels with ZeroMQ dependencies"), which is marked merged. Mooncake's live deployment guide documents `-DENABLE_KV_EVENTS=ON`, `--kv_events_bind_endpoint`, and `--kv_events_backend_id` as present, working configuration. Net: the specific PR named in the original locus rationale (#1251) is a dead end, but treating that as "Mooncake never shipped KV-event publishing" would be wrong — the capability shipped through its successors and was being enabled in release builds in the same week as this research run. The `dev/kv-indexer` branch referenced in the issue #977 comment thread, and whether it is now redundant with the merged capability, remains unconfirmed (not resolved within this locus's source budget).

**P2P source selection ([[experimental-enable-p2p-prefix-cache-sharing-llm-d]]).** P2P prefix-cache sharing is explicitly scoped to "peers serve pulls from their CPU offload tier" of the native Tiered Prefix Cache path (vLLM `OffloadingConnector` CPU tier). The `p2p-source-producer` selects a source pod from CPU-tier holders using its own selection heuristic (within one index block of the best cached prefix, weighted to avoid overloading a source, gated by `minCachedTokenDelta`) — not by reading the wire-level `locality` field the Jul 2026 RFC thread introduced for exactly this purpose (`(CPU, LOCAL)` vs `(FS, REMOTE)` worked example). Given the router's event struct doesn't parse `locality` at all (see above), this is consistent: P2P today is a bespoke mechanism layered on the native CPU-tier index, not (yet) a consumer of the new locality semantics.

## Evidence synthesis

Two separate claims need to be kept apart, and the corpus lets us separate them cleanly.

**Claim 1 — "Are out-of-tree-connector blocks architecturally visible to llm-d's indexer at all?"** The answer is conditionally yes, by construction, not by connector-specific integration — and this is now confirmed as the *documented design intent* on the LMCache side, not just an inference from llm-d's docs. llm-d's indexer never talks to LMCache, Mooncake, or KVBM directly — it only ever subscribes to the standard `vllm`/`sglang` ZMQ KVEvents topic (`kv@<pod-ip>:<port>@<model>`) that the **engine process** (vLLM/SGLang) itself publishes. LMCache's own docs state explicitly that it "passes the events to SGLang or vLLM to publish them using their messaging system" rather than running a separate transport — the exact mechanism the llm-d docs' "regardless of which backend is in use" claim requires. But three qualifications survive this confirmation: (a) it requires explicit opt-in flags on both LMCache and vLLM sides — nothing about this is automatic or default; (b) it is documented against LMCache's *deprecated* in-process connector, with the newer MP-mode architecture still building out its own re-emission path (`ZmqKVEventSink`, landed Aug 27 2026); and (c) there is a confirmed, currently-open bug (#3532) where the CPU-tier `BlockStored` event specifically fails to reach the ZMQ subscriber in LMCache's connector even though LMCache's own internal code generates it — GPU-tier events work, CPU-tier events (the offload case this locus cares about most) do not, as of the last evidence in the corpus. Mooncake's picture inverted during this investigation: the specific unmerged PR the loci-analyst flagged (#1251) is confirmed dead, but the capability it was building toward shipped via a different PR chain and was being wired into release-wheel CI in the same week as this research run — so "Mooncake's KVEvent publisher is unmerged" is no longer an accurate summary; "shipped, but via a different path than the one first documented, and its production maturity/default-on status is unconfirmed" is more accurate.

**Claim 2 — "Does tier/connector identity change routing decisions?"** Only coarsely, and this claim is unaffected by the LMCache/Mooncake findings above. The scorer's `KVCacheBackendConfig` is a flat string→weight table keyed on whatever `medium`/`DeviceTier` string an event carries. Today's default vocabulary is GPU/CPU (and a generic FS/disk bucket) — there is no per-connector weight (an LMCache-CPU block and a native-OffloadingConnector-CPU block score identically if both report medium `"CPU"`, and per the LMCache worked example they do use the same lowercase `medium='cpu'` convention). The two fields that would let a router go further — `locality` (LOCAL/REMOTE, needed to reason about P2P reachability) and `ownership` (a connector-supplied secondary-tier identifier) — exist in vLLM's wire format as of the Sep 4 2026 commit but are **not parsed** by llm-d-router's own `BlockStoredEvent`/`BlockRemovedEvent` structs as of v0.10.0. This is a load-bearing, dated fact, not an inference: the Go struct definition is directly in front of me and simply does not have those fields. P2P source selection, which is the one llm-d feature that most obviously needs locality semantics, uses its own bespoke CPU-tier-holder heuristic instead, consistent with the router not yet consuming `locality`.

## Committed position

The evidence supports a synthesis verdict, not a binary yes/no, and it has sharpened (not just been confirmed) over the course of this investigation. llm-d's KV-cache indexer is architecturally connector-agnostic by design — it listens to the engine's own KVEvents stream, not to any connector's private API — and this is no longer just llm-d's own marketing claim: LMCache independently documents deliberately piggybacking on vLLM's/SGLang's own event publisher for exactly this reason, and Mooncake shipped a working KV-event-publishing capability (via PR #4060 and predecessors, not the dead-end #1251) that is being enabled in release wheels as of this week. So the *architecture* claim — "any connector can be made visible to llm-d's router because the engine, not the connector, is the event source" — is now well-evidenced on both the llm-d side and the two named out-of-tree connectors' sides. What remains genuinely unresolved, and is the operationally important finding, is that visibility is opt-in, connector-version-dependent, and currently has a documented gap in the exact case (CPU-tier offload) that matters most: LMCache's deprecated connector generates but drops CPU-medium events before they reach the ZMQ bus, a bug still open as of Sep 4 2026, fixed only in a newer, still-migrating LMCache mode. Layered on top of that: even when a connector's events do reach the router cleanly, tier identity still collapses into a coarse GPU/CPU/(generic-storage) weight bucket — the finer-grained `locality` and `ownership` fields vLLM shipped in September 2026 specifically to let connectors distinguish themselves and support P2P-style reasoning are not yet consumed by llm-d-router's own event-decoding struct (v0.10.0), so no routing decision today can differentiate "held by LMCache" from "held by the native FS backend," or use locality to reason about cross-peer reachability beyond the router's own bespoke P2P heuristic (which itself is scoped only to the native CPU tier). Practically: an operator running LMCache or Mooncake alongside llm-d should not assume prefix-aware routing scores those connectors' cache the same way it scores native-tier cache by default — they must (a) explicitly enable KV-event publishing on both the connector and the engine side, (b) verify with a subscriber script or DEBUG logs that the specific tier they're using actually reaches the ZMQ bus (LMCache's CPU tier is a known-bad case as of this corpus), and (c) confirm the emitted `medium` string has an entry in `kvCacheBackendConfigs`, since the corpus does not specify what the scorer does with an unrecognized medium — a real gap given Change72's own warning that stale or misunderstood placement state causes routers to "score or route... incorrectly."

- **Position:** llm-d's indexer is protocol-agnostic by design and both major out-of-tree connectors (LMCache, Mooncake) are documented/observed to feed it via the engine's own KVEvents publisher rather than a private channel — but visibility is opt-in, not default, and is confirmed broken for LMCache's CPU-offload tier in its (deprecated) connector as of the most recent evidence; even where visible, out-of-tree blocks are scored with the same coarse per-medium weight as native blocks, and llm-d-router v0.10.0 does not yet consume the `locality`/`ownership` fields vLLM added in Sep 2026 that would let it reason about connector identity or cross-peer reachability.
- **Confidence:** medium-high on the architecture claim (now supported by primary sources on both the llm-d side and the LMCache/Mooncake side, not just llm-d's own docs); medium on the operational-completeness claim (the LMCache CPU-tier bug and Mooncake's shipped-but-unconfirmed-default status are both dated Jun–Sep 2026 evidence that could already be superseded); high on the "no locality/ownership consumption, coarse medium-only weighting" claim (direct Go struct evidence, unambiguous).
- **Boundary conditions:** This position holds for llm-d-router through v0.10.0 and llm-d docs through the "dev" (0.9-adjacent) branch, vLLM main through commit d9e2b52 (Sep 4 2026), LMCache through the version documented at the fetched `docs.lmcache.ai` page (explicitly the deprecated in-process connector — MP mode may already behave differently), and Mooncake through PR #4060/#4039 (Sep 11–14 2026). It does not describe Mooncake's or LMCache's internal routing capabilities used standalone (both have their own cache-aware routing logic outside llm-d). It will stop holding for the "locality/ownership not consumed" half the moment llm-d-router's `kvevents` package is updated — plausible on a short timescale given the wire fields landed just 10 days before this research run.
- **What would change this position:** (1) A merged llm-d-router PR/release note showing `BlockStoredEvent`/`BlockRemovedEvent` gaining `Locality`/`Ownership` fields would flip the "not yet consumed" claim. (2) A fix or version bump confirming LMCache's CPU-tier `BlockStored` event reaches the ZMQ bus in MP mode (not just the deprecated connector) would resolve the "confirmed broken" qualifier to "fixed in current default mode." (3) Direct confirmation that Mooncake's `ENABLE_KV_EVENTS` is on by default in a stable release (vs. still opt-in/experimental) would upgrade "shipped but unconfirmed default status" to "shipped and default."
- **Evidence weight:** 4 primary/ground-truth sources (vLLM `kv_events.py`, llm-d-router `pkg/kvevents` and `pkg/kvcache` Go docs, llm-d-kv-cache `architecture.md`/`configuration.md`) directly support "coarse medium bucket, no locality/ownership consumption." 1 primary LMCache doc page + 1 primary GitHub bug report support "designed to piggyback on the engine publisher, but CPU-tier path confirmed broken in the documented (deprecated) connector." 2 primary GitHub PR threads (superseding the dead #1251) support "Mooncake's KV-event publishing shipped via a different path than first tracked, default status unconfirmed." 1 structured source-analysis digest of a vLLM maintainer thread supports "the wire contract itself was still being negotiated and self-corrected through mid-2026."

## Open questions

- Is LMCache's newer MP-mode `ZmqKVEventSink` (landed Aug 27 2026) confirmed to fix the CPU-tier event-drop bug from issue #3532, and is MP mode now the default LMCache deployment path? The corpus has the commit reference but not a confirmation test.
- What is the scorer's behavior when a `BlockStored`/`BlockRemoved` event carries a `medium`/`DeviceTier` string with no matching entry in `kvCacheBackendConfigs` (silently dropped/zero-weighted, defaulted to some fallback weight, or an error)? This determines whether an unconfigured out-of-tree connector's blocks are invisible-by-omission or actively mis-scored.
- Does NVIDIA KVBM's vLLM connector emit engine-compatible KVEvents? The corpus has no direct evidence either way; llm-d's own doc only asserts "the integration pattern is the same for KVBM and other connector-compatible engines," without confirmation.
- Is `ENABLE_KV_EVENTS` on by default in a stable Mooncake release, or still an opt-in/experimental build flag? PR #4060 enables it in release *wheels*, which is closer to "available" than "default-on for all deployments."
- Is there a newer llm-d-router release (post-v0.10.0) that updates the `kvevents` package to consume `locality`/`ownership`? Given the Sep 4 2026 vLLM commit is very recent relative to this research run (Sep 14 2026), a check of llm-d-router's latest release notes/CHANGELOG would be worthwhile before final publication.
- What became of the `dev/kv-indexer` Mooncake branch referenced in issue #977's comment thread — is it now redundant with the PR #4060 capability, or does it cover different ground (e.g., the RadixTree indexer for Mooncake-Conductor specifically)?
