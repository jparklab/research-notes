# Source Analysis — Sticky Until Saturated: Token-Aware Routing in llm-d

**Original source:** [[sticky-until-saturated-token-aware-routing-in-llm-d-llm-d]]
**Source type:** article (technical blog post, llm-d.ai, published alongside/around the llm-d 0.9 release)

**Your judgment:** This is the single most load-bearing primary source for the research_query — it is llm-d's own engineering writeup of exactly how the current default scheduler combines prefix-cache affinity with load, why it replaced the prior heuristic blend, and the closed-form derivation of the saturation threshold. It functions as the authoritative technical spec, not commentary.

*Suggested by [[sticky-until-saturated-token-aware-routing-in-llm-d-llm-d]] — source analyst's digest of the full source body*

## Thesis / Central claim
llm-d's router should combine exactly one KV-cache-affinity signal with exactly one load signal chosen to match the workload's actual bottleneck — prefill compute or decode slots — rather than blending many heuristic signals with hand-tuned weights. The affinity filter keeps requests sticky to the endpoint that already holds their prefix in cache, but releases stickiness once that endpoint's load exceeds a saturation threshold τ that is derived in closed form from a single hardware calibration measurement plus an operator-chosen TTFT degradation ceiling, rather than tuned empirically per workload.

## Methodology / Basis of claims
Controlled A/B benchmark comparison of five router/scheduler configurations (k8 round-robin baseline, token-load-aware/"prefix+token", active-request-aware/"run-req", the prior default "legacy blend", and a workload-agnostic latency-predictor pipeline) across three synthetic-but-workload-catalog-derived traffic shapes (code-generation, reasoning, b2b-saas), on a fixed hardware testbed (10x, 8x for b2b-saas, Qwen3-32B pods on vLLM, TP=2 across 2xH100, `max-num-batched-tokens=8192`, GKE, behind a Gateway API `InferencePool`). Load generated via `inference-perf`; each (workload, configuration, concurrency) cell run once (no confidence intervals — the source is explicit about this: "we report achieved values rather than confidence intervals"). The τ threshold itself is derived analytically (not swept): `τ_sat = R_peak × T_max = (B × T_max)/T(B)`, where `R_peak` comes from one calibration measurement per (model, accelerator, engine), and validated qualitatively via the b2b-saas hit-rate/failure-mode behavior rather than a grid search. Portability of the formula is argued via a measured cross-(model, accelerator, engine) table (8 rows) rather than a systematic sensitivity study.

## Key findings / Claims (with specific numbers where present)
1. **Two-signal architecture, workload-matched.** Prefill-bound traffic (long prompts) uses `prefix-cache-affinity-filter` (affinity threshold 0.8) + `token-load-scorer` + `max-score-picker`, routing on uncached prefill tokens in flight. Decode-bound traffic (long outputs) uses the same affinity filter + `active-request-scorer` + `max-score-picker`, routing on active streams.
2. **What it replaced and why.** The prior default was a four-signal weighted blend: `prefix-cache-scorer (weight=3) + queue-scorer (weight=2) + kv-cache-utilization-scorer (weight=2) + no-hit-lru-scorer (weight=2)`, no affinity filter — prefix locality enforced only via the weight-3 scorer. Two motivating failure modes: (a) the blend's emergent behavior was "hard to predict and harder to tune"; (b) over-indexing on cache affinity without an explicit saturation release causes hot-spotting — a warm endpoint keeps absorbing load past the point a cold endpoint would be faster.
3. **Filter mechanics.** Each endpoint gets an affinity score = fraction of incoming prompt tokens already cached there. Endpoints with affinity ≥ `affinityThreshold` (0.8) form the restricted candidate set; if none clears the bar, all endpoints pass through unfiltered.
4. **Saturation override (two historical parameterizations, now unified).** Experiment-era interface: `maxTokensInFlightPenalty` (=τ, in tokens) — a cold endpoint re-enters the candidate set once its uncached-tokens-in-flight is ≥τ lower than the warm endpoint's. Current (llm-d main) interface: unified into a single time-domain gate — every endpoint's TTFT is estimated (from `peakPrefillThroughput` by default, or from the latency predictor via `ttftSource`), and stickiness breaks when the best warm endpoint's estimated TTFT exceeds the best non-warm endpoint's by more than `maxTTFTPenaltyMs`. With the throughput source this is mathematically identical to the token-gap rule: gate fires when in-flight gap exceeds τ = R_peak × T_max, computed internally.
5. **τ derivation (closed form).** `R_peak = B / T(B)` where B = `max-num-batched-tokens` and T(B) = measured wall-clock time to prefill one full chunk (one calibration measurement). At saturation, in-flight uncached tokens drain at R_peak, so a new arrival's queueing time ≈ τ/R_peak; solving for τ under an operator TTFT-degradation ceiling T_max gives `τ_sat = R_peak × T_max = (B × T_max)/T(B)`.
6. **Reference calibration: Qwen3-32B/H100.** T(B=8192)=0.40s (single-request quadratic fit) → R_peak=20,480 tok/s. With T_max=14s, τ_sat=286,720 (=35×8192, "35 chunks"). Table of τ_sat by T_max: 10s→205k, 14s→286,720, 18s→369k, 25s→512k.
7. **Shipped defaults reconcile with the experimental threshold via a different calibration method.** The shipped recipe (`calibrate.sh`) measures `peakPrefillThroughput=15,928` tok/s (median TTFT of repeated random-token requests through the full request path — lower than the paper's single-request fit) with `maxTTFTPenaltyMs=18,000ms` default; 15,928×18s = 286,704 ≈ the paper's 286,720. The source explicitly reconciles the two numbers rather than treating them as inconsistent.
8. **R_peak is not portable — it is a property of the whole serving path, not the accelerator.** Measured table across 8 (model, accelerator, engine) paths: gpt-oss-120B/H100 (vLLM, TP=1, sparse MoE) = 39,065 tok/s (highest, despite being the largest model, because prefill touches few active params); Qwen3-32B/TPU v7x (vLLM, TP=8) = 27,336; Qwen3-32B/TPU v6e = 26,290; GLM-5.2-NVFP4/8xB200 (SGLang, TP=8, production Vertex AI fleet) = 24,027; Qwen3-32B/H100 anchored (vLLM, TP=2) = 20,480; Qwen3-Coder-480B-FP8/TPU v7x = 16,444; Qwen3-VL-32B/H200 (vLLM, TP=2) = 15,751; Qwen3-32B/H100 on SGLang (TP=2) = 15,360. The source flags one published value as wrong: "The SGLang / H100 row corrects the value currently published in the matrix, 30,720, which is 2× too high."
9. **Non-transplantability demonstrated concretely.** Moving τ=286,720 from Qwen3-32B/H100 onto gpt-oss-120B/H100 would set the valve ~1.9x too low (fires while warm endpoint has headroom); onto Qwen3-VL-32B/H200 ~1.3x too high (fires late, breaches SLO). Even within one accelerator family (TPU v7x), Qwen3-32B supports τ=383,000 but Qwen3-Coder-480B only 230,000.
10. **Benchmark results, three workloads.** Code-generation (prefill-bound, mean 70k-token prompts): prefix+token throughput plateaus ~47k in_t/s by conc=60, TTFT-p90 stays <40s through conc=60; knee at conc=60 (matched) vs conc=30 (k8), 46k vs 16k in_t/s = 2.9x. Reasoning (decode-bound): run-req (active-request-scorer) has lowest TPOT-p90 and highest out_t/s; knee conc=350 (matched) vs conc=250 (k8), 7.0k vs 6.8k out_t/s (~parity); prefix+token is competitive but doesn't beat run-req. B2B-saas (pathological prefill-bound, fixed 150-prompt/750-variant corpus): prefix+token knee QPS=38 vs k8 QPS=18, 90k vs 45k in_t/s = 2.0x; legacy blend actually achieves *lowest* TTFT-p90 on this specific workload (bespoke tuning advantage) and sustains higher hit rate (96-97% vs prefix+token's 70-73%) at very high QPS (50+) because the saturation valve on prefix+token engages and briefly redistributes traffic away from warm endpoints — the legacy blend has no such valve.
11. **Affinity filter is a structural no-op for decode-bound traffic in this benchmark.** On reasoning's 250-token shared system prompt, best-case affinity is 0.25 (first issue) and observed hit rates never clear the 0.8 threshold even on repeats, so the filter passes all endpoints through and the active-request-scorer operates on the full set.
12. **B2B-saas bimodality — a specific caveat about τ tuning.** The cluster settles into one of two steady states depending on τ: stable partition (each endpoint owns a prefix subset, high hit rate) or eviction-churn cascade (every endpoint tries to cache every prefix, hit rate collapses); "small changes in τ can flip the cluster from one state to the other." The source explicitly disclaims using b2b-saas to derive a precise optimal τ: "the bimodality means such a claim wouldn't generalize even within b2b-saas, let alone across workloads."
13. **Token-load-scorer formula (lookahead).** `score(endpoint) = current_uncached_in_flight(endpoint) + prompt_tokens × (1 - hit_rate(endpoint))`. With streaming and default `addEstimatedOutputTokens=false`, in-flight counter tracks only unprefilled tokens (released once first streamed chunk arrives). Optional `addEstimatedOutputTokens=true` holds an output estimate `round(inputTokens × outputRatio)` (default ratio 1.5) until response completion, approximating KV-cache occupancy — described as an available but non-default configuration.
14. **Deployment status.** Ships as default in llm-d's optimized-baseline, agentic-serving, multimodal-serving, and P/D-disaggregation guides; in production at Google Cloud Vertex AI, Red Hat, and Mistral (per the source's own claim — unverified independently within this source).
15. **P/D-disaggregation as the "limiting case."** When prefill and decode run in separate pools, the two-regime taxonomy stops being a workload property the operator must diagnose and becomes structural: every request exercises both bottlenecks, one pool at a time. P/D guides ship both matched configurations simultaneously, each pool independently calibrated.
16. **Multimodal-serving required different constants** (reported as already shipped, not the paper's own experiment): `affinityThreshold` drops 0.8→0.6 (multimodal prompts' cacheable fraction tops out near 0.7, so 0.8 could never engage); `maxTTFTPenaltyMs` doubles 18s→36s (text-only calibration underestimates vision-encoder time, so predicted TTFT runs light of wall-clock — "effective τ doubles for image-heavy traffic"). Benchmark-validated to parity with the previously shipped weighted blend, per the source.

## Caveats, limitations, contradictions
- **No statistical confidence.** Explicitly: "Each (workload, configuration, concurrency level) combination is run once; we report achieved values rather than confidence intervals." All throughput/latency numbers in this source are single-run point estimates, not means with error bars.
- **b2b-saas explicitly flagged as non-representative / not for tuning.** The source itself calls it "a stress test... a poor benchmark for hyperparameter sweeps" and disclaims any precise-τ claim from it, due to bimodal steady-state convergence that depends on ramp-stage seeding (two runs of the same config can converge to different absolute numbers, though relative ranking is claimed stable).
- **Legacy blend wins on its own turf.** The matched (prefix+token) configuration does NOT beat the legacy blend on b2b-saas TTFT-p90 or high-QPS hit rate — the source is candid that "a carefully tuned weight set will outperform a general configuration on the specific workload it was tuned for." The claimed advantage of the new default is legibility/portability, not universal dominance.
- **Two different calibration methodologies produce different R_peak numbers for the same hardware path** (20,480 single-request fit vs 15,928 shipped recipe's median-TTFT-of-repeated-requests) — reconciled only because the product R_peak×T_max lands close (286,720 vs 286,704), which is somewhat coincidental given the shipped T_max (18s) differs from the paper's T_max (14s) specifically to compensate.
- **One matrix entry is self-corrected mid-document**: "The SGLang / H100 row corrects the value currently published in the matrix, 30,720, which is 2× too high" — implies the shipped configuration-matrix.md has (or had) an error; a depth investigator should verify current state of that file rather than trust this post's snapshot.
- **τ does not transplant — stated as a hard limitation, not softened.** Concrete worked examples show 1.9x and 1.3x errors from naive transplant; requires re-calibration per (model, accelerator, engine, max-num-batched-tokens).
- **Active-request-scorer / decode-bound regime under-tested.** Only one workload (reasoning) tests the decode-bound matched configuration, and the affinity filter is a no-op throughout that entire test (never engages), so the "composability" claim for the decode-bound case rests on the filter passing through — not on any test of the filter actually gating decode traffic.
- **Latency-predictor pipeline sensitivity uncharacterized.** "The 5s value can be raised if observed TTFT regressions warrant a tighter override; we have not characterized the sensitivity systematically."
- **Self-declared open follow-ups**, several partially addressed since: regime-shift-within-conversation (agentic/tool-use) partially addressed via agentic-serving guide but "a systematic study of regime shift within single conversations remains open"; mixed-traffic (simultaneous code-gen + chat) untested; high-prefix-reuse *unbounded*-corpus production traces untested (only the artificial fixed-150-prompt b2b-saas exists); latency-predictor's advantage on dynamically-shifting-bottleneck production traffic is asserted as "plausible" but explicitly "untested here."
- **Source is a vendor/project blog post, not peer-reviewed.** It is written by the llm-d project about its own default change — inherently a first-party account; benchmark setup, workload choice, and framing (e.g., calling k8/legacy-blend failures "cliff failures") are the authors' own characterizations. Per domain notes, code/design docs outrank blog marketing but this specific post carries substantial quantitative/methodological content (closed-form derivation, calibration table) that functions more like an engineering report than pure marketing — treat the numeric/mechanism claims as primary evidence, but treat framing language ("the results back the change") as advocacy.
