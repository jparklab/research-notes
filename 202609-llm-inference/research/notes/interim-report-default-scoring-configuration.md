# Interim report: default-scoring-configuration

**Locus question:** What is llm-d's actual current default cache+load scoring scheme — the legacy weighted multi-scorer blend, or the newer "sticky until saturated" token-aware design — and is the newer design strictly better or just more predictable/portable? Pin each configuration to the llm-d release that shipped it as default.
**Flavor:** dialectical

## What the corpus already said

The width corpus supplied two incompatible-looking accounts. [[request-scheduler-llm-d]] (llm-d dev-branch docs, `/docs/dev/architecture/core/router/epp/scheduling`) documents the Filter→Score→Pick pipeline and states "Final endpoint score = sum over scorers of (scorer_score in [0,1] * weight)" — an abstract weighted-sum mechanism — but also lists `prefix-cache-affinity-filter` (with a "TTFT load gate" to break stickiness) as a *filter*, i.e. the same doc that describes the legacy weighted-blend math already documents the newer affinity-filter+gate plugin as an available component. The doc explicitly warns: "Not all of the plugins listed below are configured by default. Only a curated subset is enabled in the default configuration" — but the inline link target for "default configuration" resolves back to the same page (a scrape/anchor artifact), so the width sweep could not actually see what the curated default is. [[sticky-until-saturated-token-aware-routing-in-llm-d-llm-d]] and its digest [[source-analysis-sticky-until-saturated-token-aware-routing-in-llm-d]] document the replacement design in full technical depth (see below). [[predicted-latency-based-scheduling-for-llms-llm-d]] documents a third configuration. None of the three width-corpus sources pinned a configuration to a specific numbered llm-d release, which is exactly the gap this locus was opened to close.

## What the new sources say

**[[llm-d-v09-hardened-for-scale-llm-d]]** (v0.9 release blog, "Hardened for Scale") turns out to contain the direct, load-bearing version pin the corpus was missing. Verified against the raw note body: **"Sticky-until-saturated routing is now the [default strategy across all guides](https://llm-d.ai/blog/sticky-until-saturated-token-aware-routing). Requests stick to the endpoint with the best prefix cache match until that endpoint reaches a saturation threshold, then spill to the next-best option. This balances cache reuse against load distribution without manual tuning."** This is an unambiguous first-party statement that v0.9 is the release that flipped the token-aware design to default across llm-d's well-lit-path guides. The same post separately introduces a formal Plugin Stability Lifecycle (Alpha/Beta/Stable, gating experimental plugins behind `--allow-experimental-plugins`), Router HA, production-safe flow-control defaults, and GPU-utilization-aware routing via DCGM — none of which are the scoring-default change itself, but they establish v0.9 as the release where scheduling-default and plugin-governance changes both landed together.

**[[configuration-llm-d]]** (`/docs/dev/architecture/core/router/epp/configuration`, fetched Sep 2026 — the canonical `EndpointPickerConfig` schema reference) is the resolution of the broken "default configuration" link from the width sweep, and it complicates the v0.9 pin rather than contradicting it. It contains two illustrative examples, neither of which is the sticky-until-saturated design: a minimal getting-started example wiring only `prefix-cache-scorer` at `weight: 1 # Default`, and a second example explicitly labeled "recommended for a typical production setup" that is the **legacy weighted blend**:
```
schedulingProfiles:
- name: default
  plugins:
  - pluginRef: label-selector-filter        # Optional: not in default profile
  - pluginRef: prefix-cache-scorer          # Recommended: not in default profile
    weight: 3.0
  - pluginRef: kv-cache-utilization-scorer  # Recommended: not in default profile
    weight: 2.0
  - pluginRef: queue-scorer                 # Recommended: not in default profile
    weight: 2.0
  - pluginRef: max-score-picker             # Default picker (auto-injected if omitted)
```
Every scorer line here is annotated "not in default profile," and the page separately states that a genuinely empty `schedulingProfiles` falls back to an auto-generated profile that "references ALL Filter/Scorer/Picker plugins" — which errors on multiple Pickers and is an anti-pattern guardrail, not a usable zero-config default. Read together with the v0.9 blog, this means: **the v0.9 blog's "default across all guides" claim is true of the well-lit-path guides (optimized-baseline, agentic-serving, multimodal-serving, P/D-disaggregation), but the canonical schema-reference page's own illustrative "recommended" example had not been updated to match, as of this same-week fetch** — a documentation-lag gap between the product-level default and the generic reference docs, not a second competing default.

**[[llm-dguidesrecipesroutercalibration-at-main-llm-dllm-d-github]]** (`guides/recipes/router/calibration` README) is the primary source for the calibration procedure behind `tau`. It confirms the plugin-level default `peakPrefillThroughput=15928` tok/s is "calibrated for Qwen 32B on H100 80GB (TP=2)," while "the agentic-serving guide ships 16444 for Qwen3-Coder-480B-FP8 on TPU v7x" — different guides ship different calibrated constants for the same plugin, confirming non-transplantability empirically. **[[llm-dguidesrecipesroutercalibrationconfiguration-matrixmd-at-main-llm-dllm-d-git]]** (the calibration recipe's `configuration-matrix.md` data table, newly fetched) is the primary source behind that 15,928 number: "the measured value for the reference path gpu/vllm: Qwen3-32B on NVIDIA H100 80GB vLLM v0.23.0 TP=2, CHUNK_SIZE=8192." Measured range across the matrix spans 1,970 tok/s (CPU, Llama-3.2-3B) to 39,065 tok/s (gpt-oss-120B/H100, sparse MoE); AMD and Intel XPU rows are flagged with a dagger as unmeasured proxies borrowed from the nearest measured path, explicitly marked for re-measurement. Notably, this matrix file's SGLang/H100 row still reads 30,720 tok/s as of this fetch — exactly the value the sticky-until-saturated blog post itself calls out as stale ("corrects the value currently published in the matrix, 30,720, which is 2× too high"). That the correction is in the blog prose but not yet in the matrix file is a second, small, concrete instance of the same documentation-lag pattern seen in the schema-reference page.

**[[llm-d-04-achieve-sota-performance-across-accelerators-llm-d]]** (v0.4 release blog) is where the legacy blend's distinguishing member, `no-hit-lru-scorer`, is introduced: "Enhances intelligent scheduling with tier-aware prefix-cache affinity (configurable weighted scoring...) and introduces the no-hit-lru-scorer, which distributes 'cold' requests... on 8x Qwen3-32B/16x H100 at 50 QPS with 150 shared prefixes, this cut P99 TTFT in half (18.3s to 8s)." This is the earliest release-pinned appearance of a weighted-scorer-blend component in the corpus, giving the legacy blend a v0.4 origin to set against the token-aware design's v0.9 promotion.

**[[llm-d-05-sustaining-performance-at-scale-llm-d]]** (v0.5 release blog) confirms that as of v0.5, predictive latency-based routing was **not yet shipped** — it is listed only as roadmap: "Roadmap: predictive TTFT/TPOT-based routing, proactive KV 'pinning' APIs, and end-to-end distributed tracing." v0.5's own scheduling contribution was active-active HA (KV-events subscription manager with dynamic pod discovery) and LoRA-precise prefix caching, not a scorer/filter default change. This places the third configuration (predicted-latency scheduling) somewhere after v0.5 and, per the corpus, still without an explicit "now default" statement anywhere — it is described (by the sticky-until-saturated post itself) as "a separate, non-default 'latency-predictor' pipeline... explicitly recommended only for mixed/high-variance traffic, not shipped as the default."

Independently, [[intelligent-inference-scheduling-with-llm-d-on-red-hat-ai-red-hat-developer]] (Red Hat Developer, published June 11 2026 — before the v0.9 window) describes the "default scorers" as "prefix-cache-scorer + queue-scorer, with optional load-aware-scorer" — a legacy-family variant, corroborating that mid-2026 (pre-v0.9) production documentation was still describing the legacy blend rather than the affinity-filter+gate design, consistent with a v0.9 cutover.

## Evidence synthesis

The version-pinning half of this locus is now resolved with a direct primary-source quote: **v0.9 ("Hardened for Scale") is the release the project itself credits with making sticky-until-saturated the default "across all guides."** The legacy weighted blend (`prefix-cache-scorer` w=3 + `queue-scorer` w=2 + `kv-cache-utilization-scorer` w=2 + `no-hit-lru-scorer` w=2, per the sticky-until-saturated post's own naming of what it replaced) traces its distinguishing component to v0.4, and the Red Hat article shows a legacy-family default still current in production documentation less than two weeks before the v0.9 tag (v0.9.0 tagged 23 Jun 2026 per [[releases-llm-dllm-d-router]]; Red Hat article published 11 Jun 2026). Predicted-latency scheduling is a third, parallel, explicitly-non-default configuration — v0.5's own roadmap still listed it as future work, and the sticky-until-saturated post itself describes it as an opt-in pipeline for high-variance traffic, not a default anywhere in the corpus.

What remains genuinely unresolved, and is worth reporting as its own finding rather than smoothing over, is that "default across all guides" and "the documentation's own recommended example" are two different things that currently disagree. The canonical `EndpointPickerConfig` schema-reference page — the page a practitioner would read to understand the config *format* rather than follow a specific named guide — still shows the pre-v0.9 legacy blend as its "recommended for a typical production setup" illustration, annotated with a note that none of those scorers are wired by default even there. A reader who follows one of the four named well-lit-path guides gets sticky-until-saturated; a reader who instead builds a config from the generic schema reference will copy the older blend. This is a documentation-currency gap, not a second competing product default, and it is corroborated by a second small artifact of the same lag: the calibration recipe's own `configuration-matrix.md` table still carries the erroneous 30,720 tok/s SGLang/H100 value that the sticky-until-saturated blog post itself flags as "2× too high."

On the "strictly better vs. more predictable/portable" question, the evidence is unambiguous and comes from the new design's own advocates. The sticky-until-saturated source states plainly: "A carefully tuned weight set will outperform a general configuration on the specific workload it was tuned for" — and demonstrates this concretely on the b2b-saas workload, where the legacy blend beats the matched configuration on both TTFT-p90 and hit-rate-at-high-QPS (96–97% vs 70–73%) because it has no saturation valve to redistribute traffic away from warm endpoints once they're hot. The matched configs win specifically on cross-workload *portability*: one calibration measurement (`peakPrefillThroughput`, via `calibrate.sh`) derives `tau` in closed form, versus hand-tuning four weights per workload — and the configuration-matrix data table is direct, independent evidence that this portability problem is real and large in practice (1,970 to 39,065 tok/s measured range across hardware paths, a ~20x spread), not a hypothetical the blog invented to justify the change.

## Committed position

llm-d's current default is the token-aware "sticky until saturated" design — `prefix-cache-affinity-filter` (threshold 0.8) plus exactly one workload-matched load scorer (`token-load-scorer` for prefill-bound traffic, `active-request-scorer` for decode-bound traffic), gated by a saturation threshold `tau = R_peak × T_max` — and this is pinned squarely to **v0.9 ("Hardened for Scale")**, per the release blog's own sentence: "Sticky-until-saturated routing is now the default strategy across all guides." The legacy weighted blend (`prefix-cache-scorer` w=3 + `queue-scorer` w=2 + `kv-cache-utilization-scorer` w=2 + `no-hit-lru-scorer` w=2) is the prior default, traceable to v0.4 where its distinguishing scorer (`no-hit-lru-scorer`) was introduced, and it remained the documented default through at least the Red Hat Developer account of 11 June 2026, twelve days before the v0.9.0 router tag. Predicted-latency scheduling (XGBoost TTFT/TPOT sidecar) is a third, explicitly non-default, opt-in configuration for mixed/high-variance traffic, still not promoted to default in any source the corpus covers. A report should flag one live inconsistency rather than paper over it: llm-d's own canonical `EndpointPickerConfig` schema-reference documentation has not caught up to the v0.9 change — its "recommended for a typical production setup" example is still the legacy blend — so a practitioner's actual default depends on whether they installed one of the four named well-lit-path guides (gets sticky-until-saturated) or hand-built a config from the generic schema docs (gets the legacy blend, or an even more minimal single-scorer example). On "strictly better": no. The new design's own single-run benchmark concedes TTFT-p90 and cache-hit-rate-at-high-QPS to the legacy blend on the b2b-saas workload specifically because the legacy blend has no saturation-release valve that would otherwise sacrifice hit rate for load balance; the new design's real advantage is that `tau` is derivable from one hardware calibration measurement and travels across workloads without re-tuning four weights by hand, evidenced independently by the calibration matrix's ~20x cross-hardware spread in the underlying `peakPrefillThroughput` constant. Predicted-latency scheduling is a further step in the same direction (eliminating manual weight-tuning entirely via a learned model) but trades in more operational complexity (a trained regression sidecar, continuous retraining) and was benchmarked against a GAIE-upstream (1,1,1)-weighted "Load+Prefix" baseline, not against llm-d's own (3,2,2) legacy blend or the sticky-until-saturated config — so its 4-of-5-scenario win and 43%/70% production-trace gains do not directly establish it as better than either of llm-d's own two configurations.

- **Position:** v0.9 ("Hardened for Scale") is the llm-d release that made the token-aware sticky-until-saturated design (`prefix-cache-affinity-filter`@0.8 + workload-matched scorer + tau-gate) the default across llm-d's well-lit-path guides, superseding the v0.4-originated legacy weighted blend; the new design is more portable/predictable via one-measurement calibration, not strictly better — it concedes TTFT-p90 and high-QPS hit rate to a bespoke-tuned legacy blend on at least one benchmarked workload, and the project's own generic config-reference documentation has not yet been updated to reflect the v0.9 default.
- **Confidence:** high on the v0.9 version pin (direct first-party quote: "Sticky-until-saturated routing is now the default strategy across all guides," corroborated by the Red Hat article showing the legacy default still current 12 days pre-tag); medium-high on the "documentation lag" finding (two independent artifacts — the schema-reference page's stale example and the calibration matrix's stale 30,720 value — both dated to the same fetch window); medium on "not strictly better," since that claim rests on the new design's own single-run, no-confidence-interval benchmark, though the specific concession (legacy blend wins on b2b-saas TTFT-p90/hit-rate) is stated candidly against the source's own interest, which raises its credibility even if the magnitude isn't statistically rigorous.
- **Boundary conditions:** This reading applies to llm-d's router/EPP scheduling layer as of the v0.9 release and dev-branch docs fetched in Sep 2026. "Default across all guides" is scoped to the four named well-lit-path guides (optimized-baseline, agentic-serving, multimodal-serving, P/D-disaggregation); it is not established that every Helm chart or third-party deployment path (this locus did not fetch raw chart `values.yaml`) inherits the same default. The "not strictly better" claim is scoped to the three workloads actually benchmarked (code-generation, reasoning, b2b-saas) on Qwen3-32B/H100 — it does not generalize to untested regimes (the source itself flags mixed-traffic and unbounded-corpus production traces as untested).
- **What would change this position:** Direct inspection of a shipped Helm chart's `values.yaml` showing a `schedulingProfiles` block that does NOT match sticky-until-saturated would undercut the "default across all guides" breadth claim. A multi-run, confidence-interval benchmark showing the token-aware design beating the legacy blend even on adversarial/pathological workloads like b2b-saas would overturn "not strictly better." Evidence that the schema-reference docs page has since been updated to the affinity-filter example would resolve the documentation-lag finding as transient rather than a real gap in project hygiene.
- **Evidence weight:** 1 first-party release blog directly states the v0.9 version pin, corroborated by 1 third-party (Red Hat) pre-v0.9 account of the prior default and 1 GitHub Releases page establishing the v0.9.0 tag date; 1 primary engineering blog + 2 GitHub primary sources (calibration README, configuration-matrix.md) support the portability/non-transplantability argument with measured data (not just the blog's framing); 2 primary canonical-docs sources (configuration-llm-d schema reference, request-scheduler-llm-d scheduling reference) support the documentation-lag finding. No source in the corpus contradicts the v0.9 pin itself; the only tension is between "default" (guide-level, confirmed) and "documented recommendation" (schema-reference page, stale) — which this note treats as a lag, not a contradiction of the pin.
