# Interim report: extension-mechanism

**Locus question:** Which extension mechanism maximizes llm-d reuse for non-pod backends: file-discovery fed by an external generator (no Go), an out-of-tree EndpointDiscovery plugin in a thin downstream EPP build (exported registry, undocumented, no precedent), an in-tree fork (documented, merge burden), embedding llm-d scheduling/kv-cache packages in a custom router, or upstreaming the plugin — and what does each cost across llm-d's ~monthly release cadence?
**Flavor:** dialectical

## What the corpus already said

The width sweep already established the core architectural fact: llm-d-router's discovery subsystem was deliberately redesigned around a pluggable `EndpointDiscovery` interface so the EPP can run without Kubernetes at all — no `ctrl.GetConfig()`, no controller manager, no `InferencePool` CRD, no K8s RBAC ([[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]). The contradiction graph's `out-of-tree-plugin-registration` cluster (`research/runs/llmd-router-nonk8s-backends-54b774/temp/contradiction-graph.json`) had already framed the live tension precisely: side A says the registry is an exported package-level map with an exported `Register()` ([[registrygo]], [[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]]), side B says the only *documented* path is editing `runner.go`'s unexported `registerInTreePlugins()` ([[llm-d-routerdocscreate_new_filtermd-at-main-llm-dllm-d-router-github]], [[runnergo]]), and the graph's own `scope_overlap` note already concluded "both right: technically sound but undocumented, unprecedented, and exposed to internal-API drift." My job was to resolve whether that residual undocumented/unprecedented risk is disqualifying or just a cost to price in — and to rank all five mechanisms named in the locus, not just the two the contradiction graph captured.

## What the new sources say

The corpus already contained the full source of `registry.go`, `runner.go`, `main.go`, `plugin.go` (file-discovery), the PR #908 review thread, PR #1007, PR #2434, and the `releases-llm-d/llm-d` timeline; I read all of these in full rather than from summaries, and the load-bearing lines are quoted below. I also dispatched one fetcher sub-task to specifically audit the locus rationale's claim that "no downstream precedent exists" — that came back with a genuinely new, load-bearing finding (issue #2105), incorporated below.

**`cmd/epp/runner/runner.go`** ([[runnergo]]) settles the mechanics precisely. `Runner` is a builder-pattern struct (`NewRunner()`, `WithExecutableName`, `WithRequestControlConfig`, `WithSchedulerConfig`, `WithCustomCollectors`, `Run(ctx)`) — a normal, importable Go type, not gated behind `internal/`. Plugin registration happens via `r.registerInTreePlugins()`, called from inside `parseConfigurationPhaseOne`, which itself is called at the top of `Run()` — i.e., **after** any external package's `init()` has already run (Go guarantees all `init()` functions across the whole program complete before `main()` begins, and `Run()` executes after `main()` starts). This ordering means a separate binary that blank-imports a plugin package (which calls `plugin.Register()` in its own `init()`) will already have its plugin type sitting in the shared `Registry` map by the time `registerInTreePlugins()` runs and starts adding the ~90 in-tree registrations I counted in that function body. There is no exported `WithPlugins(...)` or `RegisterPlugin(...)` method on `Runner` — the only injection seam is the package-level global.

**`registry.go`** ([[registrygo]], corroborated by a second independent fetch, [[llm-d-routerpkgeppframeworkinterfacepluginregistrygo-at-main-llm-dllm-d-router-g]]) confirms the seam is functionally complete, not a crippled subset: `Register`, `RegisterAsDefaultProducer`, `RegisterWithPluginDependencies`, and `RegisterDeprecated` all funnel through the same exported map writes (`Registry[pluginType] = factory`). The file lives under `pkg/` (not `internal/`), carries no package-level doc comment, and has **zero "not a public API" / "internal use only" disclaimer of any kind** — confirmed by reading the file twice, from two separate fetches taken weeks apart in fetch time. Critically, **there is no duplicate-key guard** — `Register` unconditionally overwrites `Registry[pluginType]`. Whichever `init()` runs last for a given `pluginType` string wins silently, with no panic, warning, or log line. A downstream author who is not careful about picking a distinctive plugin-type string (e.g., naming it `file-discovery` instead of something namespaced like `acmecorp-slurm-discovery`) could silently shadow or be shadowed by an in-tree plugin.

**PR #908** ([[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]]) is the single most decisive piece of evidence for *intent*. Author Ezra Silvera, explaining why discovery had to be split out of the datalayer package: *"We aim to also support non k8s in the future so we need to keep the datalayer clean: we want K8s, file, Slurm, and Ray discovery all as plugins. If discovery lives inside the datalayer, the datalayer gets contaminated with infrastructure-specific code (ctrl.Manager, fsnotify, etc.), which defeats the whole point of the abstraction."* This confirms the interface was purpose-built for exactly the user's scenario (non-pod, non-k8s backends), and confirms K8s-specific machinery is confined to the K8s discovery plugin implementation, not the shared `DiscoveryNotifier`/datastore path — a from-scratch discovery plugin for a Slurm- or Ray-like backend needs zero Kubernetes client-library imports. The same PR also surfaces an unresolved design debt: the endpoint identifier is `types.NamespacedName` (a Kubernetes type), which a reviewer flagged as "too k8s centric," and the author agreed but deferred fixing it. A non-k8s plugin must still mint synthetic `Namespace`/`Name` strings to satisfy this type — a minor friction cost, not a blocker.

**`discovery.md`**'s "Writing a custom discovery plugin" section ([[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]) is the one piece of documentation that is *not* unambiguously in-tree-only. It gives a complete, compiling code skeleton for a from-scratch `EndpointDiscovery` implementation and instructs: *"Register the factory in the runner before calling `Run`: `fwkplugin.Register(myplugin.PluginType, myplugin.Factory)`."* Unlike `create_new_filter.md`, this does not say "edit runner.go" — it is agnostic about where that `Register()` call lives, which is technically consistent with calling it from a separate `main.go`. But it is also not an endorsement of the out-of-tree pattern; it simply doesn't foreclose it.

**`create_new_filter.md`** ([[llm-d-routerdocscreate_new_filtermd-at-main-llm-dllm-d-router-github]]) is unambiguous the other way, for a different plugin category (scheduling filters): step 1 of "Hooking the filter into the scheduling flow" is *"Add an import and a `plugin.Register` call in `runner.go`"* inside `registerInTreePlugins()`. There is no out-of-tree alternative offered, even though the exact same `Register()` function is being called. This is a genuine internal documentation inconsistency across the two tutorials, not a resolved position.

**Issue #2105** ([[framework-define-a-panic-isolation-posture-for-plugin-extension-points-issue-210]]) is the single new, load-bearing finding from the follow-up search, and it is the closest thing to a maintainer-adjacent policy statement found anywhere in the corpus. Opened Jul 21, 2026 by contributor LukeAVanDrie, still open/unassigned/needs-triage at fetch time, it asks the project to record a decision on panic isolation because *"a panicking plugin kills the EPP process from any extension point; nothing recovers plugin invocations anywhere in the framework."* Of the three options the issue proposes, option 2 is the load-bearing sentence for this locus: *"Documented at-your-own-risk: in-tree plugins are the supported surface; out-of-tree plugins that panic take the process down, stated loudly in the plugin developer docs."* This is the first and only place in the entire corpus where "out-of-tree plugins" is named as a real, contemplated category distinct from in-tree ones — but it is one contributor's *proposed* framing in an untriaged, uncommented, unlinked-to-any-PR issue, not a ratified maintainer decision. It does not resolve whether out-of-tree registration is supported; it shows that *if* the project formalizes a position, "in-tree is supported, out-of-tree is at-your-own-risk" is the framing currently on the table. It also surfaces a concrete, previously-unweighed technical risk: **there is no panic recovery anywhere in the plugin-invocation path**, in-tree or out-of-tree — a panicking `Start()` goroutine in a custom discovery plugin takes down the whole EPP process, not just that plugin's functionality, regardless of which extension mechanism is chosen.

**A repo-wide GitHub issue search** ([[issues-llm-dllm-d-router-github]]) for `"out-of-tree" OR "out of tree"` returned exactly two hits across the entire issue history: #2105 (above) and one incidental, unrelated text match (#2258, a capacity-aware admission-lifecycle feature request). No GitHub Discussions results. Combined with a direct fetch of the current `CONTRIBUTING.md` (16 lines, delegates to the org-level guide, covers only issue-claiming etiquette, no mention of third-party/external plugins), this **confirms the audited absence** the locus rationale flagged as a hypothesis: there is no downstream repo, blog post, conference talk, CONTRIBUTING.md guidance, or ratified maintainer statement anywhere establishing out-of-tree plugin registration as a supported pattern. The search queries run: `"llm-d-router" "cmd/epp/runner" import`, `github.com/llm-d/llm-d-router/cmd/epp/runner site:github.com`, `"llm-d-router" custom discovery plugin fork`, `"llm-d-router" plugin.Register external`, `llm-d-router issues "out of tree" OR "out-of-tree" plugin`, `llm-d-router discussions custom plugin without fork`, `llm-d-router CONTRIBUTING.md "third-party plugin" OR "external plugin"` — all came back empty except the #2105 hit.

**Release/config-churn evidence** ([[releases-llm-dllm-d]], [[discovery-plugins-k8s-and-file-based-endpoint-discovery-by-ezrasilvera-pull-requ]], [[config-consolidate-discovery-plugins-under-a-single-discovery-sectio-llm-dllm-d]]) lets me answer the locus's explicit cadence question with real dates rather than an estimate. `llm-d/llm-d` shipped v0.3.0 (10 Oct 2025) through v0.9.0 (17 Aug 2026) — 9 minor releases in roughly 10 months, i.e., close to but slightly slower than monthly (a new minor roughly every 5-6 weeks). More important than the top-line cadence is that the discovery subsystem specifically has changed shape three times in about four months: (1) the interface itself was renamed `DiscoveryPlugin` → `EndpointDiscovery` and *moved packages* (`interface/discovery` → `interface/datalayer`) during PR #908's review (Apr 28 – May 3, 2026); (2) PR #1007 (merged May 25, 2026) moved the config key `discovery.pluginRef` from a top-level `EndpointPickerConfig` field to nested under `dataLayer`; (3) PR #2434 (merged Aug 25, 2026, explicitly a "follow up #2341") nested it *again*, from `dataLayer.discovery.pluginRef` to `dataLayer.discovery.endpoints.pluginRef`, splitting `discovery` into `endpoints`/`peers` subsections. That's three breaking or near-breaking reshapings of the exact surface a custom discovery plugin must target, landing roughly every 6-8 weeks — faster than the project's own overall release cadence, because this specific subsystem is still under active design churn (each config change did ship a backward-compatibility shim, but the *Go-level* `EndpointDiscovery` interface and factory signature are a separate surface with no such shim).

**`pkg/epp/framework/plugins/README.md`** ([[llm-d-routerpkgeppframeworkpluginsreadmemd-at-main-llm-dllm-d-router-github]]) adds two facts directly useful for weighing the mechanisms: first, every plugin — in-tree or not — is Alpha/Beta/Stable, with "none Stable pre-1.0," and Alpha plugins require `--allow-experimental-plugins` or the EPP refuses to start; a custom out-of-tree plugin registers itself with whatever `StabilityLevel` its own author chooses via `Register(pluginType, stability, factory)`, so this gate is self-administered, not a barrier. Second, the "multi-cluster" plugin variants are a documented case of the EPP's candidate endpoints being **clusters, not pods** — `multicluster-file-discovery` reads `clusters.yaml`, "the same format as the pod file discovery, except an address may be a hostname," proving the endpoint model already treats non-pod, non-IP-literal addressing as a first-class case reachable purely through `dataLayer.discovery.endpoints.pluginRef` configuration.

## Evidence synthesis

Two things are true simultaneously and neither is in serious doubt after reading the source directly: (1) out-of-tree registration works today, by construction of Go's `init()` ordering and the package-level `Registry` map — this is not a hack that depends on an implementation accident, it is the same mechanism every in-tree plugin uses, just invoked from a different `main()`; and (2) the project has never ratified this in writing, has one tutorial (`create_new_filter.md`) that actively models the *opposite* workflow, has exactly one open, untriaged, uncommented issue (#2105) that even names "out-of-tree plugins" as a category — and that issue's own proposed framing, if adopted, would formalize out-of-tree as tolerated-but-unsupported rather than endorsed — and has zero downstream examples in the corpus of anyone actually doing it, confirmed by an audited absence search rather than assumed. The dialectical question is what to do with that gap between "technically sound" and "documented and precedented."

### Position A: out-of-tree plugin + thin downstream `main()` importing `cmd/epp/runner` is the right default

The case for this is that it is genuinely lightweight in the one dimension that matters for a discovery-only integration: you write one Go file implementing a ~3-method interface (`TypedName`, `Start`, optionally `Ready`), one `init()` call, and a `main.go` that is nearly identical to the upstream's own 15-line `main.go` ([[maingo]]) — `runner.NewRunner().Run(ctx)` — plus a blank import of your plugin package. You get the entire scheduler, kv-cache scoring, flow control, HA/leader-election, ext_proc gRPC server, and Prometheus metrics stack for free, unmodified, because you are running the *same* `Run()` code path upstream runs, not a copy of it. Nothing about your integration lives inside a forked copy of llm-d-router's source, so there is nothing to rebase on every release — you bump a `go.mod` version pin and recompile. PR #908's own design rationale (Slurm/Ray named explicitly as target backends) shows this is squarely inside what the interface was built for, and the multi-cluster precedent shows non-pod addressing is already a first-class, shipped configuration shape. Issue #2105, read charitably, does not contradict this: even its "at-your-own-risk" framing treats out-of-tree as viable, just not warrantied — which is a cost (see mitigations below), not a disqualifier.

### Position B: without a ratified, maintainer-endorsed path or any existing example, out-of-tree registration is an unsupported technique dressed as a stable API, and a fork (or upstreaming) is the defensible choice

The case for this sharpened materially with the audited-absence search: it is not merely that no maintainer has said yes — a contributor has floated, in writing, in an open GitHub issue, the exact framing that out-of-tree is a second-class, unsupported category ("in-tree plugins are the supported surface"), and that framing has sat untriaged for almost two months without pushback or endorsement either way, which is itself information (the project has bigger priorities than settling this, and no one has stepped in to say "no, out-of-tree is fine"). `create_new_filter.md` remains the only plugin-authoring tutorial the project ships that talks about hooking a plugin into a running EPP, and it tells every reader to edit `runner.go`. Given the demonstrated config/interface churn (renamed/moved once, reshaped twice, in ~4 months) and the missing duplicate-key guard, and now the missing panic-recovery guarantee that #2105 surfaces (a panicking plugin — in-tree or out — takes down the whole process), a team betting production infrastructure on an unendorsed technique with zero precedent, no compatibility promise, and no crash isolation is accepting real operational risk with no one to ask when it breaks.

Both positions are consistent with the same evidence; they disagree about how much weight "the closest thing to a policy statement is an untriaged issue proposing to call this unsupported" should carry against "it works, was designed to support exactly this, and the alternatives are strictly worse on cost."

## Committed position

The evidence adds up to a staged recommendation, not a single winner-take-all mechanism, because the five options in the locus solve different sub-problems and are not mutually exclusive. First: if the non-pod backend can be reduced to a periodically-refreshed list of `address:port` + labels, use **file-discovery fed by an external (non-Go) generator** — it is already shipped, stable enough to be listed as a "New Capability" in llm-d v0.8/v0.9 release notes, requires writing zero Go code, and carries none of the registry, panic-isolation, or interface-churn risk because you never touch `pkg/epp/framework/interface/plugin` at all. Second, only when the backend genuinely needs push-based updates, richer per-endpoint metadata, or logic a flat file can't express: use the **out-of-tree `EndpointDiscovery` plugin in a thin downstream `main()`** (Position A) over an in-tree fork, because the mechanism is not a trick — it is Go's ordinary `init()`-before-`main()` guarantee applied to a package-level registry that every in-tree plugin already uses, PR #908's own design rationale explicitly names Slurm/Ray-shaped non-k8s backends as the intended audience, and the multicluster precedent proves non-pod addressing is a first-class, already-shipped path through the same config surface. Now that the audited-absence search is complete, I weight the "no precedent, no endorsement" risk as real but manageable with two concrete mitigations the evidence points to directly: (i) wrap your plugin's `Start()` goroutine in its own `recover()` regardless of what the framework does, since #2105 confirms the framework provides none, and (ii) pick a namespaced, collision-proof `PluginType` string, since `Register()` has no duplicate-key guard. The in-tree fork buys you nothing an out-of-tree plugin doesn't already get for free (same dependency graph, same interface, same config surface, same absence of panic recovery) while adding a rebase-conflict obligation against a subsystem whose config shape has changed twice and whose Go interface has been renamed once in the last four months. Third, reject embedding llm-d's scheduling/kv-cache packages into a hand-built custom router as a default: it is not lighter-weight than the plugin approach — you inherit the identical transitive dependency graph (`runner.go` imports the full plugin catalog unconditionally regardless of which plugins you configure) — while forcing you to reimplement the ext_proc gRPC server, config loader, HA/draining, and health-check wiring that `Run()` already gives you, and it multiplies your exposure to breaking changes from a handful of interfaces (`EndpointDiscovery`, `DiscoveryNotifier`) to dozens (`SchedulerConfig`, `Director`, `Endpoint`, the whole `requestcontrol` package). Fourth, pursue **upstreaming** in parallel, not instead: the maintainers have said in writing they want Slurm/Ray-class discovery plugins, and the four-PR file-discovery chain (#1080/#1081/#1218 plus #908/#1007) is a working template for how such a contribution gets reviewed and merged — but this does not replace shipping now, since merge timing isn't yours to control, most real non-pod backends will have proprietary elements that can't go upstream wholesale, and upstreaming is also the only path that would eventually settle issue #2105 in your favor by establishing out-of-tree (or your specific in-tree contribution) as a recognized, supported pattern.

- **Position:** For a backend that needs more than a static/semi-dynamic endpoint list, build a thin downstream `main()` that imports `github.com/llm-d/llm-d-router/cmd/epp/runner`, blank-imports a custom `EndpointDiscovery` plugin package that registers itself via `init()` + `fwkplugin.Register()` under a distinctive, non-colliding plugin-type string, wraps its `Start()` goroutine in its own panic recovery, and calls `runner.NewRunner().Run(ctx)` unmodified — this maximizes reuse at lower ongoing cost than an in-tree fork or a from-scratch router, and should be paired with a file-discovery-only fallback for the subset of the deployment that is expressible as a static list, plus a parallel upstreaming conversation for the discovery backend itself.
- **Confidence:** medium-high on the technical soundness (source-code-verified twice, from two independent fetches: exported registry, `init()`-ordering, no `internal/` barrier, tagged/importable module per pkg.go.dev v0.10.0). Medium, not high, on the "recommended default" ranking, because the audited-absence search — now complete — found the project's only writing on this exact question (#2105) leans toward framing out-of-tree as unsupported-but-tolerated, which is consistent with Position A being viable but not with treating it as risk-free.
- **Boundary conditions:** This holds for discovery-only integration (getting non-pod endpoints into the datastore). It does NOT extend to replacing scheduling/scoring logic itself with non-router code — `create_new_filter.md`'s in-tree-only instructions govern that surface, and no equivalent "write it as a separate package" doc language exists for scorers/filters/pickers the way `discovery.md` provides for discovery. It also assumes the backend's identity model can be shoehorned into `types.NamespacedName` (namespace+name strings) and IPv4-or-hostname-style addressing; backends needing richer identity are outside what I verified. It assumes the operator accepts that a panic anywhere in the plugin-invocation path (in-tree or out) currently has no framework-level recovery per #2105, and mitigates this at the plugin-code level rather than waiting on upstream.
- **What would change this position:** (a) issue #2105 resolving toward option 2 ("documented at-your-own-risk") being formally merged into the plugin developer docs would not change the ranking but would raise confidence to high, since it converts an inferred posture into a written one; (b) issue #2105 resolving toward a stricter option (e.g., disallowing/detecting out-of-tree registration, or requiring plugins to be compiled into the official binary) would flip the recommendation toward fork-and-upstream; (c) evidence that `registerInTreePlugins()` has ever silently overwritten a community-chosen plugin-type string (a real collision incident) would elevate the duplicate-key-guard risk from theoretical to demonstrated; (d) a fourth config-schema reshaping of `dataLayer.discovery.*` within weeks of this note would push the interface's "still churning" characterization from "recent history" to "ongoing pattern," strengthening the case for pinning tightly and re-testing every release regardless of mechanism.
- **Evidence weight:** Technical viability of out-of-tree registration: source-code-certain (registry.go read in full from two independent fetches, runner.go, main.go). Design intent (Slurm/Ray as first-class targets): one maintainer PR-review quote, high confidence. Documentation posture: mixed/contradictory between two official tutorials (create_new_filter.md vs. discovery.md). Precedent/endorsement: audited absence confirmed by a 7-query search sweep plus direct CONTRIBUTING.md and issue-tracker fetches — zero downstream examples, zero ratified policy, one open untriaged issue (#2105) whose only proposed framing leans against treating out-of-tree as fully supported.

## Open questions

- Whether issue #2105 gets triaged/resolved, and in which direction, before the user's implementation window — worth a calendar check against llm-d-router's issue-triage cadence.
- Whether a fourth reshaping of the `dataLayer.discovery.*` config surface is already proposed/planned for v0.10 (targeted September 2026 per [[llm-d-v09-hardened-for-scale-llm-d]]) — worth checking the v0.10 milestone/issue tracker directly.
- Whether `cmd/epp/runner` carries any implicit "not a public API" understanding among maintainers despite living outside `internal/` and carrying zero disclaimer in either fetch of registry.go — not found in any doc in the corpus; #2105 is adjacent evidence but doesn't resolve this directly.
- GitHub code search for cross-repo importers of `github.com/llm-d/llm-d-router/cmd/epp/runner` hit an auth wall during the follow-up search and was not completed — a logged-in GitHub code search (or `pkg.go.dev`'s "Imported By" listing for the module) would give a more definitive precedent count than the web-search sweep did.
