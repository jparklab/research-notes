# Interim report: custom-discovery-plugin-design

**Locus question:** Since llm-d ships no dynamic discovery backend, what should a production custom EndpointDiscovery plugin (Consul/etcd/cloud SD/Slurm/Ray-fed) look like — watch vs poll, initial enumeration + Ready semantics, single-goroutine notifier ordering, health filtering, identity synthesis (NamespacedName, --pool-namespace), labels for P/D roles — using Dynamo (etcd/NATS), production-stack (StaticServiceDiscovery), RAMSES (Postgres-fed) and the file plugin as design references?
**Flavor:** synthesis (treated as convergent — no opposing camps, but a load-bearing correction to the width corpus)

## What the corpus already said

The width sweep already assembled the core interface contract and the file-discovery plugin as the only shipped example. [[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]] (PR #908, merged) captures the author's own rationale for making discovery a separate pluggable layer: *"We aim to also support non k8s in the future so we need to keep the datalayer clean: we want K8s, file, Slurm, and Ray discovery all as plugins. If discovery lives inside the datalayer, the datalayer gets contaminated with infrastructure-specific code (ctrl.Manager, fsnotify, etc.)."* [[llm-d-routerpkgeppframeworkinterfacedatalayerdiscoverygo-at-main-llm-dllm-d-rout]] gives the exact interface at HEAD (`Start`, `Ready`, `DiscoveryNotifier.Upsert/Delete`), and [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]] is the canonical doc with a full custom-plugin skeleton and the resolved config path `dataLayer.discovery.endpoints.pluginRef`. [[plugingo]] and [[llm-d-routerpkgeppframeworkpluginsdatalayerdiscoveryfile-at-main-llm-dllm-d-rout]] cover the only shipped implementation, FileDiscovery. [[endpoint-metadata-updates-do-not-trigger-endpoint-notification-events-issue-1403]] documents a real correctness bug (metadata-only updates didn't fire notifications) fixed in v0.9.0. [[llm-d-routerpkgeppframeworkpluginsschedulingfilterbylabelrolesgo-at-main-llm-dll]] gives the closed set of `llm-d.ai/role` values the scheduler's P/D filters read from the generic label map. The width corpus also holds three external analogues already summarized at a useful level of depth: Dynamo's README ([[github-ai-dynamodynamo-a-datacenter-scale-distributed-inference-serving-framewor]]), production-stack's router config via DeepWiki ([[router-configuration-vllm-projectproduction-stack-deepwiki]]), and the RAMSES HPC paper ([[automated-dynamic-ai-inference-scaling-on]]). Critically, the existing note on PR #1007 ([[discovery-plugins-k8s-and-file-based-endpoint-discovery-by-ezrasilvera-pull-requ]]) states the PR — which would have delivered the only Kubernetes-native, watch-based `EndpointDiscovery` plugin implementations (`inference-pool-discovery`, `static-selector-discovery`) — was "merged May 25 2026." **This is factually wrong, and the error matters a great deal for this locus's design question** (see below).

## What the new sources say

I spent most of this locus's fetch budget correcting and hardening that one fact rather than skimming more secondary material, because it changes the effort estimate and the reference-design recommendation materially. I verified directly against the GitHub REST API (not scraped prose) that:

- `GET /repos/llm-d/llm-d-router/pulls/1007` returns `"merged": false, "merge_commit_sha": null, "closed_at": "2026-05-25T10:35:40Z"`.
- The PR's own file-change list (`GET .../pulls/1007/files`) shows it *did* add `pkg/epp/framework/plugins/datalayer/discovery/k8s/k8s_discovery.go` and `pod_extractor.go` in its branch — but a full recursive tree listing of `main` today (`GET /repos/llm-d/llm-d-router/git/trees/main?recursive=1`) shows **no `discovery/k8s/` directory exists anywhere in the current tree** — only `discovery/file/`.
- The PR's own comment thread supplies the reason. The maintainer (ahg-g) pushed back: *"This PR is very large and I advise against merging it as is and recommend to break it into smaller PRs."* The author (ezrasilvera) then wrote `/hold` and, on 2026-05-13: *"Don't merge this PR for now. Instead we will interduce the change in stages starting from the file discovery. The first two PRs in the path to support filediscovery can be found in #1080 and #1081."* The closing comment on 2026-05-25 reads: *"Replace with teh file discovery PRs."*
- PRs #1080 and #1081 (both confirmed merged, 2026-05-14) shipped only the plumbing FileDiscovery needed (`BackendUpsert/Delete`, `DiscoveryBackendStore`, `NewDiscoveryNotifier`) — not the K8s plugin refactor.
- I additionally confirmed via `grep` on the raw HEAD `cmd/epp/runner/runner.go` that the branch point is exactly what the abandoned PR would have removed: `Run()` still calls `ctrl.GetConfig()` and stands up a controller-runtime manager directly (line ~274) for the Kubernetes default path, entirely separate from `resolveDiscovery`/`runWithFileDiscovery`, which only fires when `dataLayer.discovery.endpoints` is configured.

I also delegated a fetcher subagent to land four corroborating/supplementary sources, all of which landed and materially sharpen the poll-vs-watch design guidance below:

- **[[watcherrs]]** — Dynamo's `ModelWatcher` (`lib/llm/src/discovery/watcher.rs`). This is a *consumer* of an abstract `DiscoveryStream`, not the raw etcd/NATS wire client (that lives deeper in the `dynamo_runtime` crate, unfetched), but it is still a useful structural analog: `ControllerHost::list_instances()` performs `self.drt.discovery().list(DiscoveryQuery::AllModels)` — an explicit full-enumeration call kept separate from the incremental `DiscoveryEvent::Added`/`Removed` stream, the same List-then-Watch split llm-d-router's `Ready()`-before-watch contract assumes. Its test harness (`apply_discovery_event`) gates each event behind an explicit ack so the controller finishes processing one event before the next is delivered — sequential, non-interleaved application is enforced in tests, not just documented. No reconnect/resync logic is visible in this file, so it does not resolve the harder etcd-watch-reconnect question.
- **[[blocking-queries-consul-hashicorp-developer]]** — Consul's official blocking-query contract. This changes my effort estimate for Consul specifically (see synthesis below): a blocking GET with `index=<X-Consul-Index>` and `wait=<duration>` is long-polling, not a persistent stream, and HashiCorp's own docs hand a plugin author the exact edge-case list to code against: reset the tracked index to 0 if a response's index is *lower* than the last one seen (raft snapshot restore or KV-list edge cases), sanity-check `index > 0`, and client-side rate-limit the loop (token bucket, burst ~2) rather than sleeping, since sleeping delays delivery. The doc's own words: *"the return of a blocking request is no guarantee of a change."*
- **[[health-http-api-consul-hashicorp-developer]]** — Consul's Health HTTP API. `/v1/health/service/:service?passing=true` is a documented, server-side health filter — *"Specifies that the server should return only nodes with all checks in the passing state. This can be used to avoid additional filtering on the client side."* This is the exact Consul-side mechanism for the "only Upsert healthy endpoints" contract discussed below; a plugin does not need to fetch every instance and filter client-side.
- **[[service_discoverypy]]** — production-stack's actual `service_discovery.py` (superseding the DeepWiki secondary summary already in the vault). The `ServiceDiscovery` ABC has exactly one required method, `get_endpoint_info() -> List[EndpointInfo]`; `get_health()` and `close()` have default/no-op implementations. `StaticServiceDiscovery` is a genuinely useful hybrid: topology is fixed at construction (parallel `urls`/`models` lists, length-asserted), but health is *not* static — when `static_backend_health_checks=True` it spawns a background thread that calls `check_model_health()` on an interval (default 60s) and filters unhealthy URLs out of `get_endpoint_info()`'s return value without ever changing the underlying list. Its Kubernetes implementations (`K8sPodIPServiceDiscovery`, `K8sServiceNameServiceDiscovery`) use the official `kubernetes.watch.Watch()` client in a background thread with an ad hoc reconnect: catch any exception, sleep 0.5s, retry the watch — no exponential backoff, no explicit mention of `resourceVersion`-based resume shown in the note. That is a useful calibration point: a real, apparently production-used discovery backend's reconnect logic is a flat retry loop, not a sophisticated resync protocol — the bar for "good enough" is lower than a from-scratch design might assume, though it also means naive reconnect can silently miss events during the gap unless the client re-lists on reconnect (not confirmed either way from this source).

The blog post ([[no-kubernetes-no-problem-llm-d-now-runs-anywhere-llm-d]]) independently confirms the same gap from the roadmap side: it lists four discovery strategies in ascending sophistication and explicitly puts the fourth in the future-work bucket — *"Orchestrator-native discovery plugin (future work) - for the most dynamic case, a dedicated `SlurmDiscovery` or `RayDiscovery` plugin against the same `EndpointDiscovery` interface, talking to the orchestrator directly with no file in the loop."* The three strategies that are NOT future work — static file, generator script + static file, generator script + `watchFile: true` — are all variations on the one shipped plugin. The Ray and Slurm "generator" patterns it documents are literally a cron/webhook script that calls `ray.nodes()` or `scontrol show hostnames` and rewrites `endpoints.yaml`, which FileDiscovery's fsnotify watch then picks up. This is corroborating, independent confirmation (blog roadmap language, written by the same team, at a different time, for a different purpose) of the same fact the PR-history dig established: **as of the current release train, nobody — including the llm-d-router maintainers themselves — has shipped a *watch-based, live-backend* `EndpointDiscovery` plugin.** The only production pattern in current use for anything other than Kubernetes' own pod watch is poll/regenerate a file.

## Evidence synthesis

**The interface itself is genuinely backend-agnostic and small**, and every corpus source that touches it agrees on the same three hard constraints, which is the strongest signal in this locus:

1. *Initial enumeration + Ready() semantics.* `docs/discovery.md` and `discovery.go`'s doc comments state implementations SHOULD enumerate all known endpoints via `notifier.Upsert` before entering a watch loop, "to avoid serving an empty datastore at startup," with an explicit carve-out for mechanisms whose watch protocol guarantees no missed events (list+watch is the named example — ironic, since the k8s discovery plugin that would have used this carve-out never shipped). `Ready()` "is closed at most once per Start invocation," "only after a successful initial sync," and explicitly "zero endpoints is a valid outcome" — a plugin author must not gate `Ready()` on `len(endpoints) > 0`. Dynamo's `ModelWatcher` independently validates the same List-before-Watch split (`list_instances()` as a distinct call from the `DiscoveryEvent` stream).
2. *Single-goroutine notifier ordering.* This is stated identically in the interface doc comment, the docs.md prose, and the PR #908 review thread: `DiscoveryNotifier` is "NOT goroutine-safe. All calls must be made sequentially from a single goroutine," and "an Upsert followed by a Delete for the same endpoint must arrive in that order, or the endpoint will be incorrectly left in the datastore." FileDiscovery's own `Start`/`load` implementation is the concrete proof this is achievable simply: it runs a single `for { select }` loop over `ctx.Done()`, `watcher.Events`, and `watcher.Errors`, and `load()` is only ever called from that one loop — never from a second goroutine. Dynamo's test harness enforces the equivalent property (one event fully processed before the next is delivered) with an explicit ack gate, not just a code comment — worth copying as a testing pattern, not just a runtime one.
3. *No generic health gate off Kubernetes.* `docs/discovery.md` is explicit that Kubernetes' aggregate `Ready` condition (and custom readiness gates) is a K8s-only mechanism: *"a custom backend must replicate itself"* — the doc's own phrase, describing this as one of the things "inactive" outside K8s. Nothing in the datastore automatically expires or health-checks a non-Kubernetes endpoint; if a plugin's backend doesn't tell it an endpoint died, the datastore will route to it forever. Consul's `/v1/health/service/:service?passing=true` and production-stack's `StaticServiceDiscovery` background health-check thread are two independent, already-shipped answers to exactly this gap in two different ecosystems — a custom llm-d-router plugin should copy the shape of one of these (server-side filter where available, client-side polling loop where not) rather than invent a third.

**The identity-synthesis gap flagged in the PR #908 review was never closed.** A reviewer asked whether `Delete(id types.NamespacedName)` was "too k8s centric" and whether the interface should carry an explicit `UniqueID` instead; the author agreed ("several other places using NamespacedName and we should switch to ID") but deferred it. `EndpointMetadata.ID` is still `types.NamespacedName{Name, Namespace}` at HEAD. This is a real design tax on non-k8s plugin authors: they must synthesize a stable, restart-durable two-part identity (e.g. a Consul service ID split into name+partition, or an etcd key path split at a chosen delimiter) even though nothing about their backend has a natural "namespace" concept. `--pool-namespace` (flag > `NAMESPACE` env var > `"default"` fallback, per docs.md) is a *different* namespace — the router-instance-level pool identity used in metrics/logs — and must not be conflated with each `EndpointMetadata.ID.Namespace`, which is a per-endpoint grouping key defaulting to `"default"` in the file schema.

**External analogues converge on the same two-or-three-tier shape llm-d-router chose, and the newly-fetched sources refine rather than overturn that picture.** Dynamo explicitly makes etcd/NATS *optional* — required "only for Slurm or other distributed deployments," not for local dev or Kubernetes — mirroring llm-d-router's own split between the zero-dependency file plugin and a hypothetical coordination-service-backed plugin. Production-stack's `ServiceDiscovery` ABC ships exactly three implementations in practice (`K8sServiceDiscovery` variants, `StaticServiceDiscovery`, and a no-op `ExternalOnlyServiceDiscovery`), with `StaticServiceDiscovery` explicitly built for "non-Kubernetes deployments or testing" — the same tiering, arrived at independently by a different project against a different scheduler — but its *implementation* is not purely static: it layers a periodic health-check thread underneath a fixed topology, which is precisely the hybrid this report recommends for a Consul- or Postgres-backed llm-d-router plugin (fixed-or-slow-changing topology fetch, faster health re-check). RAMSES is the most different of the three: its Web Gateway does a live per-request lookup against a Postgres table rather than maintaining a locally-cached, event-driven set the way llm-d-router's datastore does, so it validates the "coordination-store-fed" *idea* but not the "push-notifier" *mechanism* — a Postgres-backed `EndpointDiscovery` plugin for llm-d-router would need to add a poll-and-diff loop (structurally identical to `FileDiscovery.load()`: snapshot the query result into a map, `Upsert` everything present, `Delete` anything in the previous snapshot but absent from the new one) rather than copy RAMSES's per-request-query pattern directly, because the router's plugin contract is push/cache, not pull/proxy. Consul is the one backend in this locus's evidence set with a fully documented, well-understood long-poll primitive (blocking queries) — which means "watch vs poll" is not a strict binary for Consul specifically: a blocking-query loop is still just a sequence of HTTP request/response cycles (no persistent-connection state machine to manage), and HashiCorp's docs hand a plugin author the complete edge-case list (index regression, index sanity check, client-side rate limiting) up front.

## Committed position

The evidence adds up to a three-tier recommendation, not a strict poll-vs-watch binary, and the newly-fetched Consul and production-stack sources are what forced the split from two tiers to three. **Tier 1 — interval poll + diff** (generalize `FileDiscovery.load()`: snapshot a query result into a map, `Upsert` everything present, `Delete` anything absent from the previous snapshot) is the right default for any backend with no cheap long-poll primitive: a generic REST cloud-SD API, a Postgres table (RAMSES-style), a plain `ray.nodes()` call. Budget roughly 2-4 engineer-days — it is a near-mechanical transliteration of ~200 lines of already-reviewed, tested reference code, plus backend-specific health filtering. **Tier 2 — long-poll / blocking-query** applies specifically where the backend offers one, as Consul does: replace the `time.Ticker` with a blocking GET carrying the last-seen index, apply `?passing=true` for health, and code the three documented edge cases (index regression, index>0 sanity check, client-side rate limiting). This is barely more code than Tier 1 — still a synchronous request/response loop, not a connection state machine — and gets near-real-time updates for perhaps 1-2 additional engineer-days over Tier 1, because HashiCorp's own docs supply the complete failure-mode checklist. **Tier 3 — genuine persistent-connection watch** (etcd `Watch`, a cloud provider's push-based SD stream, or a from-scratch Kubernetes-style watch client) is where the real risk lives: budget 1-2 engineer-weeks, because llm-d-router itself has zero in-repo precedent for this shape — its one attempt (PR #908 → #1007) to ship a watch-based Kubernetes discovery plugin under this exact interface was explicitly abandoned by its own author as too large and risky to review, and the interface's own doc comments name Kubernetes list+watch as the reference case for the "no separate initial enumeration needed" carve-out while that very plugin never shipped. The one piece of comfort from the new evidence is production-stack's own Kubernetes watch client: its reconnect logic is a flat catch-sleep(0.5s)-retry loop, not a sophisticated resync protocol, suggesting "good enough" for a first cut of Tier 3 is lower-effort than a textbook implementation would suggest — but "good enough" here still risks silently missing events during a reconnect gap unless the plugin re-lists after every reconnect, which is exactly the kind of correctness detail that has no test coverage anywhere in this evidence set. Reserve Tier 3 for cases where Tier 1/2 staleness has a named, measurable cost (autoscaling-driven churn, short-lived RL rollout workers where GPU-seconds are wasted routing to now-dead endpoints during the poll window) rather than defaulting to it because "watch feels more correct" — the team that owns this exact interface tried that and backed out.

- **Position:** Use a three-tier decision rule for a custom (non-k8s) `EndpointDiscovery` plugin: Tier 1 (poll+diff, ~2-4 days) as the default; Tier 2 (long-poll/blocking-query, +1-2 days over Tier 1) wherever the backend natively supports it (Consul is the clearest case in this evidence set); Tier 3 (persistent watch, ~1-2 weeks, no in-repo precedent, must design and test reconnect-then-relist explicitly) only when named staleness costs justify it.
- **Confidence:** high on the structural/interface facts and the PR #1007 abandonment (source-verified against HEAD via direct API/raw-source reads, confirmed three independent ways); medium-high on the three-tier framework, which is now supported by a fully-documented mechanism (Consul blocking queries) rather than asserted from the interface contract alone; medium on the specific day-count estimates, which remain my calibrated judgment, not a reported number — no team in this evidence set has published effort spent building a from-scratch non-k8s `EndpointDiscovery` plugin for llm-d-router specifically.
- **Boundary conditions:** This holds for the current interface generation (post-#908, i.e. `Ready()` present, `dataLayer.discovery.endpoints.pluginRef` config shape) and for llm-d-router versions ≥ v0.9.0 (needed for the endpoint-metadata-update notification fix in #1403/#1404 — an older version will silently starve any consumer of `endpoint-notification-source`, e.g. precise-prefix-cache KV-event subscribers, on metadata-only changes such as address or role-label updates). It does not address peer discovery (`dataLayer.discovery.peers`), a structurally separate, more recently added mechanism (config consolidated 2026-08-25) outside this locus's source budget. The Tier 2 "barely more code than Tier 1" claim is specific to backends with a documented long-poll primitive (Consul, etcd's older long-poll-style watch); it does not generalize to backends with no such primitive, which have no middle tier and must choose between Tier 1 and Tier 3 directly.
- **What would change this position:** A published or observable case where a poll-and-diff or blocking-query plugin caused a correctness/availability incident specifically attributable to staleness (not implementation bugs) would strengthen the case for defaulting to Tier 3 in that class of deployment. Discovery that any part of the abandoned PR #1007 k8s-plugin refactor has since been revived under a new PR number would supply the missing in-repo Tier-3 precedent and should lower both the effort estimate and the risk premium attached to Tier 3 above — this is worth a direct follow-up search the next time this locus is revisited, since I did not find one in this pass.
- **Evidence weight:** 3 primary-source facts (interface doc comments, FileDiscovery's complete source, PR #908 review thread) directly support the ordering/Ready/health-gap findings with no contradiction anywhere in the corpus. The PR #1007 abandonment is confirmed by 3 independent mechanisms (PR REST API state, tree-listing absence, the PR's own closing comment) plus 1 corroborating source (the blog's future-work framing) — very high confidence on that specific fact. The three-tier framework is supported by pattern-matching across 4 independent external systems (Dynamo, production-stack, RAMSES, Consul's own documented primitives) that converged on variants of tiered topology/health handling, but the tier boundaries and day estimates are my own synthesis, not a claim any single source makes explicitly — flagged as medium confidence accordingly.

## Open questions

- Has any part of the abandoned PR #1007 k8s-plugin refactor been revived under a different PR number since 2026-05-25? A targeted search of merged PRs referencing "k8s_discovery" or "inference-pool-discovery" post-abandonment would resolve this and could change the effort estimate for Tier 3.
- Dynamo's actual etcd/NATS wire-level watch implementation (in `dynamo_runtime`, not `lib/llm/src/discovery/watcher.rs`) was not reached this pass; it would be the most directly transplantable Tier-3 reference if it documents a specific resync-token or lease-renewal pattern, since `watcher.rs` itself is a consumer layer above that logic.
- Whether `--pool-namespace`'s interaction with per-endpoint `EndpointMetadata.ID.Namespace` has any documented multi-tenancy implication (e.g., can two pools share endpoint namespaces without collision) was not explored — out of scope for this locus's budget but relevant to a "cloud SD" backend spanning multiple accounts/projects.
- Whether production-stack's Kubernetes watch client actually re-lists after a reconnect (versus resuming blind from the last known state) was not confirmed from the fetched summary — this is the single detail that would validate or refute using its reconnect loop as a "good enough" Tier-3 calibration point.
