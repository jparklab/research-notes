# Interim report: kubernetes-vs-slurm-control-plane-evidence

**Locus question:** On a shared on-premise cluster, when does keeping Slurm or plain systemd beat Kubernetes, and what exactly does each choice give up in autoscaling, isolation and gateway capability?
**Flavor:** dialectical
**Budget note:** 0 new fetches; all 8 substantive vault notes read in full (body text). Budget spent on reading, not fetching, because the vault already held the primary sources.

## What the corpus already said
The width sweep held five HPC/institutional primary accounts: DHinfra.at [[design-and-operation-of-a-federated-gpu-cluster]], GWDG Chat AI [[research-paper]], Argonne FIRST [[first-federated-inference-resource-scheduling-toolkit-for]] plus its gateway repo [[github-argonne-lcffirst-inference-gateway-for-batch-and-interactive-llm-requests]] and ALCF docs [[alcf-inference-endpoints-alcf-user-guides]], Sandia's dual-platform report [[experience-deploying-containerized-genai-services]], STREAM [[stream-multi-tier-llm-inference-middleware-with]] and ExaServe [[exaserve-large-scale-llm-serving-on-exascale]]; and one Kubernetes-side counterweight, Red Hat's study [[evaluating-kubernetes-performance-for-genai]]. The baseline report's "control plane covered by KServe" verdict is conditional on a Kubernetes substrate none of the HPC accounts have.

## What the sources say (from full text)

**DHinfra.at (arXiv 2609.10552, preprint, ~1.5 FTE).** Table 3 "Design decisions and rejected alternatives": "Service orchestration | Chosen: Docker Compose + systemd | Not adopted: Kubernetes / K3s | Deciding reason: About ten services on a handful of nodes; Compose is sufficient and simpler. K3s is a growth path past roughly fifteen services or per-user pod isolation." CRITICAL NUANCE the summary hid: Compose+systemd orchestrates only the ~10 *platform* services on the head node. The GPUs are still scheduled by **Slurm**: "Each model's launch command allocates GPUs as a Slurm job under a single trusted service account and runs the engine (vLLM, or llama.cpp for one-slot models) in a container ... (salloc -> srun -> docker run ...) ... A GPU is therefore held only while its model is loaded ... Slurm, not the router, arbitrates the GPUs." The router is llama-swap, which "holds no GPUs; it is an HTTP front for engine lifecycle." So DHinfra is Slurm + llama-swap, not "no scheduler". User containers: Enroot+Pyxis rejected Docker for users because "Docker's root daemon is equivalent to root on the node; unsafe for multi-tenant user containers" (yet the service account path uses root Docker - a deliberate trusted/untrusted split). Storage: "Benchmarked: the head node's 22-drive ZFS pool over InfiniBand beats a compute node's two-drive local NVMe (140 GB cold start ~5 s vs ~20 s)." Mechanism stated: it is a 22-drive ZFS pool (aggregate bandwidth, plus likely ARC cache) over RDMA vs a 2-drive NVMe; so the inversion is a statement about drive count and fabric, not about NFS being inherently faster than NVMe. Single-site, one benchmark, preprint.

**Control-plane build (DHinfra).** FastAPI console/gateway behind Traefik forwardAuth; Redis caches auth for 60 s; Postgres holds budgets, models, usage, ACLs; "per-project token budgets, model access-control lists, and an OpenAI-compatible gateway"; "daily and weekly" budget windows per group, cap frozen at window rollover "cap = member_count x default_per_user_per_window"; per-model input/output "cost factors" so "a cheap small model can be priced below 1.0"; per-model concurrency semaphore; approval queue worked by "a separate worker, pm-agent". Their related-work framing is explicit: "Our serving layer reuses these components [vLLM]. The work specific to our platform is the policy layer around them."

**GWDG Chat AI (Slurm-native).** Rejection reason, verbatim: trying other approaches "would require replacing Slurm with another scheduling system such as Kubernetes. This would disrupt existing users and workflows of such a system and force users to migrate to the new system. By keeping the existing resource manager, the inference service could operate side by side with user workloads and utilize gaps in the Slurm scheduling." What it surrenders is stated by the authors themselves: "Slurm does not inherently provide an option to scale up the number of jobs as the number of requests increases, requiring additional efforts to implement automatic scaling"; "Slurm does not implement mechanisms to ensure constant availability such as health checks"; "An infrastructure that is dedicated and tailored to running production services may therefore consistently outperform the architecture proposed in this paper"; cold loads "can take multiple minutes" versus seconds for serverless functions. Implementation: a scheduler script uses squeue/sbatch, lock file, a routing table of (service,node,port), random port per job because "Slurm provides no network virtualization", "selected randomly out of all eligible instances, effectively performing random load balancing", and autoscaling from "the average number of concurrent requests to each service within a predefined time window"; scale-down is by letting jobs "expire without resubmitting them". Access is gated by SSH ForceCommand and a cloud-interface script. Engine: open-source vLLM. (I did not find usage totals I could verify in the extract beyond table-of-figures stubs; do not cite GWDG volume figures from this pass.)

**FIRST/ALCF.** Gateway: "asynchronous Django-Ninja API application that connects to a PostgreSQL database and communicates with Globus", Nginx in front, Globus Compute as dispatch layer which can target "Kubernetes pod, or ... batch-scheduler submission (e.g., PBS or Slurm)". NOTE Sophia runs **PBS**, not Slurm (cold start "submitted to the cluster's scheduler (e.g., PBS)"). Autoscaling is a Globus Compute endpoint feature: admins set "maximum number of parallel inference tasks within a node, and the maximum number of nodes an LLM can scale up to"; hot nodes "released after an extended idle period (currently 2 hours)"; co-location (70B on 6 GPUs + 8B/7B on remaining 2 of 8). Cold start: scheduler queue wait plus load, with a 405B "potentially needing 800 GB or more of VRAM" across nodes. Scale: "Since its deployment on July 2024, this service has processed 8.7 million inference tasks, served 76 users in total, and generated over 10 billion tokens. About 4.1 million tasks were single interactive requests. The other 4.6 million tasks were packaged into 49 batch requests, which generated over 6.2 billion tokens." Sophia = 24-node shared cluster. ALCF docs [[alcf-inference-endpoints-alcf-user-guides]]: four active backends - Sophia A100 via vLLM (endpoints incl. /chat/completions, /responses, /messages, /completions, /embeddings, /batches), Metis SN40L, Minerva B200, Tara GH200 ("DirectAPI"); tokens valid 48 h, "internal policy requires re-authentication every 30 days"; I counted 19 listed institutional IdP domains (ANL, ALCF, Ames, BNL, FNAL, LANL, INL, JLab, LBNL, LLNL, NERSC, NETL, NREL, NLR, ORNL, PPPL, PNNL, Sandia, SLAC). Audited absence: no node counts or usage for Metis/Minerva/Tara anywhere in the vault; none inferred. Note the platform has since added non-vLLM "DirectAPI" backends - the gateway is engine-agnostic.

**Sandia [[experience-deploying-containerized-genai-services]].** The counter-case inside one institution: both HPC (Slurm/Flux) and multi-tenant OpenShift clusters ("Goodall" H100+InfiniBand; "CEE-OpenShift" A100/H100 "for larger-scale production deployments"). Same vLLM containers on both; on Kubernetes they "migrated to using the recently added Helm chart provided by the upstream vLLM project"; runtime friction is on the HPC side (Apptainer runs as calling user and the vLLM container "crash[es] at startup using Apptainer's default configuration"). Evidence that a lab hosts *user-facing services* on Kubernetes and *batch/experimental* on HPC.

**STREAM and ExaServe.** STREAM (UIC, PEARC'26): Slurm persistent GPU job on an H100 NVL, Apptainer ("HPC clusters do not permit Docker"), Globus Compute CPU worker, LiteLLM OpenAI gateway with tiers local/HPC/cloud; a CUDA 12.9 image vs driver 12.4 mismatch silently disabled Marlin AWQ kernels (20.1 tok/s) - an HPC driver-lag cost. ExaServe (UChicago/Argonne): states that mainstream stacks "typically assum[e] a Kubernetes-style control plane and an external load balancer, services not exposed within batch HPC allocations"; on Aurora 1-256 nodes (3072 vLLM replicas), 27.1k req/s non-streaming, centralized streaming proxy plateaus ~4.7k req/s, Ray Serve O(N^2) control-plane bring-up ~30 min at 256 nodes; it also uses LiteLLM as gateway. Exascale demo, not a shared-user service.

**Red Hat [[evaluating-kubernetes-performance-for-genai]] - CLOUD testbed.** All experiments ran on ROSA (managed OpenShift 4.19.16 / K8s 1.32) on a single AWS p4d.24xlarge (8x A100) - not on-prem hardware. It shows what Kubernetes adds that the Slurm scripts lack: Gateway API Inference Extension / llm-d EPP routing. "Random Scheduling (~500 ms) is approximately 6.25 times slower than Precise Scheduling (~80 ms)", with p99 TTFT "up to 20 times slower". The random-vs-cache-aware contrast is exactly GWDG's design (random) versus the K8s-native alternative. Vendor-authored (Red Hat), single-model/single-node-class setup; treat as a recommendation-grade result for the size of the gap, not evidence of on-prem deployment. Caveat: the gain depends on workload prefix reuse (their summarization workload).

## Evidence synthesis
**Capability absent vs implemented differently.** Autoscaling: present in both, implemented as a user-space loop. GWDG's is concurrency-average-driven sbatch/expire; FIRST's is Globus Compute max-node/idle-timeout policy; DHinfra's is llama-swap load-on-first-request plus per-model Slurm allocation. All three pay scheduler queue time plus weight load on every scale-up (GWDG: "multiple minutes"; FIRST: queue + 800 GB-class 405B load). What is genuinely **absent** is (a) sub-minute scale-out from a pre-warmed pool unless idle nodes are held (FIRST's 2 h hot hold is precisely the buy-back, at the price of idle GPUs), (b) cache-aware/queue-aware routing (GWDG random; DHinfra concurrency semaphore only; Red Hat shows ~6x mean TTFT and up to 20x p99 on a prefix-heavy workload), (c) network virtualization/service discovery/health checks (GWDG: random ports, probe loop, "Slurm provides no network virtualization"). Isolation goes the other way: HPC gets rootless containers (Enroot/Pyxis, Apptainer), SSH-ForceCommand and POSIX permissions, plus fair-share accounting and gap-filling next to training jobs; Kubernetes offers namespaces/quotas (Sandia's multi-tenant OpenShift) but DHinfra says K3s is warranted only for "per-user pod isolation".

**What both camps build identically.** Every account independently wrote the same four components, regardless of substrate: (1) an OpenAI-compatible front door (FIRST Django-Ninja+Nginx; DHinfra FastAPI+Traefik; GWDG API gateway + HPC proxy; STREAM and ExaServe LiteLLM; ALCF serves /chat/completions, /responses, /messages, /embeddings, /batches); (2) identity/authz integration (Globus Auth + ~19 DOE IdPs; Authentik SAML/OIDC via ACOnet; SSH keys/ForceCommand); (3) per-tenant accounting (DHinfra daily/weekly group token budgets with cost factors; FIRST Postgres usage log and TPM rate limiting; Slurm accounting for GWDG/DHinfra); (4) model lifecycle/warm-pool management (llama-swap tiers, Globus hot nodes, scheduler-script routing table). Meanwhile the engine (vLLM, llama.cpp) and schedulers (Slurm/PBS) are always open-source and reused; none wrote an inference engine. The "built own" surface is thus the policy/admission/accounting/lifecycle layer, and DHinfra says so in terms.

**Disagreement is mostly definitional.** "Kubernetes vs Slurm" is not one choice: DHinfra uses Slurm for GPUs and Compose/systemd for services; FIRST abstracts the scheduler behind Globus Compute and lists Kubernetes as one backend; Sandia runs both with identical containers. The rejected thing in each case is a *second control plane*, not Kubernetes per se.

### Position A (keep Slurm/PBS/systemd): switching cost and population fit dominate
GWDG: replacing Slurm "would disrupt existing users and workflows"; DHinfra: ten services, 1.5 FTE, Compose "sufficient and simpler"; FIRST: Argonne's existing PBS fleet and Globus federation across sites; ExaServe: leadership machines are Slurm/Flux/PBS and offer no K8s. Strongest evidence: working production at 8.7M requests / 10B+ tokens on a 24-node Sophia, with 76 users - at the author-stated cost of cold starts and random routing.
### Position B (Kubernetes): the missing capabilities are exactly the inference-specific ones
Red Hat's EPP/GAIE result (random ~500 ms vs ~80 ms TTFT; p99 up to 20x), Sandia's use of OpenShift for "production deployments" and Helm-chart deployment of upstream vLLM, and GWDG's own concession that a dedicated service infrastructure "may consistently outperform". Weakness: the K8s evidence is cloud-hosted and vendor-authored; no on-prem K8s inference account in the vault discloses scale.

## Committed position
Control-plane choice on-premise is determined by **who already owns the GPUs and what scheduler they already run**, not by inference performance: where a batch scheduler is the incumbent and a research-computing population depends on it (GWDG, ALCF, DHinfra), teams keep Slurm/PBS and spend their engineering on a thin custom policy layer, accepting minutes-scale cold starts and non-cache-aware routing; where a dedicated, service-oriented GPU pool exists (Sandia's OpenShift clusters, the SSC-style pattern - numbers quarantined), Kubernetes with Gateway API Inference Extension is chosen and buys cache-aware routing. The baseline's "control plane covered by KServe" is therefore true only conditional on that second population; for the HPC population the same gap is filled by 1) a scheduler-script or llama-swap lifecycle manager and 2) a hand-built gateway, and that gap-filling code is the most reproducible "build our own" finding in the whole locus. Load-bearing reason: every source that rejected Kubernetes cited organizational cost (disrupted users, small team, 10 services), never a technical limit, while every source that lists what is lost (random routing, minutes-long cold starts, no health checks) is the HPC authors themselves.

- **Position:** On-prem control-plane choice follows incumbent scheduler and team size; Slurm-keepers trade cache-aware routing and fast scale-out for zero migration, and all populations hand-build the OpenAI-compatible gateway + identity + token-budget + warm-pool layer.
- **Confidence:** medium-high (~75%) on the convergence claim (5 independent accounts); medium (~55%) on the causal claim that organizational fit, not performance, drives the choice, because the sample is academic/national-lab and self-selected (enterprise/regulated K8s deployments are underrepresented).
- **Boundary conditions:** Holds for research-computing and small-team shared clusters of roughly 10-100 GPU nodes with mixed batch and inference users. Does not generalize to dedicated enterprise inference fleets (KServe/llm-d territory) or to air-gapped enterprise estates, where the vault has no disclosed evidence.
- **What would change this position:** A disclosed on-prem Kubernetes inference deployment of comparable scale (tens of nodes, user counts) that reports cache-aware routing benefits in production, or a Slurm site adopting GAIE/llm-d-style routing while keeping Slurm; or a Slurm-keeper citing a technical (not organizational) reason for rejection.
- **Evidence weight:** 5 primary accounts (DHinfra, GWDG, FIRST/ALCF, Sandia, STREAM) support, ExaServe supports for leadership systems, 1 vendor cloud-testbed study (Red Hat) supplies the K8s counter-quantification; the NFS/RDMA 5 s vs 20 s finding is a single-site preprint benchmark with an unequal comparison (22-drive ZFS vs 2-drive NVMe), so cite it as "aggregate storage fabric can beat undersized local NVMe", not "NFS beats NVMe".
