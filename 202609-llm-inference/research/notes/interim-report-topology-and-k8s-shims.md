# Interim report: topology-and-k8s-shims

**Locus question:** Which deployment topology fits which backend estate: router fully outside Kubernetes (file/custom discovery), router inside Kubernetes targeting out-of-cluster backends (file discovery via ConfigMap or custom plugin), or making backends real pods (Slinky slurm-operator) so stock InferencePool works — and are EndpointSlice/virtual-kubelet shims ever viable for the EPP?
**Flavor:** dialectical

## What the corpus already said

The width corpus already resolves most of the hard edges of this question, more thoroughly than the loci rationale assumed:

- [[inferencepool-kubernetes-gateway-api-inference-extension]]: `InferencePool.spec.selector` "specifies which Pods belong to this pool. The labels in this selector must exactly match the labels applied to your model server Pods" — selection is defined at the spec level as Pod-only.
- [[discovery-plugins-k8s-and-file-based-endpoint-discovery-by-ezrasilvera-pull-requ]] (merged PR #1007) describes proposed `inference-pool-discovery`/`static-selector-discovery` k8s-flavored plugins — but a direct fetch of current `main` (see new-sources §4a below) shows the **as-shipped** architecture is different: there is no `k8s/` discovery-plugin directory at all in `pkg/epp/framework/plugins/datalayer/discovery/`, only `file/`. Default Kubernetes discovery is still the original plain controller-runtime `pod_reconciler.go`, and `docs/discovery.md` states the plugin interface "replaces that mechanism" rather than re-expressing it as a sibling plugin. Either way, both the PR's stated design and the as-shipped reconciler watch **Pod objects directly** via the K8s API, not Services or EndpointSlices — the EndpointSlice-irrelevance conclusion holds regardless of which description is current.
- [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]] and [[no-kubernetes-no-problem-llm-d-now-runs-anywhere-llm-d]]: llm-d-router already ships a first-class `file-discovery` EndpointDiscovery plugin, fully decoupled from Kubernetes, with a documented custom-plugin authoring path.
- [[github-interlink-hqinterlink-slurm-plugin-github]] and [[introduction-interlink]]: interLink/virtual-kubelet-for-Slurm is egress-only (Tsocks SSH tunnel) and explicitly out-of-scope for long-running services.
- [[github-slinkyprojectslurm-operator-run-slurm-on-kubernetes-a-slinky-project-gith]]: Slinky makes Slurm workers real Pods, so stock InferencePool works — at the cost of pulling the Slurm fleet into K8s's own node/pod scheduling domain.
- [[endpointslices-kubernetes]] / [[both-endpoints-and-endpointslices-not-working-with-service-abstraction-for-exter]]: manual EndpointSlice authoring is a viable but fragile pattern for a **plain Kubernetes Service** (port-naming footgun, kube-proxy-only visibility) — but per the PR #1007 finding above, this machinery is irrelevant to InferencePool/EPP routing, which never consults EndpointSlices.

## What the new sources say

**1. [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]] (docs/discovery.md, read in full).** This is the authoritative spec for the whole discovery subsystem and directly targets the hybrid-topology sub-question. It gives a complete file-discovery worked example (`10.0.0.1:8000` / `10.0.0.2:8000` vLLM instances, `epp --pool-name slurm-job-42 --pool-namespace slurm --config-file ...`) and states plainly: "On bare metal, in Slurm, in Ray, or in any container without the Downward API, neither source is set and the pool is labeled `default`... Pass `--pool-namespace` explicitly." It documents exactly which Kubernetes-only features go dark in file-discovery mode (`InferenceModelRewrite`, `InferenceObjective`, `k8s-notification-source`) and states the runner "emits a one-time log at startup naming these inactive features" — i.e. the degradation is self-documenting at runtime, not a silent trap.

**2. [[llm-d-routerconfigchartsreadmemd-at-main-llm-dllm-d-router-github]] (config/charts/README.md, read in full).** The Helm charts have no first-class `--set` toggle for file-discovery — `router.modelServers.matchLabels` is required whenever `inferencePool.create=true`, confirming the earlier corpus finding of an "absence." But the same doc documents two escape hatches that make the *hybrid* topology (EPP running in-cluster as a normal Helm-managed Deployment, discovery pointed at out-of-cluster backends) mechanically reachable without forking the chart: `router.epp.pluginsCustomConfig` ("additional raw ConfigMap entries keyed by file name") and `router.epp.volumes`/`volumeMounts` ("extra volumes for EPP pod"). Together these let an operator inject a hand-authored `EndpointPickerConfig` containing a `file-discovery` block plus mount a ConfigMap holding `endpoints.yaml`, entirely through documented values.yaml keys. The same doc's HA section states Active-Passive mode "automatically enables the `--ha-enable-leader-election` flag," which is a Kubernetes Lease-backed mechanism — meaning even in hybrid mode the EPP's own HA lifecycle stays K8s-native while its backend target set is decoupled from Pods. This is the load-bearing evidence for the hybrid branch: nobody documents it as a named deployment mode, but the chart's own escape hatches are exactly what it needs.

**3. [[plugingo]] (file/plugin.go source, read in full).** `WatchFile enables hot-reload via fsnotify: edits, atomic renames, and ConfigMap-style symlink swaps trigger a reload of the file.` This is a deliberate engineering choice — ConfigMap volume mounts update via atomic symlink swap, and the plugin was written to survive that specific update pattern. A plugin with no Kubernetes ambitions would not need to special-case symlink swaps; this is corroborating (not just permissive) evidence that in-cluster-EPP-with-ConfigMap-mounted-file-discovery is an anticipated deployment shape, not just a theoretical possibility. The same file shows `validateAddress` is "injected at construction so a variant can loosen it" — and [[llm-d-routerpkgeppframeworkpluginsreadmemd-at-main-llm-dllm-d-router-github]] confirms the shipped variant: `multicluster-file-discovery` accepts hostnames where stock `file-discovery` requires IPv4 literals ("clusters.yaml follows the same format as the pod file discovery, except an address may be a hostname").

**4. [[github-virtual-kubeletvirtual-kubelet-virtual-kubelet-is-an-open-source-kubernet]] (README, read in full, targeting the PodIP/readiness semantics question).** The core `PodLifecycleHandler` interface a VK provider implements is: `CreatePod`/`UpdatePod`/`DeletePod`/`GetPod`/`GetPodStatus`/`GetPods`, all operating on real `corev1.Pod`/`*corev1.PodStatus` objects, and `NodeProvider.Ping` is "intended to be lightweight... called periodically as a heartbeat to keep the node marked as ready." Nothing in the interface constrains what `PodStatus.PodIP` a provider reports, or requires it to be reachable from anywhere — that is entirely provider-defined.

**4a. [[pod_reconcilergo]] (`pkg/epp/controller/pod_reconciler.go`, fetched to close out this exact question — resolved, not left open).** This is the actual, current default-discovery code path (see the correction in "What the corpus already said" above). The event-admission filter is pure label-selector match: `CreateFunc: func(ce event.CreateEvent) bool { pod := ce.Object.(*corev1.Pod); return c.Datastore.PoolLabelsMatch(pod.GetLabels()) }` (identical for Update/Delete/Generic). The reconcile-time datastore-admission gate is: `if !podutil.IsPodReady(pod) || !c.Datastore.PoolLabelsMatch(pod.Labels) { c.Datastore.PodDelete(pod.Name); return nil }` — and `IsPodReady` itself is only `!pod.DeletionTimestamp.IsZero()` (rejects if terminating) plus a scan for `corev1.PodReady == ConditionTrue`. Critically, the datastore layer that turns an admitted Pod into a routable endpoint (`podUpdateOrAddIfNotExist`) uses `pod.Status.PodIP` **verbatim, with no emptiness or format validation** — an empty or bogus PodIP is not a rejection condition, it just produces a broken endpoint address downstream. There is no check anywhere in this path on `pod.Spec.NodeName` or `pod.Status.Phase`. This directly and completely answers the locus's highest-value question: a virtual-kubelet-backed Pod object with a matching label set and a provider-set `Ready=True` condition passes through every filter in the default Kubernetes discovery path, identically to a Pod created by a real kubelet — nothing in this code is kubelet- or node-scheduling-aware. The only thing standing between such a Pod and working end-to-end routing is whether `PodStatus.PodIP` is actually reachable from the gateway's data-plane network, which is a property of the specific VK provider, not of the EPP or the Pod API object.

## Evidence synthesis

The three "make it look like Kubernetes" strategies the loci rationale groups together are not equally dead. EndpointSlice-shimming is a **category error**, not a hard-but-viable option: it targets `kube-proxy`'s Service-routing path, and PR #1007 confirms InferencePool's own discovery plugin never touches Services or EndpointSlices — it lists Pods directly by label selector. Authoring EndpointSlices for a non-pod backend does nothing for EPP-mediated routing; it would only matter if someone routed traffic through a plain Kubernetes Service in front of the InferencePool/EPP path entirely, which defeats the purpose of using the EPP's scheduling logic at all.

Virtual-kubelet is architecturally different from EndpointSlice-shimming: it produces literal `corev1.Pod` API objects, and — now confirmed directly from `pod_reconciler.go`'s source, not just inferred from the interface contract — neither the VK framework nor the EPP's default Kubernetes discovery path has any structural reason to reject one that is labeled correctly, Ready, and IP-bearing. The admission logic is exactly two conditions (label match, aggregate `Ready`), and the endpoint-construction logic downstream uses `pod.Status.PodIP` verbatim with no validation. This means the corpus's framing ("interLink excludes long-running services, Slurm plugin egress-only, therefore VK is not viable") is locally correct but doesn't generalize as an architecture-level verdict — it's an artifact of interLink specifically being an HPC/batch-job-shaped provider with an egress-only network model, not a limitation of virtual-kubelet or the EPP as mechanisms. A VK provider with genuine bidirectional pod networking (the corpus's own example, Liqo, "extends real pod-to-pod networking across peered clusters") would in principle let InferencePool select and route to it successfully, with zero EPP-side changes. The practical verdict is about **available providers**, not about the **VK or EPP contract**: for the HPC/Slurm estate this locus and its sibling loci care about, the one production VK integration point (interLink) is a dead end for reasons specific to HPC batch scheduling and SSH-tunnel networking, not because virtual-kubelet-shimmed pods are categorically unroutable or unselectable.

Slinky is the mirror-image trade of a custom discovery plugin: it buys zero router customization by paying with full custody transfer of the compute fleet to Kubernetes' own node/pod scheduler (`NodeSet` DaemonSet mode literally "schedules one pod per Kubernetes node that matches the NodeSet's pod template" — the Slurm workers must be Kubernetes nodes). For a team standing up a new GPU fleet and willing to make K8s the primary orchestrator, this is a legitimate, lower-maintenance answer. For a team with an existing, independently-governed HPC allocation — the population implied by "customize router to support backends other than k8s pods" — this is not a topology option at all, because it requires exactly the migration the user is trying to avoid.

The file-discovery / custom-EndpointDiscovery-plugin path is not merely "the fallback when the other two fail" — it is the one path upstream has actually built, documented, and hardened (ConfigMap-symlink-swap handling, hostname-capable variants already shipping for the multicluster case, a documented five-method interface for writing entirely new discovery plugins). The three deployment topologies map onto three distinct organizational realities rather than three tiers of the same solution:

1. **Router fully outside Kubernetes** (bare `epp` + Envoy processes, file-discovery, no cluster at all): correct when neither the router nor the backends are Kubernetes-managed. This is the explicitly named use case in [[standalone-epp-issue-1838-kubernetes-sigsgateway-api-inference-extension]] ("Mistral asked for those two deployment modes independently") and in the no-Kubernetes-deployment guide (bare metal, Slurm, Ray, RL post-training frameworks).
2. **Router inside Kubernetes, backends outside** (EPP as a Helm-managed Deployment with HA/leader-election, `file-discovery` fed by a ConfigMap whose entries point at external IPs/hostnames): correct when the operator wants Kubernetes to manage the *router's* lifecycle (scaling, HA, RBAC, GitOps via Helm) but the backend fleet is external, legacy, or managed by a different team/orchestrator. This is mechanically supported today via `pluginsCustomConfig` + `volumes`/`volumeMounts`, but is not a named, first-class chart mode — someone still has to write the controller/cron/CI step that keeps the ConfigMap in sync with the real backend fleet, and this is the piece with no off-the-shelf component in the corpus.
3. **Backends converted to real Pods (Slinky)**: correct only for teams building/operating the compute fleet fresh and willing to hand primary scheduling control to Kubernetes.

## Committed position

The router-customization strategy this query is actually asking for is topology 1 or 2 — a custom or file-based `EndpointDiscovery` plugin — and the report's decision rule should present the choice between "router in-cluster" and "router out-of-cluster" as orthogonal to the discovery mechanism, not as competing strategies: file-discovery works identically in both places, so the real fork is organizational (who manages the router's own lifecycle?), not technical. EndpointSlice-shimming should be dropped from the strategy table entirely — it is not a weaker version of a k8s-native path, it is a non-answer, because InferencePool's discovery plugin never reads EndpointSlices. Virtual-kubelet shimming should be kept in the report only as a narrow, named exception (Liqo-style cross-cluster pod networking) and explicitly rejected as a general HPC/Slurm strategy, with the reason stated precisely: it is not that VK-backed pods are unselectable, it is that no production VK provider for HPC targets deliver bidirectional Pod-IP reachability, and building one from scratch (implementing `PodLifecycleHandler` + `NodeProvider`, replicating kubelet heartbeat semantics) is strictly more engineering than implementing the EPP's own 5-method `EndpointDiscovery` interface to do the identical job with a fraction of the surface area. Slinky is correctly scoped in the corpus as "convert the estate" rather than "customize the router," and should be presented as an alternative to this whole research question, not a branch of it — it answers "how do I avoid writing a discovery plugin" at the cost of "how do I avoid Kubernetes owning my HPC fleet."

- **Position:** The decision rule is organizational, not technical: use file/custom `EndpointDiscovery` (in- or out-of-cluster router, per who should own the router's lifecycle) for any estate you don't want K8s to schedule; use Slinky only if you're willing to make K8s the primary scheduler for that estate; drop EndpointSlice-shimming from consideration entirely (wrong layer — InferencePool's discovery plugin watches Pods, never EndpointSlices, confirmed in the merged PR #1007 implementation); keep virtual-kubelet shimming only as a named exception for cross-cluster pod-networking providers (Liqo-class), not as a general non-k8s-backend strategy, because the one production HPC-shaped VK provider (interLink) is egress-only by design, not because VK-backed pods are structurally unselectable.
- **Confidence:** high on the EndpointSlice-is-a-non-sequitur and Slinky-is-a-different-question claims (directly confirmed by primary source-of-truth — `pod_reconciler.go` at HEAD and Slinky's NodeSet scheduling semantics); high on the virtual-kubelet architectural-viability claim (upgraded from medium-high after directly reading `pod_reconciler.go` and `podutil.IsPodReady`: the admission path is exactly label-match + aggregate-Ready + non-terminating, with `PodStatus.PodIP` consumed verbatim and unvalidated downstream — confirmed, not inferred); medium on the hybrid-topology-is-supported claim (mechanically plausible and well-evidenced via chart escape hatches + the ConfigMap-symlink-swap engineering choice, but zero named production deployments of exactly this shape appear anywhere in the corpus — it is an inference from capability, not an observed pattern).
- **Boundary conditions:** The "EndpointSlice is irrelevant" claim holds specifically for InferencePool/EPP-mediated routing; it does not hold for a deployment that routes through a plain Kubernetes Service in front of (or instead of) the EPP, where the [[both-endpoints-and-endpointslices-not-working-with-service-abstraction-for-exter]] port-naming footgun is fully applicable. The virtual-kubelet claim holds only where the VK provider gives the pod a genuinely routable IP from the gateway's network vantage point; it does not extend to any provider (interLink included) whose networking model is asymmetric/egress-only.
- **What would change this position:** A first-party llm-d/GIE doc or issue thread that explicitly recommends or documents the router-in-cluster-with-external-file-discovery pattern as a named mode (rather than my inference from chart escape hatches) would raise the hybrid-topology confidence to high. On the virtual-kubelet claim, the code-level question is now closed (confirmed no `Spec.NodeName`/`Status.Phase` gate exists as of the HEAD commit fetched); what would still change that position is evidence of a *newer* commit adding such a gate, or evidence that Envoy's ORIGINAL_DST data-plane path (not the EPP's admission logic) imposes its own reachability precheck that would behave differently for a VK-backed Pod than a kubelet-backed one — I did not check the Envoy/gateway data-plane side within this locus's budget.
- **Evidence weight:** EndpointSlice-non-sequitur — direct read of `pod_reconciler.go` at HEAD (primary, decisive) + `docs/discovery.md` + 2 corroborating spec docs; the merged-PR description turned out to be imprecise about final plugin naming/structure, which the code read corrected. Slinky-is-different-question — 1 primary repo README (NodeSet scheduling semantics, decisive) with no counter-evidence found. Virtual-kubelet architectural view — 3 primary sources (VK README interface contract, EPP discovery.md readiness semantics, `pod_reconciler.go` + `podutil.IsPodReady` source) support the "no categorical block" reading directly and at the code level; 2 primary sources (interLink docs, interlink-slurm-plugin repo) support the "no viable production HPC provider" reading; these are complementary, not contradictory. Hybrid topology — 2 primary sources (chart README escape hatches, file-discovery fsnotify symlink-swap comment) support feasibility; 0 sources document it as an observed or recommended deployment.

## Open questions

- **Resolved during this investigation:** whether the EPP's Kubernetes discovery path filters candidate Pods on anything beyond label-selector match + aggregate Ready condition. Answer: no — confirmed directly from `pod_reconciler.go` and `podutil.IsPodReady` at HEAD (see [[pod_reconcilergo]]). This also surfaced a minor correction to the vault: [[discovery-plugins-k8s-and-file-based-endpoint-discovery-by-ezrasilvera-pull-requ]]'s summary describes PR #1007 as shipping separate `inference-pool-discovery`/`static-selector-discovery` k8s plugins under a `k8s/` directory, but a direct fetch of current `main` found no such directory — only `file/` exists under `pkg/epp/framework/plugins/datalayer/discovery/`, and the default K8s path is still the original plain controller-runtime reconciler. Downstream steps citing that PR's plugin names for the K8s discovery path should use `pod_reconciler.go` as the current source of truth instead; this doesn't change any conclusion in this note, since both descriptions agree the mechanism is Pod-label-selector-based, not EndpointSlice-based.
- No corpus source names a real production deployment running llm-d's EPP in-cluster with file-discovery pointed at out-of-cluster IPs (the "hybrid" topology). This absence was searched for specifically (vault search across the full corpus tag) and not found; the hybrid-topology argument in this note is a capability inference from chart mechanics, not an observed case study.
- Whether GKE's `InferencePoolImport` mechanism (from [[multi-cluster-gke-inference-gateway-helps-scale-ai-workloads-google-cloud-blog]] and [[api-overview-kubernetes-gateway-api-inference-extension]]) could be repurposed as a non-k8s-backend seam is worth a follow-up locus — it is the one documented mechanism where InferencePool-adjacent routing reaches outside a single cluster's Pod set, but it is GCP-proprietary plumbing over real InferencePools in real clusters, not a general-purpose non-pod backend mechanism, and I did not have budget to chase it further here.
- Not checked within this locus's budget: whether Envoy's `ORIGINAL_DST` data-plane forwarding path (as opposed to the EPP's own Go admission logic) imposes any reachability/health precheck that would behave differently for a virtual-kubelet-backed Pod IP than a kubelet-backed one.
