# Interim report: observability-layer-oss-maturity

**Locus question:** Is the open-source LLM observability layer mature enough to adopt as-is — and does any of it close the engine-internal-metrics gap that forced Netflix to write its own proxy?
**Flavor:** dialectical

## What the corpus already said

The contradiction graph's `oss-control-plane-sufficiency` cluster already uses two of this locus's facts as Side-A ("operators must build") evidence: Netflix's custom HTTP metrics proxy (because "Triton's built-in Prometheus bridge surfaces only 9 of 40+ vLLM metrics, missing token throughput, KV cache utilization and prefix cache hit rate") and the OTel GenAI semantic conventions' Status: Development rating, read as meaning "there is no standard to adopt for exactly the signals gateways route on." The consensus-claims artifact's `gateway-is-where-internal-teams-build` claim calls Netflix's proxy "a sixth instance" of in-house building, "at the adjacent observability seam" next to the gateway layer where it locates most build-vs-buy activity. Neither artifact distinguishes (a) Langfuse/Phoenix/OpenLLMetry's licence shape, (b) the instrumentation-vs-platform split, or (c) whether Netflix's specific gap was a Triton-bridge problem or a genuine vLLM/standards gap — that reconciliation had not been done before this investigation.

## What the new sources say

**Langfuse licensing** ([[confirmation-of-self-hosted-oss-usage-without-ee-license-production-observabilit]], [[github-langfuselangfuse-open-source-agent-evals-observability-trace-evaluate-and]]): the repo is MIT except `ee/` directories, which carry a separate commercial licence gated by `LANGFUSE_EE_LICENSE_KEY`. A practitioner-run compliance thread (GitHub Discussion #13737, May 2026) got an AI-support-bot-sourced but doc-citing confirmation that EE gates exactly: "Project-level RBAC Roles, Protected Prompt Labels, Data Retention Policies, Audit Logs, Server-Side Data Masking, UI Customization, Organization Creators, Org Management API/SCIM, and Instance Management API" — governance/compliance features, not the core observability functionality (tracing, evals, prompt management, experiments, annotation, playground, dashboards), which is confirmed fully MIT with no usage limits. The official Docker image ships the EE code paths inert; self-hosters do not need to strip them. Notably the thread got no sign-off from a human Langfuse maintainer — the asker needed exactly that for a compliance file, and never got it; this is itself an audited absence about Langfuse's own responsiveness to licence-compliance questions.

**Phoenix licensing** ([[arize-phoenix-or-arize-ax-phoenix]], [[github-arize-aiphoenix-ai-observability-evaluation-github]]): Elastic License 2.0 — not OSI-approved — confirmed directly in the repo's licence section. But Arize's own FAQ states, quoted directly: "There is no closed core and no paywalled tier within Phoenix itself: no Phoenix feature is gated by the commercial offering, and Phoenix will never decline to build a feature because Arize AX offers it." The Phoenix/Arize-AX split is entirely about *who operates it* (self-hosted vs. managed SaaS with auto-scaling and SLAs), not which features exist. Arize explicitly recommends Phoenix for "the most regulated, air-gapped environments" where "a commercial offering is largely off the table."

**Instrumentation-layer licensing** ([[github-arize-aiopeninference-opentelemetry-instrumentation-for-ai-observability]], [[github-traceloopopenllmetry-open-source-observability-for-your-genai-or-llm-appl]]): OpenInference's LICENSE file (directly fetched) confirms Apache-2.0, independent of Phoenix's ELv2 — the instrumentation and the storage/UI platform carry *different* licences even though Arize ships both. OpenLLMetry is Apache-2.0 with no enterprise carve-out visible in-repo.

**Gateway-layer comparison** ([[enterprise-litellm]]): LiteLLM's own framing is explicit and quoted directly: "Enterprise is a license key on the same Gateway image you may already run... each layer includes everything below it." The gated layer adds "Org and team admins" and "Per-team logging" on top of an open-source AI Gateway that already has budgets/rate limits. Enterprise is scoped for "100+ users or 10+ production AI use cases," and the enterprise feature list names Tag-based Budgets and delegated team administration specifically.

**OTel GenAI semantic conventions** ([[semantic-conventions-genaidocsgen-aigen-ai-metricsmd-at-main-open-telemetryseman]], [[semantic-conventions-genaidocsgen-aigen-ai-spansmd-at-main-open-telemetrysemanti]], [[github-open-telemetrysemantic-conventions-genai-github]]): both the spans and metrics docs state, verbatim, **"Status: Development"** (pre-Experimental; breaking changes can land at any time). The metrics spec defines four families — client operation duration, model-server request/TTFT/TPOT, workflow, agent/tool — and explicitly disclaims completeness: "These are initial Generative AI client metric instruments and attributes but more may be added in the future." No KV-cache, queue-depth, or batch-size metric exists anywhere in the spec.

**vLLM's native `/metrics` endpoint** ([[production-metrics-vllm]], fetched this session from `docs.vllm.ai/en/latest/usage/metrics.html`): directly contradicts any reading that engine-internal telemetry is missing from the open-source engine itself. Confirmed present, verbatim from the docs table: `vllm:kv_cache_usage_perc` (Gauge, "KV-cache usage. 1 means 100 percent usage"), `vllm:prefix_cache_hits` / `vllm:prefix_cache_queries` (Counters, token-level), `vllm:external_prefix_cache_hits/queries` (cross-instance KV-connector sharing), `vllm:num_requests_running` / `vllm:num_requests_waiting` / `vllm:num_requests_waiting_by_reason` (capacity vs. deferred), `vllm:generation_tokens` / `vllm:prompt_tokens` / `vllm:iteration_tokens_total` (throughput), plus NIXL KV-connector, HiSparse KV-connector, CPU-offload-connector, speculative-decoding, and MFU-utilization metric families. There is no literal "batch size" metric, but `vllm:num_requests_running` is the documented proxy. Every metric family the locus asked about (KV-cache, queue depth, throughput, batch proxy) is natively present.

**The Netflix gap, read precisely** ([[in-house-llm-serving-at-netflix-by-ai-platforms-model-runtime-team-and-by-netfli]], corroborated by [[netflix-in-house-llm-serving-infrastructure-at-scale-zenml-llmops-database]]): the blog's own words settle thread (3) directly: "vLLM writes metrics to `PROMETHEUS_MULTIPROC_DIR` as `.db` files; Triton reports server-level metrics through its own Prometheus endpoint. **Neither is aware of the other**, and Triton's built-in bridge surfaces only 9 of 40+ vLLM metrics." Netflix's fix — "a lightweight HTTP proxy that merges both into a single `/metrics` endpoint: it fetches Triton metrics via HTTP, reads vLLM metrics from disk using Prometheus's `MultiProcessCollector`" — is explicitly a Triton-bridge workaround, not a vLLM-metrics backfill: it reads vLLM's own already-complete metrics directly off disk. Netflix fronts vLLM through Triton for a reason unrelated to observability (a unified JVM control plane spanning legacy gRPC ML models and new OpenAI-compatible LLM traffic); the metrics gap is a side effect of that specific architectural choice, not of vLLM or the OSS ecosystem.

**What a direct-scrape deployment actually gets, out of the box** ([[metrics-llm-d]], [[llm-ddocsoperationsobservabilitypromqlmd-at-main-llm-dllm-d-github]], [[monitor-llm-routing-with-the-kubernetes-inference-extension-datadog]]): llm-d's shipped Kustomize monitoring component creates Prometheus PodMonitors that scrape vLLM's `/metrics` directly (curl-verifiable on port 8000), with a ready PromQL library already written against `vllm:kv_cache_usage_perc`, `vllm:prefix_cache_hits_total`/`queries_total`, `num_requests_running`/`waiting`. The Gateway API Inference Extension's EPP scores endpoints on exactly these fields (queue depth, KV-cache locality, adapter state) per Datadog's own engineering write-up. A FinOps guide in the corpus ([[gpu-cloud-finops-for-ai-teams-cost-allocation-per-project-chargeback-and-tag-bas]]) independently confirms the same direct-scrape pattern in production cost-attribution use: "LiteLLM proxy in front of vLLM... joined against vLLM's own Prometheus token counters" (`vllm:prompt_tokens_total`, `vllm:generation_tokens_total`), with no bridge or proxy required. Three independent sources converge on the same fact: scrape vLLM directly and you get everything; bridge it through something else (as Netflix did, through Triton) and you may lose fields.

**Where Langfuse/Phoenix/OpenLLMetry actually sit** — confirmed this session not to touch any of the above. [[integrations-phoenix]] (Phoenix's own integrations index, fetched this session) lists only: Developer Tools, Tracing Integrations, Eval Model Integrations, Evaluation Integrations, Span Processors, Sandboxes — zero Prometheus- or infra-metric-shaped categories. Web-search-sourced corroboration (search performed by the fetcher subagent, not independently fetched due to Langfuse bot-walling the page — escalations #34–37 queued): "vLLM currently only exports token counts and latency metrics to Langfuse, and the LLM input and output need to be manually captured in a separate trace using the Langfuse SDK" — i.e., even Langfuse's own documented vLLM path is request/trace-level (token counts, latency), never KV-cache or queue depth. Phoenix's documented vLLM path runs through `openinference-instrumentation-litellm` with LiteLLM as a proxy — again an application-trace capture, not a Prometheus scrape. OpenLLMetry's README instruments outbound SDK calls the application makes *to* providers (OpenAI, Anthropic, Gemini, Watsonx, SageMaker, Vertex) and vector DBs — if vLLM is instrumented at all via OpenLLMetry, it is as "an OpenAI-compatible endpoint being called," identical treatment to any other provider, never as the engine process itself.

**Promptfoo** ([[github-promptfoopromptfoo-test-your-prompts-agents-and-rags-red-teamingpentestin]]): adjacent eval/red-team tool, MIT, no enterprise carve-out visible in-repo, confirms the eval slot is also open and permissively licensed, though it is evals/red-teaming rather than observability proper and doesn't bear on the engine-metrics question.

## Evidence synthesis

### Position A: the OSS observability layer is mature enough to adopt as-is, full stop

Every licence examined this session is workable for an internal platform team. Phoenix is the strongest case — Arize's own words rule out any paywalled-feature risk, and Arize affirmatively steers regulated/air-gapped buyers toward it despite the non-OSI ELv2 label, which should reassure a legal reviewer more than the licence name alone would. Langfuse's core observability functionality (tracing, evals, prompt management, datasets, playground) is unconditionally MIT; only org-governance and compliance features sit behind `ee/`, and those gated features are not what "observability" means to an engineer wiring up traces. OpenLLMetry and OpenInference are both clean Apache-2.0 with no enterprise seam at all. On the engine-metrics side, the artifact-level gap simply does not exist: vLLM's own `/metrics` endpoint, confirmed directly from its official documentation, already emits every metric family the locus asked about, and llm-d ships a complete, ready-to-use Prometheus/PromQL pipeline against those exact metric names out of the box, with zero custom code. A platform team standing up vLLM behind llm-d or the Gateway API Inference Extension today gets KV-cache utilization, prefix-cache hit rate, and queue depth in Grafana without writing anything.

### Position B: real in-house glue is still required, just not where the locus's framing assumed

The locus's framing conflates two different things under "the observability layer." Langfuse, Phoenix, and OpenLLMetry are LLM-*application* observability tools — they trace calls, capture prompts/completions, and run evals. None of the three ingests Prometheus server metrics; this is now directly confirmed for all three (Phoenix's own integrations index lists no such category; Langfuse's documented vLLM path is token-count-and-latency-only; OpenLLMetry instruments outbound client calls, not the serving process). A platform team that assumes adopting Langfuse or Phoenix will give it KV-cache/queue-depth visibility will get nothing — not because those tools are immature, but because they were never built to do that job. The actual engine-metrics observability stack is a different, older, boring one: Prometheus + Grafana + whatever PromQL you write (or copy from llm-d). That stack is mature and sufcient when scraping vLLM directly — but there genuinely is no cross-engine standard (OTel GenAI semconv Status: Development, no KV-cache/queue-depth coverage at all), so a shop running vLLM *and* SGLang *and* Triton/TensorRT-LLM must hand-maintain separate PromQL/dashboard definitions per engine (`vllm:kv_cache_usage_perc` vs. `sglang_token_usage`, confirmed divergent naming in [[llm-ddocsoperationsobservabilitypromqlmd-at-main-llm-dllm-d-github]]) rather than writing one query against a standard name. That is real, durable glue — just narrower and differently located than "Netflix had to write a metrics proxy, therefore the observability layer is immature" implies.

### The audited absence

Four independent search angles (web search, run by the fetcher subagent; corroborated by failed vault searches on my end for "company uses Langfuse production internal LLM serving," "OpenLLMetry instrumentation vLLM server," etc.) found no named organization's own engineering account describing production use of Langfuse, Arize Phoenix, or OpenLLMetry to observe a self-hosted internal inference deployment. What surfaced instead was vendor docs, listicles, and tutorial walkthroughs (not named-operator production accounts). This corroborates the orchestrator's framing (analyst a's prior search) rather than overturning it, and extends it: the only named-operator account of engine-level metrics observability anywhere in this corpus remains Netflix's custom proxy — and even that account is explicitly a Triton-bridge fix, not evidence that the OSS *observability* ecosystem (in the Langfuse/Phoenix/OpenLLMetry sense) is immature, since those products were never in Netflix's metrics path at all. Two of Langfuse's own integration/docs pages and Traceloop's own integrations index (escalations #34–37) remain bot-walled and unresolved as of this writing; resolving them is unlikely to overturn the finding given independent web-search corroboration of the same "trace-level only" fact, but it is the one loose thread.

## Committed position

The locus as posed contains a category error, and resolving that error is the finding: Langfuse, Phoenix, and OpenLLMetry are mature, permissively-licensed, adopt-as-is tools for their actual job — LLM-application tracing, evaluation, and prompt management — and none of the three licence shapes (Phoenix: nothing gated; Langfuse: only governance/compliance gated; OpenLLMetry/OpenInference: fully Apache) blocks legal review or air-gapped deployment the way LiteLLM's Enterprise gate (which withholds a capability — tag-based cost attribution and delegated team admin — central to the gateway's own core use case) arguably does. But none of the three was ever a candidate to close Netflix's gap, because none of them touches engine-internal Prometheus metrics at all — confirmed this session for all three independently. The gap itself, examined directly against vLLM's own documentation, is not a vLLM gap or an OSS-ecosystem-maturity gap: vLLM's native `/metrics` endpoint already emits KV-cache utilization, prefix-cache hit rate, queue depth, and token throughput in full, and llm-d's out-of-the-box Prometheus pipeline already consumes all of it with no custom code, for any team that scrapes the engine directly. Netflix's custom proxy was a Triton-bridge-specific fix, made necessary by Netflix's own choice to front vLLM through Triton for unrelated reasons (a unified serving control plane across legacy ML and new LLM workloads) — an engine-direct deployment never encounters the problem Netflix solved. The one genuine, durable, unresolved gap is standards-level and narrower than either framing suggests: OTel's GenAI semantic conventions remain Status: Development with zero engine-internal metric coverage, so only a multi-engine shop (vLLM + SGLang + Triton, say) that wants one portable dashboard/alerting vocabulary across engines must still hand-write and maintain that translation layer — a real but scoped piece of glue, not a general indictment of the observability layer's maturity.

- **Position:** Adopt-as-is holds for both halves of "observability" examined separately — LLM-app tracing (Langfuse/Phoenix/OpenLLMetry, all workably licensed) and engine-internal metrics (vLLM's native `/metrics` plus llm-d's out-of-the-box Prometheus pipeline, for a direct-scrape deployment) — but only because they are different stacks solving different problems; the one real residual glue requirement is cross-engine metric-name standardization for shops running more than one inference engine.
- **Confidence:** high on the licence-shape claims and on "vLLM's native metrics are complete" and "Netflix's gap was Triton-bridge-specific" (all primary-source, directly quoted, from the vendor's own docs/blog). Medium-high on "Langfuse/Phoenix/OpenLLMetry never ingest engine metrics" (confirmed for Phoenix by direct fetch of its own integrations index; confirmed for Langfuse and OpenLLMetry via README text plus web-search corroboration rather than a direct fetch of Langfuse's bot-walled vLLM-integration page specifically — escalations #34–37 still queued). Medium on the audited-absence claim (four search angles, consistent null result, but not an exhaustive search of every company engineering blog).
- **Boundary conditions:** This applies to a team that scrapes vLLM directly (Kubernetes PodMonitor/ServiceMonitor style, as llm-d and the Gateway API Inference Extension do by default). It does not automatically apply to a team that fronts vLLM through an intermediary serving layer (Triton, a custom gRPC gateway, anything that re-exports or merges metrics) unless that intermediary is confirmed to pass through all upstream metrics — Netflix's case shows that assumption can silently fail. It also does not apply to a multi-engine shop wanting one standardized metric vocabulary across vLLM/SGLang/Triton; that shop needs custom translation regardless of how mature any single engine's native metrics are.
- **What would change this position:** A documented case of a team that scrapes vLLM directly (no bridging layer) still needing custom glue to get KV-cache/queue-depth into dashboards would falsify the "adopt-as-is for direct-scrape deployments" half. A Langfuse, Phoenix, or OpenLLMetry release that adds native Prometheus-server-metrics ingestion (not just app-trace capture) would close the category gap and merge the two "observability" meanings this report had to split apart — worth re-checking given how fast these products are shipping (Langfuse's EE feature list and OpenLLMetry's instrumentation list both show commits within the last several days of this fetch). A named-organization account surfacing after this session describing production use of Langfuse/Phoenix/OpenLLMetry specifically for engine-internal observability would overturn the audited-absence finding.
- **Evidence weight:** 9 primary-source documents read directly and quoted (vLLM's own metrics docs, Netflix's own blog, Arize's own FAQ and integrations index, Langfuse's own README and GitHub discussion, OpenInference's own LICENSE, OTel's own semconv spec, LiteLLM's own docs, llm-d's own metrics/PromQL docs) carry this locus; 0 sources contradict the "vLLM native metrics are complete" or "Netflix's gap was Triton-specific" findings; the audited-absence claim rests on search-engine coverage (4 queries) rather than exhaustive primary-source review, and is the softest part of this note.

## Open questions

- Escalations #34–37 (Langfuse's own `/docs/integrations/other/vllm` and related pages, Traceloop's own integrations-introduction doc) remain bot-walled; resolving them would firm up but is unlikely to overturn the "trace-level only" finding given independent web-search corroboration already obtained.
- Whether any other organization besides Netflix has hit a comparable bridge-induced metrics gap (fronting vLLM through something other than direct Prometheus scrape) was not checked — this would indicate whether Netflix's problem is a one-off architectural artifact or a recurring pattern wherever vLLM sits behind a unifying serving layer.
- SGLang's native metrics completeness was not independently verified the way vLLM's was (confirmed only that its metric names differ, e.g. `sglang_token_usage`, from [[llm-ddocsoperationsobservabilitypromqlmd-at-main-llm-dllm-d-github]]); if SGLang's native surface is less complete than vLLM's, the cross-engine standards gap would be more consequential than stated above.
- Whether the Gateway API Inference Extension's reference-implementation governance dispute (documented elsewhere in this corpus) has any parallel brewing over whose metric *names* become the de facto standard was not investigated.
