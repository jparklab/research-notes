# Interim report: cache-salt-lora-multitenant-routing

**Locus question:** When prefix caches are partitioned for tenant isolation via vLLM `cache_salt` or per-adapter block-key separation for LoRA, how does llm-d's KV indexer and prefix-cache scorer account for those partitions — does routing still find the right pod, and does it defeat the reuse that makes cache-aware routing valuable? Also: is cross-tenant prefix reuse a timing side channel, and does llm-d propagate/enforce isolation, and at what cost to affinity?

**Flavor:** dialectical

## What the corpus already said

The width corpus had the pieces but not the synthesis, as the loci-analyst rationale predicted. [[rfc-cache-salting-for-secure-and-flexible-prefix-caching-in-vllm-issue-16016-vll]] documents vLLM's `cache_salt` mechanism: an optional per-request field injected into the hash of the first block, motivated explicitly by "Leaking Secrets from Prefix Caches" timing attacks. Only the "single-barrier" design (one salt per request, seeding the chain root) shipped, in vLLM 0.9 (PR #17045, merged May 2025); the "multi-barrier" per-message-salt design that would let a shared org preamble stay cached while protecting only the divergent tail was never merged into upstream vLLM as of the RFC thread. [[llm-d-05-sustaining-performance-at-scale-llm-d]] claims as a v0.5 headline: "Cache-aware routing now supports LoRA adapters... preventing the 'thundering herd' problem," but gives zero block-key mechanics. [[governing-the-kv-cache]] (arXiv 2608.09225) argues shared, unsalted caches leak prompts via TTFT timing with up to 100% attack success rate (ASR) across three independent published attacks (PromptPeek/NDSS 2025, EarlyBird, InputSnatch), and that root-salting "retains an estimated 93% of the prefix-cache benefit" only if injected at the *divergence boundary* rather than the chain root — a refinement it explicitly says is unmeasured and unshipped ("current engines do not expose" an offset parameter). [[kv-cache-indexer-llm-d]] documents that the precise-prefix-cache-scorer's Index is built from `KVEvents` (`BlockStored`/`BlockRemoved`/`AllBlocksCleared`) with LoRA and multimodal fields folded into block keys, but does not mention `cache_salt` at all — this silence was the actual gap the locus was built to close.

## What the new sources say

**vLLM's own event schema confirms `cache_salt` is a designed hand-off point, not an afterthought.** [[vllmvllmdistributedkv_eventspy-at-main-vllm-projectvllm-github]] — vLLM's `distributed/kv_events.py` source — documents the `extra_keys` field on `BlockStored`-type events: "Extra keys used in block hash computation, one entry per block in `block_hashes`. Each entry contains MM identifiers, LoRA name, `cache_salt`, prompt embedding hashes, etc. for that specific block. **Exposed for external KV cache consumers to reconstruct block hashes.**" This is the exact interface llm-d's router consumes.

**llm-d's precise-prefix-cache-producer explicitly recomputes salt-aware block keys.** The primary source is the plugin's own README, fetched twice consistently ([[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcachere]] and the directory listing [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcache-a]]): "Block keys are recomputed by the EPP from `TokenizedPrompt` (tokens, model, multimodal features, **cache salt**) on both the lookup path and the KV-event ingestion path... The cross-engine requirement is that the engine emits, in its KV-events, the hash-affecting inputs the EPP hashes: `token_ids`, and `extra_keys` carrying multimodal identifiers and `cache_salt`." The README gives an explicit per-engine compatibility table:

| Engine | `extra_keys` in KV-events | `cache_salt` |
|---|---|---|
| vLLM | emitted | "in block-0 `extra_keys`; salted prefixes isolated **and precise-routed**" |
| SGLang | not emitted | "baked into engine block hashes but not surfaced; salted requests are precise-cache misses until SGLang emits `extra_keys`" |

And critically: **"Salt isolation is enforced by the engine regardless; the above affects only routing accuracy for salted requests."** Security and routing affinity are architecturally decoupled in llm-d's design — the router's (in)ability to see the salt never determines whether isolation holds, only whether reuse is found.

**LoRA-precise caching is verified in code, not just the blog.** [[kvevents-package-githubcomllm-dllm-d-routerpkgkvevents-go-packages]] shows the `BlockStoredEvent` Go struct carries `LoraID *int` and `LoraName *string` fields alongside `ExtraKeys [][]any`. Combined with [[kv-cache-indexer-llm-d]]'s description ("if a `LoraName` is present, it is used in place of the base model name when deriving block keys... cache hits are correctly scoped to the adapter"), the v0.5 blog's "LoRA-precise prefix caching" claim checks out against primary source, not just marketing copy.

**But none of this is the default.** [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducer-at-main-llm-dllm-d]] (directory README) states the generic `prefix-cache-scorer` must be pointed at the precise producer by name (`prefixMatchInfoProducerName: precise-prefix-cache-producer`); "**Without the `prefixMatchInfoProducerName` field, the scorer falls back to the auto-spawned approx producer**" — silently, no error. [[prefix-cache-aware-routing-llm-d]] (llm-d.ai v0.9 docs) confirms the approximate implementation is the lightweight, zero-dependency default: "Since the EPP does not natively contain a tokenizer, it approximates tokens using character-to-token ratios... builds a rolling hash chain... maintains an in-memory LRU index of which prefix hashes were recently sent to which Pods." A dedicated fetch of the approximate producer's own README ([[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerapproximateprefixrea]]) found **zero occurrences** of `cache_salt`, `salt`, `LoRA`, `tenant`, or `principal` anywhere in the document. Its index key is described purely as `(cluster, block)` for the multi-cluster variant or just the token-hash block for the single-cluster variant — no tenant, model, or adapter dimension at all.

**None of the corpus's own performance case studies mention isolation.** A direct grep of [[accelerate-multi-turn-llm-workloads-on-openshift-ai-with-llm-d-intelligent-routi]] and [[how-llm-d-prefix-cache-routing-made-qwen-7b-on-eks-23x-faster-dev-community]] — the two sources cited for opposing_position A — found zero mentions of `salt`, `tenant`, or `isolation` in either (the one "isolated" hit in the OpenShift AI piece is "isolated prompts" meaning single-turn, unrelated to tenancy). This confirms opposing_position A's characterization is accurate as far as it goes: llm-d's own marketing and benchmark write-ups never raise isolation because llm-d's architecture treats isolation as entirely delegated to the engine/gateway layer, not something the router provides.

## Evidence synthesis

### Position A: cross-tenant reuse is an unqualified performance win in llm-d's own materials

This is literally true of what's published. Every llm-d-authored benchmark and architecture doc in the corpus describes prefix-cache-aware routing purely as a throughput/TTFT optimization, with no isolation caveat. That is not an oversight to be corrected by reading harder — it reflects a real architectural choice: llm-d does not implement or enforce cache isolation itself. Isolation is a property of whatever cache-key scheme the *inference engine* computes (vLLM's `cache_salt`, or its absence) and of whatever *gateway/auth layer* decides to set that salt per tenant. The router's job, by design, is to mirror whatever partitioning the engine already enforces — it "recomputes" keys, it does not invent a salting policy. So Position A's evidence base (the corpus's own case studies) is not naive; it's describing the default, unsalted configuration, which is the only configuration llm-d itself ships an opinion about.

### Position B: shared caches leak via timing side channels, and isolation costs most of the reuse benefit

This is also correct, but the "costs most of the reuse benefit" clause needs to be split by which salting design is actually shipped versus proposed. Root/single-barrier salting — the *only* variant merged into vLLM (0.9, PR #17045) — genuinely destroys nearly all *cross-tenant* prefix sharing, because it salts the chain root and every downstream block inherits that salt via hash-chaining. It does **not** destroy *intra-tenant* reuse (multi-turn conversation extension, repeated calls from the same salted client) — that reuse chains normally after block 0. The boundary/multi-barrier salting that would let a shared system-prompt preamble stay cached while only the divergent tail is isolated is a real, sound idea (present as design (B) in the original RFC and elaborated in [[governing-the-kv-cache]]'s Section 4.2), but it is unshipped in vLLM as of the read sources — the RFC thread shows only design (A) merged, and one recent (Aug 2026) drive-by GitHub comment claims an unmerged draft PR (#52655) upstreaming design B with specific benchmark numbers (93%+ reuse retained, timing AUC ~0.5). That single comment is from a low-activity account, is uncorroborated anywhere else in the corpus, and its numbers are suspiciously precise for an unmerged draft — I am treating it as an unverified claim, not evidence that boundary salting is production-available. As things stand, an operator choosing to salt chooses between full cross-tenant reuse + full timing exposure, or (with root salting) full tenant isolation + reuse collapsed to session-local only.

Separately, [[governing-the-kv-cache]] itself deserves a calibration flag: its ablation numbers (0.0%/100.0% ASR columns, 12.6% audit-scheduler improvement, 31.6% evolutionary tipping point) are described as "analytic controls" from a seeded, deterministic simulation, not from an independent empirical attack against a real multi-tenant deployment — the paper is explicit about this itself ("Simulation vs. production... extended field experiments with real adversarial tenants remain future work"). The load-bearing, independently-corroborated fact from this source is narrower and more solid: three real published attacks exist (PromptPeek/NDSS 2025, EarlyBird, InputSnatch — all separately present in the corpus as [[the-early-bird-catches-the-leak-unveiling-timing]], [[inputsnatch-stealing-input-in-llm-services-via-timing-side-channel-attacks]], [[i-know-what-you-asked-prompt-leakage-via]]), the vLLM RFC itself was motivated by this literature independent of this synthesizing paper, and HMAC/root-salting is the correct-in-principle mitigation (cryptographic collision resistance genuinely defeats a hash-equality oracle). I did not independently read the three primary attack papers within this locus's source budget — that's a real gap, noted below.

## Committed position

The two positions are not actually in tension once you separate "what does llm-d's router do" from "what does llm-d's router *decide*." Isolation is never the router's job in this architecture — it is enforced entirely by the inference engine's cache-key computation, and llm-d's precise-prefix-cache-producer is a well-built mirror of that: for vLLM, it recomputes the same salted/LoRA-partitioned block keys the engine already hashes (via the `extra_keys` interface vLLM documents as being "exposed for external KV cache consumers to reconstruct block hashes"), so routing *does* still find the right pod for a salted or LoRA-scoped request — reuse is preserved wherever the engine's own cache would have hit, and correctly scored zero wherever it wouldn't. The "defeats reuse" cost that Position B raises is real, but it is a cost of root-salting *at the engine layer*, not a cost the router adds — with one clean, documented exception: on SGLang, the router's precise path is currently blind to `cache_salt` (SGLang doesn't emit `extra_keys`), so salted SGLang traffic keeps its isolation (engine-enforced regardless) but loses 100% of its routing affinity, a router-attributable cost absent for vLLM. The genuinely load-bearing finding, though, is that this salt-aware behavior requires an explicit operator opt-in (`prefixMatchInfoProducerName: precise-prefix-cache-producer`); the silent default fallback — the approximate producer, confirmed via both the v0.9 docs and a direct README fetch to have zero tenant/salt/LoRA awareness and a shared, unpartitioned per-pod LRU keyed on raw character-approximated text — means an operator who turns on `cache_salt` for isolation but leaves the router on its default scorer gets correct isolation (safe) with routing that keeps chasing phantom prefix matches that can never actually hit (affinity silently evaporates, no data leaks through routing itself since the local LRU isn't API-exposed). And an operator running the (more common, judging by the corpus's own unqualified case studies) default approximate router *without* `cache_salt` is running precisely the unprotected, globally-shared-cache configuration the published timing attacks target, with llm-d contributing no independent mitigation of its own.

- **Position:** llm-d's precise routing path is genuinely salt- and LoRA-aware for vLLM (it recomputes block keys from the same `extra_keys` vLLM emits, so routing finds the correct pod without defeating engine-enforced isolation), but this is opt-in configuration, not a default; the default approximate scorer is completely blind to `cache_salt`/tenant/adapter identity, and llm-d itself never enforces isolation — it only ever mirrors whatever the engine and gateway layer already decided.
- **Confidence:** high on the mechanics (precise producer is salt/LoRA-aware for vLLM, salt-blind by fallback default, SGLang precise-cache-misses on salted traffic) — these are corroborated across four independent primary sources (llm-d-router README/directory listing, vLLM's `kv_events.py`, the `kvevents` Go package, and a direct fetch of the approximate producer's README). Medium on the broader "how bad is the default exposure in practice" security framing, since the quantitative ASR/efficiency numbers rest substantially on one synthesizing paper whose empirical claims are explicitly simulation-based rather than field-measured, and I did not independently verify the three underlying attack papers within this locus's budget.
- **Boundary conditions:** the salt-aware routing finding applies specifically to the llm-d-router `precise-prefix-cache-producer` wired to a vLLM backend on the versions documented (README last touched Sep 5, 2026; vLLM `cache_salt` since 0.9). It does not extend to SGLang backends (precise routing degrades to cache-misses for salted traffic) or to any deployment left on the default approximate scorer (no salt/tenant awareness at all, regardless of engine).
- **What would change this position:** (1) independent confirmation that vLLM's boundary/multi-barrier salting design actually merges upstream (currently only a single unverified GitHub comment claims a draft PR) — if it ships and llm-d's producer is updated to consume a salt-offset parameter, the "isolation costs most of the reuse benefit" half of Position B weakens substantially; (2) a field measurement (not simulation) of ASR against a real llm-d deployment running the default approximate scorer without `cache_salt` — this exists conceptually but I found no llm-d-specific instance of it, only generic-vLLM/SGLang timing measurements; (3) evidence that SGLang has added `extra_keys` emission, which would close the one clean router-attributable affinity gap identified here.
- **Evidence weight:** 4 primary-source code/doc artifacts (llm-d-router precise-producer README ×2 fetches, vLLM `kv_events.py`, `kvevents` Go package, approximate-producer README) directly support the "precise=salt-aware, approximate=salt-blind-default" claim; 1 vendor blog post claims LoRA support (corroborated by code); 1 synthesizing academic-style paper (uncertain provenance/polish) supplies the security framing, itself citing 3 attack papers present in the corpus but not independently re-verified here; 0 sources contradict the core mechanics finding.

## Open questions

- Does the multi-barrier/boundary-salting design (vLLM RFC design B) have any real upstream traction beyond the single unverified Aug 2026 GitHub comment claiming PR #52655? Worth a follow-up check closer to a final-report cite-check pass.
- Has anyone measured actual cache-hit-rate degradation on a real llm-d deployment with `cache_salt` enabled versus disabled? All efficiency numbers in this locus are either vLLM-generic or from the (simulation-heavy) governing-the-kv-cache paper.
- Does SGLang's roadmap include `extra_keys` emission for KV-events? Not found in this corpus; would close the SGLang affinity gap.
- I did not independently read the full text of PromptPeek (NDSS 2025), EarlyBird, or InputSnatch within this locus's 4-source budget — only governing-the-kv-cache's summary of them. Recommend the width/security-adjacent locus (if any) verify the headline ASR numbers directly.
