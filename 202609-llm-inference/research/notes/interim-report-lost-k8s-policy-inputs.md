# Interim report: lost-k8s-policy-inputs

**Locus question:** What replaces the Kubernetes-only policy inputs off-cluster — InferenceObjective priority/SLO (FlowControl priority bands), InferenceModelRewrite (model aliasing, canary splits), PodMonitor metrics discovery — using static config, the Inference Payload Processor, or the gateway tier?
**Flavor:** synthesis

## What the corpus already said

The width sweep already surfaced the core fact and a genuine internal tension in how it's worded. [[no-kubernetes-no-problem-llm-d-now-runs-anywhere-llm-d]] (the llm-d.ai blog announcing file-discovery) states the router is "platform-invariant by construction" for scoring/filtering/FlowControl, then immediately qualifies: "A few features are still configured through Kubernetes CRDs — per-request priority from `InferenceObjective`, and `InferenceModelRewrite`-driven model-name rewriting — so outside Kubernetes they fall back to static configuration or are not yet available." Analyst B flagged this as a tension between the "one routing stack, platform-invariant" marketing claim and the corpus's own "inactive features" list — my read is it isn't a contradiction so much as an equivocation: "platform-invariant" describes the *scheduling* plugins (scorers/filters/pickers), which genuinely are unchanged; the FlowControl/model-rewrite carve-out is about *policy inputs* that in K8s mode arrive via CRD-watching reconcilers, which is a separate subsystem from the discovery interface the post is actually about.

## What the new sources say

[[llm-ddocsinfrastructureno-kubernetes-deploymentmd-at-main-llm-dllm-d-github]] (llm-d/llm-d docs/infrastructure/no-kubernetes-deployment.md) gives the tightest official list of what's out of scope without Kubernetes: "`InferenceObjective`-driven FlowControl, the `InferenceModelRewrite` model-name rewriter, and `PodMonitor`-based Prometheus discovery. Scoring, prefix-cache affinity, saturation-based admission, and Prometheus metrics on `--metrics-port` all work." Note it specifically indicts "FlowControl" as a casualty, not just "SLO objectives."

[[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]] (llm-d-router's own `docs/discovery.md`, the most current and most precise source — Sept 2 2026 commit) narrows this further and, read carefully, resolves the apparent conflict: "**`InferenceModelRewrite`** (model name rewriting for traffic split or canary). The reconciler is not started; `ds.ModelRewriteGet` returns nil for every request. There is no file-mode equivalent today." And: "**`InferenceObjective`** (per-request SLO objectives). The reconciler is not started; objective lookups return nil. Plugins that depend on per-request SLO data will see no objectives configured." This doc does **not** say FlowControl itself is disabled — only that the *objective-lookup* step that FlowControl optionally consumes returns nil off-cluster. That is a materially narrower claim than the blog/no-k8s-deployment.md's "InferenceObjective-driven FlowControl... is out of scope," and it is the newer, code-adjacent, higher-authority source per this run's evidence-ranking convention (code/merged-PR docs outrank vendor blogs).

[[llm-d-flow-control-priority-queuing-for-shared-gpu-inference-red-hat-developer]] (Red Hat Developer, Aug 27 2026, v0.10.0) confirms FlowControl's priority-band mechanics are driven entirely by two HTTP header values resolved into a "flow key": "Once a request reaches the Endpoint Picker, the objective and fairness ID (priority and tenant) header values are resolved into a flow key... **Missing objectives default to priority 0.**" Crucially, [[configuration-llm-d]] (llm-d.ai EndpointPickerConfig reference) shows the `flowControl` section — `priorityBands`, `fairnessPolicyRef`, `orderingPolicyRef`, `saturationDetector` — is plain YAML read once at EPP startup, explicitly **not** a reconciled Kubernetes CRD: "the configuration is not reconciled by a controller and is only read on startup." So the band topology and fairness/ordering policy engine are already platform-neutral; only the per-request *priority assignment* step depends on a K8s-only reconciler.

My targeted fetch of the canonical header reference, [[epp-http-headers-reference-llm-d]] (llm-d Router v0.9 API reference, ground-truth tier), pins down exactly what that dependency is. The three load-bearing headers: `x-llm-d-inference-objective` "names an `InferenceObjective` resource in the same namespace as the `InferencePool`; EPP looks it up to apply priority/performance goals" (i.e., the header carries a **name to resolve via CRD**, not a raw integer — off-cluster this lookup returns nil, per discovery.md, so every request silently lands in the default band); `x-llm-d-inference-fairness-id`, which "groups requests for fairness-based flow control; defaults to `default-flow` if omitted" — a plain opaque string with **no CRD dependency at all**; and `x-llm-d-model-name-rewrite`, documented as "an explicit per-request override of the model name, **an alternative to the server-side rule-based `InferenceModelRewrite` API**." That last header is a ready-made, already-shipped bypass for the exact CRD the corpus says has "no file-mode equivalent today" — it just isn't packaged as one in the docs the width sweep read.

[[application-gateway-for-containers-inference-gateway-microsoft-learn]] and [[routing-agent-traffic-is-really-three-decisions-aks-engineering-blog]] corroborate the pattern from the GIE-vendor side (Azure's implementation, using the pre-rename `x-gateway-inference-objective` / `X-Gateway-Model-Name` headers that llm-d v0.9 now treats as deprecated read-aliases): priority and model selection in this whole plugin family are designed as **header-carried decisions that any upstream component can set**, with the CRD as only one (Kubernetes-native) way to populate them. The AKS post independently confirms InferenceObjective "carries only an integer priority, no criticality enum" — consistent with a lightweight, header-transportable value, not something intrinsically tied to apiserver watches.

On PodMonitor: [[metrics-llm-d]] documents PodMonitor purely as a Kustomize-deployed Prometheus Operator CRD that "creates PodMonitors that scrape model server metrics"; the underlying `/metrics` endpoints on vLLM and the EPP (`--metrics-port`, port 9090) are plain Prometheus exposition format, confirmed working off-cluster by [[llm-ddocsinfrastructureno-kubernetes-deploymentmd-at-main-llm-dllm-d-github]]. This is the least interesting of the three losses — PodMonitor is a Prometheus-Operator scrape-target-discovery convenience, not a routing-policy input, and every non-Kubernetes Prometheus deployment already solves "how do I discover scrape targets" with `file_sd_config` or `static_configs`.

## Evidence synthesis

Two of the three "lost" inputs are not actually lost — they're mis-filed. FlowControl's policy engine (bands, fairness, ordering, saturation detection) is static YAML today even on Kubernetes; what's missing off-cluster is exactly one lookup step (name → priority via the InferenceObjective CRD), and the router already ships an unrelated escape hatch for the model-rewrite half of the problem (`x-llm-d-model-name-rewrite`) that the corpus's parity-focused sources never connected back to this locus. PodMonitor is a non-issue: it's solved by generic Prometheus tooling, not by anything llm-d-specific.

The one real, unresolved gap is **priority-band assignment**. Off-cluster, `x-llm-d-inference-objective` is dead on arrival (its reconciler never starts, so the lookup always returns nil, and the request falls back to default priority 0 with `default-flow` fairness), and no file-backed or header-value-is-the-integer alternative ships today. `x-llm-d-inference-fairness-id` (tenant fairness) works out of the box off-cluster with zero code — it's a bare string key, and I found no source suggesting it needs a K8s object of any kind. That asymmetry (tenant fairness ships, priority does not) is itself interesting and not something either of the corpus's original sources called out explicitly; it falls out of triangulating discovery.md, the Red Hat FlowControl piece, and the header reference together.

For model-name rewrite / canary, the practical substitute is two-tiered by how much you need: (1) an explicit per-request model choice is already solved — set `x-llm-d-model-name-rewrite` yourself; zero EPP code. (2) A *weighted* canary split (the actual "80/20 traffic split" use case InferenceModelRewrite targets) still requires something to make the weighted random choice and inject the header — that decision-making has no shipped component. The corpus's Inference Payload Processor (IPP, successor to Body-Based Routing) is a red herring for this specific sub-problem: per [[llm-d-v09-hardened-for-scale-llm-d]], IPP "extracts the model name from request bodies and sets routing headers, letting HTTPRoutes direct traffic to the appropriate InferencePool" — it's a *read* path (body → header, for routing to a different pool/gateway), not a *write* path that could inject a canary decision. It solves a different problem (multi-model gateway fan-out) than InferenceModelRewrite (aliasing/canary within one served model identity). I could not fetch the IPP repo directly (escalation-queued), but nothing in any corpus note attributes canary-decision logic to it, and its documented mechanism (extract-and-forward) has no obvious slot for injecting a weighted random header value it didn't read from the body.

## Committed position

The right way to build this is not "wait for llm-d to ship non-K8s InferenceObjective/InferenceModelRewrite equivalents" (per discovery.md, that work is explicitly deferred — the PR that shipped file-discovery left `InferenceObjectiveReconciler` and `InferenceModelRewriteReconciler` on the old controller-runtime pattern with a TODO for a follow-up) — it's to build a small, targeted custom EPP plugin that resolves priority statically, and to push model-rewrite/canary logic to the gateway tier where the router already gives you a header-based hook. Concretely:

**Replacement table (lost input → substitute → effort):**

| Lost K8s-only input | Substitute | Effort |
|---|---|---|
| FlowControl priority-band *topology* (bands, fairness/ordering policy, saturation detector) | None needed — already static YAML in `EndpointPickerConfig.flowControl`, not CRD-reconciled even on K8s | Zero |
| Per-tenant fairness (`x-llm-d-inference-fairness-id`) | None needed — plain header, defaults to `default-flow`, no CRD dependency found in any source | Zero |
| Per-request priority via `InferenceObjective` name lookup | Custom `Admitter`/`DataProducer` plugin (auto-wired via the documented Go-interface pattern in [[configuration-llm-d]]) that maps a request attribute (API key, header, path) to a priority integer from a static file — mirroring the FileDiscovery pattern (read-once + optional `fsnotify` reload) but for priority instead of endpoints | Moderate — new Go plugin, but the auto-wiring contract and file-watch pattern are both already proven in-tree |
| Explicit per-request model selection (simple case of InferenceModelRewrite) | `x-llm-d-model-name-rewrite` header, already documented as the shipped alternative to the CRD | Zero — just have the caller or gateway set the header |
| Weighted canary/traffic-split model rewriting | Gateway-tier logic (Envoy Lua/ext_proc filter, or a thin sidecar) that makes the weighted random choice and sets `x-llm-d-model-name-rewrite` per request | Low-moderate — no EPP code changes; logic lives entirely upstream of the router |
| `PodMonitor`-based metrics scrape-target discovery | Static Prometheus `scrape_configs` (`static_configs` or `file_sd_config`) pointing at known EPP (`:9090`) and vLLM (`--metrics-port`) addresses | Zero — generic Prometheus practice, not llm-d-specific |

The single highest-leverage build item for the user's stated goal (customize the router for non-K8s backends while reusing as much of llm-d as possible) is the static-priority plugin, because it's the only piece with a genuine functional gap and no already-shipped escape hatch; everything else is either free (static config) or already has a documented header-based bypass the corpus's initial sweep didn't connect to this locus.

- **Position:** Of the three "lost" K8s policy inputs, only per-request priority assignment is a genuine gap requiring new code (a static/file-backed priority-resolution plugin); PodMonitor is fully solved by generic Prometheus config, and InferenceModelRewrite's simple case is already solved by the `x-llm-d-model-name-rewrite` header, with only weighted canary-splitting needing (gateway-tier, not EPP-tier) new logic.
- **Confidence:** medium-high. The header semantics and "reconciler not started / lookup returns nil" mechanics are stated directly and consistently across three independent, high-authority sources (discovery.md, the Red Hat FlowControl article, and the epp-http-headers reference). The synthesis step — that this makes tenant fairness free and priority the one real gap — is my triangulation across those sources, not a single source's explicit claim, so I'd call the overall framing medium-high rather than high.
- **Boundary conditions:** This holds for llm-d-router at the v0.9–v0.10 HEAD state documented in this corpus (Sept 2026). It assumes the deployer is willing to write and maintain a small Go plugin against the `Admitter`/`DataProducer` auto-wiring interfaces (Alpha-tier per the v0.9 Plugin Stability Lifecycle, requiring `--allow-experimental-plugins`) rather than waiting on upstream. It does not cover SLO-target-based admission (`x-llm-d-slo-ttft-ms`/`x-llm-d-slo-tpot-ms`, latency-predictor-driven admitters) — those appear even more tightly coupled to per-request objective data than raw priority and were out of this locus's source budget to verify.
- **What would change this position:** Discovery of a merged PR or release note explicitly shipping a file-backed or header-integer-based `InferenceObjective` substitute (i.e., the "follow-up PR" that discovery-plugins-k8s-and-file-based-endpoint-discovery flagged as deferred, if it has since landed) would demote the priority plugin from "build it yourself" to "already exists — just configure it." Evidence that `x-llm-d-inference-fairness-id` actually does require some K8s-side registration I haven't seen would also revise the "tenant fairness is free" claim downward.
- **Evidence weight:** 4 primary/ground-truth sources support the header-substitution reading (discovery.md, configuration-llm-d, epp-http-headers-reference-llm-d, Red Hat FlowControl article); 1 source (the llm-d.ai blog) uses looser language ("InferenceObjective-driven FlowControl... out of scope") that a naive reading would take as contradicting this; I resolve that as imprecision in the blog rather than a real conflict, based on the more precise and more recent discovery.md wording. No source directly confirms a static-priority plugin has been built by anyone; that part of the recommendation is architectural inference from the documented plugin-interface contract, not observed practice.

## Open questions

- Has anyone (llm-d-incubation, a vendor, or a community plugin) actually shipped a file-backed or static InferenceObjective-equivalent priority plugin? Not found in this budget; worth a dedicated search if the final report wants to cite prior art rather than a from-scratch recommendation.
- Does `x-llm-d-inference-fairness-id` genuinely have zero K8s dependency, or does some fairness policy (e.g. `global-strict-fairness-policy`) consume per-tenant quota objects that themselves live in a CRD? The sources read here describe the header and the policy names but not every fairness policy's internal state requirements.
- What does the IPP repo itself say about extensibility — could its body-extraction path be forked/configured to also perform weighted canary assignment, closing the one gateway-tier gap in the table above without hand-rolling an Envoy filter? The IPP repo was escalation-queued and unavailable this pass.
