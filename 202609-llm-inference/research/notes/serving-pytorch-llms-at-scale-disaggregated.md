summary: 'PyTorch Conference deck (Cong Liu, Google; Maroon Ayoub, IBM Research) on
  llm-d''s disaggregated inference. Describes llm-d explicitly as an ''open-source,
  k8s-native, pluggable inference stack'' with an ''LLM aware inference gateway +
  LLM aware autoscaler''. Details the P/D inference scheduler decision flow: a threshold
  on ''% new tokens to prefill'' decides disaggregation vs. no-disaggregation; when
  disaggregating, D-picking plugins include kv cache utilization and queue depth,
  P-picking plugins include prefix cache hit and queue depth. Confirms the routing
  sidecar behavior mirrors the GitHub repo README: in non-disaggregation mode (no
  x-prefiller-host-port header) it simply forwards to the local decode node; in disaggregation
  mode it first sends the request to the prefill node with max_tokens=1, then forwards
  to the local decode node, which pulls the KV cache from prefill via the NIXL connector.
  Gives two concrete well-lit-path benchmark topologies: ''P/D over RDMA'' -- 8xH200
  GPUs, InfiniBand OR RoCE RDMA, Llama-3.3-70B-Instruct-FP8, 4x TP=1 prefill workers
  + 1x TP=4 decode worker; and ''Wide-EP with P/D'' -- 32xH200 GPUs, InfiniBand OR
  RoCE RDMA, DeepSeek-R1-0528, 1x DP=16 prefill worker + 1x DP=16 decode worker. Best-practice
  guidance: P/D disaggregation pays off for large models (Llama-70B+, not 8B), longer
  ISL (e.g. 10k ISL | 1k OSL vs 200|200), and sparse MoE with wide-EP opportunities;
  tune via heterogeneous parallelism (fewer-parallelism/more-replica P workers vs.
  more-parallelism/fewer-replica D workers) and xPyD ratio. Flags two ''future work''
  ideas not yet shipped: (1) ''decode-first'' PD where the router opportunistically
  picks a decoder first (since the router lacks visibility into remote KV-cache storage)
  and only falls back to P/D if the decoder reports low cache hit; (2) ''deferred
  decoder picking'' -- picking D only after prefill completes, using freshest load
  metrics, instead of picking P and D both at request-arrival time (today''s behavior,
  which can use stale load data since the request lands on D later).'

P/D Best Practices
P/D disaggregation is not a target for all workloads. We suggest exploring P/D disaggregation for 
workloads with:
●
Large models (e.g. Llama-70B+, not Llama-8B)
●
Longer input sequence lengths (e.g 10k ISL | 1k OSL, not 200 ISL | 200 OSL)
●
Sparse MoE architectures with opportunities for wide-EP
●
As a result, as you tune your P/D deployments, we suggest focusing on the following parameters:
●
Heterogeneous Parallelism: deploy P workers with less parallelism and more replicas and D 
workers with more parallelism and fewer replicas
●
xPyD Ratios: tuning the ratio of P workers to D workers to ensure balance for your ISL|OSL ratio
