# On-Premise Internal LLM Inference: The Stack Below the Engine

Organisations serving large language models from hardware they own, for internal users, converge on a narrow arrangement. The inference engine — the process holding weights in accelerator memory, batching requests against them and streaming tokens back — is adopted as shipped. vLLM is the default in every documented population, from a four-GPU single server to a 24-node national-laboratory cluster; llama.cpp appears only where aggressive quantization is what makes a model fit [[ecient-deployment-of-a-685b-parameter-open]], [[design-and-operation-of-a-federated-gpu-cluster]]. The scheduler is whatever the institution already ran. What organisations write themselves is a four-part policy layer: an OpenAI-compatible front door, identity integration, per-tenant token accounting, and model lifecycle management [[first-federated-inference-resource-scheduling-toolkit-for]], [[realtime-and-batch-processing-of-gpu-workloads-infoq]]. Nobody in the record writes an engine, and the platforms sold for the purpose wrap the same open ones [[vmware-private-ai-foundation-with-nvidia-91]].

One property of the evidence governs everything below. On-premise operators mostly do not publish, and those that do are not a random sample: the ACM Technology Policy Council finds such arrangements "tend to be less frequently disclosed", and "it is therefore reasonable to assume that more procurement arrangements exist than are publicly documented" [[buy-versus-build-an-llm-a-decision-framework-for-governments]]. The sites publishing peer-reviewed detail are research-computing centres, also the population sitting on purchased GPUs and round-the-clock demand. These cases map where on-premise works, not how often it is attempted.

## 1. What Changes When Deployment Is Strictly On-Premise

"Strictly on-premise" covers an owned or colocated datacentre, a private cloud on owned hardware, an air-gapped or classified enclave, and an existing high-performance computing (HPC) cluster acquiring an inference tenant. They differ in almost everything except the engine.

| Dimension | Rented cloud GPUs | Strictly on-premise |
|---|---|---|
| Serving engine | vLLM, as-is | Identical; llama.cpp for extreme quantization |
| Control plane | Chosen, usually Kubernetes | **Inherited** — whichever scheduler holds the GPUs [[experience-deploying-containerized-genai-services]] |
| Facility | Abstracted away | **Yours**: power, cooling, feeder capacity [[ai-rack-densities-are-forcing-a-rethink-of-data-center-power-and-cooling-design]] |
| Peak provisioning | Oversubscribed | **Near nameplate** at 2-4 servers [[polca-power-oversubscription-in-llm-cloud-providers]] |
| Update path | A registry pull | A staged release across a boundary [[air-gap-deployment-nvidia-nim-for-llm-and-vlm]] |
| Decision basis | Usually cost | Often a constraint: residency, air-gap, classification [[army-intelligence-article-the-united-states-army]] |

Where the driver is a constraint rather than a bill, no cost baseline applies: SS&C Technologies' architect describes a hard requirement that data not leave the datacentre, and Brazil's LNCC cites data sovereignty [[realtime-and-batch-processing-of-gpu-workloads-infoq]], [[ecient-deployment-of-a-685b-parameter-open]]. One asymmetry follows from two sources rather than any one. Microsoft's POLCA study found that LLM inference clusters "utilize only up to 80% of the provisioned power" against roughly 10% headroom for training [[polca-power-oversubscription-in-llm-cloud-providers]], and modelled traces show per-server peaks decorrelating only across many servers [[from-servers-to-sites-compositional-power-trace-generation-of]]; jointly they imply what neither states, that a two-to-four-server fleet has no tenant pool to multiplex against and so provisions nearer nameplate.

## 2. The Hardware and Facility Layer

Capacity planning on-premise is memory arithmetic first. Weights occupy accelerator memory in proportion to parameter count and numeric precision; the key-value cache — the per-token attention state an engine keeps so it need not recompute a conversation's history — scales with context and concurrency. A 70-billion-parameter model at FP16 (16-bit floating point) needs roughly 140 GB and so exceeds one 80 GB H100, which makes quantization, storing weights at lower precision, the dominant lever [[llm-inference-hardware-sizing-enterprise-gpu-guide-2026-gpusmith]]. Broadcom puts the cache term at 0.000122 GiB per token for Llama-3 8B and 0.000305 GiB for 70B, best-case with real inference time potentially 50% higher — vendor guidance, cited as recommendation [[llm-inference-sizing-and-performance-guidance-vmware-cloud-foundation-vcf-blog]]. Host CPU is the term the sizing guides omit: CPU-starved multi-GPU vLLM shows up to 7.11x higher time-to-first-token, with four to eight cores per GPU the identified floor [[characterizing-cpu-induced-slowdowns-in]].

The low camp sits at one to two chassis and the high camp at six to eight, so the "10-15 kW air limit" is a legacy-room power budget rather than a cooling ceiling: one NVIDIA DGX H100/H200 chassis is rated at 10.2 kW maximum system power and exceeds it alone [[introduction-to-nvidia-dgx-h100h200-systems-nvidia-dgx-h100h200-user-guide]]. What survives as measurement is per-server, a national-laboratory study recording an H100 HGX node peaking at 8.4 kW and a four-GPU node's Llama-3 70B inference saturating near 2.8 kW [[measurement-of-generative-ai-workload-power-profiles-for]]. The planning statement is N chassis times 6.5-10.2 kW nameplate, inference drawing about 80% of provisioned power, provisioning still sized to nameplate. An audited absence belongs here: **no named on-premise operator publishes a measured inference kilowatt figure per rack.** A search of the vault, scholarly queries on measured rack power, Uptime Institute material and ASHRAE TC 9.9 guidance returned only per-node and per-GPU measurements.

The facility layer is a step function. At the bottom it is free — a 200-person German engineering firm serves its whole company from one server with four L40S cards drawing roughly 2 kW, about EUR 200 a month of electricity, in an existing server room, on a vendor-authored account read accordingly [[private-ai-platform-for-200-employee-engineering-firm]]. At the top it is an air-to-liquid transition and a 208V-to-415V retrofit described as a multi-week electrical project [[high-density-colocation-for-ai-and-gpu-infrastructure]]. A single server needs no facility work and cannot reach the utilization that would justify it; scaling to reach it activates the facility layer.

## 3. Scheduling Shared On-Premise Clusters: Kubernetes, Slurm, and HPC Practice

Two families of software decide which process runs on which GPU. Kubernetes is a service orchestrator for long-lived processes that scale with request load; Slurm, PBS and Flux are batch schedulers that queue jobs with a fixed start and end against a fixed node pool, with fair-share accounting between projects. The fork follows resource ownership rather than inference performance.

### A. The fork follows the incumbent substrate

Every rejection of Kubernetes in this record cites organisational cost; none cites a technical limit. GWDG kept Slurm because replacing it "would disrupt existing users and workflows", and because keeping it let the service "operate side by side with user workloads and utilize gaps in the Slurm scheduling" [[research-paper]]. The Austrian cluster chose Docker Compose plus systemd because "about ten services on a handful of nodes; Compose is sufficient and simpler" [[design-and-operation-of-a-federated-gpu-cluster]]. Sandia corrects the clean binary, running GPU-equipped production OpenShift *and* Slurm and Flux with the identical vLLM image on both while its lab-wide Kubernetes platform "currently lacks GPU resources" [[experience-deploying-containerized-genai-services]]. The question is rarely Kubernetes versus Slurm on the merits; it is which platform the accelerators are attached to.

What the batch route surrenders its own authors state: no autoscaling as requests rise, no network virtualization (so a script picks a random port and checks a routing table), load balancing that is effectively random, health checks "implemented from scratch," and a cold load that "can take as long as ten minutes for larger models on our hardware configuration" — with the concession that dedicated production infrastructure "may therefore consistently outperform the architecture proposed in this paper" [[research-paper]]. A Red Hat study quantifies the routing half of that gap on a cloud testbed rather than on-premise hardware, prefix-cache-aware routing across eight vLLM replicas cutting mean time-to-first-token from about 500 ms to about 80 ms [[evaluating-kubernetes-performance-for-genai]]. In exchange the HPC route gains rootless containers, fair-share accounting and backfill into gaps beside training jobs, with model lifecycle built on both sides — Argonne's two-hour hot-node idle window and spin-up queue, the Austrian cluster's llama-swap split of resident from on-demand models [[first-federated-inference-resource-scheduling-toolkit-for]], [[new-ai-inference-service-now-ready-for-science-at-argonne]], [[design-and-operation-of-a-federated-gpu-cluster]].

Scale sets a measured ceiling on dispatch rather than the engine. ExaServe reports that on Aurora "non-streaming inference scales nearly linearly to 256 nodes, reaching 27.1 k requests/s", while "token streaming scales differently: a centralized proxy plateaus at ~4.7 k requests/s despite the model servers remaining within the service-level objective" [[exaserve-large-scale-llm-serving-on-exascale]].

### B. Partitioning relieves queueing, not under-utilization

A GPU can be subdivided three ways. MIG (Multi-Instance GPU) carves the device into hardware-isolated slices with their own memory; MPS (Multi-Process Service) enforces per-workload limits without hardware fault isolation; time-slicing interleaves processes with no isolation. Time-slicing and MPS are mutually exclusive, and the sharing mode applies per node rather than per GPU [[time-slicing-gpus-in-kubernetes-nvidia-gpu-operator]], [[github-nvidiak8s-device-plugin-nvidia-device-plugin-for-kubernetes-github]].

| Mechanism | Isolation | Measured evidence |
|---|---|---|
| MIG | Memory and fault isolation; compute and HBM but **not** the shared PCIe path [[predictable-llm-serving-on-gpu-clusters]] | Dynamic slicing raised concurrency 8→25 and cut mean job completion 28→18 min; at **equal concurrency** it slowed jobs 14→17 min and cut mean GPU utilization **45%→19%** through slice padding [[evaluating-kubernetes-performance-for-genai]]; ~1.00 req/s per GPU against ~0.76 time-sliced in NVIDIA's own test [[maximize-ai-infrastructure-throughput-by-consolidating-underutilized-gpu-workloa]] |
| MPS | Per-workload limits, no fault isolation [[github-nvidiak8s-device-plugin-nvidia-device-plugin-for-kubernetes-github]] | Co-located vLLM jobs retained 0.48-0.62 of solo throughput, pair-dependent; offline study [[elastico-elastic-configuration-and-interference-aware]] |
| Time-slicing | None [[time-slicing-gpus-in-kubernetes-nvidia-gpu-operator]] | No LLM-serving measurement; development, CI, notebooks [[gpu-sharing-on-kubernetes-time-slicing-mig-and-mps-compared-for-llm-workloads-po]] |

Both MIG results come from the same Red Hat study and must not be mixed: the throughput gain was bought with a threefold concurrency increase, while at equal concurrency slicing more than halved measured GPU busy-fraction and slowed every job. Partitioning relieves queueing and costs efficiency to do it, a poor answer to idle owned capacity; the tooling is unsettled too, the InstaSlice operator upstream of the dynamic slicer having been archived on 11 August 2026 [[github-openshiftinstaslice-operator-instaslice-operator-facilitates-slicing-of-a]]. **No controlled published comparison of vLLM under MIG versus MPS versus time-slicing with a noisy neighbour exists**; a targeted search of the MPS interference literature returned HPC physics benchmarks rather than LLM measurements [[granularity-and-interference-aware-gpu-sharing]]. The nearest evidence is a preprint in which static MIG alone missed a 200 ms p99 time-to-first-token target under synthetic contention, reaching 232 ms before a dynamic controller brought it to 199 ms [[predictable-llm-serving-on-gpu-clusters]]; neither it nor the offline MPS study is on-premise production data, and neither covers models above 7B.

The one named enterprise operator to state a partitioning decision declines it on fleet-size-relative demand: "I have four chips. I need all four chips to do everything it can", that "For me, partitioning is just too much", and that "the Llama-3.1-70B model is perfectly fine. I don't need to partition it". For now, he says, "I have nine models. They do everything my company needs". He addresses idle capacity through workload mix instead — "8 p.m. on a Tuesday is a great time to do document processing" [[realtime-and-batch-processing-of-gpu-workloads-infoq]]. Shared-cluster measurements support that remedy but none is on-premise: a 20,000-GPU inference cluster sat below 60% utilization for more than 99% of GPUs when dedicated to online workloads, while space-sharing raised cluster utilization from 26% to 76% [[muxflow-efficient-and-safe-gpu-sharing-in]], and the MLaaS in the Wild study of Alibaba PAI (NSDI '22) traces a 6,742-GPU platform at a median 0.042 GPUs per task instance [[this-paper-is-included-in-the-proceedings-of-the-2]], [[deepshare-assurance-driven-deep-learning-job]]. Three absences follow, each after searching the operator accounts above, the scholarly GPU-sharing and cluster-trace literature, and the Kubernetes GPU-operations material: **no GPU-level utilization figure exists for any on-premise Kubernetes deployment**; **no measured utilization figure exists for any named on-premise LLM inference cluster**; and **no named on-premise organisation discloses how it splits a fixed GPU pool** between inference and other tenants. The broadest circulating figure is weaker than it looks — a vendor report of 5% average GPU utilization covers roughly 23,000 clusters all on AWS, Azure or GCP, is framed as a pre-optimisation baseline, and appears in an article where one analyst puts Kubernetes AI clusters at 15-25% and another calls the 5% "a misnomer" [[ai-demand-surges-as-billions-in-compute-remain-locked]].

## 4. Air-Gapped and Classified Operation

An air-gapped enclave has no network path to the internet, so every artefact a serving stack needs — images, weights, dependencies, licences — must be staged on a connected host, carried across the boundary and verified inside. The mechanics are well documented; how organisations operate such enclaves is not documented at all.

NVIDIA's NIM air-gap guide (2.1.4) specifies a two-phase workflow: a connected host runs `download-to-cache` and optionally `create-model-store`, assets move by any allowed channel — an archive copy, `scp`, `rsync` or physical media — and the air-gapped phase must run with neither `NGC_API_KEY` nor `HF_TOKEN` set, so the container loads every asset from local storage. Its named trap is that on Kubernetes **every image referenced by the Helm chart** must be mirrored — init containers, sidecars, Helm tests, the GPU Operator [[air-gap-deployment-nvidia-nim-for-llm-and-vlm]]. Red Hat's path is the same shape through a bastion host running `oc-mirror` v2, NVIDIA CUDA only [[deploy-the-standalone-red-hat-ai-inference-container-in-a-disconnected-environme]], [[chapter-3-deploy-openshift-ai-in-a-disconnected-environment-deploy-or-decommissi]]. Sandia is the one operator account of that shape in the open: mirror the official vLLM images locally, download complete model repositories so the licence file travels with the weights, and run with offline and telemetry-suppressing environment variables, since vLLM otherwise "collects anonymous usage data by default" [[experience-deploying-containerized-genai-services]], [[usage-stats-collection-vllm]]. Licences need no callback: disconnected NVIDIA licence servers take manually uploaded files, with node-locked licences for air-gapped clients since vGPU 15.0, though extending that vGPU guide to NIM is an analyst's inference [[license-system-user-guide-nvidia-docs]].

Of three operational costs the vendor material underplays, only one has independent support. Model refresh — "without a controlled offline update pipeline, enclaves end up running year-old models" — is a vendor assertion [[air-gapped-llm-models-hardware-serving-vdf-ai]]; undiscovered egress is an unmeasured practitioner estimate of five to fifteen unknown dependencies, though the commonest named leak, a retrieval stack calling a remote embedding API, is specific enough to design against [[the-air-gapped-llm-blueprint-what-egress-free-deployments-actually-need]], [[on-prem-llm-deployment-2026-gpu-sizing-vllm-air-gapped]]; and a preprint using a synthetic attack suite reports 92% defence success across 55 infrastructure-level tests on per-department isolated instances, residual risk attributed to "credential misconfiguration and observability pipelines" [[burn-after-use-for-preventing-data-leakage-through-a]]. Vendor air-gap claims need verification: Nutanix's FAQ describes a dark-site bundle behind a support-portal login while its launch blog says air-gapped cases "will have to find other solutions" [[nutanix-enterprise-ai-faqs]], [[introducing-nutanix-enterprise-ai-a-simple-way-to-deploy-llms-and-secure-endpoin]]. Model licences are a further accreditation surface on one analyst's reading, Apache-2.0 weights being "the licence you can hand to an accreditor without a cover memo" [[best-air-gapped-llm-stack-apache-weights-on-vllm-beat-nvidias-fee-the-daily-brie]].

The absences are the finding. **No named organisation publishes an air-gapped LLM deployment with disclosed scale**; searching beyond the vendor documentation sets returned only marketing, search-optimised content and a single-author repository, the last forcing `--dtype float16`, AWQ 4-bit weights and `--enforce-eager` on Turing cards lacking BF16 and FP8 [[github-wu840407enterprise-airgapped-llm-production-reference-architecture-for-se]]. Classified serving is acknowledged at scale with its stack withheld: the US Army's AI2C describes CamoGPT as "currently deployed to NIPR (IL5 including CUI) and SIPR (IL6)" [[what-we-do-ai2c]], and an Army AL&T article reports roughly 75,000 users, quoting its data engineer that "our team does not train LLMs; we simply host published, open-source models that have been trained by companies like Meta, Google and Mistral" [[army-intelligence-article-the-united-states-army]]. Across that AI2C material, the AL&T article and the Defense Department announcements below, **no engine, GPU count, node count or accreditation artefact is disclosed for CamoGPT or any other classified programme.** Wholesale engine adoption is well evidenced for HPC centres, universities, enterprises and sovereign research programmes, and not evidenced for classified networks.

## 5. Government and Regulated-Industry Deployments

Regulated on-premise deployment is usually narrated as regulation forcing institutions to own hardware. The primary instruments do not say that; each requires jurisdiction, specific controls, auditable evidence, or an accredited enclave — and the enclave may belong to someone else.

| Instrument | Date read | Core requirement | Owned hardware? |
|---|---|---|---|
| HIPAA Security Rule, per the regulator's summary [[summary-of-the-hipaa-security-rule-hhsgov]] | current | "flexible, scalable, and technology neutral" safeguards | No |
| The EBA's outsourcing guidelines (EBA/GL/2019/02) [[final-report-on]] | 25 Feb 2019 | Third-country critical outsourcing permitted "subject to additional safeguards" | No |
| RBI payment-data directive [[data-localisation-requirement-in-reserve-bank-of-india-rbi-storage-of-payment-sy]] | 2018 | Payment data stored only in India | No — in-jurisdiction |
| The DoD Cloud Service Provider SRG, V1R1 [[unclassified-2]] | 14 Jun 2024 | §5.2.2.4: Impact Level 6 data only in a DoD or federal community cloud, "on-premises or off-premises in any cloud deployment model that restricts the physical location"; §5.2.2.3 likewise for IL5 | No — even at SECRET the enclave may be off-premises |
| SecNumCloud v3.2 [[premier-ministre]] | 8 Mar 2022 | §19.2 EU storage and administration; §19.6 EU-seated provider, non-EU holdings capped at 24% individually, 39% collectively | No — it regulates the **provider** |
| DORA (EU) 2022/2554 Arts 28-30 [[digital-operational-resilience-act-dora-article-28]], [[digital-operational-resilience-act-dora-article-29]], [[digital-operational-resilience-act-dora-article-30]] | applies 17 Jan 2025 | Register of information, concentration-risk assessment, audit rights, exit plans permitting transfer to another provider or, as one permitted route, "reincorporate them in-house" | No — in-house is one permitted route |

IL6 — a SECRET enclave — explicitly permits off-premises hosting, while §3.7.4 adds that IL6 offerings are "not considered 'commercially available'" and "may only be provided by CSPs under contract to the DOD" [[unclassified-2]]. SecNumCloud answers the extraterritorial-law problem by regulating who may own the provider rather than telling customers to buy servers [[premier-ministre]]. A practitioner analysis notes that business associate agreements are obtainable from commercial providers, naming as the real drivers dependency-chain length, extraterritorial reach including the CLOUD Act, in-border directives and audit evidence [[hipaa-compliant-llm-on-prem-phi-inference-without-a-baa]]. US defence accordingly runs toward procurement: GenAI.mil launched on 9 December 2025 with Google's Gemini for Government first, an official calling it "a collection of stovepiped commercial products that you lock yourself into"; the Army Enterprise LLM Workspace runs on Ask Sage IL5 software-as-a-service inside the Army's cArmy Cloud; DISA's INDOPACOM SIPRNet chatbot was explicitly research; and on 1 May 2026 the Department of Defense signed agreements with eight firms for IL6 and IL7 networks, authorisation status unclear [[the-era-of-genaimil-is-here-users-have-mixed-reactions-and-many-questions-defens]], [[army-launches-army-enterprise-llm-workspace-the-revolutionary-ai-platform-that-w]], [[disa-launching-experimental-cloud-based-chatbot-for-indo-pacific-command-defense]], [[dod-expands-its-classified-ai-work-with-8-companies-excluding-anthropic-amid-ong]], [[classified-networks-ai-agreements-soldier-systems-daily-soldier-systems-daily]].

The residue that compels self-operated hardware is narrow: classification enclaves, air-gap requirements, subprocessor bans, control-of-infrastructure directives and round-the-clock batch volume. The clearest control-of-infrastructure instance reaches the record only through a vendor customer story — an anonymised West African Tier-1 bank whose central bank required customer-data AI processing "within the country's borders, on infrastructure under the bank's direct control", answered with an air-gapped platform of 32 H100s running Llama 3.1 70B in tensor-parallel groups of four under vLLM [[sovereign-llm-platform-west-african-tier-1-bank]]. Sovereign national programmes, by contrast, are infrastructure programmes: the CNAS Sovereign AI Index v2.0 (August 2026) counts 184 government-backed projects across 67 countries, infrastructure rising to 80% of new projects, most model projects fine-tuning foreign open weights [[cnas-insights-sovereign-ais-second-wave-is-coming-into-view-cnas]].

Two claims that looked like evidence failed verification: a pharma consultancy's Mayo Clinic on-premise claim is absent from the npj review it cites, and the Fortune-100 healthcare case it leans on never says on-premise, reporting only that "data movement regulations forced the company to deploy models separately in each region of presence" [[fortune-100-healthcare-ships-llm-use-cases-truefoundry]]. For the same reason no on-premise adoption percentage appears here; the circulating figures trace to one untraceable vendor compilation. The absence of named regulated deployments is part broken and part intact: SS&C gives financial services one named operator with disclosed architecture and scale, while for healthcare the only named institution with a disclosed GPU count is a university hospital running Falcon-7B-Instruct on a single H100 across 287 queries [[implementing-local-open-source-llms-for-chatbot-based-document-retrieval-in-a-un]], and a radiology review argues the hardware barrier directly, many clinical centres lacking A100/H100-class GPUs and the power and cooling for them [[the-role-of-high-performance-gpurole-of-high-performance-gpu-resources-in-large]].

## 6. On-Premise Vendor Platforms and Appliances

Four commercial platforms are sold as an alternative to assembling the open stack. None replaces the engine; each occupies a layer above or below it — the virtualisation substrate, the Kubernetes control plane, the endpoint-management surface, or supported-runtime packaging.

| Platform (version, date) | Layer replaced and licence basis | Binding constraint |

| NVIDIA AI Enterprise + NIM | Supported runtime and model containers over TensorRT-LLM or vLLM; $4,500/GPU/yr list to $22,500 perpetual, per physical GPU regardless of size [[pricing-nvidia-enterprise-licensing-guide]] | Production use requires the licence; development capped at 16 GPUs |
| VMware Private AI Foundation 9.0/9.1; Private AI Services 2.1 (2026) | Virtualisation plus a gateway over vLLM, Infinity, llama.cpp; Cloud Foundation subscription **plus** add-on **plus** vGPU/AI Enterprise [[vmware-private-ai-foundation-with-nvidia-91]] | "At least 3 GPU-enabled ESX hosts"; "You cannot use the MIG sharing mode for NVIDIA GPUs with NVIDIA NIMs" [[requirements-for-deploying-vmware-private-ai-foundation-with-nvidia]] |
| Red Hat OpenShift AI / AI Inference 3.4-3.5 | Kubernetes and MLOps plane over KServe with vLLM, llm-d; OpenShift plus OpenShift AI subscription [[deploy-an-llm-inference-service-on-openshift-ai-red-hat-developer]] | Disconnected install NVIDIA CUDA only; llm-d needs OCP 4.20+ and three operators [[chapter-3-deploy-openshift-ai-in-a-disconnected-environment-deploy-or-decommissi]] |
| Nutanix Enterprise AI | Deployment UI and token management over NIM or Hugging Face models; Nutanix licence, no public price | Any CNCF-certified Kubernetes but NVIDIA GPUs only; text models only [[nutanix-enterprise-ai-faqs]] |

Two readings coexist. A commercial platform makes self-hosting supportable for a team that cannot absorb upstream churn — the money buys the NIM Production Branch's nine-month stable API and support only on NVIDIA-Certified Systems — yet nothing in the serving path requires it, the same reseller account noting that vLLM, TensorRT-LLM under Apache-2.0 and Triton under BSD-3 all run unlicensed [[nvidia-ai-enterprise-licence-pricing-subscription-eurokommerz]]. Magnitudes decide which applies: one analyst prices eight GPUs of AI Enterprise at $36,000 a year against roughly $3,400 for the same open model bought hosted at a billion tokens a month [[best-air-gapped-llm-stack-apache-weights-on-vllm-beat-nvidias-fee-the-daily-brie]]. Because the basis is per physical GPU, the licence scales with installed hardware rather than with tenants or utilization; and unless these platforms expose extension points, customers depend entirely on the vendor roadmap [[private-generative-ai-offerings-nutanix-vmware-and-microsoft-msandbuorg]]. No independent account of operating any of the four at disclosed scale appears in the reachable record, which is why every row above is vendor recommendation rather than deployment evidence.

## 7. Where the Adopt / Buy / Build Boundary Moves On-Premise

The boundary between what a team adopts, buys and writes does not move when deployment becomes on-premise. It acquires new jobs on the same side of it.

| Layer | Open-source choice | Vendor choice | Built in-house |
|---|---|---|---|
| Serving engine | vLLM; llama.cpp for extreme quantization | NIM containers; the VMware runtime | **Never** |
| GPU scheduling | Slurm, PBS, Flux; Kubernetes with the GPU Operator, Kueue | OpenShift AI, vGPU pools, Nutanix | Scheduler scripts, submit-and-expire loops |
| Request front door | LiteLLM, llama-swap, Ray Serve | Vendor gateways, KServe with llm-d | **Almost always** — FastAPI, Django-Ninja, Envoy |
| Identity | Globus Auth, Authentik, Keycloak | Platform RBAC | The integration and the policy |
| Quota and token accounting | Slurm accounting, LiteLLM keys | Platform endpoint tokens | **Almost always** — budgets, cost factors |
| Model lifecycle | llama-swap, idle-release timers | Model catalogue UI | Hot-node retention, spin-up queues |
| Air-gap weight distribution | Local registries, Harbor, NFS | `oc-mirror` v2, modelcar images | The signed-bundle refresh pipeline |
| Facility and capacity sizing | — | Reference architectures | All of it |

Five deployments answering different questions — federated scientific access, university self-service, Slurm-native web serving, enterprise multi-tenancy, exascale scaling — arrive at the same inventory, and the Austrian cluster's authors state it plainly: "Our serving layer reuses these components. The work specific to our platform is the policy layer around them: per-project token budgets, model access-control lists, and an OpenAI-compatible gateway" [[design-and-operation-of-a-federated-gpu-cluster]]. The counter-direction sharpens the reading: Sandia reports that it "had developed our own custom deployment files, however, we have since migrated to using the recently added Helm chart" provided by the upstream vLLM project [[experience-deploying-containerized-genai-services]]. Packaging converges upstream; policy does not. On-premise adds two jobs — batch-scheduler dispatch, the origin of Argonne's job endpoint and GWDG's routing table, and offline weight distribution, where ExaServe broadcasts weights from a head node over MPI to each node's tmpfs because shared Lustre added more than 600 seconds of start-up at 256 nodes [[exaserve-large-scale-llm-serving-on-exascale]].

### A. Four baselines, and the 200-fold spread between them

| Baseline | Reported break-even | When it is the right comparison |
|---|---|---|
| Hyperscaler hourly GPU rental | 5.2 months against on-demand; 8.5 / 13.4 / 14.8 against one-, three- and five-year reserved [[on-premise-vs-cloud-generative-ai-total-cost-of-ownership-2026-edition-lenovo-pr]] | You would genuinely have rented equivalent GPUs at list price, around the clock |
| The same open model as a hosted API | 162B / 324B / 522B tokens a year, i.e. 44% / 88% / 141% of round-the-clock capacity for a two-GPU server [[on-premise-llm-and-rag-for-the-enterprise-what-60k-really-buys-you-ask-this-guy]] | The default for internal serving: capability held constant, seller priced near marginal cost |
| A closed frontier API | ">=50M tokens/month" for large models; 0.3-69.3 months across 54 scenarios [[a-cost-benefit-analysis-of-on-premise-large]] | Measures a quality premium on-premise cannot capture, since closed weights cannot be installed |
| Displaced per-seat SaaS | ~3.5 months: EUR 48k against EUR 14k a month of subscriptions [[private-ai-platform-for-200-employee-engineering-firm]] | Small deployments genuinely retiring seat licences |

The gap between the second and third rows is the most informative quantity in the economics: one study puts break-even at 50 million tokens a month while the same-open-model arithmetic puts it at roughly 9-14 billion tokens a month per two-GPU server — the same question about 200x apart, the difference entirely attributable to the comparator [[a-cost-benefit-analysis-of-on-premise-large]], [[on-premise-llm-and-rag-for-the-enterprise-what-60k-really-buys-you-ask-this-guy]]. The first row carries conditions its headline omits: those break-even hours are continuous hours at list rental price with no staff line anywhere in the model, capital is amortised over a five-year lifecycle at 12% annual maintenance while the system is written down to "$0 recovery", and the accompanying per-token comparison runs against a nano-class proprietary API at roughly $1.25 per million output tokens rather than a commodity host of the same open weights [[on-premise-vs-cloud-generative-ai-total-cost-of-ownership-2026-edition-lenovo-pr]]. A methodology study isolates the sensitivity, finding effective cost on identical H100s spanning $0.21 to $15.25 per million output tokens purely as a function of offered load [[beyond-per-token-pricing]]. Three unrelated methods then converge on roughly 55-80% sustained utilization of peak throughput as the threshold, matching the independent 44-88% figure: a utilization divisor applied to the vendor's own cost-per-token; a vendor model of 100 owned H100s over three years concluding that ownership beats rental "only at high utilization (≥75%) and at scale (≥50 GPUs)" [[the-3-year-tco-of-owning-100-h100-gpus-a-full-capital-allocation-breakdown-merca]]; and a single-developer study reporting shared on-premise allocation saving 40.1% on total cost of ownership while dedicated reservation costs 43.8% more than a cached API [[inference-economics-of-enterprise-coding-agents]]. The optimistic headline needs conditions attached: the vendor's payback hours are continuous, so 5.2 months is a 100%-duty-cycle claim, the model carries no staff line, and it is internally inconsistent — "under four months" in its abstract against "as little as 6 months" in its summary [[on-premise-vs-cloud-generative-ai-total-cost-of-ownership-2026-edition-lenovo-pr]]. The academic study on the other side excludes staffing and maintenance by construction [[a-cost-benefit-analysis-of-on-premise-large]].

### B. The two terms nobody publishes

Staff and depreciation account for 77-83% of true on-premise cost in the median and high scenarios while electricity is only 4-14% [[on-premise-llm-and-rag-for-the-enterprise-what-60k-really-buys-you-ask-this-guy]] — and staff is the term no operator publishes. The reason is structural rather than a search failure: the most transparent GPU cost disclosures available are academic recharge rates, built to recover hardware while the institution absorbs people elsewhere. A University of California campus schedule recovers hardware "over a 5 year period at 60% use" and states that "these campus funds pay for the people, the baseline infrastructure, and vendor maintenance" [[4-resource-allocations-rcic-100-documentation]]. The fullest published basis, from Denmark's DeiC National HPC Centre at SDU, prices academic access on "the full cost of ownership" including server rooms, cooling, "the required electrical components to connect to the power grid (e.g. transformers)" and whole-facility electricity — while stating that "the costs for IT-service support are not included in the estimate. Currently, this cost is very low being 1.5 FTE" [[service-charges-sdu-escience]]. After searching those rate schedules, the operator papers and the vendor cost models, **no operator publishes a staff-inclusive total cost of ownership for a named on-premise LLM platform.** The nearest ratios are the Austrian cluster's roughly 1.5 full-time-equivalent staff and SS&C's team of 40 against 80 GPUs across a broader AI organisation [[design-and-operation-of-a-federated-gpu-cluster]], [[realtime-and-batch-processing-of-gpu-workloads-infoq]] — jointly implying a staffing range spanning more than an order of magnitude, an inference rather than a sourced figure. That absence limits the sceptical case as much as the vendor case, since the 77-83% claim cannot be checked against any operator's number.

Residual value is the other omitted term, and the disagreement is the finding. Listing-based series put three-year H100 residuals at 45-55% used and 70-75% refurbished [[the-illusion-of-stability-unpacking-h100-gpu-market-value-trends-silicon-data-gp]]; the only transaction-based series puts them at 27-39% of list in 2026 falling to 5-7% by 2028, warning that that advertised asks are not realised sales at a median dealer ask 1.16x realised [[h100-price-2026-what-a-used-h100-and-hgx-node-sell-for]]. The organisations with the most data moved in opposite directions, one hyperscaler shortening server useful lives in 2025 while another extended them the same quarter [[used-gpu-market-a100-h100-pricing-depreciation]].

### C. What moves the boundary through 2027

Four forces in the 2026 record pull in different directions. Falling inference prices threaten any payback computed against fixed API prices, but the decline is partly capturable: Epoch AI measures declines "ranging from 9x to 900x per year" depending on milestone while warning that "The fastest price drops in that range have occurred in the past year" [[llm-inference-prices-have-fallen-rapidly-but-unequally-across-tasks-epoch-ai]], and one decomposition attributes roughly 103.7% of the decline to total-factor productivity with "GPU hardware contributing only −0.9%" [[tiered-super-moores-law-price-evolution-production]] — so an owner adopting newer open weights on hardware already bought captures much of it, bearing hardware-generation risk instead. Second, the facility step hardens as rack-scale Blackwell-class systems arrive with fixed power envelopes and mandatory liquid cooling, turning the question from *how many chassis* into *does the building qualify*, decided in facilities budgets on multi-year lead times [[is-your-data-center-ready-for-the-nvidia-gb200-nvl72-sunbird-dcim]], [[ai-inference-colocation-power-cooling-and-network-requirements-for-gpu-ready-dat]]. Third, a committed-use API discount of roughly 45% would by itself erase the shared-allocation advantage, a lever the API providers control and the owner does not [[inference-economics-of-enterprise-coding-agents]]. Pulling the other way, agentic traffic raises tokens per task sharply — Argonne's users report that because "tool calls can be frequent and might involve large inputs and outputs, token consumption can be much higher than conversation style usage" [[alcf-launches-first-large-scale-ai-inference-service-for-open-science-argonne-le]]. If that holds, the utilization threshold that fails for office-hours chat becomes easier to clear, and the build surface shifts from request-level gateways toward session, budget and tool-permission management. Together these point toward on-premise consolidating around shared multi-tenant platforms, constraint-driven enclaves and batch-heavy pipelines, and away from dedicated single-workload clusters.

## 8. What Carries Over From General Self-Hosting Unchanged

The general picture of self-hosted internal inference organised its open-source/custom boundary around capability-gap recency, inherited infrastructure, policy ownership and supply-side incentives, concluding that only the first closes with software maturity. On-premise deployment leaves that intact, strengthens two legs and qualifies one.

| Finding in the general picture | Status on-premise |
|---|---|
| Inference engine: covered, settled | **Unchanged**, one exception — llama.cpp where sub-2-bit quantization is the enabling trick [[ecient-deployment-of-a-685b-parameter-open]] |
| Control plane covered by Kubernetes-native projects | **Conditional** — only where a Kubernetes substrate exists; research sites use scheduler scripts and llama-swap [[research-paper]] |
| Policy ownership is non-transferable | **Reinforced** — five independent accounts built the same four components |
| Inherited infrastructure predicts custom code | **Stronger** — the inherited asset is a scheduler and a user base, not a gateway [[research-paper]] |
| Gateway mechanics covered without integration debt | **Qualified by a measured ceiling** — a centralized streaming proxy saturates while model servers stay inside their objective [[exaserve-large-scale-llm-serving-on-exascale]] |
| Migrations away from custom code are deliberate | **Unchanged**, with a new instance at the packaging layer [[experience-deploying-containerized-genai-services]] |
| Evals in-house; guardrails by composition; tracing as-is | **Unchanged** — unaffected by where the hardware sits |
| Chargeback enforcement gated commercially | **More acute** — token budgets and cost factors hand-built at every site [[design-and-operation-of-a-federated-gpu-cluster]] |
| Disclosure flatters the publisher | **Confirmed** — two apparent counter-examples failed verification [[fortune-100-healthcare-ships-llm-use-cases-truefoundry]] |

One row is stale rather than qualified: its only on-premise classified entry ran Text Generation Inference, archived in March 2026 [[on-premise-llm-and-rag-for-the-enterprise-what-60k-really-buys-you-ask-this-guy]]. Five areas have no counterpart in the general picture and are where this report's content sits: the hardware and facility layer; batch-scheduler operation, with its ten-minute cold starts and hot-node retention; disconnected operation; per-physical-GPU licence economics; and the cost-structure inversion in which staff and depreciation dominate while electricity does not. Two on-premise-only decision tests join the general picture's four: whether a constraint removes the comparison baseline entirely, and whether the deployment sits below the facility step or above it.
