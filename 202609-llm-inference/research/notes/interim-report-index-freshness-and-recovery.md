# Interim report: index-freshness-and-recovery

**Locus question:** Does llm-d's event-driven KV-block index reliably reflect true per-pod cache state, or does it go stale on restarts, pod loss, and offloaded-tier eviction — and how much of that gap is actually closed as of this report's date (September 2026)?
**Flavor:** dialectical

## What the corpus already said

The width sweep already captured the design-side promise and the failure-side documentation for this locus, laid out as a contradiction-graph cluster (`index-freshness-and-recovery`, `decision_relevance: high`). Side A sources ([[kv-cache-indexer-llm-d]], [[precise-prefix-cache-routing-llm-d]], [[kvevents-package-githubcomllm-dllm-d-routerpkgkvevents-go-packages]]) describe a near-real-time, event-driven index with active-active multi-replica convergence, 2-second default speculative-TTL entries to bridge the routing-to-confirmation gap, and reference-count dedup to prevent premature eviction when multiple sources reference a block. Side B sources ([[recover-kvblockindex-from-a-disruptive-event-issue-372-llm-dllm-d-kv-cache]], [[fix-index-blocks-with-unknown-parent-using-empty-parent-hash-by-rishabhsaini-pul]], [[dynamic-speculative-ttl-for-unified-prefix-cache-scoring-issue-544-llm-dllm-d-kv]], [[kvblock-inmemoryindexlookup-tests-emptiness-and-reads-entries-without-the-pod-ca]], [[source-analysis-rfc-multi-tier-kv-offloading-vllm-issue-38260]]) document concrete failure paths: index-clearing restarts dropping blocks, an interim fix that was closed unmerged, pod-crash/scale-down invalidation that remains a proposal, a read-path concurrency bug, and an unresolved tiered-eviction-ownership contract on the vLLM side. My job was to verify current code state and pin the timeline precisely.

## What the new sources say

I fetched vLLM PR #45177, "fix: include topic frame in KV events replay response" ([[fix-include-topic-frame-in-kv-events-replay-response-by-rishabhsaini-pull-reques]]), the hard dependency the corpus's issue #372 discussion named as blocking llm-d's real recovery fix. I confirmed directly from the PR's merge event that **tlrmchlsmth merged commit 2f3f441 into vllm-project:main on Jul 7, 2026**, after 84 CI checks passed, closing the loop the corpus notes had only described as "requires #45177 to merge first." The PR's own description states the bug precisely: vLLM's replay buffer stored `(seq, payload)` while the live PUB path sends `[topic, seq, payload]`, so a subscriber requesting replay via the ROUTER socket got responses missing the topic frame — which carries the pod identifier and model name (`kv@<podIP>@<modelName>`) that "external consumers like llm-d's GAIE indexer" need to attribute replayed events to the correct pod. Without this fix, even a working replay-consumer on the llm-d side would have received unattributable events. Two downstream llm-d PRs cite #45177 as their dependency and are themselves merged: `llm-d/llm-d-router#1887` and `llm-d/llm-d#2196`. This is a directly load-bearing confirmation: the corpus's claim that PR #1887 "depends on vllm-project/vllm#45177 (merged)" is verified true, and dates the dependency's resolution to five weeks before llm-d's own fix landed (Jul 7 → Aug 6, 2026).

I also re-fetched issue #544 directly to get its current state rather than relying on the corpus snapshot. Confirmed: **still open, unimplemented, and now marked stale by the repo's stale-bot as of Sep 4, 2026** (90 days of inactivity; will auto-close after 30 more days of continued inactivity, absent a new comment). The issue's only substantive activity since the design was posted is a Jun 6, 2026 question from maintainer ahg-g asking whether the health-monitor/dynamic-TTL work is a "must have" for the next release — **that question was never answered**. "PR 2" (the sub-task that would call `Index.Clear()` on detected pod disappearance, covering crash/scale-down cases where no `AllBlocksCleared` event arrives) remains a design-plan line item with no linked implementation, dependent on a separate, also-unshipped generation-counter mechanism (#437). This is a directly-verified, same-day re-check, not an inference from a stale summary — the gap is real and, per the stale-bot's own clock, drifting toward auto-closure without resolution rather than toward being fixed.

I also re-examined the full text of [[kvevents-package-githubcomllm-dllm-d-routerpkgkvevents-go-packages]] (the v0.10.0 godoc) specifically for what `SubscriberManager.RemoveSubscriber` does on pod departure. The documented behavior is narrow: "RemoveSubscriber removes a subscriber for the given pod identifier" — i.e., it tears down the ZMQ subscription. Nothing in the godoc's exported surface (nor in `EnsureSubscriber`'s no-op/replace semantics for endpoint changes) indicates that removing a subscriber also purges that pod's existing entries from `kvblock.Index`. This directly corroborates issue #544's framing: index cleanup on pod disappearance is not a byproduct of subscription teardown — it is a distinct, currently-unshipped mechanism.

I additionally read [[router-design-nvidia-dynamo-documentation]] as an architectural comparator: Dynamo's KV Router uses "per-worker monotonic event IDs and gap detection triggering full-state resync" — i.e., the same class of mechanism llm-d's PR #1887 just shipped (dual sequence watermarks, gap detection via `seq > lastSeq+1` triggering replay). This tells me llm-d's Aug 2026 fix brings it to rough architectural parity with an already-shipped competitor pattern, not to a novel or unusually robust design — the fix is table stakes that llm-d lacked for five months, not an innovation.

## Evidence synthesis

The precise timeline, reconstructed from primary GitHub sources across two repos:

- **Mar 1, 2026** — issue #372 opened: after a GAIE/EPP restart clears the in-memory index, `BlockStored` events whose parent isn't in the freshly-cleared index get dropped at `pkg/kvevents/pool.go:297`, cascading to drop all descendant blocks. The router is fully blind to pre-restart cache-resident blocks until affected prefixes age out and get regenerated by new traffic.
- **Jun 12–Jul 3, 2026** — PR #663 (interim fix: index blocks with unknown parent using `EmptyBlockHash` instead of dropping them) was fully implemented, reviewed, and had a passing regression-test suite, but was **closed without merging** on Jul 3. A Copilot reviewer had flagged, on Jun 16, that the fix treated *all* `GetRequestKey` errors as "parent not found," which could mask genuine storage/serialization/corruption errors — a real correctness concern, not just review nitpicking. The author's own commit message for the superseding work states "Remove pool.go EmptyBlockHash fallback (separate PR #663)."
- **Jun 30–Jul 14, 2026** — PR #691 (first attempt at the real fix: consume vLLM's replay buffer on subscriber reconnect) was closed in favor of landing the equivalent work directly in the post-migration `llm-d-router` repo.
- **Jul 7, 2026** — vLLM PR #45177 merged, fixing the replay-response topic-frame bug that made replay data unusable to external consumers. (Directly verified this session.)
- **Aug 6, 2026** — PR #1887 merged into `llm-d-router`: the real fix. On subscriber connect, the ZMQ DEALER proactively replays buffered events to rebuild the index immediately; it detects sequence gaps and requests targeted replay; it tracks **dual watermarks** (`lastSeq` = indexed, `lastLiveSeq` = arrived-on-wire) specifically to stop replay overlap from inflating dedup reference counts; it detects sequence **reset** (pod restarted, kept the same IP, so `EnsureSubscriber` no-ops) and clears index/dedup state for that source. Pre-merge review on Jul 30 caught two real correctness bugs in earlier revisions of this same PR (double-storing already-buffered events during gap replay, and a cooldown-timer bug that re-sent an entire frozen event window on retry) — evidence that even the "final" fix needed iteration to get right, not a clean first-pass implementation.
- **Total time from bug report to shipped, dependency-satisfied fix: 158 days** (Mar 1 → Aug 6, 2026), spanning two closed PRs, one cross-repo migration, and one upstream vLLM dependency.

Separately — and this is the crux of where I diverge from a simple "it's fixed now" reading — **pod loss is not the same failure mode as router restart, and it is not covered by any of the above.** PR #1887's sequence-reset detection only fires when a pod *restarts and keeps the same IP* (so the existing subscriber's `EnsureSubscriber` call is a no-op and the reset is observable on the same ZMQ connection). A pod that is killed and never replaced (scale-down) or replaced with a new pod at a new IP produces no such signal on the router's existing subscription — `RemoveSubscriber` (confirmed from the godoc, verbatim above) only tears down that pod's ZMQ subscription; it does not document clearing the pod's existing index entries. Issue #544's "PR 2" — a KV-Events Health Monitor that would call `Index.Clear()` when it detects a pod has disappeared — is the mechanism that would close this gap, and I re-fetched the issue directly this session to confirm it remains **open, unimplemented, and stale-bot-flagged as of Sep 4, 2026**, with a maintainer's Jun 6, 2026 prioritization question ("is this a must-have?") never answered. Issue #544 was opened Apr 27, 2026; as of this report (Sep 14, 2026) it has been open 140 days with no shipped fix and is now on a 30-day clock toward auto-closure for inactivity rather than toward resolution.

The practical severity of stale pod-loss entries is bounded but real: because llm-d's block keys are content-addressed hashes rather than pod identities, a stale entry pointing at a departed pod would cause the scorer to award prefix-affinity credit to a pod that either (a) no longer exists (routing there fails or gets rerouted — a latency/availability cost, not silent corruption) or, more insidiously, (b) has been replaced by a differently-IP'd new pod that doesn't actually hold those blocks (a false cache "hit" that becomes a cache miss at generation time inside vLLM, i.e., silent recompute — an efficiency loss disguised as a correct routing decision, not a crash). Neither is catastrophic, but both directly undercut the "near-real-time, reliably reflects true per-pod cache state" framing for this specific and still-open failure class.

A second, structurally distinct gap sits on the vLLM producer side rather than the llm-d consumer side: [[source-analysis-rfc-multi-tier-kv-offloading-vllm-issue-38260]] documents a vLLM maintainer (Change72) stating plainly, in the RFC #38260 thread on multi-tier KV offloading (Jun 23, 2026): "whoever owns eviction should also provide invalidation. Otherwise, routers may score or route based on stale placement state." As of that thread's most recent activity (Jul 14, 2026, PR #48281 formalizing a medium/locality split), this invalidation-ownership question for secondary/offloaded tiers was still being actively worked out, not resolved — meaning that for CPU/disk/remote-storage tiers specifically (as opposed to the GPU-resident, `AllBlocksCleared`-covered case this locus's restart-recovery fixes address), the freshness guarantee is weaker still and depends on a metadata contract (`medium`/`locality`) that only stabilized in mid-July 2026.

A third item, [[kvblock-inmemoryindexlookup-tests-emptiness-and-reads-entries-without-the-pod-ca]] (issue #2698) and its fix [[perfkvcache-match-prefixes-over-an-ordered-index-walk-by-nilig-pull-request-2680]], is real but should not be weighted heavily against index-freshness: it is a check-then-act race in the *read* path (`InMemoryIndex.Lookup`), not the write/event path, its own issue text states it "does NOT corrupt routing today" because the downstream matcher walks keys in order and stops at the first empty-entries key, and it was fixed within 5 days (opened Sep 4, merged Sep 9, 2026) as part of a larger, well-benchmarked performance rewrite (190x latency / 7,600x memory reduction on the cited AMD EPYC 9655P benchmark, n=6). This is evidence of a healthy, fast-moving engineering process on the read side, not an open freshness hazard.

### Position A: the index is near-real-time and self-healing

The strongest version of this case: every restart/cold-start failure mode documented in the corpus's own issue #372 has a shipped, merged fix as of Aug 6, 2026 (PR #1887), verified in this session to have its upstream vLLM dependency (PR #45177) also merged (Jul 7, 2026). The fix is architecturally sound — dual watermarks specifically engineered to prevent dedup-count corruption from replay overlap, sequence-reset detection for same-IP pod restarts, proactive replay on connect so the index doesn't wait for live traffic to refill. Active-active multi-replica convergence (every router replica subscribes to every pod independently) means no single router replica's restart is a single point of staleness for the fleet. Speculative TTL entries (2s default) mean the router isn't even blind during the sub-second window between a routing decision and the confirming KV event. For the specific, common operational scenario this locus's own corpus evidence centers on — an EPP/router pod restarting — the system is now measurably self-healing and the "index-freshness" concern the width sweep flagged has a dated, verified resolution.

### Position B: the index still goes stale in gaps that current fixes don't cover

The strongest version of this case does not dispute that #372 got fixed — it disputes that #372 was the whole problem. Three residual gaps survive PR #1887 unaddressed: (1) pod loss without a graceful signal (crash, scale-down, non-same-IP replacement) has no automatic index cleanup — `RemoveSubscriber`'s documented behavior is subscription teardown only, and the purpose-built fix for this (#544's health-monitor-driven `Index.Clear()`) is, confirmed by direct re-fetch this session, a 140-day-old open proposal with zero linked merged PRs and now sliding toward stale-bot auto-closure rather than toward implementation; (2) offloaded/tiered cache invalidation ownership is, by a vLLM maintainer's own admission in the corpus's RFC digest, an unresolved "routing-correctness requirement" as of Jul 2026, meaning any router (including llm-d) consuming tier-placement events is scoring against a metadata contract that only partially stabilized weeks before this report; (3) even the fix that did ship took 158 days end-to-end and included one closed-unmerged interim attempt (PR #663) that a reviewer flagged as capable of masking genuine errors — the "index self-heals via natural regeneration" fallback that shipped in that period was a lesser guarantee than the documentation implies, dressed up as acceptable because tail-first eviction ages stale entries out eventually.

## Committed position

The evidence supports a synthesis that is not symmetric: for the single failure mode the corpus's own issue history centers on — router/EPP process restart — Side A's claim is now true and dated with primary-source precision (PR #1887 merged Aug 6, 2026, dependency PR #45177 merged Jul 7, 2026, both verified directly in this session). But the locus question asks about reliability "on restarts, pod loss, and offloaded-tier eviction" as a set, and for two of those three, Side B has the better evidence: pod loss without a graceful shutdown signal has no shipped invalidation mechanism (issue #544's `Index.Clear()`-on-disappearance proposal is unimplemented, 140 days open, stale-bot-flagged as of Sep 4 2026 and drifting toward auto-closure, with a maintainer's priority question never answered), and offloaded-tier invalidation ownership was, per a vLLM maintainer's own words in the RFC thread this corpus already captured, still an unresolved correctness question as recently as five weeks before router-restart recovery shipped. The read-path race (#2698) is real but immaterial to freshness — it's a telemetry bug, fixed fast, and the issue's own text says so. The honest summary is: llm-d closed its highest-profile, most-discussed freshness bug in August 2026 after a five-month, two-repo, cross-dependency fix cycle, but the design promise of "reliably reflects true per-pod cache state" still overstates what's shipped, because the pod-loss and tier-eviction gaps are structurally different problems that the restart fix does not touch and that remain, respectively, a stalling unimplemented proposal and an open upstream contract question.

- **Position:** llm-d's KV-block index freshness guarantee should be read as scoped, not blanket: reliable and now well-engineered for router/EPP-process restart (verified fixed Aug 6, 2026, five months after the bug was reported), but still structurally exposed on ungraceful pod loss (no automatic `Index.Clear()` on pod disappearance — #544 unimplemented and stalling toward auto-closure) and on offloaded/tiered-cache invalidation (ownership contract unresolved as of Jul 2026 per vLLM maintainer statement) as of this report's date.
- **Confidence:** high on the restart-fix timeline and merge chain (directly verified from primary GitHub sources: issue text, PR merge events, two freshly re-fetched PRs/issues confirming both the upstream dependency and #544's current stale state). Medium-high on the pod-loss severity characterization — the absence of a clearing mechanism is confirmed from the official godoc's documented scope, but I did not read the pod-discovery reconciler's actual implementation, only its exported interface, so an undocumented internal side effect could narrow (not eliminate) the gap.
- **Boundary conditions:** this position holds for llm-d as of Sept 14, 2026, on the `llm-d-router` v0.10.0 line described in the corpus. It does not generalize past this date — both #544 and the vLLM tier-invalidation contract are live, moving targets; #544 could either ship or auto-close within roughly 30 days of this report per the stale-bot's own clock. It also assumes Kubernetes pod-IP semantics (new pod = new IP, not reused) hold in the deployment; if a cluster's CNI reuses IPs for replacement pods, PR #1887's sequence-reset detection would incidentally catch some pod-loss cases it wasn't designed for, narrowing the practical severity of the gap I'm flagging.
- **What would change this position:** a merged PR closing #544's `Index.Clear()`-on-pod-disappearance mechanism, or a direct code read of the pod-discovery reconciler (not just the kvevents godoc) showing that pod removal from Kubernetes already triggers index cleanup through a path this corpus didn't surface (e.g., a `PodDiscoveryConfig` reconciler behavior distinct from `RemoveSubscriber`) would substantially weaken the pod-loss half of my position. Similarly, a merged vLLM PR establishing a concrete invalidation-ownership contract for offloaded tiers (beyond the medium/locality metadata split) would close the tier-eviction half.
- **Evidence weight:** 5 primary GitHub sources (2 issues re-fetched fresh this session, 2 merged PRs read directly, 1 closed-unmerged PR) plus 1 godoc plus 1 RFC-thread digest support the "restart fixed, pod-loss and tier-eviction still open" reading; 0 sources in the corpus or newly fetched contradict it — the tension is real but it is a scope/timeline distinction, not a factual disagreement between sources arguing opposite claims about the same failure mode.

## Open questions

- Does the `PodDiscoveryConfig` Kubernetes reconciler (mentioned in the kvevents package config, `PodLabelSelector`/`PodNamespace`) trigger any index cleanup when a pod disappears from the Kubernetes API, independent of the ZMQ-level `RemoveSubscriber`? The godoc I read documents the config surface but not the reconciler's internal behavior — a direct source read of `pkg/kvevents/pod_reconciler.go` (or equivalent) would settle this more precisely than inference from `RemoveSubscriber`'s documented scope.
- What specifically happens to a stale index entry once its pod is gone and a request scores it as a hit — does the EPP/scheduler have a fallback path (retry against next-best pod) that makes this cheap, or does a bad routing decision to a dead pod cost a full request timeout? This determines whether the pod-loss gap I'm flagging is a minor tail-latency tax or a user-facing failure mode, and the corpus doesn't address it directly.
- Issue #544 is now on a stale-bot clock (auto-closes ~30 days after the Sep 4, 2026 stale mark absent activity). Worth a late-pipeline re-check before final publication if the run extends past early October 2026, since auto-closure without a linked fix would harden (not resolve) the gap this report describes.
