This PR implements FileDiscovery, described in the PR body as "the first EndpointDiscovery backend for non-Kubernetes deployments."

BEHAVIOR: FileDiscovery reads a YAML or JSON file listing inference endpoints and drives their lifecycle in the datastore via DiscoveryNotifier. On startup it loads endpoints from the file and emits one Upsert per entry so the datastore is populated before the EPP begins serving traffic. It can optionally watch the file with fsnotify and reconcile additions/removals on every write -- "allowing zero-downtime endpoint updates without restarting the EPP." On reload it diffs the previous snapshot against new file contents and removes stale endpoints. Configured via EndpointPickerConfig.dataLayer.discovery.pluginRef pointing to a plugin instance of type "file-discovery" with "path" and "watchFile" params. NOTE (important caveat): as of this PR the plugin is "fully implemented and tested in isolation but is not yet usable end-to-end" -- the runner wiring, config detection, and runWithFileDiscovery execution path shipped separately in the follow-on PR #1218 (4/4); until #1218 merged, setting dataLayer.discovery.pluginRef in the config had no effect.

CONFIG SCHEMA (evolved during review): the per-endpoint YAML/JSON schema is EndpointEntry{ Name string; Namespace string (optional); Address string; Port string }. A "MetricsHost" field was added, then briefly renamed to "MetricsPort" to let operators point metrics scraping at a different port than inference traffic (motivated by "vLLM running inference on :8000 but /metrics on :9090"), then a reviewer pointed out the EPP "can not scrape and serve on different IPs, only same IP and different port is feasible (and deprecated)" -- the author ultimately DROPPED the metrics-port override entirely, so the final shipped behavior always scrapes Prometheus metrics from the same address:port the endpoint serves inference on, with no way to configure a separate metrics port via the file-discovery plugin as merged.

NOTABLE LIMITATION: a commit titled "file-discovery: validate IPv4 only and reject IPv6 addresses" shows the plugin explicitly rejects IPv6 endpoint addresses -- IPv6 backends cannot be registered via file-discovery as of this PR.

K8S RESIDUE: despite being the non-Kubernetes discovery backend, the internal endpoint-identity tracking still uses Kubernetes' types.NamespacedName as the map key type (`endpoints map[types.NamespacedName]struct{}`, renamed from `current` during review) -- confirming the k8s-shaped identifier gap flagged as unresolved in PR #908 persisted into this implementation. The plugin also depends on "sigs.k8s.io/yaml" for YAML parsing (chosen because it "converts all to json" so json struct tags alone suffice) -- a Kubernetes-ecosystem library, though used here purely as a YAML-to-JSON codec with no live cluster dependency.

RESILIENCE FIXES made during review (both by reviewer nilig/vMaroon, addressed by author): (1) a "partial-Upsert atomicity bug that can leave zombie endpoints in the datastore" during file load; (2) "missing watcher re-add that breaks watchFile mode after atomic renames" -- fixed via a commit "re-attach fsnotify watcher after atomic rename and ConfigMap rotation." That commit message explicitly names ConfigMap rotation as a scenario the plugin must tolerate, implying the file-discovery plugin is also designed to work when the backing file is mounted into a Kubernetes pod from a ConfigMap (which Kubernetes updates via atomic symlink swap) -- i.e. file-discovery is usable BOTH fully outside Kubernetes (e.g. a flat file on a Slurm node) AND inside a Kubernetes pod as an alternative to the native K8s/InferencePool discovery plugin.
