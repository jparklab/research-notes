Architecture: KVCache-centric disaggregation that goes beyond simple prefill/decode splitting (as in DistServe/Splitwise/TetriInfer, all cited as prior art) by also disaggregating the KV cache itself into a separate pool spanning CPU/DRAM/SSD across the GPU cluster's otherwise-underutilized resources, connected via GPUDirect RDMA through a component called Messenger. A global scheduler, Conductor, selects prefill/decode instance pairs per request to jointly optimize cache reuse, instance load, and TTFT/TBT SLOs; KVCache blocks are identified by chained prefix hashes (block size 512 tokens) enabling exact prefix-cache matching, with a heuristic hot-spot migration scheme that replicates frequently-hit blocks without needing precise future-usage prediction. For long-context prefill, Mooncake introduces chunked pipeline parallelism (CPP) — explicitly novel ('to our knowledge, this is the first application [of pipelined parallelism] in the inference stage') — instead of cross-node tensor or sequence parallelism, because CPP needs cross-node communication only at pipeline-stage boundaries, overlapping with compute; combined with layer-wise asynchronous KVCache load/store that overlaps transfer with attention computation layer-by-layer. Explicitly chose NOT to adopt chunked-prefill-into-decoding-batch (SARATHI, cited) as its primary technique, because prefill nodes need different cross-node parallelism than decode nodes and because keeping prefill out of VRAM-constrained decode batches frees VRAM. Under severe overload (a documented real condition for Kimi, not a hypothetical), Mooncake implements a prediction-based Early-Rejection policy: naive early rejection (reject before prefill if no decode slot will be free) causes load oscillation, which the predictive version mitigates. PRODUCTION DATA: releases an open-sourced 1-hour real request trace (23,608 entries) with timestamp/input_length/output_length/block-hash fields (text scrubbed for privacy) — paper states average input length 8,590 tokens, average output length 182 tokens, input:output ratio ~720 (reflecting Kimi's long-context use case). Cache-hit analysis on this trace: LRU/LFU/length-aware caching all plateau around a 55% hit ratio as capacity grows past 50,000 blocks (34% hit ratio at 1,000-block capacity), and the paper separately states real reusability on Kimi's live traffic is markedly lower than open-source benchmarks suggest, reaching up to 90% only for specific high-repetition products like its chat-to-paper service (papers.cool). Cache-block popularity is extremely skewed: over 50% of blocks are never reused while a minority are hit tens of thousands of times. Benchmark numbers: against vLLM on simulated long-context workloads (16k-128k prompts), Mooncake shows 50%-525% higher throughput under identical TTFT/TBT SLOs; under a real-workload replay (10P+10D Mooncake vs 20-instance vLLM), both systems hit ~100% TTFT-SLO compliance but only 57% of vLLM requests met the TBT SLO versus ~100% for Mooncake, letting Mooncake handle 75% more real requests at the same SLO. In an 8P+8D cluster overload test replaying 23,000 real requests at 2x speed, the naive-reject baseline rejected 4,183 requests versus 3,771 (early rejection) and 3,589 (prediction-based early rejection).
