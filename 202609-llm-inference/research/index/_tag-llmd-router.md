- [[configuration-llm-d]] — Configuration | llm-d — llm-d dev docs, the canonical EndpointPickerConfig schema/mental-model reference (fetched Sep 2026) -- the single richest source on plugin taxonomy and wiring rules. Top-level schema: apiVersion (llm-d.ai/v1alpha1, constant), kind: EndpointPickerConfig, plugins, featureGates, requestHandler, flowControl, schedulingProfiles, dataLayer. Config is explicitly NOT a reconciled CRD -- read once at startup, no hot reload. Models the config as a graph: Plugins are 'Nodes' (instantiated by type+parameters), structural sections like schedulingProfiles/flowControl are 'Edges' (wiring by pluginRef name), and flat fields (maxBytes, defaultRequestTTL) are static runtime config. Validation enforces valid pluginRef references, unique names, and that metrics extractors form a DAG (no circular data dependencies). KEY MECHANISM for the plugin-registration question: 'Auto-Wiring' -- if a plugin declared in the top-level plugins list implements a specific Go interface (Admitter, DataProducer, or advanced hooks PreRequest, ResponseHeaderProcessor, ResponseBodyProcessor), the system automatically discovers and binds it to its lifecycle role WITHOUT an explicit wiring edge in schedulingProfiles/flowControl/etc -- i.e. plugin role dispatch is interface-based reflection over Go types registered at compile time, not purely declarative. Documents Admitters (early accept/reject before queueing) and Data Producers (per-request context gathering, e.g. predicted-latency-producer feeding latency-slo-admitter) as this auto-wired category. Documents Parsers (requestHandler.parsers, default openai-parser/anthropic-parser/vllmhttp-parser dispatched by request path, e.g. /v1/chat/completions) and notes the older single 'parser' field is deprecated in favor of the list (llm-d-router#1308). Scheduling Profile execution order is fixed: Filters -> Scorers -> Picker; a profile can have at most one Picker (runtime error otherwise); when schedulingProfiles is omitted, an auto-generated 'default' profile references ALL Filter/Scorer/Picker plugins, which errors if multiple Pickers exist top-level. Profile Handler plugin is required only when multiple SchedulingProfiles exist (e.g. disaggregated prefill); a single profile implicitly uses SingleProfileHandler. dataLayer.sources[].pluginRef must implement the DataSource interface and dataLayer.sources[].extractors[].pluginRef must implement the Extractor interface -- default metrics-data-source+core-metrics-extractor injection is ADDITIVE (appended to user-supplied sources) unless injectDefaults:false or a metrics-data-source is already present. - [[data-layer-llm-d]] — Data Layer | llm-d — llm-d dev docs, canonical Data Layer design page -- the single most direct answer to 'where do pod/Kubernetes assumptions live and what are the plugin interfaces.' Defines the Data Layer as a Source -> Extract -> Attribute pipeline enriching thread-safe/type-safe Endpoint objects. Names THREE extension-point interface pairs: (1) PollingDataSource + Extractor -- periodic pull, e.g. metrics-data-source (polls a Prometheus-compatible /metrics endpoint of a model server) + core-metrics-extractor (multi-engine-aware, maps engine-specific metric names to standard internal keys like KVCacheUsagePercent/WaitingQueueSize); a Collector goroutine is started per endpoint by the runtime. (2) NotificationSource + NotificationExtractor -- reacts to Kubernetes resource changes; concrete k8s-notification-source watches a single configurable Kubernetes GVK (CRD or core API) and is bound to the controller-runtime manager, dispatching NotificationEvents on create/update/delete (docs note: 'There are currently no upstream extractors that require this source' as of this snapshot). (3) EndpointSource + EndpointExtractor -- reacts to EPP-internal endpoint lifecycle events (add/update/delete) via endpoint-notification-source, independent of Kubernetes, for cache init/cleanup. CRITICAL FINDING for non-k8s backends: only the NotificationSource/k8s-notification-source pairing is intrinsically Kubernetes-coupled (it binds to controller-runtime and watches a GVK); the PollingDataSource and EndpointSource interfaces are backend-agnostic by design -- metrics-data-source polls whatever URL/address an Endpoint object carries, and endpoint-notification-source only reacts to endpoints already in the EPP's own datastore regardless of how they got there. This means the actual Kubernetes-pod dependency is concentrated in whichever DataSource populates the endpoint datastore in the first place (the pod/endpoint discovery mechanism itself), not in the metrics-polling or endpoint-lifecycle machinery. `evergreen`
