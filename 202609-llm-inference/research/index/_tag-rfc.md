- [[rfc-cache-salting-for-secure-and-flexible-prefix-caching-in-vllm-issue-16016-vll]] — [RFC]: Cache Salting for Secure and Flexible Prefix Caching in vLLM · Issue #16016 · vllm-project/vllm — vLLM GitHub RFC #16016 (opened Apr 3, 2025 by dr75, closed May 6, 2025) proposing cache salting to defend vLLM's prefix cache against the timing side-channel attack described in 'Leaking Secrets from Prefix Caches' (arXiv:2411.18191): an attacker can guess candidate token blocks and infer cache hits (hence prior use by another tenant) from response latency, potentially reconstructing private prompts block by block. Proposes two designs: (A) single-barrier -- one cache_salt string per request, injected into the hash of the first block, restricting reuse to requests sharing that salt; (B) multi-barrier -- a cache_salt_map keyed by message index, allowing hierarchical isolation (e.g., an org-level salt on a shared document plus a user-level salt on the follow-up question, so the document's KV is shared org-wide while the question stays private even from other org members). Salts are base64-encoded 256-bit strings, not passed to the model, used only for block hashing. Maintainer comaniac initially suggested piggybacking on auth tokens (à la OpenAI's org-scoped cache sharing) instead; author dr75 countered that vLLM has only one global API key and that org-scoped-only sharing (OpenAI's model) is less flexible than salt hierarchies (e.g., nested tenant-of-tenants isolation). RFC concludes design (B) is the long-term target but recommends shipping (A) first for simplicity; (A) shipped in PR #17045. This directly explains the cache_salt / extra_hashes mechanism documented in vLLM's Automatic Prefix Caching design doc. A 2026 follow-up comment (user vpfkfl753, PR #52655) reports implementing multi-barrier as token-range salt regions and claims a synthetic timing-side-channel probe showed unsalted cross-tenant cache reuse is fully distinguishable via response usage/timing (reported timing AUC 1.0) while salted isolation reduces distinguishability to near-chance (AUC 0.462-0.551) with a measured throughput cost from lost cross-tenant cache reuse; this is a single commenter's self-reported, non-peer-reviewed benchmark and should be treated as an unverified claim, not confirmed vLLM behavior. `evergreen`
- [[rfc-kv-cache-layout-combining-all-layers-per-block-issue-27742-vllm-projectvllm]] — [RFC]: KV cache layout combining all layers per block · Issue #27742 · vllm-project/vllm — vLLM RFC #27742 (opened Oct 29, 2025 by orozery, closed 'not planned'/stale May 2026 after the uniform-model case shipped) is the original design rationale for the KV cache memory-layout change repeatedly cited elsewhere as the source of order-of-magnitude KV-transfer throughput gains. Motivation: for simple (non-Hybrid-Memory-Allocator) models, vLLM's default KV cache layout breaks each logical block's data into num_layers non-contiguous per-layer segments (further fragmented by k/v and kv_heads dimensions), which is costly for two transfer-heavy consumers -- NixlConnector (P/D disaggregation, GPU-to-host-buffer/other-agent) and OffloadingConnector (GPU-to-CPU). Proposes allocating one contiguous tensor holding all layers' KV data per block instead of one tensor per layer, reducing fragments to copy by a factor of num_layers. Author reports an initial measured 4x transfer-time improvement for both NixlConnector and OffloadingConnector on Llama-3.1-8B-Instruct, with no noticeable degradation in plain model-execution performance. New layout is opt-in, selected only when (1) the model has a simple uniform (non-HMA) layout and (2) the configured KV connector class explicitly requests it via a new classmethod. Discussion thread with maintainers (ApostaC, heheda12345, ronen tlrmchlsmth) covers extending the approach to Hybrid Memory Allocator models with heterogeneous per-layer page sizes (e.g., DeepSeek V3.2's two KV cache types with different hidden sizes), concluding the uniform-page-size case (is_kv_cache_page_size_uniform) is tractable but arbitrary heterogeneous page sizes per layer (UniformTypeKVCacheSpecs) are not solved by this scheme. The uniform-model implementation shipped in PR #27743 (linked from this RFC), which is the change the Jan 2026 vLLM offloading-connector blog post credits with the observed 0.11.0->0.12.0 throughput jump. `evergreen`
- [[rfc-multi-tier-kv-offloading-via-the-vllm-offloading-connector-issue-38260-vllm]] — [RFC]: Multi-tier KV offloading via the vLLM offloading connector · Issue #38260 · vllm-project/vllm — vLLM GitHub RFC #38260 (opened Mar 26, 2026, by dannyharnik) proposing the multi-tier KV offloading architecture that later shipped as the TieringOffloadingSpec (see kv-offloading-usage-guide-vllm and tiered-kv-cache-offloading-in-vllm-vllm-blog for the shipped feature). Defines a single primary tier (CPU DRAM, exclusive GPU access) plus multiple secondary tiers (storage, remote-node P/D, P2P), orchestrated by a new TieringManager. Key design principles as stated in the RFC: (1) always cascade a confirmed block to every secondary tier asynchronously; (2) primary tier is the sole gateway to GPU memory; (3) staged promotion -- lookup() returns None while a secondary-tier hit is being promoted to primary, and the scheduler retries; (4) all SecondaryTierManager methods (lookup/submit_store/submit_load/get_finished/touch) run non-blocking in the scheduler process, with actual data movement on the worker thread only for GPU<->CPU; (5) each secondary tier owns its own eviction policy. CPU memory is mandated to be stored in canonical TP-rank-1 form regardless of the vLLM node's actual TP rank, enabling cross-TP-rank sharing/storage. Comment thread (through Jul 2026) tracks the RFC's evolution into shipped PRs: #40020 (multi-tier data plane), #41968 (object-store tier), #43468 (self-describing KV events for single-tier CPUOffloadingSpec, explicitly NOT yet supported for TieringOffloadingSpec because tier promotions can create primary-tier store events with no live GPU job to describe), #46544 (opt-in hash-only BlockStored events for secondary tiers, with medium naming MEDIUM_CPU/MEDIUM_FS/MEDIUM_OBJ added alongside existing MEDIUM_GPU), and #48281 (tier locality: 'medium says what the storage is; locality says where it sits relative to the publishing instance'). A maintainer (Change72) states explicitly that stale KV placement state is a routing-correctness hazard: 'whoever owns eviction should also provide invalidation. Otherwise, routers may score or route based on stale placement state.' NOTE: several later comments (user coltonottley, Jul 2026) present extremely detailed self-reported 'production' benchmark numbers (exact byte counts, token counts, decode tok/s) for an unmerged downstream fork implementing canonical TP1 CPU-primary storage; these are unverified, self-reported claims by a single GitHub commenter, not peer-reviewed or merged into vLLM, and should not be cited as vetted vLLM performance characteristics. `evergreen`
