- [[blocking-queries-consul-hashicorp-developer]] — Blocking Queries | Consul | HashiCorp Developer — Official Consul blocking-queries semantics. Mechanism: endpoints that support blocking return header X-Consul-Index (a raft-index snapshot marker); client resends the same request with query param index=<last X-Consul-Index> plus wait=<duration> (max 10m, default 5m, plus up to wait/16 jitter) and the server holds the HTTP request open until a change occurs past that index or the timeout elapses -- long polling, not a persistent stream. Quote: 'the return of a blocking request is no guarantee of a change' (timeout or an idempotent write can return with no actual change). Implementation-detail requirements a client MUST follow: (1) reset index to 0 if a returned index is LOWER than the previous value (raft snapshot restore, KV list edge cases, Consul upgrades changing watch granularity) -- failing this can miss updates indefinitely or busy-loop; (2) sanity-check index > 0 after each response, since index=1 is always safe to request for not-yet-existent data; (3) rate-limit the blocking loop client-side (token-bucket, burst ~2) to avoid degrading into a busy loop when data churns fast, rather than sleeping (which delays delivery). Streaming backend (Consul 1.10+) is a materialized-view alternative to long polling, engaged automatically when index or cached params are set if the endpoint supports it; it omits X-Consul-LastContact/X-Consul-KnownLeader and marks responses with X-Consul-Query-Backend: streaming. A minority of agent-local endpoints (state not raft-indexed) instead use hash-based blocking: header X-Consul-ContentHash + query param hash=<value>, opaque (not orderable), otherwise same wait/timeout contract. RELEVANCE TO LOCUS: this is the direct analog to a poll-vs-watch decision for a Consul-backed EndpointDiscovery plugin -- a plugin would issue a blocking GET against /v1/health/service/:service with index tracking (see companion note health-http-api-consul-hashicorp-developer for the passing=true health-filter parameter), not a bare interval poll, to get near-real-time updates without tight polling. `evergreen`

Confirms this repo is the successor/rename of llm-d-kv-cache-manager (the fetch of the old repo's v0.4.0 valkey_example URL redirected here). Key findings directly on the focus questions:

(1) ENDPOINT IDENTITY: ZMQ topic format is literally "kv@<pod-ip>:<port>@<model>" -- pod identity in the index is a network address (IP:port), not a Kubernetes pod name/UID. The VLLMAdapter "parses kv@<pod-ip>:<port>@<model-name> topic strings." PodEntry objects in the index carry this IP:port identity plus DeviceTier and a Speculative flag.

(2) PUSH VS PULL -- the doc explicitly describes TWO SUPPORTED "Event Delivery Modes," which is the key architectural fact for non-Kubernetes backends: "Centralized -- every model-server pod connects (zmq.PUB) to a single endpoint hosted by the host process (zmq.SUB). Simpler to configure; works naturally with a single host replica" (pods dial out to a fixed, known host address -- no pod discovery needed at all, host just binds tcp://*:5557 and listens). Versus "Pod discovery -- each model-server pod binds its own ZMQ socket; the host process discovers pods via Kubernetes label selectors and creates per-pod subscribers. This mode supports active-active multi-replica deployments -- each replica independently subscribes to every pod and sees the full event stream." So: in Centralized mode the connection is pod-initiated (push, no discovery mechanism required, backend-agnostic); in Pod-discovery mode the connection is host/indexer-initiated per pod (host acts as ZMQ client dialing out), and pod discovery is explicitly Kubernetes-label-selector-based in the shipped implementation.

(3) DISCOVERY MECHANISM: confirmed Kubernetes-specific in Pod-discovery mode ("the host process discovers pods via Kubernetes label selectors") -- this is the piece that would need to be swapped out for a non-Kubernetes backend. The Centralized delivery mode is the natural escape hatch: it requires zero discovery infrastructure since pods proactively connect to a static, configured host endpoint.

(4) IDENTITY MAPPING / DUAL-KEY DESIGN: the indexer cannot derive a "request key" (its own FNV-64a-over-CBOR hash of token chunks, used for scoring lookups from a prompt) from an "engine key" (the model server's own internal content-addressing hash for a block, carried in KV-Events) or vice versa -- the two hash spaces are independent. The bridge is built on ingestion: BlockStored events carry both the engine key and the token chunk, so the worker computes the request key from tokens and records an engine_key -> request_key mapping; BlockRemoved events carry only the engine key and use that mapping to find and evict the request key. Scoring never touches engine keys. This dual-key bridge is orthogonal to pod identity (which is IP:port from the topic) -- separately, whatever the EPP/scheduler uses as its own "endpoint name" for a candidate pod (e.g., a Kubernetes Endpoint/pod IP from the InferencePool) must match the same IP:port string the indexer extracted from the ZMQ topic for the score lookup to resolve to the correct routable endpoint; the doc does not describe an explicit secondary identity-reconciliation step beyond this literal IP:port string match.

BLOCK INDEX BACKENDS (pluggable, relevant to non-k8s persistence/architecture choices): In-Memory two-level LRU (default, ~100M keys x 10 pod entries capacity), Cost-Aware Memory (Ristretto, byte-budgeted, for variable-size multimodal/LoRA entries), and Redis/Valkey (external TCP server, Valkey is Redis-wire-compatible/BSD-licensed with experimental RDMA transport) -- explicitly noted as adding "a network hop per lookup" and tying "host availability to the external store," with the caveat that shared external state is "rarely necessary since each in-memory replica converges from the event stream" via Pod-discovery mode's independent per-replica subscription.

Other architecturally load-bearing details: CPU offloading emits a second BlockStored with the same engine key, a device tier, but no tokens (content unchanged) -- relies on a strict GPU-then-CPU event-ordering guarantee from the same pod. KV-block hashing uses chained FNV-64a over CBOR(parentHash, tokenChunk, extra), block size default 16 tokens, seeded by a configurable hashSeed + model name; the "extra" field folds in LoRA adapter name/ID or multimodal content hashes so different adapters/modalities produce independent key chains. Internal tokenization (tokenization.Pool) is explicitly DEPRECATED; new integrations must tokenize externally (host process or sidecar) and call Indexer.ScoreTokens directly with token IDs -- the indexer is "agnostic to the tokenizer source as long as the resulting token IDs match what the engines emit." The pure-Go ZeroMQ implementation used means the indexer does not require libzmq on the host. Speculative entries (TTL-cache-based, caller-configured) close the blind spot between a routing decision and the confirming BlockStored event.
