This is architecturally close to what the user's query is asking for: the router's dispatch logic is written against an engine/backend abstraction (an object exposing prep_recv/remote_send/start_generate), completely decoupled from how those engine instances are deployed (the paper's own engines are bare processes on GPUs, not K8s pods) — swapping the backend substrate only requires the engine objects to expose the same three async methods, not a K8s-specific service-discovery layer. Claims up to 47% reduction in job completion time (JCT) versus existing static disaggregation strategies via the new 1P1D-balance pattern, attributing the gain to fine-grained load rebalancing that a fixed-strategy router cannot express. - [[gateway-api-inference-extensiondocsproposals004-endpoint-picker-protocol-at-main]] — gateway-api-inference-extension/docs/proposals/004-endpoint-picker-protocol at main · kubernetes-sigs/gateway-api-inference-extension · GitHub — GIE proposal 004, the Endpoint Picker Protocol spec (status: Implemented, versioned to v1.0.0 dated 2025-07-29). Defines the wire contract between a data-plane proxy (e.g. Envoy) and the EPP over Envoy ext_proc, which the EPP MUST implement including streaming mode. Endpoint identity on the wire is purely ip:port strings, not k8s object references: the data plane can restrict the EPP to a subset via filterMetadata key envoy.lb.subset_hint / x-gateway-destination-endpoint-subset (list of ip:port); if unset the EPP selects from the InferencePool selector's endpoint set.
