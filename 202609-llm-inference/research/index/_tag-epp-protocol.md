Author's stated rationale, in direct response to reviewing the Envoy dynamic_forwarding LB policy work (envoyproxy/envoy#38757): the existing design only supported one fallback endpoint, and if EPP needs to communicate multiple fallback candidates, it is cleaner to send one ordered list in one header than to split primary/fallback across two headers or metadata entries -- 'from the proxy's perspective, I will prefer only one source to get the external specified endpoints... the proxy could iterate the endpoints list in order and select the first valid one. - [[gateway-api-inference-extensiondocsproposals004-endpoint-picker-protocol-at-main]] — gateway-api-inference-extension/docs/proposals/004-endpoint-picker-protocol at main · kubernetes-sigs/gateway-api-inference-extension · GitHub — GIE proposal 004, the Endpoint Picker Protocol spec (status: Implemented, versioned to v1.0.0 dated 2025-07-29). Defines the wire contract between a data-plane proxy (e.g. Envoy) and the EPP over Envoy ext_proc, which the EPP MUST implement including streaming mode. Endpoint identity on the wire is purely ip:port strings, not k8s object references: the data plane can restrict the EPP to a subset via filterMetadata key envoy.lb.subset_hint / x-gateway-destination-endpoint-subset (list of ip:port); if unset the EPP selects from the InferencePool selector's endpoint set. The EPP returns its pick via the x-gateway-destination-endpoint HTTP header AND the envoy.lb dynamic_metadata namespace (both required to match; mismatch is undefined behavior), as one or more comma-separated ip:port endpoints — first valid one used sequentially for retries. Constraints: 503 Service Unavailable if the EPP fails to set a destination when no endpoints are ready, 429 Too Many Requests to shed load. A 2026-07-23 amendment (PR #3003, 'clarify EPP endpoint backend scope') scoped the ordered endpoint list to the specific InferencePool backend that produced it: on same-backend retry the data plane continues down that backend's list; on route-level retry/failover to a different InferencePool backend, the data plane MUST invoke that backend's EPP and MUST NOT reuse the previous backend's endpoints, and x-gateway-destination-endpoint-served (health/serving confirmation) must be reported to the EPP tied to whichever backend produced the terminal response. Also specifies gRPC Health Checking Protocol services (liveness, readiness, ext_proc service check) the EPP must expose. `evergreen`
