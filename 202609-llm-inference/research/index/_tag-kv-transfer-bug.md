- [[bug-pd-multi-tier-supplies-nothing-when-the-producer-already-holds-the-blocks-is]] — [Bug]: PD Multi Tier supplies nothing when the producer already holds the blocks · Issue #52808 · vllm-project/vllm — Closed upstream vLLM GitHub issue #52808 (opened Aug 18 2026 by nilig, same reporter as llm-d-router#2438) diagnosing a root-cause defect in vLLMs PD Multi Tier KV-offload path (remote_decoder/remote_prefiller, secondary tier type=p2p, OffloadingConnector with TieringOffloadingSpec). When a producer already holds the requested prefix blocks (i.e. the prefix cache worked), it creates no store job, so the consumers fetch demand parks in the demanded map and is never matched -- the consumer waits out the hard-coded _LOAD_TIMEOUT_S=30.0s and recomputes locally. Effect is inverted from intent: the better the producers prefix cache, the more often PD Multi Tier fails to deliver. Root cause: P2PTierManager.on_new_request defaults offloading_context to BLOCK_LEVEL policy, which skips prefix-hit chunks from being offloaded (next_stored_chunk_idx stays at num_chunks), and grep confirms REQUEST_LEVEL is never declared by any tier (p2p/fs/obj/example) in v0.27.1 or main, so the cascade to request-level tiers never runs. Reproduced with isolated HTTP calls: warm producer -> consumer took 32.9s vs 0.16s cold; identical in a real P/D pair (30.2s/0 bytes warm vs 0.086s/256MiB cold). At scale (8 producers + 8 consumers, 10,800 requests, shared-prefix workload): fetch-demand match rate fell from 93.8% (cold) to 51.5% (warming) to 36.7% (warm) as producer cache warmed up. 6,083 load timeouts logged against 10,800 requests; PD Multi Tier ended up SLOWER than plain NIXL P/D on identical hardware (1571s vs 1032s wall time to completion; mean TPOT 92ms vs 10.7ms). Maintainer liranschour confirmed the fix direction: the p2p tier should declare REQUEST_LEVEL (bug, not by design). `evergreen`
