- [[from-llm-inference-to-agentic-workloads]] — From LLM Inference to Agentic Workloads: — HKUST researchers with Alibaba Group and ByteDance engineers build AgentSysBench, a measurement toolkit + benchmark of 10 representative agentic applications (coding, research, RAG, search, assistant agents) with unified systems-level instrumentation, combining controlled deployments (4,641 benchmark requests, 64,924 LLM calls, 118,274 tool calls) with real production traces (178,799 production sessions in a single day, including 373,678 search queries from one agentic-search application and 4,389 web fetches from an Openclaw-like application).

SIX MEASURED PROPERTIES THAT DISTINGUISH AGENTIC WORKLOADS FROM CONVENTIONAL LLM SERVING (the paper's central contribution, each independently load-bearing):
(1) Execution is heavyweight and stateful -- non-LLM components (retrieval, sandboxes, tool execution) dominate end-to-end latency in 5 of the 10 benchmarked applications, and sandbox working-set memory peaks at 28 GB per session, meaning model inference is 'no longer the sole cost center.'
(2) Components have heterogeneous resource affinity (GPU-bound inference, memory-bound retrieval, CPU-bound sandboxes) whose task latencies diverge by up to 32x within a single application pipeline -- e.g. a RAG pipeline's bottleneck shifts between embedding and vector-database operations as inputs change, so application-level latency averages mask large per-request variance.
(3) Bottlenecks shift across requests, models, and deployments rather than sitting at a fixed stage.
(4) Production sessions hold state idle for minutes to hours between active steps (observed only in production traces, not controlled benchmarks) -- these sessions are neither finished nor actively consuming compute, but treating them as finished loses resumable state, while treating them as live wastes memory/disk.
(5) A 'control-plane tax': auxiliary LLM calls plus context overhead from tool schemas, raw observations, and safety checks crowds out productive compute and context, growing over multi-step sessions.
(6) Heavy cross-request redundancy in production: among 373,678 search queries from one production agentic-search app, 27% of unique queries recur and account for 67.3% of all search API calls; in a separate production app issuing 4,389 web fetches, 24% of distinct URLs recur and account for 64% of fetch invocations -- redundancy invisible to single-task synthetic benchmarks.

FOUR DESIGN INTERVENTIONS DERIVED FROM THESE FINDINGS, WITH MEASURED GAINS: task-disaggregated/task-aware serving cuts latency 29-40%; communication-aware (agent-aware) co-location placement improves up to 4.5x; state offloading reduces memory usage by 4.6x; tool-result caching removes 35.2% of redundant search calls and saves 19.3% of aggregate search latency. The paper's implication for serving-system design: systems built on conventional LLM-inference assumptions (model inference as sole cost center, request-level statelessness, fixed bottleneck location) misallocate resources for agentic workloads; serving systems need context-budget-aware tool interfaces, a first-class 'waiting' lifecycle state distinct from 'done', and query/object-level caching for external tool calls. `review`
- [[kvcache-cache-in-the-wild-characterizing-and-optimizing-kvcache-cache]] — KVCache Cache in the Wild: Characterizing and Optimizing KVCache Cache — Shanghai Jiao Tong University researchers with Alibaba Group engineers present the first systematic characterization of KV-cache (KV$) reuse patterns from production traces at Alibaba Cloud (ALIYUN), covering two representative workloads: Trace A (a to-C workload -- browser/mobile chatbot users) and Trace B (a to-B workload -- developers sending OpenAI-compatible API calls). This is cloud-provider multi-tenant production data, useful as a proxy for how internal platform operators should think about prefix-cache sizing and eviction, not itself an internal-enterprise deployment.

KEY MEASURED FINDINGS: (1) Ideal (infinite-capacity) KV-cache hit rates are 62% (Trace A, to-C) and 54% (Trace B, to-B) -- lower than previously reported numbers on synthetic/ShareGPT-style datasets, meaning synthetic benchmarks overstate achievable cache benefit. (2) KV-cache reuse is highly skewed: 10% of KV-cache blocks contribute 77% of all reuses. (3) Contrary to the expectation that multi-turn conversations dominate cache reuse, single-turn requests account for 97% of KV-cache reuses in the to-B (API) workload -- single-turn reuse is NOT a negligible phenomenon and must be designed for, not just multi-turn session locality. (4) User-level reuse is also skewed: 19% of users in Trace A and just 4% of users in Trace B account for more than 90% of cache block hits, motivating the authors' recommendation to prioritize intra-user over inter-user KV-cache reuse in system design. (5) KV-cache lifespan is ephemeral: P99 lifespan of KV-cache entries in the to-B workload is 97 seconds, meaning a relatively small cache suffices -- specifically, cache capacity of about 2x per-GPU HBM is enough to approach the ideal infinite-capacity hit rate under common GQA configurations (for this workload). (6) Reuse-time and reuse-probability distributions vary by request category (API vs chat, and number of turns) but are predictable within a category from historical data, which the paper exploits to build a workload-aware cache eviction policy that outperforms generic (LRU-style) eviction, especially under limited cache capacity. `review`
