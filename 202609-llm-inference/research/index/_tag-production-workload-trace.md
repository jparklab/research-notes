- [[cost-efficient-large-language-model-serving-for-multi-turn-conversations-with]] — Cost-Efficient Large Language Model Serving for Multi-turn Conversations with — CachedAttention / AttentionStore (Gao, He, Sharma, Kang, Jevdjic, Deng, Yang, Yu, Zuo — National University of Singapore + Shanghai Jiaotong + Huawei Cloud, arXiv 2403.19708, USENIX ATC'24) is the system Mooncake's own related-work section names as its closest concurrent architecture ('a concurrent work with us... The architecture of Mooncake shares many design choices with AttentionStore'). Motivating data from real ShareGPT conversation logs: 73% of real ChatGPT conversations are multi-turn, and because serving engines discard a session's KV cache when it goes idle and recompute it from scratch on the next turn, up to 99% of prefilling cost in multi-turn conversations is pure repetitive recomputation of KV cache the engine already computed once. AttentionStore is the hierarchical KV-cache storage system (GPU HBM -> host memory -> disk) that persists KV caches across turns instead of discarding them; CachedAttention is the attention mechanism/scheduling layer built on top of it. Three concrete engineering techniques, each solving a problem the paper demonstrates empirically: (1) layer-wise pre-loading and asynchronous saving overlap KV-cache transfer with GPU compute to hide access latency to slower storage tiers (motivated by the paper's own measurement that LLaMA-65B's free HBM space is fully consumed by KV cache in 14 seconds if caches are simply retained in GPU memory, ruling out an HBM-only retention strategy); (2) scheduler-aware fetching/eviction pre-fetches KV caches likely to be accessed from disk into host memory using hints from the inference job scheduler, because most caches end up on disk (tens of TBs capacity vs. host memory's hundreds of GBs) where random-access latency is poor; (3) decoupled positional encoding lets saved KV caches survive context-window truncation (e.g., LLaMA-2's 4K limit) by re-embedding position information only at load time, rather than invalidating the entire cached session when old tokens are dropped. Evaluated on the real ShareGPT dataset: reduces TTFT by up to 87%, improves prompt-prefilling throughput by up to 7.8x, and cuts end-to-end inference cost by up to 70% for multi-turn conversations. Authored primarily by Huawei Cloud interns/researchers, making it an institutional sibling to Mooncake and TetriInfer (also Huawei-affiliated) within this corpus's disaggregation literature. `review`
- [[distserve-disaggregating-prefill-and-decoding-for-goodput-optimized]] — DistServe: Disaggregating Prefill and Decoding for Goodput-optimized — DistServe (Zhong et al., Peking University / UC San Diego / StepFun, OSDI'24, arXiv 2401.09670) — the origin paper for prefill/decode disaggregation, directly cited as precedent by Mooncake, llm-d, and NVIDIA Dynamo. Diagnoses two root causes of poor goodput in colocated serving: (1) prefill-decoding interference — a single prefill job added to a decoding batch measurably slows both (Figure 2: adding one prefill job to a 13B-model decoding batch significantly elongates TPOT, worse with longer prompts), and chunked-prefill-with-piggyback (cites vLLM/Sarathi-style approaches [3,9]) only partially masks this at the cost of O(N^2) redundant KV-cache HBM->SRAM reloads when prefill is split into N chunks; (2) resource/parallelism coupling — colocation forces one parallelism plan to serve both a compute-bound prefill phase (benefits from intra-op parallelism) and a memory-bandwidth-bound decode phase (benefits from different scaling), forcing over-provisioning. DistServe's fix: assign prefill and decode to physically separate GPU instances, each independently scaled/parallelized, with a bandwidth-aware placement algorithm that colocates same-pipeline-stage prefill/decode segments on one node so KV-cache transfer rides NVLINK rather than cross-node links; decode instances 'pull' KV cache from prefill instances (buffering burstiness in the prefill GPU's memory) rather than prefill 'pushing' it. Reports a simple FCFS online scheduler, periodic workload-pattern-triggered replanning (placement algorithm reruns in seconds; weight reload takes minutes — both far under the hourly timescale at which real traffic patterns shift), and explicitly defers preemption and fault tolerance to future work, naming the specific failure mode (a single decode instance fault can cripple multiple dependent prefill instances). Implementation: ~6.5K LOC Python (placement algorithm, OpenAI-API-compatible frontend, orchestration layer) + ~8.1K LOC C++/CUDA execution engine, using Ray actors for distributed GPU workers, NCCL for cross-node and async CudaMemcpy for intra-node KV transfer; integrates continuous batching, FlashAttention, and PagedAttention, and serves OPT/LLaMA. Evaluated on a 4-node/32-GPU A100 cluster across three real workload shapes with measured token-length distributions — ShareGPT chatbot traces (avg input 755.5 / output 200.3 tokens), HumanEval code completion (avg input 171.3 / output 98.2), LongBench summarization (avg input 1738.3 / output 90.7) — against vLLM and DeepSpeed-MII baselines. Headline result: serves 7.4x more requests or sustains 12.6x tighter SLOs than state-of-the-art colocated systems (vLLM/DeepSpeed-MII) while keeping >90% of requests within TTFT/TPOT constraints; against vLLM specifically, DistServe sustains 1.8x-3.2x tighter SLO and up to 4.6x higher request rate in various configurations, and up to 3x-8x higher throughput in a related-work comparison table. Explicitly names Splitwise and TetriInfer as concurrent disaggregation papers it does not claim precedence over. `review`
- [[mooncake-a-kvcache-centric-disaggregated-2]] — Mooncake: A KVCache-centric Disaggregated — Mooncake (Qin, Li, He, Zhang, Wu, Zheng, Xu — Moonshot AI + Tsinghua/MadSys, arXiv 2407.00079, tech report) is first-person production evidence: this is the actual serving platform for Kimi, Moonshot AI's commercial LLM chatbot, described by its own operators (not a paper about a hypothetical system). It is the direct origin of the open-source kvcache-ai/Mooncake project (6.6k GitHub stars per prior note) and its MooncakeStoreConnector is now integrated into llm-d and referenced by vLLM/SGLang KV-cache tooling. Architecture: KVCache-centric disaggregation that goes beyond simple prefill/decode splitting (as in DistServe/Splitwise/TetriInfer, all cited as prior art) by also disaggregating the KV cache itself into a separate pool spanning CPU/DRAM/SSD across the GPU cluster's otherwise-underutilized resources, connected via GPUDirect RDMA through a component called Messenger. A global scheduler, Conductor, selects prefill/decode instance pairs per request to jointly optimize cache reuse, instance load, and TTFT/TBT SLOs; KVCache blocks are identified by chained prefix hashes (block size 512 tokens) enabling exact prefix-cache matching, with a heuristic hot-spot migration scheme that replicates frequently-hit blocks without needing precise future-usage prediction. For long-context prefill, Mooncake introduces chunked pipeline parallelism (CPP) — explicitly novel ('to our knowledge, this is the first application [of pipelined parallelism] in the inference stage') — instead of cross-node tensor or sequence parallelism, because CPP needs cross-node communication only at pipeline-stage boundaries, overlapping with compute; combined with layer-wise asynchronous KVCache load/store that overlaps transfer with attention computation layer-by-layer. Explicitly chose NOT to adopt chunked-prefill-into-decoding-batch (SARATHI, cited) as its primary technique, because prefill nodes need different cross-node parallelism than decode nodes and because keeping prefill out of VRAM-constrained decode batches frees VRAM. Under severe overload (a documented real condition for Kimi, not a hypothetical), Mooncake implements a prediction-based Early-Rejection policy: naive early rejection (reject before prefill if no decode slot will be free) causes load oscillation, which the predictive version mitigates. PRODUCTION DATA: releases an open-sourced 1-hour real request trace (23,608 entries) with timestamp/input_length/output_length/block-hash fields (text scrubbed for privacy) — paper states average input length 8,590 tokens, average output length 182 tokens, input:output ratio ~720 (reflecting Kimi's long-context use case). Cache-hit analysis on this trace: LRU/LFU/length-aware caching all plateau around a 55% hit ratio as capacity grows past 50,000 blocks (34% hit ratio at 1,000-block capacity), and the paper separately states real reusability on Kimi's live traffic is markedly lower than open-source benchmarks suggest, reaching up to 90% only for specific high-repetition products like its chat-to-paper service (papers.cool). Cache-block popularity is extremely skewed: over 50% of blocks are never reused while a minority are hit tens of thousands of times. Benchmark numbers: against vLLM on simulated long-context workloads (16k-128k prompts), Mooncake shows 50%-525% higher throughput under identical TTFT/TBT SLOs; under a real-workload replay (10P+10D Mooncake vs 20-instance vLLM), both systems hit ~100% TTFT-SLO compliance but only 57% of vLLM requests met the TBT SLO versus ~100% for Mooncake, letting Mooncake handle 75% more real requests at the same SLO. In an 8P+8D cluster overload test replaying 23,000 real requests at 2x speed, the naive-reject baseline rejected 4,183 requests versus 3,771 (early rejection) and 3,589 (prediction-based early rejection). All experiments reportedly use a dummy LLaMA2-70B-architecture model over replayed real-trace timing/lengths/cache-hash metadata (no real user text) to protect customer data while preserving reproducibility; the trace is open-sourced at github.com/kvcache-ai/Mooncake. `review`
- [[splitwise-efficient-generative-llm-inference-using]] — Splitwise: Efficient Generative LLM Inference Using — Splitwise (Patel, Choukse, Zhang, Shah, Goiri, Maleki, Bianchini — Microsoft + Univ. of Washington, ISCA 2024, arXiv 2311.18677) is the earliest widely-cited phase-splitting paper in this corpus and first-person Microsoft/Azure production evidence: its characterization is built on real production traces 'taken from two Azure LLM inference services on November 11th 2023' representing the two dominant real-world request classes — coding and conversation — a 20-minute subset of which is open-sourced at github.com/Azure/AzurePublicDataset (AzureLLMInferenceDataset2023). DistServe, Sarathi-Serve, Mooncake, and the 'Taming the Titans' survey all cite Splitwise as the paper that established the prompt/token-generation phase split as a serving primitive; Mooncake explicitly credits Splitwise's arXiv release as 'at the early stage of the development of Mooncake, which further motivated our progress.' Core technique: rather than disaggregating onto identical hardware, Splitwise explicitly leverages diverging GPU scaling curves (NVIDIA A100 vs H100: 3.43x more FLOPs, only 1.64x more HBM bandwidth, 1.75x more power, 2.16x more cost per machine per hour) to run the compute-bound prompt-computation phase on newer/faster GPUs and the memory-bandwidth-bound token-generation phase on cheaper/older GPUs, transferring KV-cache state between machines over datacenter-grade InfiniBand back-plane interconnects. Designs both homogeneous and heterogeneous cluster configurations optimized respectively for throughput, cost, and power. Evaluated on Llama2-70B and BLOOM-176B using the Azure production traces: Splitwise-based clusters achieve up to 1.4x higher throughput at 20% lower cost than non-split designs, or alternatively 2.35x more throughput under identical power and cost budgets. Also introduces time-between-tokens (TBT) as a formal streaming-latency metric alongside TTFT/E2E-latency/throughput. Explicitly critiques the leading pre-disaggregation batching schemes (request-level batching and continuous batching) for forcing prompt-phase requests to preempt ongoing token-generation batches, which shortens TTFT at the cost of substantially higher tail E2E latency for in-flight requests. `review`
- [[taming-throughput-latency-tradeoff-in-llm-inference-with-sarathi-serve]] — Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve — Sarathi-Serve (Agrawal et al., Microsoft Research India / Georgia Tech, OSDI'24, arXiv 2403.02310) — the origin paper for chunked-prefill, a technique now implemented in vLLM's V1 scheduler. Diagnoses the existing throughput-vs-latency tradeoff as a consequence of scheduler design: decode-prioritizing systems (FasterTransformer) protect time-between-tokens (TBT) latency but waste GPU cycles running small decode-only batches; prefill-prioritizing iteration-level batchers (Orca, vLLM) maximize throughput by eagerly scheduling prefills whenever memory frees up, but this causes 'generation stalls' — the paper measures a stall in vLLM lasting several seconds when serving Yi-34B on two A100s against an arxiv-summarization trace (Figure 1a). Introduces two techniques: (1) chunked-prefills, splitting a prefill request into near-equal compute-sized chunks processed over multiple iterations; (2) stall-free scheduling, which coalesces ongoing decodes with one or more prefill chunks from new requests into each batch up to a fixed chunk-size budget, so new request admission never pauses in-flight decodes. The near-uniform per-iteration compute this creates also balances pipeline-parallel micro-batches, substantially reducing pipeline bubbles. Benchmarked against vLLM and Orca across four model/hardware configurations (Mistral-7B on 1 A100; Yi-34B on 2 A100 with TP-2; LLaMA2-70B on 8 A40; Falcon-180B on 8 A100 with TP4-PP2 over commodity 100Gbps ethernet, deployed on Azure NC96ads v4 VMs) using two traces built from real request-length distributions: openchat_sharegpt4 (real multi-round ChatGPT-4 conversations, high prompt-length variance) and arxiv_summarization (long prompts, low output-length variance) — the paper states the latter is 'representative of LLM workloads such as Microsoft M365 Copilot and Google Duet AI.' Headline results: up to 2.6x higher serving capacity for Mistral-7B, up to 3.7x for Yi-34B, and up to 5.6x end-to-end serving-capacity gain for Falcon-180B under pipeline parallelism, all measured under explicit tail-latency SLOs (P99 TBT at 5x or 25x unconstrained decode-iteration time for strict/relaxed settings, following Patel et al.'s Splitwise methodology). Explicitly contrasts itself with the disaggregation approach (Splitwise, DistServe, TetriInfer): disaggregation fully eliminates prefill-decode interference and gives better TTFT, but requires KV-cache migration across replicas (needs high-bandwidth interconnect) and leaves prefill-replica GPU memory underutilized since only decode replicas store KV cache; the paper explicitly defers a quantitative chunked-prefill-vs-disaggregation comparison to future work. Notes that a subsequent system, APIServe, adopted chunked prefills from Sarathi for ahead-of-time prefill recomputation in multi-turn API serving. Source released at github.com/microsoft/sarathi-serve. `review`
