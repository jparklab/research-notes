Explains two required components: (1) Request Flow Orchestration -- EPP selects a P/D worker pair via a disagg-profile-handler that runs a decode-profile first, consults a 'decider' on how much of the prompt is cached on D, and only invokes the prefill-profile (selecting a P endpoint too) if the uncached suffix is large; both P and D endpoints belong to the SAME InferencePool, distinguished by the llm-d.ai/role label (values: prefill, decode, prefill-decode) which the prefill-filter/decode-filter plugins use to filter candidates -- and (2) Efficient KV Transfer, typically over RDMA via NIXL. - [[networking-for-distributed-inference-in-llm-d-llm-d]] — Networking for Distributed Inference in llm-d | llm-d — Dense llm-d engineering blog post (co-authored with NVIDIA) on the networking stack underlying P/D disaggregation -- highly relevant to non-k8s backend feasibility because it describes NIXL/vLLM's NixlConnector mechanics as fundamentally pod-topology-agnostic.

NIXL (NVIDIA Inference Xfer Library) is the sole KV-transfer layer llm-d uses; it exposes a unified transfer API abstracting UCX (RDMA), libfabric (AWS EFA), UCCL, and Mooncake backends behind a common plugin interface, over accelerators (CUDA/ROCm/XPU), fabrics (InfiniBand/RoCE/EFA/TCP), memory types (GPU VRAM/CPU DRAM) and storage (local SSD, HF3FS, S3). Backends declare capabilities (memory types, local/remote transfer, notification support) and implement registration/metadata-exchange/connection/prepare-post-check-release primitives; NIXL itself handles plugin discovery, descriptor validation, metadata exchange, backend selection and async request lifecycle -- none of this machinery references Kubernetes.

Critically for non-k8s feasibility: vLLM's NixlConnector operates pull-based (D reads KV blocks from P's GPU memory via one-sided RDMA READs) with LAZY, DECENTRALIZED pairing -- 'the first time D sees an unknown P engine it performs a background handshake that exchanges metadata over ZMQ, validates a compatibility hash, and bootstraps the RDMA path... New instances are paired automatically following the same mechanism, with no centralized service-discovery plane required.' Transfers are zero-copy. Additional connector features: heterogeneous TP between P/D (D computes which remote TP rank to read and fetches the matching slice), Hybrid Memory Allocator support for SSM-hybrid architectures (Jamba/Mamba), and fault tolerance via a configurable kv_lease_duration with D-side heartbeats (P auto-frees blocks if D crashes) and a kv_load_failure_policy (fail=default, error immediately; recompute=fall back to local prefill on D).

llm-d contributed a UCCL backend to NIXL starting in v0.5, targeting hardware UCX doesn't cover. Benchmarks (via nixlbench, 1-8GB payloads) compared UCCL/UCX/Mooncake across 100G RoCE, 400G InfiniBand, and 100G TCP: on RoCE all three converge near line rate (~12.0-12.2 GB/s of 12.5 GB/s theoretical); on 400G IB at batch=1000, UCCL and UCX both hit ~49.5 GB/s (~99% of 50GB/s line rate) while Mooncake saturates at ~42 GB/s (84%) due to higher per-block posting latency (2-17ms vs ~12us UCCL / ~283us UCX); at batch=10,000 Mooncake drops further to 38-42GB/s while UCX/UCCL hold ~49.5GB/s. Over TCP, GPU-to-GPU: UCCL achieves 4.7-4.9 GB/s (1GB in 211ms avg, P99 217ms) by leveraging NCCL CUDA kernels to chunk/pipeline GPU-to-CPU-to-network; UCX manages only 0.55 GB/s (1.8s for 1GB, 14.4s at 8GB, ~9x slower); Mooncake does not support GPU-to-GPU TCP at all. CPU-to-CPU over TCP at 1GB: UCCL 216ms, UCX 263ms (22% slower), Mooncake 298ms (38% slower); sustained throughput ~4.9/4/3.5 GB/s respectively.

Operationally, llm-d is adding 'preflight check' tooling (llm-d-preflight-checks.py) that gates vLLM startup inside the pod -- on failure the pod exits non-zero so Kubernetes reschedules it -- and a pause mode (LLMD_PREFLIGHT_CHECKS=pause) that holds vLLM startup for runtime networking tests, resumed via a POST to the script's /exit endpoint. This tooling is packaged as an agent skill in the llm-d/llm-d-pd-utils repo (/llm-d-preflight-checks, /llm-d-networking-tests) with a Helm-chart integration tracked as llm-d/llm-d#1580. Explicitly frames networking as the binding constraint on TTFT for disaggregated serving, and states 'considering KV Cache management' (CPU-memory offload paths) and observability (correlating network- and app-level metrics) as active/open work areas. `evergreen`

- [[pull-dont-recompute-peer-to-peer-kv-cache-sharing-in-llm-d-llm-d]] — Pull, Don't Recompute: Peer-to-Peer KV Cache Sharing in llm-d | llm-d — Introduces P2P (peer-to-peer) KV cache sharing in llm-d, an opt-in scheduling mechanism that adds a third option beyond 'wait for the cache owner' or 'recompute': route to the best endpoint for load and copy (pull) the finished KV over the network. Any vLLM instance can act as Consumer (pulls matching KV blocks from a peer instead of recomputing) or Producer (serves blocks from its CPU offload tier). Mechanically, the router's Endpoint Picker (EPP) compares the peer with the most cached tokens against the load-selected destination; if the peer holds enough more cached prefix (minCachedTokenDelta) to beat the measured transfer crossover, it names that peer as KV source, and the producer writes matching blocks over NIXL (CPU-to-CPU, no GPU compute involved) — a normal cache miss still falls back to full computation. Transfer-vs-recompute economics were measured directly: on gpt-oss-120B/H200, pull beat recompute at every measured prefix length from 2K tokens (-56%) to 49K tokens (-88%); on a 753B GLM MoE testbed (KV footprint ~93KB/token) the crossover was ~8.7K tokens, with pull 61% faster than recompute at 24K tokens. Production-shaped benchmark: on GLM-5.2-FP8 across 32x H200 P/D-disaggregated at concurrency 64 (AIPerf trace replay, SemiAnalysis Weka coding-agent corpus), P2P improved successful throughput by 4.6% with approximate routing and 9.7-11.1% with precise routing (average +9.6% successful throughput, +11.8% input-token throughput across 3 repeats), while median TTFT fell up to 25%. A document-Q&A workload (192 48K-token docs, 128 active conversations, gpt-oss-120B/16 H200 pods) showed load-aware placement + P2P beating pure prefix affinity by +35% throughput and lower p99 TTFT (16.6s vs 25.2s) at the cost of higher median TTFT (0.6s vs 0.3s). For P/D session continuity, P2P let a prefill worker pull decode-generated history instead of recomputing it: on an agentic-serving workload (24 conversations, prompts averaging 61.9K tokens), median TTFT dropped 6.3x (6.83s to 1.09s) and throughput rose 50%. P2P is off by default because the crossover threshold is deployment- and fabric-specific and must be calibrated (recommended via the p2p-kv-cache-sharing guide) to avoid pulls costing more than recomputation. `evergreen`

Mechanism: the request's originating pod is the KV cache source (computed the prefix, cached a copy in CPU tier); the router names that source on a later request sharing the prefix but scheduled elsewhere; the scheduled pod (consumer) pulls the prefix blocks rather than recomputing, with the source's GPU never touched, so a pull costs the source zero prefill capacity.
