- [[standalone-epp-issue-1838-kubernetes-sigsgateway-api-inference-extension]] — Standalone EPP · Issue #1838 · kubernetes-sigs/gateway-api-inference-extension — GIE issue #1838 'Standalone EPP' (opened by ahg-g, a GIE maintainer, Nov 7 2025; closed completed Mar 4 2026) is the design-rationale thread for why standalone (non-InferencePool, non-Gateway-API-provisioned) EPP deployment exists. ahg-g frames it as a maturation ladder: 'The idea is to offer deployment modes that allow the least amount of friction for users as they mature in the journey from simple deployments to full fledged ones that integrate with Gateway API. The end goal is to land users on k8s and the gateway api, but many users are not there yet.' He enumerates four deployment modes: (1) orchestrator-agnostic static endpoint config with ZERO k8s dependency (no reconcilers started at all); (2.1) k8s-native, no Gateway API/CRD dependency, endpoints found via pod-selector+port flags; (2.2) k8s-native, extension CRDs used for richer EPP features but proxy statically configured (typically sidecar); (2.3) full Gateway-API-provisioned mode. Corresponding to this he identifies exactly three discovery mechanisms EPP should support: 1) InferencePool (reconciler-driven), 2) podSelector, 3) static set of endpoints -- each as its own pluggable 'discovery plugin.' Contributor nirrozenbaum initially argued modes (1) and (2.1) were unnecessary and 'awkward to develop... under kubernetes-sigs and say it's going to be with zero dependency on k8s,' but ahg-g countered with concrete demand: 'We hear this from batch inference and RL customers. In fact, Mistral asked for those two deployment modes independently.' ahg-g explicitly rejects requiring any control-plane dependency for the static/orchestrator-agnostic mode -- 'I don't think we need to offer anything beyond a static set of endpoints because otherwise we need to build or create a dependency on a control plane, which goes against the main motivation behind this mode' -- and cites sgl-project/sglang's sgl-router prefill/decode disaggregation static-endpoint config as the model to follow. Contributor elevran proposed generalizing service discovery further to include DNS resolvers and etcd/Consul/cloud-service backends, listed as options for mode (1). This thread is the direct motivating-use-case evidence for why standalone EPP (and thus non-pod backend support) exists: friction reduction for non-k8s-native batch-inference and RL workloads, not a rejection of k8s but a staged on-ramp. `evergreen`
