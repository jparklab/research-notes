Explains two required components: (1) Request Flow Orchestration -- EPP selects a P/D worker pair via a disagg-profile-handler that runs a decode-profile first, consults a 'decider' on how much of the prompt is cached on D, and only invokes the prefill-profile (selecting a P endpoint too) if the uncached suffix is large; both P and D endpoints belong to the SAME InferencePool, distinguished by the llm-d.ai/role label (values: prefill, decode, prefill-decode) which the prefill-filter/decode-filter plugins use to filter candidates -- and (2) Efficient KV Transfer, typically over RDMA via NIXL. With GPUDirect RDMA, GPU memory is registered directly with the NIC so transfers bypass the CPU. `review`

- [[networking-for-distributed-inference-in-llm-d-llm-d]] — Networking for Distributed Inference in llm-d | llm-d — Dense llm-d engineering blog post (co-authored with NVIDIA) on the networking stack underlying P/D disaggregation -- highly relevant to non-k8s backend feasibility because it describes NIXL/vLLM's NixlConnector mechanics as fundamentally pod-topology-agnostic.

NIXL (NVIDIA Inference Xfer Library) is the sole KV-transfer layer llm-d uses; it exposes a unified transfer API abstracting UCX (RDMA), libfabric (AWS EFA), UCCL, and Mooncake backends behind a common plugin interface, over accelerators (CUDA/ROCm/XPU), fabrics (InfiniBand/RoCE/EFA/TCP), memory types (GPU VRAM/CPU DRAM) and storage (local SSD, HF3FS, S3). Backends declare capabilities (memory types, local/remote transfer, notification support) and implement registration/metadata-exchange/connection/prepare-post-check-release primitives; NIXL itself handles plugin discovery, descriptor validation, metadata exchange, backend selection and async request lifecycle -- none of this machinery references Kubernetes.

Critically for non-k8s feasibility: vLLM's NixlConnector operates pull-based (D reads KV blocks from P's GPU memory via one-sided RDMA READs) with LAZY, DECENTRALIZED pairing -- 'the first time D sees an unknown P engine it performs a background handshake that exchanges metadata over ZMQ, validates a compatibility hash, and bootstraps the RDMA path... New instances are paired automatically following the same mechanism, with no centralized service-discovery plane required.' Transfers are zero-copy. Additional connector features: heterogeneous TP between P/D (D computes which remote TP rank to read and fetches the matching slice), Hybrid Memory Allocator support for SSM-hybrid architectures (Jamba/Mamba), and fault tolerance via a configurable kv_lease_duration with D-side heartbeats (P auto-frees blocks if D crashes) and a kv_load_failure_policy (fail=default, error immediately; recompute=fall back to local prefill on D).

llm-d contributed a UCCL backend to NIXL starting in v0.5, targeting hardware UCX doesn't cover. Benchmarks (via nixlbench, 1-8GB payloads) compared UCCL/UCX/Mooncake across 100G RoCE, 400G InfiniBand, and 100G TCP: on RoCE all three converge near line rate (~12.0-12.2 GB/s of 12.5 GB/s theoretical); on 400G IB at batch=1000, UCCL and UCX both hit ~49.5 GB/s (~99% of 50GB/s line rate) while Mooncake saturates at ~42 GB/s (84%) due to higher per-block posting latency (2-17ms vs ~12us UCCL / ~283us UCX); at batch=10,000 Mooncake drops further to 38-42GB/s while UCX/UCCL hold ~49.5GB/s. Over TCP, GPU-to-GPU: UCCL achieves 4.7-4.9 GB/s (1GB in 211ms avg, P99 217ms) by leveraging NCCL CUDA kernels to chunk/pipeline GPU-to-CPU-to-network; UCX manages only 0.55 GB/s (1.8s for 1GB, 14.4s at 8GB, ~9x slower); Mooncake does not support GPU-to-GPU TCP at all. CPU-to-CPU over TCP at 1GB: UCCL 216ms, UCX 263ms (22% slower), Mooncake 298ms (38% slower); sustained throughput ~4.9/4/3.5 GB/s respectively.

Operationally, llm-d is adding 'preflight check' tooling (llm-d-preflight-checks.py) that gates vLLM startup inside the pod -- on failure the pod exits non-zero so Kubernetes reschedules it -- and a pause mode (LLMD_PREFLIGHT_CHECKS=pause) that holds vLLM startup for runtime networking tests, resumed via a POST to the script's /exit endpoint. This tooling is packaged as an agent skill in the llm-d/llm-d-pd-utils repo (/llm-d-preflight-checks, /llm-d-networking-tests) with a Helm-chart integration tracked as llm-d/llm-d#1580. Explicitly frames networking as the binding constraint on TTFT for disaggregated serving, and states 'considering KV Cache management' (CPU-memory offload paths) and observability (correlating network- and app-level metrics) as active/open work areas. `review`

THE INTERFACE (final form, after review): originally named DiscoveryPlugin at pkg/epp/framework/interface/discovery/discovery.go, renamed to EndpointDiscovery and physically MOVED to under the datalayer package (pkg/epp/framework/interface/datalayer/discovery.go) per the author's own design rationale. *** THE SINGLE MOST DIRECTLY RESPONSIVE QUOTE TO THE RESEARCH QUERY ***, from the PR author (Ezra Silvera) explaining why Discovery must be a separate, pluggable component from the datalayer: "We aim to also support non k8s in the future so we need to keep the datalayer clean: we want K8s, file, Slurm, and Ray discovery all as plugins. If discovery lives inside the datalayer, the datalayer gets contaminated with infrastructure-specific code (ctrl.Manager, fsnotify, etc.), which defeats the whole point of the abstraction." This CONFIRMS that (a) the llm-d-router maintainers designed the discovery abstraction specifically to be backend-agnostic across Kubernetes, flat files, Slurm, AND Ray, and (b) Kubernetes-specific machinery (ctrl.Manager, i.e. controller-runtime) lives ONLY inside the k8s discovery plugin implementation, not in the shared datalayer/notifier code path -- meaning a from-scratch non-k8s DiscoveryPlugin implementation does not need to touch or depend on any Kubernetes client libraries.

The author also articulated the architectural boundary precisely: "Discovery is upstream of the datalayer, not a peer, the datalayer only activates per endpoint AFTER discovery creates it... Discovery answers 'which endpoints exist?' [while] the datalayer answers 'what is the state of known endpoints?' (metrics, KV cache, queue depth)" -- i.e. a custom backend integration needs a Discovery plugin (topology/existence) and can reuse the existing datalayer machinery (health/metrics polling) unmodified, PROVIDED the backend exposes compatible metrics endpoints.

One open design question flagged but explicitly NOT resolved in this PR: a reviewer asked "I wonder if this is not too k8s centric and we should include an explicit UniqueID in the endpoint metadata?" referring to the use of Kubernetes' types.NamespacedName as the endpoint identifier type in Delete(id types.NamespacedName) -- the author agreed this is a real gap ("several other places using NamespacedName and we should switch to ID") but deferred it as out of scope, meaning as of this PR the endpoint identifier type itself still carries a k8s-shaped type even though the interface is otherwise backend-agnostic; downstream PRs (e.g. the file-discovery series #1080/#1081) may or may not have resolved this -- worth checking.
