- [[cacheroute-planned-prefix-affinity-routingfor-large-scale-llm-serving]] — CacheRoute: Planned Prefix-Affinity Routingfor Large-Scale LLM Serving — CacheRoute (Meta, Aug 2026) is a planned prefix-affinity router that produces strong negative-result evidence on when cache-affinity routing fails. Core claim: cache-blind balancing disperses prefix reuse (return time to cache lengthens); fixed/pinned affinity restores locality but maps key skew directly onto server queues, overloading whichever server holds a hot key; reactive cache-aware routers (citing Preble and DualMap/Yuan-2026 as examples) still forfeit the warm prefix once a destination fills and traffic spills over. CacheRoute resolves this with a periodic offline routing plan: it admits only the highest-rate keys into a warm-prefix slot allocation, gives overloaded keys multiple destinations sized to cap expected per-destination load, places assignments via longest-processing-time-first (LPT) list scheduling, and falls back to cache-blind power-of-two-choices for unadmitted traffic; the table stays fixed for a control interval rather than remapping per request. On Llama-3.3-70B fp8 across 60 H100 GPUs (30 tensor-parallel-2 destinations), CacheRoute sustains 176 QPS at p99<=3.5s SLO vs 76 QPS for the strongest baseline (Preble) -- 2.3x -- and raises served KV-cache hit rate from 64.1% (cache-blind) to 93.2%. Ablation on an 8B model isolates the two mechanisms: affinity alone raises hit rate to 88% but creates 3.46x load imbalance; adding LPT placement keeps 90% hit rate while cutting imbalance to 1.24x, moving the SLO knee from 240 to >=500 QPS. CRITICALLY, two 32B counterexample workloads show affinity routing can actively HURT: when affinity recovers little KV work (hit rate only rising from 1.1% to 11.8% or 0.8% to 8.5%), the residual load skew from pinning is not offset, and capacity falls to 0.50-0.67x of flat load balancing (a straight loss) or merely ties it. The paper explicitly recommends gating any cache-affinity deployment with a shadow replay rather than enabling it from workload statistics alone, since model size alone does not predict which regime a workload falls into. Additional negative results: bursty arrivals (Gamma process, CV=1.9) cut CacheRoute's 3.5s capacity by one step (180->160 QPS); stale routing plans (one interval old under a lognormal rate-drift random walk) lose up to 3.0 points of KV hit and 858ms of p99 in worst-case transitions, and installing a freshly recomputed plan causes a transient 13.6-point KV-hit drop during cache rewarming. `evergreen`

- [[efficient-memory-management-for-large-language]] — Efficient Memory Management for Large Language — The original PagedAttention/vLLM paper (Kwon et al., UC Berkeley/Stanford/UCSD, SOSP 2023, arXiv 2309.06180) — foundational prior art for all KV-cache-aware routing discussed elsewhere in this batch, and the mechanism llm-d's own KV-cache manager builds on. Proposes PagedAttention, an attention algorithm inspired by OS virtual memory paging: KV cache is stored in fixed-size, non-contiguous 'pages' (blocks) referenced via a block table, eliminating internal/external memory fragmentation and enabling near-zero KV cache memory waste. This block-based storage also enables flexible KV cache sharing within and across requests (e.g., parallel sampling, beam search, shared system prompts) via copy-on-write block reference counting. This block/page abstraction and the block-hash-based cache lookup it enables is the direct ancestor of the block-hashing and prefix-tree matching schemes used by SGLang RadixAttention, NVIDIA Dynamo's KV router, AIBrix, and llm-d's KV cache manager. `evergreen`

- [[kv-offloading-usage-guide-vllm]] — KV Offloading Usage Guide - vLLM — vLLM docs reference for configuring the OffloadingConnector (single-tier CPUOffloadingSpec or multi-tier TieringOffloadingSpec). Only the CPU primary tier has direct GPU access; secondary tiers (fs, obj, p2p) never touch GPU memory -- all GPU<->secondary transfers stage through CPU. Config surface includes cpu_bytes_to_use (total host bytes, not per-worker), block_size/blocks_per_chunk, eviction_policy (built-in lru/arc or custom via cache_policy_module_path), offload_prompt_only (default true -- only prefill blocks offloaded, not decode), and self_describing_kv_events (opt-in richer BlockStored/BlockRemoved payloads with block hashes, token_ids, block_size, parent hash, LoRA/group metadata for external KV-event consumers to index offloaded blocks). Filesystem and object-store secondary tiers publish hash-only BlockStored KV events with a 'locality' field (LOCAL/REMOTE relative to the publishing instance) that is NOT inferred from tier type -- an obj tier is not implicitly REMOTE. Cross-process/cross-instance KV sharing (shared filesystem mount, shared object bucket, or P2P) works by default because block content hashes are deterministic across instances via a fixed NONE_HASH seed, EXCEPT under the non-cryptographic xxhash/xxhash_cbor prefix-caching-hash-algo, which requires manually matching PYTHONHASHSEED across all instances or cross-instance cache sharing silently fails. Documents in detail the P2P orchestration-layer protocol most relevant to llm-d: the P2P secondary tier itself only executes lookups/transfers -- the router/EPP orchestration layer decides which peer to pull from and drives every transfer via three mutually-exclusive-ish keys in the request's kv_transfer_params (remote_decoder, remote_prefiller, remote_kv_source), each carrying a kv_request_id plus, for prefiller/kv_source roles, remote_host/remote_port of the specific peer. remote_decoder+remote_kv_source is the only legal dual-role combination. Gives the full runtime handshake: consumer sends LookupMsg (kv_request_id + block hashes) at on_schedule_end, producer replies with hit hashes, consumer calls submit_load for hits only, producer performs NIXL WRITE and sends TransferDone; classic P/D mode (remote_prefiller set) skips the lookup round-trip entirely since the decoder assumes the prefiller holds all its blocks. Also documents per-request max_offload_tokens to cap how many prefix tokens are eligible for offload (e.g., cache a shared system prompt but not user-specific tail tokens). `evergreen`
- [[kv-cache-indexer-llm-d]] — KV-Cache Indexer | llm-d — v0.7 architecture doc (marked no-longer-actively-maintained but describes still-current design) for the KV-Cache Indexer, the EPP subcomponent enabling precise prefix-cache-aware routing. Three cooperating parts: an Index (block key → pods mapping built from KVEvents: BlockStored, BlockRemoved, AllBlocksCleared, published over ZMQ by vLLM/SGLang), a Data Producer (tokenizes prompts once per request so downstream components share the result), and a Scorer (precise-prefix-cache-scorer, finds the longest consecutive prefix of cached blocks per pod, since block i requires the unbroken prefix 0..i-1 due to causal attention; a worked example shows Pod A scoring 4/5 blocks, Pod B 2/5 due to a chain break, Pod C 0). Speculative Indexing (recommended for production) inserts short-lived predicted entries immediately after a routing decision with a default 2-second TTL to cover the gap before a confirming KVEvent arrives.
