- [[published-as-a-conference-paper-at-iclr-2026]] — Published as a conference paper at ICLR 2026 — DualMap (ICLR 2026, Huawei + HUST) formalizes the cache-affinity vs. load-balancing conflict in KV-cache-aware LLM serving routers: pure cache-affinity routing (e.g., consistent hashing on prefix) causes severe load imbalance under skewed prompt popularity, overloading nodes serving hot prefixes while cold-prefix nodes idle, driving TTFT SLO violations; pure load-balancing (Least Loaded) scatters shared prefixes and destroys cache hit rate. Prior systems (Mooncake, Preble, Dynamo) only partially resolve this by routing a subset of requests by cache-affinity and the rest by load, operating in a single mapping space. DualMap instead hashes each request's partial prefix with two independent hash functions to get two candidate instances (power-of-two-choices), then picks the better one via three mechanisms: SLO-aware routing (switch to load-aware once predicted TTFT exceeds SLO), hotspot-aware rebalancing (migrate requests off overloaded instances), and dual-hash-ring scaling (avoid full remap on cluster resize). - [[tokenlake-a-unified-segment-level-prefix-cache-pool]] — TokenLake: A Unified Segment-level Prefix Cache Pool — TokenLake (Peking University + StepFun) diagnoses three structural failure modes of instance-local cache-aware routing (the prefix-tree-per-instance model used by systems like llm-d's KV-cache-aware router, SGLang, Mooncake): (1) load imbalance -- instances with high prefix hit rates become memory-bandwidth over-utilized while cold instances sit idle, because the router can only route whole requests to whichever instance already holds the matching prefix tree; (2) redundancy -- to rebalance computation, hot shared prefixes (system prompts, shared documents) get replicated across multiple instances, wasting memory; (3) fragmentation -- because a full prefix must reside on one instance to form a contiguous prefix tree, memory slots scattered across instances cannot be pooled together. These problems compound under PD (prefill/decode) disaggregation, since prefill and decode instances have different memory-bandwidth profiles and must each separately hold the same prefix cache to avoid recomputation. TokenLake's fix decouples cache management from scheduling via a declarative interface (exposing query tensors, prefix caches, and cache-aware ops) and manages cache at sub-request segment granularity with a heavy-hitter-aware load-balancing algorithm, letting the scheduler dispatch elastically without needing to track prefix locality. On real-world workloads (CharacterAI/Kimi report 75-95% production hit rates as baseline context), TokenLake improves throughput up to 2.6x and 2.0x and cache hit rate up to 2.0x and 2.1x versus state-of-the-art cache-aware routing and cache-centric PD-disaggregation baselines respectively. `evergreen`
