Explains two required components: (1) Request Flow Orchestration -- EPP selects a P/D worker pair via a disagg-profile-handler that runs a decode-profile first, consults a 'decider' on how much of the prompt is cached on D, and only invokes the prefill-profile (selecting a P endpoint too) if the uncached suffix is large; both P and D endpoints belong to the SAME InferencePool, distinguished by the llm-d.ai/role label (values: prefill, decode, prefill-decode) which the prefill-filter/decode-filter plugins use to filter candidates -- and (2) Efficient KV Transfer, typically over RDMA via NIXL. The Routing Proxy Sidecar runs in each decode pod and reads the x-prefiller-host-port header (one or more prefill pod addresses, comma-separated/multi-value) set by the proxy/EPP; if present it executes the disaggregated path (send prefill request, capture KV transfer metadata, forward enriched request to local decoder), otherwise it proxies decoder-only. It documents TWO KV-transfer protocol implementations the sidecar must speak: vLLM's nixlv2 (default) -- a two-phase sequential protocol using kv_transfer_params and max_tokens=1, with fallback to decoder-only on prefiller server errors (5xx) but no retry on client errors -- and SGLang's sglang connector, a concurrent protocol using bootstrap_host/bootstrap_port/bootstrap_room parameters where prefill fires asynchronously (goroutine with context.WithoutCancel) while decode runs synchronously, coordinating out-of-band via the bootstrap room. NIXL is the only KV-transfer engine llm-d currently focuses on; it needs RDMA (InfiniBand or RoCE, both supported via UCX and UCCL backends; TCP-X and EFA supported by UCCL; libfabric supports IB only) for efficient transfer, falls back to slow TCP without RDMA (dev/test only), and NVLink transfer works only for local development since 'it cannot cross pod boundaries' in Kubernetes deployments. With GPUDirect RDMA, GPU memory is registered directly with the NIC so transfers bypass the CPU. `review`

Gives two concrete well-lit-path benchmark topologies: 'P/D over RDMA' -- 8xH200 GPUs, InfiniBand OR RoCE RDMA, Llama-3.3-70B-Instruct-FP8, 4x TP=1 prefill workers + 1x TP=4 decode worker; and 'Wide-EP with P/D' -- 32xH200 GPUs, InfiniBand OR RoCE RDMA, DeepSeek-R1-0528, 1x DP=16 prefill worker + 1x DP=16 decode worker. Best-practice guidance: P/D disaggregation pays off for large models (Llama-70B+, not 8B), longer ISL (e.g. 10k ISL | 1k OSL vs 200|200), and sparse MoE with wide-EP opportunities; tune via heterogeneous parallelism (fewer-parallelism/more-replica P workers vs. more-parallelism/fewer-replica D workers) and xPyD ratio.
