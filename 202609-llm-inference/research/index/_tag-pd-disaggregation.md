- [[disaggregated-serving-llm-d]] — Disaggregated Serving | llm-d — Current (v0.9, as of the fetch banner referencing the v0.9 'hardened for scale' release) llm-d architecture doc on P/D disaggregated serving. Explains two required components: (1) Request Flow Orchestration -- EPP selects a P/D worker pair via a disagg-profile-handler that runs a decode-profile first, consults a 'decider' on how much of the prompt is cached on D, and only invokes the prefill-profile (selecting a P endpoint too) if the uncached suffix is large; both P and D endpoints belong to the SAME InferencePool, distinguished by the llm-d.ai/role label (values: prefill, decode, prefill-decode) which the prefill-filter/decode-filter plugins use to filter candidates -- and (2) Efficient KV Transfer, typically over RDMA via NIXL. The Routing Proxy Sidecar runs in each decode pod and reads the x-prefiller-host-port header (one or more prefill pod addresses, comma-separated/multi-value) set by the proxy/EPP; if present it executes the disaggregated path (send prefill request, capture KV transfer metadata, forward enriched request to local decoder), otherwise it proxies decoder-only. It documents TWO KV-transfer protocol implementations the sidecar must speak: vLLM's nixlv2 (default) -- a two-phase sequential protocol using kv_transfer_params and max_tokens=1, with fallback to decoder-only on prefiller server errors (5xx) but no retry on client errors -- and SGLang's sglang connector, a concurrent protocol using bootstrap_host/bootstrap_port/bootstrap_room parameters where prefill fires asynchronously (goroutine with context.WithoutCancel) while decode runs synchronously, coordinating out-of-band via the bootstrap room. NIXL is the only KV-transfer engine llm-d currently focuses on; it needs RDMA (InfiniBand or RoCE, both supported via UCX and UCCL backends; TCP-X and EFA supported by UCCL; libfabric supports IB only) for efficient transfer, falls back to slow TCP without RDMA (dev/test only), and NVLink transfer works only for local development since 'it cannot cross pod boundaries' in Kubernetes deployments. With GPUDirect RDMA, GPU memory is registered directly with the NIC so transfers bypass the CPU. `evergreen`

The pods (gaie-pd-epp, infra-pd-inference-gateway-istio, decode, prefill) all ran healthy (1/1) with valid HTTPRoute and a responsive gateway, but the P/D Coordinator Grafana dashboard showed all NIXL KV-transfer metrics as 'No Data' -- Avg KV Transfer Time, Avg MB per Transfer, Total KV Transfers all empty, and Failed KV Transfers=0 not because transfers succeeded but because none were attempted. Root cause: NIXL requires GPU-to-GPU transfer over RDMA (InfiniBand or RoCE) using ibv_reg_mr to pin GPU memory for zero-copy transfer between SEPARATE physical GPUs; on a single GH200 with prefill and decode pods time-sliced onto the same physical GPU, there is no RDMA path -- both pods share the same physical memory space and NIXL's transport layer cannot initialize, so the sidecar opens port 5600 but nothing moves. The llm-d pd-disaggregation guide documents this requirement explicitly (its inference-scheduling guide's default benchmark config targets 16 GPUs across 8 model servers) but it is easy to overlook because every other layer (pods, EPP, HTTPRoute, Prometheus) still looks healthy. Consequently the system silently collapsed back into aggregated serving with WORSE performance than plain aggregated serving: end-to-end latency was 6.5x higher, TTFT 3.7x higher, and inter-token latency (ITL) 3.5x higher (ITL rose from 5ms to 17.5ms) than the prior aggregated-serving baseline, because (1) gpu-memory-utilization was halved to 0.45 per pod, shrinking the KV cache budget and increasing evictions, (2) both pods time-slice-compete for the same physical GPU cycles, and (3) the EPP's Ready Pods count showed only 1 of 2 pods as ready -- the prefill pod, despite being healthy, was never receiving routed traffic (0% KV cache utilization, near-zero throughput), so the decode pod handled 100% of both prefill and decode work under a halved memory budget. The author proposes a 5-signal diagnostic checklist (NIXL metrics=No Data, Prefill Worker Utilization~0%, decode pod handles all throughput, Prefill TTFT=Decode TTFT identical, EPP Ready Pods less than total running pods) to detect this failure mode before assuming disaggregation is functioning. `evergreen`

- [[tokenlake-a-unified-segment-level-prefix-cache-pool]] — TokenLake: A Unified Segment-level Prefix Cache Pool — TokenLake (Peking University + StepFun) diagnoses three structural failure modes of instance-local cache-aware routing (the prefix-tree-per-instance model used by systems like llm-d's KV-cache-aware router, SGLang, Mooncake): (1) load imbalance -- instances with high prefix hit rates become memory-bandwidth over-utilized while cold instances sit idle, because the router can only route whole requests to whichever instance already holds the matching prefix tree; (2) redundancy -- to rebalance computation, hot shared prefixes (system prompts, shared documents) get replicated across multiple instances, wasting memory; (3) fragmentation -- because a full prefix must reside on one instance to form a contiguous prefix tree, memory slots scattered across instances cannot be pooled together. These problems compound under PD (prefill/decode) disaggregation, since prefill and decode instances have different memory-bandwidth profiles and must each separately hold the same prefix cache to avoid recomputation. TokenLake's fix decouples cache management from scheduling via a declarative interface (exposing query tensors, prefix caches, and cache-aware ops) and manages cache at sub-request segment granularity with a heavy-hitter-aware load-balancing algorithm, letting the scheduler dispatch elastically without needing to track prefix locality. On real-world workloads (CharacterAI/Kimi report 75-95% production hit rates as baseline context), TokenLake improves throughput up to 2.6x and 2.0x and cache hit rate up to 2.0x and 2.1x versus state-of-the-art cache-aware routing and cache-centric PD-disaggregation baselines respectively. `evergreen`

First systematic large-scale study of prefill/decode disaggregation design space: simulates hundreds of thousands of design points (model partitioning x traffic pattern x hardware config) using a proprietary datacenter-scale GPU performance simulator on Blackwell/FP4 systems, evaluating DeepSeek-R1 and Llama-3.1-70B.
