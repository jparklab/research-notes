Core design: 'host-centric' -- all KV data flows through CPU DRAM as the primary tier, with secondary tiers (filesystem, S3-compatible object storage via NIXL, or peer-to-peer RDMA) cascading from/promoting to that host copy; accelerator memory is never touched directly by secondary tiers. Operates on 'chunks' (default = one accelerator block; configurable via blocks_per_chunk). Host primary tier is a proper LRU/ARC cache, not a staging buffer -- evicted chunks survive in whichever secondary tier already received them. Reload path: scheduler checks host cache first; on miss, queries secondary tiers in configured order, returns RETRY while the tier promotes the chunk back to host. Different chunks of one request can be served by different tiers. Canonical host memory layout (page = one block of one layer, all KV heads across TP ranks gathered contiguously) means nodes with different TP/accelerator/attention-backend configs share KV data with no remapping. P2P tier explicitly states the tier itself does not choose which peer to pull from -- that is the orchestration layer's (e.g., llm-d router) job, driven through the request's kv_transfer_params; used both for classic prefill/decode disaggregation and cross-node load balancing (pulling chunks from an overloaded instance to one with spare capacity). KV events report which chunks were stored/evicted, from which tier, and with what locality (local vs remote) -- llm-d and Dynamo consume these to route requests to the instance most likely to have a cache hit, and llm-d additionally uses them to orchestrate P2P KV transfers between peers.
