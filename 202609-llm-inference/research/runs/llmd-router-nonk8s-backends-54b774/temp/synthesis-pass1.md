Customize llm-d at exactly one place — the `EndpointDiscovery` plugin interface — and reuse everything above it unchanged. That is the strategy, and llm-d's own code supports it more strongly than the project's front-door documentation does. The router's Kubernetes dependence is not diffused through the scheduling stack; it is concentrated in how the router *learns what exists*, plus a separable operations layer (leader-elected high availability, Helm packaging, custom-resource policy inputs, the prefill/decode sidecar's allowlist) that does not travel. Two decisions follow, and they are independent: **which discovery rung your backend estate needs** (a static file, a file rewritten by a generator, or a custom plugin), and **where the router process runs**, which is decided by your availability requirement rather than by your backend estate. One carve-out is mandatory: the prefill/decode sidecar is the single llm-d component you cannot reuse unchanged off Kubernetes. And one version correction governs day one: the nested discovery configuration key that current documentation teaches ships in no release yet.

## 1. llm-d Component Inventory and Kubernetes Coupling

### A. What llm-d actually is

llm-d is not one program. It is a control plane assembled from separately versioned components wrapped around inference engines it does not modify — a framing the project made explicit at v0.8 when it dropped its custom vLLM images in favour of upstream ones, calling the change "not just a packaging simplification — it is a statement about what llm-d is. The project is a control plane that wraps inference engines, not a distribution that replaces them" [[llm-d-v08-from-platform-to-control-plane-llm-d]]. Since v0.7 the routing tier is called the **llm-d Router**, "the functional combination of a Proxy and an Endpoint Picker (EPP)" — renamed because the old inference-scheduler name "conflicted with Kubernetes scheduling concepts and was too narrowly tied to the Gateway API" [[llm-d-v07-from-feature-introduction-to-production-hardening-llm-d]]. The Endpoint Picker (EPP) is a gRPC service the proxy consults once per request over Envoy's external-processing protocol; it holds all the routing intelligence and answers with a chosen backend expressed as an `ip:port` string. In a stock Kubernetes deployment it runs as an ordinary pod, sometimes two containers — a scheduler container running the picker plugins and a tokenizer container tracking prefix-cache state, sharing state over ZeroMQ [[how-llm-d-routes-model-inference-traffic-on-amazon-eks-red-hat-developer]].

That decomposition is what makes this question answerable. A control plane's coupling to Kubernetes lives in how it learns about and governs backends, not in how it talks to them.

### C. The split the table draws

Count the rows. Everything on the request path — parse, admit, filter, score, pick, emit a header — is Kubernetes-free by construction, because the protocol it terminates in was specified in terms of addresses. Everything that tells the router what exists, what matters, and who is in charge was built on controller-runtime reconcilers, because that was the cheapest correct implementation on Kubernetes. Coupling tracks the control plane's governance surface, not its data surface. No single source states that sentence; it is what the inventory entails when the coupling column is read against the function column.

The practical consequence is that a migration off pods is not a port. It is the substitution of four specific inputs: endpoint enumeration, endpoint health, coordination between router replicas, and scrape-target discovery. Three of those have cheap non-Kubernetes answers. One — enumeration — is where your engineering goes.

Two entries deserve emphasis because they are routinely underweighted, and both are operations rather than routing. High availability binds a Kubernetes primitive in every documented shape: a Lease object for leader election, or a StatefulSet with a headless Service for the priority-routing variant [[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]]. And the disaggregation sidecar's only anti-SSRF control takes input exclusively from an `InferencePool` resource and the pods its selector matches, with no static, CIDR, or flag-based alternative anywhere in the implementation [[allowlistgo]]. Section 5 turns that into a concrete off-Kubernetes obligation.

One expectation to correct before going further: the router repository's landing page is silent on all of this. The capability is real and documented in `docs/discovery.md`, but it is not marketed at the front door, and teams evaluating llm-d from its README alone will conclude wrongly that this strategy is impossible.

## 2. How the llm-d Router Discovers and Tracks Backends Today

### A. The default path, at code level

Discovery is the process by which the router builds and maintains its list of candidate backends. By default the EPP watches an `InferencePool` object and the pods its label selector matches [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]. The admission logic in the pod reconciler is startlingly thin: the event filters admit a pod when the datastore's pool labels match the pod's labels, and the reconcile-time gate deletes it unless the pod is non-terminating, still label-matching, and carries the aggregate `PodReady` condition. Downstream, `pod.Status.PodIP` is consumed verbatim, with no emptiness or format validation, and there is no check on node name or pod phase [[pod_reconcilergo]]. The EPP's permissions are correspondingly narrow — get, list and watch on pods and the inference resources, no write access [[how-llm-d-routes-model-inference-traffic-on-amazon-eks-red-hat-developer]].

That thinness is load-bearing, so state the inference explicitly. Sources establish (a) that the admission path checks only label match plus aggregate readiness [[pod_reconcilergo]], and (b) that the datastore entry any discovery source produces is an endpoint-metadata record carrying an identifier, address, port, metrics host and free-form labels [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]. Together they entail that nothing downstream of admission can tell a pod-sourced endpoint from a file-sourced one. The Kubernetes-ness of a backend is erased at the datastore boundary.

It also kills an entire family of shims before they start. `InferencePool` selects pods by label and target port — it is similar to a Service with a selector but is not one [[inferencepool-kubernetes-gateway-api-inference-extension]] [[beyond-gateway-inference-traffic-control-practice-with]]. The picker never reads Services or EndpointSlices. Hand-authoring a selectorless Service plus EndpointSlice is the officially documented route for exposing external endpoints to kube-proxy [[endpointslices-kubernetes]], and it routes nothing whatsoever through the scheduler you came for. It is a category error rather than a harder path, and it fails invisibly when attempted: a documented Kubernetes issue shows a hand-authored EndpointSlice with a named port against an unnamed Service port producing a silent kube-proxy reject while the object listed correctly in tooling [[both-endpoints-and-endpointslices-not-working-with-service-abstraction-for-exter]].

### B. Where exactly the pod assumption lives

Four places, and only four.

1. **Runner startup.** On the default path the runner fetches a cluster configuration and stands up a controller-runtime manager; the discovery-plugin path is a separate branch that skips manager setup entirely [[filediscovery-plugin-44-wiring-into-the-runner-by-ezrasilvera-pull-request-1218]]. With a plugin configured, the EPP "does not call `ctrl.GetConfig()` or start a controller manager" and "does not require an `InferencePool` CRD or any K8s RBAC," while "all scheduling, request control, and metrics collection behaviour is unchanged" [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]].
2. **Pool identity.** The `InferencePool` resource declares the selector and target ports, named by the `--pool-name` and `--pool-namespace` flags. In file-discovery mode those flags are demoted to labels: they "are not Kubernetes references in file-discovery mode; they are only used as labels in the EPP's metrics and log lines" [[llm-dguidesno-kubernetes-deployment-at-main-llm-dllm-d-github]].
3. **Health gating.** Aggregate pod readiness, including custom readiness gates, is what keeps unready workers out of the pool — a mechanism a custom source must replicate itself [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]].
4. **Custom-resource policy.** The `InferenceObjective` and `InferenceModelRewrite` reconcilers, and any Kubernetes notification source in the data layer, simply do not bind [[readmemd]].

Notice what is not on that list: scoring, filtering, picking, metric scraping, KV indexing, flow control, the ext_proc server, draining, or the wire protocol.

One residual Kubernetes-ism survives in the type system. Endpoint identity is a namespaced-name value, and the godoc still describes the metadata struct in terms of pod state [[datalayer-package-sigsk8siogateway-api-inference-extensionpkgeppframeworkinterfa]]. A reviewer flagged exactly this during the interface's merge — "I wonder if this is not too k8s centric and we should include an explicit `UniqueID`" — and the author agreed while deferring the change [[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]]. For a non-pod backend this is a naming tax, not a blocker: mint a stable two-part identity (job name plus partition, service identifier plus datacenter) and move on.

### C. The wire is already pod-free

The proxy never learns about pods. The Endpoint Picker Protocol, versioned v1.0.0 and marked implemented as of 2025-07-29, specifies that the EPP returns its choice in a destination-endpoint header and matching dynamic metadata, and that "the value of the header or metadata entry MUST contain at least one endpoint in `<ip:port>` format or multiple endpoints in `<ip:port>,<ip:port>,...` format" [[gateway-api-inference-extensiondocsproposals004-endpoint-picker-protocol-at-main]]. Off Kubernetes the flow is identical and wired statically: client to an Envoy listener, external processing over gRPC to the EPP, then an `ORIGINAL_DST` cluster reading the header and forwarding to the chosen worker's address and port [[llm-ddocsinfrastructureno-kubernetes-deploymentmd-at-main-llm-dllm-d-github]] [[distributed-llm-inference-with-llm-d-moncef-abboud]]. Client spoofing of that header is closed: system-owned headers are excluded from the passthrough loop, with a unit test asserting that an injected attacker address is replaced by the picker's own computed target [[fix-harden-header-sanitization-and-handling-logic-by-lukeavandrie-pull-request-2]] [[2025diff]].

### D. What discovery does not supply

On Kubernetes, an endpoint leaves the datastore because kubelet flipped a readiness condition and a reconciler noticed. Off Kubernetes, nothing supplies that signal. The discovery interface carries no liveness field and the framework applies no health gate; a plugin is solely responsible for upserting only endpoints it believes healthy, and the readiness channel that gates request serving says nothing about any individual endpoint [[filediscovery-plugin-44-wiring-into-the-runner-by-ezrasilvera-pull-request-1218]]. Worse, file reload failures are logged non-fatally and leave the previous datastore state in place, so the failure mode is stale-but-present endpoints rather than evicted ones [[llm-d-routerpkgeppframeworkpluginsdatalayerdiscoveryfile-at-main-llm-dllm-d-rout]]. Because the precise prefix producer installs a per-endpoint subscriber on add and tears it down only on delete, a backend that dies without anyone calling delete keeps both its live subscriber and its cache-index entries — so the scorer keeps preferring a dead machine [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcacheex]]. No source states that outright; it follows from the extractor's add-and-delete lifecycle combined with the documented statement that removal is the surrounding orchestrator's job off-cluster [[llm-ddocsinfrastructureno-kubernetes-deploymentmd-at-main-llm-dllm-d-github]]. Section 7 makes health gating the first design rule for that reason.

## 3. Extension Seams in the Router for Non-Pod Backends

### A. The interface

A plugin seam is a named Go interface the router will load an implementation of at startup, selected by a string in the configuration file. `EndpointDiscovery` is that seam for backend enumeration. The contract is three methods — `Start(ctx, notifier)`, `Ready() <-chan struct{}`, and a type name — with the plugin pushing `notifier.Upsert` and `notifier.Delete` calls into the shared datastore [[llm-d-routerpkgeppframeworkinterfacedatalayerdiscoverygo-at-main-llm-dllm-d-rout]]. Three obligations attach, and each is a common source of subtle bugs:

1. **Enumerate before watching.** Implementations "SHOULD enumerate all currently known endpoints via `notifier.Upsert` before entering the watch loop, to avoid serving an empty datastore at startup," with a carve-out only for watch mechanisms that guarantee no missed events [[llm-d-routerpkgeppframeworkinterfacedatalayerdiscoverygo-at-main-llm-dllm-d-rout]].
2. **Close the readiness channel exactly once, after the first successful sync — and zero endpoints is a valid outcome.** Never gate readiness on a non-empty set. The runner gates the ext_proc server and the health service on that channel but deliberately leaves `/metrics` ungated, so a slow startup stays observable [[filediscovery-plugin-44-wiring-into-the-runner-by-ezrasilvera-pull-request-1218]].
3. **One goroutine drives the notifier.** It is explicitly not goroutine-safe: "an `Upsert` followed by a `Delete` for the same endpoint must arrive in that order or the endpoint will be incorrectly left in the datastore" [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]].

The interface author's stated design intent names this exact use case. In the merge review he wrote that "we want K8s, file, Slurm, and Ray discovery all as plugins" precisely so the shared data layer never gets "contaminated with infrastructure-specific code (`ctrl.Manager`, fsnotify, etc.)" [[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]].

### B. The shipped reference implementation and its ceilings

`file-discovery` is the only non-Kubernetes implementation in the tree, and it is also the template you will copy. It reads a YAML or JSON file, validates each entry, upserts it, and with file watching enabled reattaches its fsnotify watcher after an atomic rename or a ConfigMap-style symlink swap, deleting endpoints absent from the new load [[llm-d-routerpkgeppframeworkpluginsdatalayerdiscoveryfile-at-main-llm-dllm-d-rout]] [[plugingo]]. Its limits are the thresholds against which your estate must be measured: the file is capped at 1 MiB; `address` must be a literal IPv4 value, with hostnames unresolved and IPv6 rejected outright; metrics are scraped from the same address and port that serves inference; a single bad entry is skipped but an unparseable file aborts startup [[readmemd]] [[file-discovery-34-add-filediscovery-plugin-with-yamljson-file-loading-and-fsnoti]]. A custom plugin escapes all three addressing limits, because it populates endpoint metadata directly and the metrics host is a first-class field defaulting to the serving address only when left empty [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]].

Two shipped precedents prove the endpoint model already tolerates non-pod shapes. The multi-cluster plugin family exists "for a cluster-scoped EPP whose candidate endpoints are clusters," and its configuration "follows the same format as the pod file discovery, except an `address` may be a hostname," with per-entry metrics address and port labels for out-of-band scraping [[llm-d-routerpkgeppframeworkpluginsreadmemd-at-main-llm-dllm-d-router-github]]. The variant is implemented by injecting a different address validator into the same plugin, deliberately so a variant can loosen it [[plugingo]]. Upstream has therefore already shipped a discovery plugin whose endpoints are not pods, whose addresses are not pod IPs, and whose metrics do not live at the serving port — through the same configuration field you will use.

### C. Registration, and the objection it invites

`docs/discovery.md` contains a section titled "Writing a custom discovery plugin" giving a complete skeleton: implement the interface, declare a plugin-type constant, expose a factory, and "register the factory in the runner before calling `Run`" [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]. The registry makes that work out of tree. It is a plain exported package-level map mutated through exported registration functions, with no internal-use disclaimer and no duplicate-key guard [[registrygo]]. Because Go runs every package's initializer before `main`, a blank import of your plugin package lands your factory in that map before the runner registers its own in-tree plugins [[runnergo]]. `cmd/epp/main.go` is a thin wrapper over `runner.NewRunner().Run(ctx)` [[maingo]], and a recursive listing of the repository confirms the structural precondition: the runner and both framework interface packages sit outside any `internal/` path, and the module carries no replace directives [[main]] [[gomod]].

**The strongest objection, stated at full strength.** You would be proposing to become the first person ever to import the runner package from outside the repository, against a young interface whose configuration shape has changed three times in four months, in a framework with no panic recovery on any plugin call path. The only plugin-authoring tutorial the project ships instructs you to edit the runner's unexported in-tree registration function [[llm-d-routerdocscreate_new_filtermd-at-main-llm-dllm-d-router-github]]. The contributing guide mentions third-party plugins nowhere [[llm-d-routercontributingmd-at-main-llm-dllm-d-router-github]]. A repository-wide issue search for out-of-tree plugins returns essentially nothing [[issues-llm-dllm-d-router-github]], and the single substantive hit — opened 2026-07-21, still needs-triage with zero comments — proposes as one of three options that in-tree plugins be declared the supported surface and that out-of-tree plugins which panic take the process down [[framework-define-a-panic-isolation-posture-for-plugin-extension-points-issue-210]]. Registration itself overwrites silently: whichever initializer runs last wins, with no panic, warning, or log line [[registrygo]].

**The answer, in three moves.** First, a scoping distinction resolves the documentation half of the objection. Two different documents were being conflated: the in-tree instruction lives in the *scheduling filter* tutorial, while `docs/discovery.md` teaches the register-before-run pattern for *discovery* plugins without saying where that call must live [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]] [[llm-d-routerdocscreate_new_filtermd-at-main-llm-dllm-d-router-github]]. Registering a custom discovery plugin is documented upstream. Only the packaging choice — doing it from your own `main()` rather than editing the repository — is an inference, and it is a mechanical one.

Second, the fork alternative dodges none of it. A fork inherits the same interface churn, the same missing panic recovery, and the same absence of precedent, and adds rebase conflicts against the exact subsystem that is moving. Out-of-tree strictly dominates.

Third, the residual risks are mitigable at the plugin level and cost a day: namespace the plugin-type string against the silent overwrite, wrap your own `Start()` goroutine in a recover because the framework provides none, pin a tagged release, and run a scheduled build against upstream `main` so interface drift surfaces in continuous integration rather than in production. The honest position is that this is a sanctioned mechanism that is unprecedented in the wild — concede the second half plainly and price it, rather than arguing it away.

One gate to remember: every plugin carries a stability level assigned at registration, and Alpha plugins require an experimental-plugins flag or the EPP refuses to start, with all in-tree plugins currently classified Alpha or Beta [[llm-d-routerpkgeppframeworkpluginsreadmemd-at-main-llm-dllm-d-router-github]].

### D. The seams you should not need

Metric scraping is a data-source and extractor pair over plain HTTP, keyed off Prometheus metric names the engine already exposes [[distributed-llm-inference-with-llm-d-moncef-abboud]]. The endpoint-extractor interface is how the KV-event path attaches to discovery; you consume it rather than implement it. Peer discovery is a structurally identical plugin interface for the router's own replicas, whose documentation names file-based discovery as a first-class feeder but whose cross-replica syncer is still described as future work [[peergo]] [[llm-d-routerdocspeer-discoverymd-at-main-llm-dllm-d-router-github]]. The cross-replica syncer itself is an opt-in surface that aggregates a plugin's per-endpoint attribute across replicas — and the precise prefix producer pointedly does not implement it, which Section 7 turns into an argument [[cross_replica_syncergo]]. Finally, the Helm charts expose no discovery knob, but structured plugin configuration, raw configuration passthrough, and extra volume mounts make the hybrid topology reachable without forking the chart [[llm-d-routerconfigchartsreadmemd-at-main-llm-dllm-d-router-github]].

## 4. Upstream State: Proposals and Work on Non-Pod and External Endpoints

### A. The chain that landed

Non-Kubernetes operation is not a rumour; it is a tracked, dated, completed release goal. The v0.8 goals issue lists it under the reinforcement-learning working group with a named owner and a design proposal, followed by the merged sequence: the pluggable discovery interface (#908), the store plumbing (#1080 and #1081), the FileDiscovery plugin (#1135), a rename (#1154), runner wiring (#1218), documentation corrections (#1338), a gRPC-parameter fix (#1362), flow control wired into file-discovery mode (#1368), and the endpoint-notification fix (#1404) [[v08-release-goals-mid-june-issue-1520-llm-dllm-d]]. The motive is stated in the same thread: non-Kubernetes mode enables llm-d in Slurm and research labs without Kubernetes. The release record confirms delivery — FileDiscovery shipped as a key feature of llm-d-router v0.9.0 on 2026-06-23, and the umbrella project's capability table lists non-Kubernetes mode as new [[releases-llm-dllm-d-router]] [[releases-llm-dllm-d]]. The v0.8 blog framed it under the heading of moving beyond Kubernetes for reinforcement-learning and Slurm workloads, stating that every previous release assumed Kubernetes and this one breaks that assumption [[llm-d-v08-from-platform-to-control-plane-llm-d]].

The upstream debate that produced it is worth reading because it bounds what arrives next. The Gateway API Inference Extension issue proposing a zero-Kubernetes mode was motivated by batch and reinforcement-learning customers, and the winning counter-proposal was precisely to "add a discovery layer... similar to scheduler pluggability" — which is literally what shipped [[standalone-epp-issue-1838-kubernetes-sigsgateway-api-inference-extension]]. In the parallel agentgateway thread a maintainer's initial dismissal was withdrawn once the batch rationale landed, the decisive point being that the picker protocol does not change between modes [[inference-support-agentgateway-as-a-standalone-provider-issue-620-agentgatewayag]].

### B. What did not land

PR #1007 would have delivered two Kubernetes-native discovery plugins, migrating the existing pod-watching logic into the new framework [[discovery-plugins-k8s-and-file-based-endpoint-discovery-by-ezrasilvera-pull-requ]]. It was **closed unmerged** after a maintainer asked for it to be broken up, with the author's own closing note pointing at the file-discovery PRs as the replacement. No Kubernetes discovery-plugin directory exists at HEAD; only the file one does, and the module's published package index at v0.10.0 lists exactly one exported discovery backend [[main]] [[llm-d-router-module-githubcomllm-dllm-d-router-go-packages]].

Two consequences follow. Describe Kubernetes discovery through the pod reconciler, not through that PR. And accept the honest cost: there is no watch-based discovery implementation anywhere in the repository to copy. The reference implementation you will copy is a poll-and-diff plugin, which conveniently is also what you should build first.

The same pattern repeats one layer up. Peer-discovery infrastructure merged on 2026-08-16, one day before the v0.10.0 tag, so that release does ship the pre-consolidation peer-discovery configuration field — deliberately with no concrete mechanism [[feat-epp-peer-discovery-infrastructure-by-evacchi-pull-request-2341-llm-dllm-d-r]]. The follow-up that supplies one is a controller-runtime reconciler watching the router deployment's own pods, opened 2026-08-21 and still open at Alpha stability [[feat-pod-watch-peer-discovery-plugin-by-evacchi-pull-request-2501-llm-dllm-d-rou]]. The newest discovery-adjacent work in the repository is Kubernetes-native.

### C. The audited absence

Across the pull-request history, **no Consul, etcd, Slurm, Ray, or cloud service-discovery plugin has been proposed or merged**. Every discovery contribution targets either a flat file or a Kubernetes primitive. The project's own roadmap ranks four strategies and puts the dynamic one in the future bucket: a static file, a generator script plus a static file, a generator plus file watching, and — as future work — "a dedicated `SlurmDiscovery` or `RayDiscovery` plugin against the same `EndpointDiscovery` interface, talking to the orchestrator directly with no file in the loop" [[no-kubernetes-no-problem-llm-d-now-runs-anywhere-llm-d]]. Read that correctly. It is not evidence the plugin is unwelcome; it is evidence that the first three tiers cover enough cases that nobody has needed the fourth yet. It also tells you there is no upstream branch to wait for.

### D. The gateway tier is moving the other way

Every conformant gateway data plane reaches backends only through an `InferencePool` that selects pods by label: Istio requires the extension resources plus a pod-label selector [[istio-kubernetes-gateway-api-inference-extension]], NGINX Gateway Fabric selects "from a pool of ready pods designated by the assigned `InferencePool`'s Selector field" [[gateway-api-inference-extension-nginx-documentation]], and kgateway's support auto-enables only when the resources exist in-cluster [[add-initial-gateway-api-inference-extension-support-issue-10411-kgateway-devkgat]]. Standalone mode is not non-Kubernetes mode either: the chart work that delivered it was retitled during review, its author scoping a picker without any custom resource as a later refactor [[helm-support-for-sidecar-injection-in-epp-by-capri-xiyue-pull-request-1821-kuber]], and the agentgateway standalone path still generates a Kubernetes Service as the addressing anchor [[add-standalone-agentgateway-proxy-support-by-danehans-pull-request-2882-kubernet]]. Meanwhile kgateway abandoned an Envoy load-balancer refactor not on technical merit but because the community decided to deprecate its Envoy data plane for AI features [[inference-refactor-plugin-to-use-override_host-lb-issue-11824-kgateway-devkgatew]], and llm-d followed by deprecating kgateway in favour of agentgateway [[refresh-support-for-kgateway-agentgateway-gie-and-gw-api-by-danehans-pull-reques]].

The synthesis a reader should carry forward: upstream is committed to platform-neutral routing and Kubernetes-first operations simultaneously, and has been consistent about both. Bet on the discovery seam. Do not bet on upstream soon supplying non-Kubernetes coordination, packaging, or observability. A deployment that stays on plain Envoy with llm-d's reference configuration is insulated from the gateway-tier churn; one that couples tightly to a specific gateway's behaviour is not.

## 5. Non-Pod Backend Types and What Each Requires from the Router

### A. The universal contract

Whatever the backend is, it must satisfy four things, all protocol-level rather than platform-level: an OpenAI-compatible HTTP endpoint at a routable address and port; a Prometheus metrics endpoint the router can scrape for queue depth, running requests and KV-cache utilisation, with engine-specific metric names selected by a label [[gateway-api-inference-extensionsite-srcguidesepp-configurationconfig-textmd-at-9]]; something that tells the router when it appears and disappears; and network reachability from the proxy for traffic and from the router for metrics and, optionally, KV events. Nothing in that list mentions Kubernetes. Scrape-target discovery is the cheapest of the substitutions and should not be counted as a loss: llm-d's own no-Kubernetes guide ships a plain static scrape configuration pointed at the router's metrics port and each worker's metrics endpoint, and PodMonitor is an operator convenience, not a routing input [[llm-dguidesno-kubernetes-deployment-at-main-llm-dllm-d-github]] [[metrics-llm-d]].

### B. Per-estate requirements

| Backend estate | Discovery rung | Health source | Notable obligation |
|---|---|---|---|
| Fixed bare-metal or VM rack | Static file | External health agent rewrites the file | Firewall must allow the router outbound to each host's serving and event ports |
| Docker / Podman / Nomad | File plus generator, or a custom plugin | Runtime health checks feed the generator | Host networking or explicit published ports |
| Slurm allocation | File plus generator (`scontrol show hostnames`), later a plugin | Job state | Router lifetime tied to the job; set the pool-namespace flag explicitly |
| Ray cluster | File plus generator (`ray.nodes()`), or a plugin | Actor liveness | Actor churn drives the poll interval |
| Service registry (Consul, etcd, cloud) | Custom plugin | Registry-native health filtering | Poll or long-poll loop plus identity synthesis |
| Remote Kubernetes clusters | `multicluster-file-discovery` | Peer cluster gateway health | Hostnames allowed; separate metrics host supported |
| Serverless GPU providers | Custom plugin, high churn | Provider API | Cold starts break saturation assumptions |
| Managed APIs (OpenAI, Bedrock, Gemini) | **Not the router's job** | Provider SLA | Route at the AI-gateway tier instead |

The managed-API row deserves its committed reading rather than a hedge. An external provider endpoint exposes none of the state the scheduler exists to exploit — no queue depth, no KV-cache utilisation, no KV events — so putting it in the pool converts every scorer into a constant and every routing decision into noise. Every credible pattern in the field puts external providers at a gateway tier above or beside the inference gateway, whether as a separate backend block or a proxy with a static model list [[routing-agent-traffic-is-really-three-decisions-aks-engineering-blog]] [[centralized-routing-for-external-and-self-hosted-llms-on-openshift-ai-red-hat-de]]. Keep the pool homogeneous.

### C. The KV-event path, where the thesis is won

The precise prefix-cache scorer is llm-d's flagship capability and the natural place for a skeptic to expect Kubernetes coupling, because the Kubernetes guide describes it in pod terms: each vLLM or SGLang pod launches with a KV-events configuration publishing over ZeroMQ on `tcp://*:5556` under the topic `kv@$(POD_IP):$(POD_PORT)@<model>`, binding its own publisher socket, while newer GPU vLLM additionally binds a replay socket on port 5559 retaining the last 10,000 batches so a restarted router rebuilds its index without waiting for traffic [[llm-dguidesprecise-prefix-cache-routingreadmemd-at-main-llm-dllm-d-github]].

The code shows that description is engineering, not gloss. The precise producer's extractor implements the generic endpoint-extractor interface, and its documented behaviour is to process "endpoint lifecycle events emitted by the endpoint-notification-source: add/update installs a per-pod ZMQ KV-events subscriber, delete tears one down" [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcacheex]]. Inside, the dial target is built arithmetically from metadata and the index key is a separate literal string formed from address and port; the same construction appears on delete, clearing index entries, and again in the scoring path [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcachepr]]. The namespaced name is used only as the subscriber manager's bookkeeping key. A bug report written for an entirely different purpose corroborates it from a third angle, describing per-endpoint subscribers "keyed on endpoint address/port" through that same notification source [[endpoint-metadata-updates-do-not-trigger-endpoint-notification-events-issue-1403]].

There are therefore two identity spaces, not one that must reconcile. Routing correctness rides on address and port, which every discovery plugin populates identically. Whatever populates those fields — a pod watch, a YAML file, your Consul plugin — feeds the same path. This is the single strongest affirmative finding in the whole analysis, and it is triangulated: the KV producer, the flow-control configuration surface, and the runner's own wiring each arrive at platform-neutrality independently.

It matters because prefix-cache routing is what you are buying. Under round-robin across eight replicas a shared system prompt is seen by any given replica only about 12.5 percent of the time, so per-replica hit rates approach zero and get worse as you scale [[gke-inference-gateway-kv-cache-aware-llm-routing-explained-spheron-blog]]. Upstream-reported benchmarks on eight vLLM replicas across sixteen H100 GPUs put P90 time-to-first-token falling from roughly 35 seconds to roughly 120 milliseconds with throughput up 151 percent [[intelligent-inference-scheduling-with-llm-d-on-red-hat-ai-red-hat-developer]], and a companion write-up reports precise scheduling at 8,730 output tokens per second against 4,429 for cache-blind routing [[kv-cache-wins-you-can-see-from-prefix-caching-in-vllm-to-distributed-scheduling]]. Those figures are vendor-reported and not independently reproduced [[best-of-both-worlds-cloud-native-ai-inference-at-scale-using-kserve-and-llm-d-ks]]; treat the magnitudes as indicative and the direction as corroborated.

Two operational notes attach. The router dials outward to each backend's event port, so it needs reachability to that port and not merely to the serving port. And the one genuine gap is data-parallel multi-rank engines: the dial port is the base socket port plus a rank index, and the file schema carries no rank field, so every file-discovered endpoint stays at rank zero [[readmemd]]. For single-rank backends that is exactly right; for multi-rank engines it is a real gap and a second reason to write the custom plugin, which can set the field directly. A simpler centralised mode also exists where per-endpoint subscription is unwanted: the standalone KV-cache library documents a static endpoint mode that binds a local socket and requires no cluster API at all [[llm-d-kv-cachedocsconfigurationmd-at-main-llm-dllm-d-kv-cache-github]].

### D. The one component you cannot reuse unchanged

Prefill/decode disaggregation splits a request so one engine computes the prompt's KV cache and another generates tokens. Pairing itself is decentralised by design — the first time a decoder sees an unknown prefiller it performs a background handshake, with no centralised service-discovery plane required — and role selection is just labels that file discovery sets natively [[networking-for-distributed-inference-in-llm-d-llm-d]] [[pd-disaggregation-llm-d]].

The security model is what does not travel. The routing sidecar forwards a request's prefill leg to whatever host and port a request header names. Its anti-SSRF protection is off by default; when enabled it "watches a specific `InferencePool` resource and maintains an allowlist of valid prefill targets based on pods matching the InferencePool selectors," returning 403 to anything else [[github-llm-dllm-d-routing-sidecar-incubating-pd-sidecar-for-llm-d-github]] [[allowlistgo]]. There is no static, CIDR, or flag-based alternative, and enabling it additionally requires cluster role bindings for pool and pod watches [[featsidecar-implement-ssrf-protection-with-inferencepool-host-port-allowlist-by]]. With protection off the allowlist check returns true unconditionally and the reverse proxy dials whatever it is handed [[proxygo]] [[chat_completionsgo]]. This is not hypothetical: the original disclosure in July 2025 demonstrated an external caller forcing the sidecar to forward a prefill body to an arbitrary internal address [[potential-ssrf-via-x-prefiller-url-or-x-prefiller-host-port-header-issue-242-llm]]. And the allowlist is a weaker net than it appears even when enabled — an open issue shows with a captured reproduction that it stores bare addresses without ports while the check strips the port from its input, so an allowlisted host with an attacker-chosen port passes [[pd-sidecar-allowlist-stores-only-pod-ip-not-hostport-issue-979-llm-dllm-d-router]].

The upstream threat model already puts the primary control elsewhere and that control is portable: the picker clears any client-supplied prefill header before setting its own, a fix whose author noted the extension protocol supports only set-header mutations so clearing was the best available [[clear-prefill-target-header-if-set-in-incoming-request-by-elevran-pull-request-2]]. But it protects only the path through the picker and does nothing for a caller with direct network reach to the sidecar port.

**The off-Kubernetes obligation is therefore a network-isolation requirement plus transport security, not a Kubernetes requirement.** Make the sidecar's port reachable only from the trusted gateway path by firewall, security group, or mesh policy, and enable prefill TLS, which is ordinary Go TLS configuration with no cluster certificate-authority dependency [[tlsgo]] [[optionsgo]]. State that as a standing requirement wherever disaggregation is used, not as a risk to review later.

### E. The one functional loss

Per-request priority via `InferenceObjective` is the single genuine gap. The objective header names a Kubernetes resource; off-cluster the reconciler never starts and lookups return nil, so every request lands in the default band [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]] [[epp-http-headers-reference-llm-d]]. Everything around it is fine. Bands, fairness policies, ordering policies and the saturation detector are static YAML read once at startup [[configuration-llm-d]]. Tenant fairness is a bare header string defaulting to a standard flow, and missing objectives default to priority zero while only sub-zero priorities are sheddable [[llm-d-flow-control-priority-queuing-for-shared-gpu-inference-red-hat-developer]]. Explicit model selection already has a shipped header alternative documented as the substitute for the rewrite resource; only weighted canary splitting needs logic, and it belongs at the gateway tier where something can make the weighted choice and set that header [[epp-http-headers-reference-llm-d]]. If you need priority tiers, the fix is a small static or file-backed admitter plugin. If you do not, skip it — declining that plugin is the single most effective way to keep your custom surface to one component.

## 6. Candidate Strategies Compared

### A. The field

Seven distinct approaches are on the table, and they are not equally serious. Two are category errors, one answers a different question, one is strictly dominated, and three form the actual ladder.

| Strategy | llm-d reuse | Maintenance burden | Feature parity | Ops complexity | Verdict |
|---|---|---|---|---|---|
| **A. Static endpoints file** | Total above the seam | Near zero | Full minus custom-resource inputs | Lowest | **Start here** — fixed estate, near-zero churn |
| **B. File plus external generator** | Total above the seam | One script | Same as A | Low | **Default for most estates** — Slurm, Ray, VM fleets |
| **C. Out-of-tree discovery plugin in a downstream `main()`** | Total (same `Run()` path) | One plugin plus a version pin and CI | A, plus rank index, hostnames, separate metrics hosts | Moderate | **The escalation, on named gates** |
| **D. In-tree fork** | Same as C | C **plus** perpetual rebase | Same as C | Moderate-high | **Strictly dominated by C** |
| **E. Embed llm-d libraries in a hand-built router** | Partial | Highest — reimplement ext_proc, config, draining, health | Degrades over time | High | **Reject** for discovery-only needs |
| **F. Kubernetes object shims (EndpointSlice, virtual pods)** | None reached | — | The picker never reads EndpointSlices | — | **Reject as a category error** |
| **G. Convert the estate to real pods (Slinky)** | Total, zero router code | Operate a Slurm-on-Kubernetes operator | Full, including policy resources and a working allowlist | High — fleet custody moves | **A different question** |
| **H. A router that ships non-pod discovery natively** | None of llm-d's picker | Vendor's | Loses llm-d's plugin depth | Low | **The real alternative, and what makes C safe** |
| **I. Upstream the plugin** | Total if merged | Review latency outside your control | Full | Low eventually | **In parallel with C, never instead** |

### B. Dispatching the shims

Making a non-pod backend look like a Kubernetes endpoint targets the wrong machinery, for the reason established in Section 2: pool membership lists pods by label selector and never consults Services or EndpointSlices. You can author perfect EndpointSlices all day and the picker will never see them.

Virtual-kubelet is architecturally different, and the distinction is worth stating precisely. It produces genuine pod objects, and since admission is only label match plus aggregate readiness with the pod IP consumed unvalidated, a correctly-labelled virtual pod would be admitted [[pod_reconcilergo]] [[github-virtual-kubeletvirtual-kubelet-virtual-kubelet-is-an-open-source-kubernet]]. The blocker is networking, not admission. interLink, the production HPC provider in this space, states in its own documentation that long-running services are explicitly not a target — it is "optimized for tasks that have a defined start and end, rather than persistent services exposing intra-cluster communication endpoints" [[introduction-interlink]] — and its Slurm plugin's networking is an SSH-tunnelled egress proxy to a login node, outward-facing by construction [[github-interlink-hqinterlink-slurm-plugin-github]]. An inference gateway must open connections into the backend. The shim is architecturally admissible and operationally dead. Keep it only as a narrow exception for cross-cluster pod-networking providers. And building a provider from scratch means implementing the full pod lifecycle and node heartbeat contract to accomplish what a three-method interface accomplishes directly.

### C. Converting the estate is a governance decision, not an engineering one

Strategy G deserves a fair hearing because its evidence is strong. NVIDIA and SchedMD's Slinky operator represents each Slurm daemon as a custom resource and manages them as pods, surfacing Slurm node states as native pod conditions, supporting scale-to-zero and drain-before-terminate, and running in production at NVIDIA on clusters exceeding 1,000 worker nodes and 8,000 GPUs with collective-communication performance matching non-containerised Slurm [[running-large-scale-gpu-workloads-on-kubernetes-with-slurm-nvidia-technical-blog]] [[github-slinkyprojectslurm-operator-run-slurm-on-kubernetes-a-slinky-project-gith]]. Slurm workers that are real pods carry real pod IPs and match a label selector, so the stock router routes to them with zero customisation, keeping leader-elected high availability, the policy resources, operator-managed scraping, and a sidecar allowlist that actually functions because a real pool exists.

The cost is custody of the fleet's scheduling. That is a governance decision, and it should be made explicitly rather than defaulted past. But it answers a different question from the one asked here: it changes what the backends are rather than what the router supports. If the organisation will not hand Kubernetes the scheduler, G is off the table and the ladder below is the answer.

### D. Steel-manning the strongest objection

The strongest case against this report's recommendation is not any of the shims. It is this: *non-pod support is a shipped, supported, tested feature in several competing routers, so stop paying for llm-d's Kubernetes-shaped assumptions and use one of them.* NVIDIA Dynamo makes the discovery backend a first-class configuration choice, with etcd or NATS required specifically for Slurm-class distributed deployments and a plain file backend otherwise, and its discovery consumer separates a full instance listing from the incremental event stream — the same list-then-watch shape you would be writing by hand [[github-ai-dynamodynamo-a-datacenter-scale-distributed-inference-serving-framewor]] [[watcherrs]]. It even ships a standalone endpoint picker explicitly designed to add KV-aware routing to a fleet of upstream vLLM pods without migrating them [[kv-aware-routing-on-kubernetes-nvidia-dynamo-documentation]]. vLLM production-stack's discovery abstraction requires one method and ships a static implementation pairing a fixed topology with a background health-check thread that filters unhealthy URLs — precisely the health gate llm-d asks you to write [[service_discoverypy]]. vLLM Router ships static worker URLs by default [[github-vllm-projectrouter-a-high-performance-and-light-weight-router-for-vllm-la]].

Every clause of that is true, and the objection concedes the wrong thing. Non-pod support is table stakes in those routers; llm-d's plugin depth is the asset you are buying — precise prefix-cache routing, load and queue awareness, saturation-gated admission, priority and fairness queuing, prefill/decode profile handling, predicted-latency scoring. Competing throughput claims exist on both sides without published harnesses [[vllm-router-a-high-performance-and-prefilldecode-aware-load-balancer-for-large-s]], so no benchmark settles it. The reproducible fact is that the entire scheduling stack survives the move, because the only thing you replace is enumeration.

### E. Why the bet is reversible

The decisive consideration is not the benchmark. Because every proxy reaches every picker through the same external-processing protocol, and NVIDIA's own stack ships a different picker behind that same protocol [[gateway-api-inference-extensiondocsproposals004-endpoint-picker-protocol-at-main]] [[kv-aware-routing-on-kubernetes-nvidia-dynamo-documentation]], choosing llm-d is reversible at the architecture level and irreversible only at the plugin level. Keeping the custom logic in one isolated plugin means switching pickers later costs one file, not an architecture. That is an argument for strategy C that no benchmark can overturn, and it is why the existence of strategy H makes C safe rather than unnecessary.

The ranking that falls out: **B for most estates, C when a named gate trips, A when the estate is genuinely fixed, I in parallel, G only if fleet custody is on the table, and D, E and F never.**

## 7. Recommended Strategy and Implementation Roadmap

**Recommendation: customise the `EndpointDiscovery` seam and nothing else. Reach it by rungs, keep the custom Go surface to one plugin, decide topology from your availability requirement, and pursue upstreaming in parallel.**

### A. Four decision rules

*Rule 1 — availability selects topology, and this is the first branch.* This inverts the intuitive framing that router placement is merely organisational. If a single router instance is acceptable — job-scoped serving, reinforcement-learning rollouts, batch, development, an HPC allocation whose lifetime equals the job's — run the router entirely outside Kubernetes: the picker binary plus Envoy as host processes or containers, using the published flag set [[llm-dguidesno-kubernetes-deployment-at-main-llm-dllm-d-github]]. If you need multi-replica availability, the tie-breaker is whether a small Kubernetes control plane is acceptable. If it is, run the picker in-cluster under the Helm chart — leader election over a Lease works normally — while the backend inventory points off-cluster, using the chart's raw-configuration and volume-mount escape hatches [[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]] [[llm-d-routerconfigchartsreadmemd-at-main-llm-dllm-d-router-github]]. If Kubernetes is unavailable anywhere, run N pickers Active-Active behind a plain layer-4 load balancer with leader election **explicitly disabled** and **precise** prefix routing on.

That last branch needs its evidence stated, because the documentation's Active-Active warning is scoped to *approximate* prefix routing, where replicas genuinely do not share state [[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]]. Measured on real GPUs, precise prefix-cache failures at 500 queries per second fall monotonically as replicas rise: 3,148 failures at one replica, then 57, 31, and 18 at four, with median time-to-first-token dropping from 165 ms to 30 ms [[evaluate-llm-d-router-both-epp-and-the-standalone-proxy-scale-limits-issue-1290]]. The mechanism is visible in code: the precise extractor implements only the endpoint-extractor interface and pointedly not the cross-replica contributor interface, so each replica converges independently by subscribing to every endpoint's event stream rather than by synchronising with peers [[cross_replica_syncergo]] [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcacheex]]. Two cautions travel with it. The standalone chart silently injects a leader-election flag whenever replicas exceed one, which turns a four-replica deployment into one-replica throughput [[llm-d-routerconfigchartsreadmemd-at-main-llm-dllm-d-router-github]]. And flow-control state stays per replica, so priority and fairness are enforced only within each replica's share of traffic [[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]].

*Rule 2 — churn and addressing select the discovery rung.* Start at the lowest rung your estate tolerates: a static file if the set is fixed, a generator plus file watching if an orchestrator can emit the list. That second rung is the documented Slurm and Ray pattern and requires zero Go [[no-kubernetes-no-problem-llm-d-now-runs-anywhere-llm-d]]. Escalate to a custom plugin when any of four gates trips: endpoints are addressed by hostname rather than IPv4 literal; the inventory exceeds the 1 MiB file budget; backends are data-parallel and need a non-zero rank index; or churn is fast enough that a regenerate-and-rewrite loop leaves a measurable window of routing to dead workers.

*Rule 3 — health gating outranks the poll-versus-watch question.* Kubernetes readiness is gone and nothing replaces it. Therefore: **only upsert endpoints you believe healthy, delete on the first failed health signal, and pin the router at v0.9.0 or newer so metadata changes actually dispatch notifications** [[endpoint-metadata-updates-do-not-trigger-endpoint-notification-events-issue-1403]]. A shipped static-discovery implementation in a comparable project gives the shape to copy: a fixed topology with a background health-check thread filtering unhealthy addresses out of the returned set [[service_discoverypy]]. Only after that is settled does the poll-versus-watch question matter, and it resolves toward polling: default to an interval poll plus snapshot diff, a near-mechanical transliteration of the file plugin's load loop [[plugingo]]; use a long-poll primitive where the registry offers one, such as a blocking query carrying the last-seen index with server-side health filtering [[blocking-queries-consul-hashicorp-developer]] [[health-http-api-consul-hashicorp-developer]]; and reserve a genuine persistent watch for cases where staleness has a named, measured cost, remembering that the repository's only attempt at a watch-based plugin was abandoned as too large to review [[discovery-plugins-k8s-and-file-based-endpoint-discovery-by-ezrasilvera-pull-requ]].

*Rule 4 — the proxy choice silently decides your failure mode.* Use Envoy with llm-d's reference configuration for any off-Kubernetes deployment. It is the documented path and the one where you can deliberately add a fallback cluster and set the external-processing failure mode [[external-processing-envoy-1400-dev-13b0a8-documentation]]. Agentgateway's standalone passthrough is fail-closed by design, with fail-open still an open issue, because in passthrough there is no configured backend set to fail open to [[support-fail-open-fallback-for-standalone-epp-inference-routing-issue-1661-agent]] [[trust-standalone-epp-selected-destinations-by-danehans-pull-request-1658-agentga]]. Do not assume fail-open off Kubernetes: llm-d's scoped fail-open is tied to a lease-transition window that does not exist without a Lease, and with a header-driven `ORIGINAL_DST` cluster the proxy has no endpoint list of its own to fall back to. The protocol's ordered fallback-endpoint list is worth enabling, because it gives per-request retry resilience that does not depend on router availability at all [[amend-the-endpoint-picker-protocol-to-support-multiple-fallback-endpoints-by-wbp]].

### B. Phases

**Phase 0 — prove the stack on your hardware with zero Go (days).** Stand up the shipped no-Kubernetes reference on two workers: file discovery, the optimised baseline plugin mix, Envoy with an `ORIGINAL_DST` cluster, and static Prometheus scrape targets [[llm-dguidesno-kubernetes-deployment-at-main-llm-dllm-d-github]]. Pin a tagged release and match the configuration key to it. On v0.10.0, write the legacy form:

```yaml
plugins:
  - name: my-endpoints
    type: file-discovery
    parameters: { path: /etc/epp/endpoints.yaml, watchFile: true }
dataLayer:
  discovery:
    pluginRef: my-endpoints        # v0.10.0 and earlier
    # endpoints: { pluginRef: my-endpoints }   # main builds only
```

Set the pool-namespace flag explicitly, since the fallback is a Kubernetes-flavoured default label meaningless in a Slurm or Ray context [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]. Exit criterion: requests route end to end, per-endpoint metrics appear, and adding or removing a line in the file changes routing without a restart.

**Phase 1 — validate the flagship scorer (days).** Enable the precise prefix-cache producer with per-endpoint discovery and pair it with the prefix-cache scorer by name, which is required or the scorer silently falls back to the approximate producer [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcachere]]. Confirm your engines publish KV events on the base socket port, plus the replay socket if you want index recovery after a restart [[llm-dguidesprecise-prefix-cache-routingreadmemd-at-main-llm-dllm-d-github]]. This is the single highest-value experiment in the plan, because the code path is verified but no published report pairs precise routing with file discovery in a running deployment. Close that absence with your own test rather than with caution.

**Phase 2 — automate the inventory (days).** Write the generator that regenerates the endpoints file from your orchestrator and rewrites it by atomic rename; the watcher reattaches after atomic renames and symlink swaps [[llm-d-routerpkgeppframeworkpluginsdatalayerdiscoveryfile-at-main-llm-dllm-d-rout]]. Make it do the work a kubelet used to do: write only healthy endpoints, and remove entries the moment a backend is gone, since deletion is what tears down its subscriber and clears its index entries. Carry role labels if you plan on disaggregation. Many estates stop at this phase permanently, and should.

**Phase 3 — the plugin, out of tree (1-3 weeks end to end, only if a Rule-2 gate tripped).** The core loop is cheap: an interval poll plus snapshot diff is roughly 2-4 days of work, a long-poll variant adds 1-2 days, and a genuine persistent watch is 1-2 weeks with no in-repo precedent to copy. The 1-3 week envelope is the phase including health gating, tests, packaging and continuous integration. Structure: one package implementing the three interface methods, with an initializer registering the factory under a namespaced type string; one `main.go` that blank-imports it and calls the runner [[registrygo]] [[maingo]]. Wrap `Start()` in your own recover. Budget the full controller-runtime dependency tree, which the runner imports unconditionally alongside the entire in-tree plugin catalogue even when you never touch a cluster [[runnergo]] [[gomod]]. Add a scheduled build against upstream `main` so interface drift surfaces as a build failure rather than a production one.

**Phase 4 — harden and contribute (continuous).** Isolate the prefill hop at the network layer and turn on prefill TLS [[optionsgo]]. Enable metrics-endpoint authentication [[2061]]. Add priority only if tiers are genuinely needed. Open an upstream issue describing your discovery backend, referencing the maintainer's stated intent to support Slurm- and Ray-class plugins [[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]], and follow the file-discovery chain's shape — interface change, plumbing, plugin, wiring, as four small pull requests rather than one large one, which is the lesson of the abandoned attempt [[discovery-plugins-k8s-and-file-based-endpoint-discovery-by-ezrasilvera-pull-requ]]. Do not block Phase 3 on it; merge timing is not yours, and most real discovery backends carry proprietary details that cannot go upstream wholesale.

### C. Standing obligations

Four commitments run across every phase and belong in the design document, not in a risk register: health-gated upsert and delete; a pinned release plus continuous integration against `main`; a deliberately chosen proxy failure mode with a fallback cluster if you want fail-open; and network isolation of the sidecar port plus prefill TLS wherever disaggregation is used. Keep the bundle to one plugin as an explicit design constraint with a named owner — running the picker on a small Kubernetes control plane to avoid writing coordination, and deferring the priority plugin until priority tiers are actually in use, are the two decisions that hold the line.

## 8. Risks, Trade-offs, and Open Questions

**The extension pattern is sound but unratified.** The mechanism is verified in source: an exported registry map, exported registration, initializer-before-main ordering, no internal barrier, no replace directives [[registrygo]] [[main]]. What is missing is a project statement blessing it. Package indexing reports no known importers for the runner or the framework interface packages as of 2026-09-11, and the one open issue that names out-of-tree plugins as a category proposes framing them as at-your-own-risk — untriaged, uncommented, one of three competing options, not policy [[framework-define-a-panic-isolation-posture-for-plugin-extension-points-issue-210]]. Price it as a cost, not a veto: the same issue confirms no plugin invocation anywhere has panic recovery, in-tree or out, so the mitigation is identical either way, and your own recover in `Start()` is not optional.

**Interface churn is the real maintenance line item.** Discovery's configuration shape changed three times in roughly four months — the interface was renamed and moved packages during review, the key moved under the data-layer section, then nested again — and the data layer's typed-attribute machinery was still being reworked on 2026-09-11 [[config-consolidate-discovery-plugins-under-a-single-discovery-sectio-llm-dllm-d]] [[llm-d-routerpkgeppframeworkinterfacedatalayer-at-main-llm-dllm-d-router-github]]. Configuration changes ship migration shims; the Go interface has no such guarantee. Budget a day per release cycle for re-verification.

**The custom surface has a tendency to grow.** The recommendation costs one plugin only if you decline the others. Priority tiers add an admitter, registered at Alpha and therefore requiring the experimental-plugins flag [[llm-d-routerpkgeppframeworkpluginsreadmemd-at-main-llm-dllm-d-router-github]]. Off-cluster multi-replica coordination would add a peer-discovery plugin, since the only one in flight is a Kubernetes pod watch and still unmerged [[feat-pod-watch-peer-discovery-plugin-by-evacchi-pull-request-2501-llm-dllm-d-rou]]. Non-Go work rounds it out: a hand-authored Envoy configuration, static Prometheus scrape configuration, and the network isolation the sidecar needs. Each addition multiplies exposure to a framework with no stability guarantees.

**The disaggregation carve-out has two separate dates.** The original SSRF disclosure (issue #242, July 2025) is historical and was addressed primarily upstream by the gateway stripping the client-supplied prefill header on ingress. The allowlist's port-matching defect (issue #979) is open now. Neither changes the recommendation, and both reinforce the same instruction: treat sidecar reachability as a firewall problem.

**The multi-replica caveats.** Flow control stays per replica, so a priority-tiered multi-tenant platform running Active-Active enforces fairness only within each replica's slice. And cross-replica session affinity was never evaluated — the scaling benchmark used independent synthetic requests — so session-pinned workloads must not assume correctness there [[evaluate-llm-d-router-both-epp-and-the-standalone-proxy-scale-limits-issue-1290]].

**Audited absences, stated as tests to write rather than reasons to hedge.** Nobody has published an end-to-end account of precise prefix-cache routing running against file discovery; the mechanism is verified in code and the deployment is undemonstrated. Nobody has published the hybrid shape either — router in Kubernetes, backends outside — which is reachable through documented chart escape hatches but is a capability inference rather than an observed pattern. The external-processing failure-mode setting in the shipped no-Kubernetes Envoy configuration is unverified, so nobody should claim fail-open off-cluster by default [[envoyyaml]]. And repeated-upsert idempotency on file reload is untested, which bears directly on whether a regenerating endpoint file churns KV-event subscribers [[file-discovery-34-add-filediscovery-plugin-with-yamljson-file-loading-and-fsnoti]].

**Falsification conditions.** Four specific commits would change this analysis, and each is plausible within two release cycles. If the panic-isolation issue is triaged toward a documented out-of-tree posture and that text lands in the plugin developer documentation, the precedent objection weakens materially. If a merged change adds a pluggable coordination primitive with a file, etcd, or Consul lock, the availability constraint that drives Rule 1 substantially collapses. If any orchestrator-native discovery plugin merges, the audited absence closes and the seam acquires the in-repo precedent it lacks. If the charts grow a first-class discovery key, the packaging objection disappears outright. Watch those four.

**Forward look, six to eighteen months.** Three trajectories converge on making this strategy cheaper rather than obsolete. The discovery abstraction is still mid-migration — the pod watch was always meant to move behind the interface so that pool discovery becomes just another plugin alongside file and service-registry discovery [[no-kubernetes-no-problem-llm-d-now-runs-anywhere-llm-d]]. When that lands, the Kubernetes path and your path become peers, and the residual namespaced-name identity type is the natural thing to fix alongside it. The router's own roadmap names a standardised model-server interface independent of whether the engine underneath is vLLM, SGLang, or TensorRT-LLM [[llm-d-v09-hardened-for-scale-llm-d]], further decoupling the router from any particular backend shape. And the protocol layer keeps hardening as the industry seam: a competing vendor ships its own picker behind it, the protocol has grown ordered fallback endpoint lists, and the design direction across the field converges on backend-agnostic schedulers addressed over ordinary transports with opaque instance identity rather than orchestrator objects [[kv-aware-routing-on-kubernetes-nvidia-dynamo-documentation]] [[rfc-mooncake-conductor-design-and-implementation-of-a-global-scheduler-module-fo]]. The prediction this licenses, stated as inference rather than as a sourced fact, is that orchestrator-native discovery plugins will eventually land upstream, and a team that wrote one against today's interface will be positioned to upstream it rather than to rewrite. The cost of being early is the interface drift you absorb; the cost of waiting is running someone else's roadmap.

The compounding implication for design is sharper than the forecast. The discovery plugin is the only artifact you own that is exposed to llm-d's internal churn; everything else you depend on is either a stable wire protocol or a configuration file. Keeping the custom surface to one plugin is therefore not merely the cheapest way to start — it is the only structure that stays cheap as the project moves under you.

**What is not recommended.** Do not fork to get a plugin. Do not shim non-pod backends into Kubernetes objects the picker never reads. Do not rebuild a router around llm-d's libraries to avoid one interface. Do not put managed provider endpoints in the pool. And do not wait for an orchestrator-native discovery plugin to appear upstream — the generator-plus-file rung is production-viable today, and the custom plugin is a week of work, not a quarter.

**The trade-off you are actually making.** Choosing llm-d for non-pod backends means accepting a discovery seam you must maintain, in exchange for a scheduling stack — precise prefix affinity, load and queue awareness, saturation-gated admission, priority and fairness queuing, disaggregation profiles, predicted-latency scoring — that simpler routers do not have. If your workload has no shared prefixes, no disaggregation, and no multi-tenant contention, that exchange is a bad deal and a router with native static discovery is the right answer. If it does, the exchange is strongly favourable, and the protocol boundary makes it smaller still: the proxy talks to whatever picker you point it at, so the plugin is the only thing you would rewrite if you ever changed your mind.
