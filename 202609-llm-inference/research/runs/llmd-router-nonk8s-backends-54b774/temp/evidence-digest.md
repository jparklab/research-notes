### 2. How the Router Discovers and Tracks Backends Today

- Multi-port InferencePools hit a hard scaling ceiling under GCP's Network Endpoint Group (NEG) limits: each port in each zone creates a dedicated NEG, capped at 50 NEGs per GCP Backend Service, so an 8-port InferencePool across 3 zones (24 NEGs) can only be aggregated from at most 2 clusters in a multi-cluster Gateway before hitting the limit.  _(empirical; 50 NEGs per Backend Service, 8 ports, 3 zones, 24 NEGs)_
  > Network Endpoint Group (NEG) limits: has a limit of 50 NEGs per Google Cloud Backend Service... an InferencePool with eight ports in a typical regional cluster (three zones) generates 24 NEGs. Therefore, a multi-cluster Gateway can only aggregate such an InferencePool from a maximum of two clusters (two clusters times 24 NEGs = 48 NEGs) before reaching the 50 NEG limit.
  [about-gke-inference-gateway-powered-by-llm-d-gke-networking-google-cloud-documen]

- kgateway's GIE support is fully Kubernetes-CRD-driven (controllers reconcile InferencePool, auto-enabled only when the CRDs exist in-cluster) with no standalone or non-k8s mode scoped.  _(empirical; #10411)_
  > Add controllers that reconcile gateway-api-inference-extension custom resources, e.g. InferencePool. The controller should be optional, i.e. only run if the configuration option is enabled and the gateway-api-inference-extension CRDs exist.
  [add-initial-gateway-api-inference-extension-support-issue-10411-kgateway-devkgat]

- When an AIGatewayRoute rule references an InferencePool, fallback behavior is entirely delegated to the InferencePool's own endpoint picker; the gateway's own backend-level priority and fallback fields are explicitly ignored for InferencePool backends.  _(empirical; default priority 0)_
  > Priority is the priority of the backend. This sets the priority on the underlying endpoints... Note: This will override the `faillback` property of the underlying Envoy Gateway Backend. This field is ignored when referencing InferencePool resources.
  [api-reference-agent-router]

- In the pre-GA v1alpha2 API, InferencePool used fields extensionRef and targetPortNumber, which have since been renamed to endpointPickerRef and targetPorts in the v1 GA spec.  _(empirical; v1alpha2)_

- The upstream fix for issue #1403 requires the datastore to dispatch EventAddOrUpdate on existing-endpoint metadata changes too, while explicitly skipping dispatch when the new metadata is identical to avoid redundant notification storms.  _(empirical; v0.9.0)_
  > Existing endpoint metadata changes should dispatch EventAddOrUpdate, just like endpoint additions, so endpoint-aware plugins can refresh their per-endpoint state.
  [endpoint-metadata-updates-do-not-trigger-endpoint-notification-events-issue-1403]

- NGINX Gateway Fabric's GIE integration is InferencePool/pod-label-selector based with no standalone or non-k8s-backend mode documented.  _(empirical; v2.7.0, v1.5.0)_
  > These pods are selected from a pool of ready pods designated by the assigned InferencePool's Selector field.
  [gateway-api-inference-extension-nginx-documentation]

- The EPP-proxy wire protocol identifies backends purely as ip:port strings, not Kubernetes object references, which makes the protocol itself backend-agnostic even though the surrounding project assumes pods.  _(empirical; v1.0.0, 2025-07-29)_

  [gateway-api-inference-extensiondocsproposals004-endpoint-picker-protocol-at-main]

- InferencePool and InferenceObjective belong to two different Kubernetes API groups (inference.networking.k8s.io and inference.networking.x-k8s.io respectively), and InferenceObjective priority is selected per-request via the client-set header x-gateway-inference-objective, defaulting to priority zero when omitted.  _(empirical; priority: 100, default priority 0)_

- InferencePool and InferenceObjective are governed by different Kubernetes API groups (inference.networking.k8s.io vs inference.networking.x-k8s.io) and InferenceObjective replaces the older InferenceModel object, dropping its criticality enum in favor of a plain integer priority while taking the served-model name from the request itself.  _(empirical; v1.0.0)_
