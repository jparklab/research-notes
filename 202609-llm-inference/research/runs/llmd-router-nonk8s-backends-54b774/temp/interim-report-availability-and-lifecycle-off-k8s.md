# Interim report: availability-and-lifecycle-off-k8s

**Locus question:** Outside Kubernetes the EPP becomes a fail-closed hard dependency and endpoint health/eviction becomes the caller's job — what is the production design for EPP HA (v0.9 multi-replica under file/custom discovery, replica consistency), health gating in lieu of pod readiness, and securing metrics scraping, ZMQ KV events and the ORIGINAL_DST header path?

**Flavor:** dialectical (named contradiction-graph cluster: "fail-open-vs-fail-closed")

## What the corpus already said

The width sweep established the basic shape of the problem without resolving it. [[support-fail-open-fallback-for-standalone-epp-inference-routing-issue-1661-agent]] shows agentgateway's standalone-EPP passthrough mode is deliberately fail-closed as of PR #1658, with maintainer howardjohn objecting that a fail-open path "has no endpoints to route to since users don't configure them" and danehans (Jun 22 2026) still soliciting user feedback before designing a real FailOpen mode — unresolved, open issue. [[inference-support-agentgateway-as-a-standalone-provider-issue-620-agentgatewayag]] shows the same tension one layer earlier: an example standalone config with `failureMode: failOpen` was pulled by danehans in Mar 2026 after howardjohn asked "if the EPP is bundled, should we expose failureMode at all?" [[llm-d-v09-hardened-for-scale-llm-d]] (the v0.9 blog) asserts Router HA "without additional coordination" and that non-leader replicas "keep their datastores populated and route traffic rather than returning 503" — a claim the corpus flagged as asserted-but-unverified against actual multi-replica mechanics. [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]] confirmed file discovery has no equivalent to Kubernetes pod-readiness gating and that a custom plugin author must replicate health semantics itself. [[metrics-llm-d]] and [[envoyyaml]] documented that the whole metrics-scrape path is PodMonitor/ServiceMonitor-CRD-based (unavailable off-k8s) and that the reference no-k8s Envoy config deliberately drops TLS on the ext_proc cluster for same-host colocation.

## What the new sources say

**[[llm-d-routerconfigchartsreadmemd-at-main-llm-dllm-d-router-github]]** (read in full this pass, not previously deep-read) was the first strong lead: *"Active-Passive Mode (Default): The chart automatically enables the `--ha-enable-leader-election` flag. Only one leader replica active-routes traffic, coordinates lease status, and maintains absolute routing state, while other replicas act as warm standbys."* And: *"in active-passive mode only the elected leader passes its readiness probe; standby replicas answer the readiness gRPC service with `NOT_SERVING` on purpose, so they never become Service endpoints."* This directly contradicts the v0.9 blog's framing that non-leader replicas "route traffic rather than returning 503" — in the shipped default HA mode, standbys do not serve traffic at all; they are excluded from the Service endpoint list entirely. The chart also documents Active-Active mode (`ha-enable-leader-election: false`) where *"all replicas process traffic concurrently"* but *"you must only use active-active compatible plugins... Avoid plugins that rely on local in-memory routing state, as this state is not synchronized across replicas."*

**[[llm-d-routerdocspeer-discoverymd-at-main-llm-dllm-d-router-github]]** confirms the synchronization gap for Active-Active is not yet closed: *"EPP replicas operating in an active-active topology need to know about each other so a **future** cross-replica syncer can exchange state... between them."* Peer discovery (`dataLayer.discovery.peers.pluginRef`) is a real plugin interface mirroring endpoint discovery — pluggable, disabled when omitted — but the doc shows only a hand-rolled example implementation, no shipping in-tree peer-discovery plugin (Kubernetes or otherwise).

**[[registrygo]]** and **[[runnergo]]** (source-level, re-verified this pass) establish that out-of-tree discovery/peer-discovery plugins ARE technically installable without patching llm-d-router itself: `plugin.Register` is an exported package-level function, and `cmd/epp/runner` exposes a builder (`NewRunner().Run(ctx)`) a third-party `main.go` can call after blank-importing a custom plugin package. This is a real customization seam, but it requires forking the binary's entrypoint — the Helm charts expose zero config surface for it.

**[[filediscovery-plugin-44-wiring-into-the-runner-by-ezrasilvera-pull-request-1218]]** gives the actual health-gating mechanism for non-k8s discovery: every `EndpointDiscovery` (and every `PeerDiscovery`) plugin must implement `Ready() <-chan struct{}`, closed once after first successful sync. The runner "gates request-serving (epp-server, health) — but not /metrics — on `Ready()` closing." There is no field in `EndpointMetadata` for liveness; a discovery plugin is solely responsible for only calling `Upsert` on endpoints it considers healthy. Off-k8s, "health" is whatever the plugin author defines it to be.

**[[fix-harden-header-sanitization-and-handling-logic-by-lukeavandrie-pull-request-2]]** and its diff (**2025diff**) directly resolve the ORIGINAL_DST-header-spoofing sub-question. Before this fix (merged upstream Dec 19 2025, cherry-picked into llm-d-router Apr 23 2026, i.e., present in the v0.9-era codebase), `generateHeaders`/`generateResponseHeaders` "acted as a transparent passthrough, appending user-supplied headers to the outgoing message." The fix adds `requtil.IsSystemOwnedHeader` backed by an explicit `OutputInjectionHeaders` blocklist that names `metadata.DestinationEndpointKey` directly, and the added test is unambiguous: a request with client-supplied `metadata.DestinationEndpointKey: "1.1.1.1:666"` produces a `generateHeaders` output where `assert.Equal(t, "1.2.3.4:8080", gotHeaders[metadata.DestinationEndpointKey])` — the header sent to Envoy is deterministically `reqCtx.TargetEndpoint` (the EPP's own scheduling decision), and any client-injected value is silently dropped. As of the current GIE/llm-d-router codebase, a client cannot use `x-gateway-destination-endpoint` on their inbound request to redirect Envoy's `ORIGINAL_DST` cluster.

**2061.diff** (GIE PR #2061, "fix prometheus auth") shows the Helm chart previously wired `--metrics-endpoint-auth=false` off of `monitoring.prometheus.enabled` rather than `monitoring.prometheus.auth.enabled` — i.e., there is an EPP-native `--metrics-endpoint-auth` flag capable of protecting the metrics endpoint, and the default posture post-fix is auth-required unless an operator explicitly opts out (`auth.enabled=false`), but pre-fix the chart silently disabled it whenever Prometheus was toggled at all. Real protection primitive; wiring was buggy until Jan 2026.

**[[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]]** — fetched last, and decisive. This is `docs/operations.md` (commit 01b983a, Sep 9 2026 — current), and it resolves the single biggest open question from the first pass of this investigation by naming the leader-election lock literally, twice. Under "4. High Availability (HA)": *"Leader Election with Fail-Open: Uses Kubernetes `coordination.k8s.io/Lease` coordination so only the elected leader serves inference extension requests. Standby pods remain idle until acquiring the lease."* And under "Leader Election and Fail-Open": *"the router coordinates active-passive replicas using Kubernetes lease-based leader election: EPP replicas contend for a `coordination.k8s.io/Lease`. The `--ha-enable-leader-election` flag enables leader election in EPP (automatically injected by Helm when `router.epp.replicas > 1`)."* No file-based, static-peer-list, or gossip alternative to `coordination.k8s.io/Lease` is named anywhere — this is a hard Kubernetes API dependency for this mode, confirmed in-doc, not an inference from suggestive vocabulary.

The same doc also shows the fail-open/fail-closed question is **already resolved for this specific path**, in exactly the direction this investigation's synthesis argues for below: *"Fail-Open Resiliency: With `router.proxy.failOpen: true` (the default in standalone mode) or `router.inferencePool.failureMode: FailOpen`, if the active leader crashes or restarts, the proxy passes requests directly to backend model servers without dropping traffic during the lease transition period."* This is scoped fail-open — active only during the multi-second window between leader loss and a standby acquiring the lease, and forwarding to already-known backend endpoints rather than an arbitrary destination — precisely the "fallback pool" shape steverogersX proposed in agentgateway issue #1661, already shipped and defaulted-on in llm-d-router's own standalone Envoy path.

The doc documents a third HA mode not found elsewhere in this corpus, **Priority Routing** (`router.proxy.mode: service` + `priorityRouting.enabled: true`): EPP pods run as a **StatefulSet with a headless Service** (`publishNotReadyAddresses: true`), Envoy health-checks each named pod (`<release>-epp-0`, `<release>-epp-1`, ...) over gRPC, and Outlier Detection ejects a failed primary in "sub-second time without lease expiration delays." This avoids the Lease API specifically but substitutes a different Kubernetes primitive (StatefulSet + headless Service + Envoy health checks) — it relocates the Kubernetes coupling rather than removing it. Of the three documented HA shapes (Lease-based leader election, StatefulSet-based Priority Routing, Fully Active-Active), none has a documented Kubernetes-independent implementation; Active-Active is the only one that doesn't need a K8s coordination primitive for the mechanism itself, but the same doc warns it "should be avoided when using approximate prefix routing" (replicas don't share prefix state, "significantly degrades prefix cache hit rates") and gives **zero** throughput benefit in Active-Passive mode ("scaling the replica count does not increase the overall EPP throughput capacity... as only the active replica handles requests" — Active-Active alone gets near-linear scaling, 2 replicas = 2.0x, 3 = 2.7x, 4 = 3.5x).

## Evidence synthesis

Multiple independent, now directly-confirmed facts converge on one conclusion: **every documented HA path for the EPP is Kubernetes-coupled at the coordination layer, even though endpoint discovery itself is not.** `docs/operations.md` names `coordination.k8s.io/Lease` explicitly for the default leader-election mode; Priority Routing substitutes a StatefulSet + headless Service for the Lease but is equally Kubernetes-native; Fully Active-Active avoids both primitives but its cross-replica state-sync consumer (peer discovery) is explicitly documented as future work, so it is safe off-k8s today only for a narrow, backend-polling-plugin allowlist, and is separately contraindicated for approximate prefix-cache routing regardless of platform. The `no-kubernetes-deployment.md` doc — llm-d's own official no-k8s guide — is silent on multi-replica EPP entirely; it describes only a single EPP process. No source anywhere in this corpus describes a working, documented, fully non-Kubernetes multi-replica EPP HA deployment.

The KV-cache-indexer's own architecture doc (already in corpus, [[llm-d-kv-cachedocsarchitecturemd-at-main-llm-dllm-d-kv-cache-github]]) independently reproduces the same pattern one layer down the stack: its active-active story ("Pod discovery... supports active-active multi-replica deployments — each replica independently subscribes to every pod") is explicitly Kubernetes-label-selector-based, while its Kubernetes-independent mode (Centralized/Static ZMQ) "works naturally with a single host replica." The one component with a genuine non-Kubernetes discovery path loses its documented multi-replica story exactly when Kubernetes is removed — the mirror image of the EPP's own problem.

On health gating, the picture is coherent and less contested: `Ready()` on the discovery interface plus self-policed `Upsert`/`Delete` is a workable substitute for Kubernetes pod-readiness — it moves the liability from the platform (kubelet + readiness gates) to the plugin author, with no compensating framework support (no timeout, no flapping protection, no liveness-vs-readiness distinction at the `EndpointMetadata` level). A careless custom discovery plugin can silently route to a dead backend indefinitely, since `watchFile` reload failures are "logged but do not terminate the plugin" and the datastore "retains its previous state" — stale-but-present endpoints, not evicted ones.

On the specific fail-open/fail-closed dialectical dispute, the newly-found `operations.md` evidence changes the shape of the argument materially: it is not a live, symmetric dispute across the whole ecosystem — it has already been resolved one way inside llm-d-router's own reference Envoy/standalone path, and resolved the *other* way, and left unresolved, inside agentgateway's separate standalone-EPP integration.

### Position A: fail-closed is the correct default for standalone/passthrough EPP (agentgateway's position)

The strongest version of this case is danehans's and howardjohn's own reasoning in #1661/#620: in agentgateway's `destinationMode: passthrough`, there is, by construction, no configured fallback backend set for Envoy to spill over to — passthrough means agentgateway "does not need to know about the backend via k8s Endpoints/EndpointSlice at all, only the EPP's decision." Fail-open in that mode has nothing concrete to fail open *to*. The Helm chart's own default for Agentgateway backs this: *"Agentgateway exposes no fail-open setting and rejects requests (fails closed) when EPP is unreachable"* — the shipped default for the newest, purpose-built standalone proxy path, not a stopgap bug by its authors' own account.

### Position B: fail-open (scoped to a known fallback set) is the correct default, and is already shipped elsewhere in the same ecosystem

`docs/operations.md` shows llm-d-router's own Envoy-based standalone path has already built exactly what agentgateway's issue #1661 is still debating: fail-open gated to the lease-transition window, routing only to already-known backend model servers, defaulted to **on** (`router.proxy.failOpen: true` is "the default in standalone mode"). InferencePool's own GA v1 spec ([[inferencepool-kubernetes-gateway-api-inference-extension]]) independently ships the same default (`failureMode: FailOpen`). The chart's own authors treat brief EPP unavailability during leader failover as an expected, recurring event fail-open exists to survive — and leader failover is not hypothetical for the default Active-Passive HA mode; the Lease transition window is its whole reason to exist. Agentgateway's own #1661 thread doesn't defend fail-closed as *correct* on the merits, only as the safe placeholder before a fallback-pool primitive lands — and llm-d-router's Envoy path shows that primitive is buildable and already shipped for one proxy implementation.

## Committed position

**This dispute is resolved, not open, once the two proxy implementations are separated.** llm-d-router's own reference Envoy-based standalone/HA path has already shipped the design this investigation's first-pass synthesis independently arrived at — scoped fail-open, gated to the leader-transition window, forwarding only to known backend endpoints, defaulted to on (`router.proxy.failOpen: true` plus `router.inferencePool.failureMode: FailOpen`). Position A (fail-closed) survives, correctly, only for agentgateway's `destinationMode: passthrough`, and only because that specific architecture has not yet built the fallback-endpoint-set primitive llm-d-router's Envoy path already has — it is not evidence that fail-closed is the right steady-state design, it is evidence of a specific, named, tracked implementation gap (issue #1661, still open) in one proxy implementation, not a principled position the ecosystem has converged on. Anyone customizing the router for non-Kubernetes backends who chooses Envoy as the front proxy inherits a solved fail-open story; anyone who chooses agentgateway inherits an explicitly unsolved one and should treat #1661 as a blocking dependency, not a future nice-to-have, before shipping multi-replica HA off-Kubernetes.

The load-bearing reason this matters specifically for non-Kubernetes backends: `docs/operations.md` confirms, without ambiguity, that **all three documented EPP HA mechanisms — Lease-based leader election, StatefulSet-based Priority Routing, and Fully Active-Active — depend on a Kubernetes primitive** (a Lease object, a StatefulSet + headless Service, or an as-yet-unbuilt peer-sync layer, respectively). A team building a custom, non-Kubernetes-backend router on top of llm-d-router's file/custom discovery plugin gets a fully working single-EPP-instance deployment (this part is genuinely Kubernetes-independent, confirmed by `no-kubernetes-deployment.md`) but has no documented path to multi-replica HA without either standing up Kubernetes anyway just to host the EPP control plane (while file-discovery still supplies the backend inventory) or building their own leader-election/fallback mechanism from the exported `plugin.Register`/`Runner` seam — an unstated, non-trivial engineering cost that the "customize the router" plan must budget for explicitly.

- **Position:** The fail-open/fail-closed dispute is resolved (fail-open scoped to a known fallback set, gated to the coordination-failure window) in llm-d-router's own Envoy/standalone path and already shipped as the default; it remains genuinely unresolved only in agentgateway's separate standalone-EPP passthrough integration. Separately, and unconditionally: every documented multi-replica EPP HA mechanism (Lease leader-election, StatefulSet Priority Routing, Active-Active) is Kubernetes-coupled, so a non-Kubernetes-backend deployment gets single-instance EPP "for free" but must engineer HA itself.
- **Confidence:** high on both claims. The Lease dependency is now a direct, literal quote ("Uses Kubernetes `coordination.k8s.io/Lease` coordination") from a current (Sep 9 2026) primary-source doc, not an inference from suggestive vocabulary as in the first pass. The fail-open-already-shipped claim is equally direct ("With `router.proxy.failOpen: true` (the default in standalone mode)..."). Only the agentgateway side of the comparison retains first-pass calibration: medium confidence, since #1661 is an open, unresolved issue and the maintainers' final design could still diverge from steverogersX's proposal.
- **Boundary conditions:** The Lease/StatefulSet/Active-Active trichotomy applies specifically to llm-d-router's Helm-chart-driven, multi-replica EPP deployment (Gateway mode or standalone mode). It does not apply to single-replica EPP (no HA question arises) or to the coordinator-service alternative architecture ([[llm-d-routerdocscoordinator_architecturemd-at-main-llm-dllm-d-router-github]]), which is explicitly stateless and needs no inter-replica coordination at all — an available escape hatch worth flagging to the orchestrator as a fourth option not framed as "HA" in the docs because it doesn't need to be.
- **What would change this position:** A merged PR or design doc shipping a non-Kubernetes lock implementation (e.g., a pluggable `Locker`/coordination interface with a file-lock, etcd, or Consul-backed implementation) for the leader-election path would overturn the "hard Kubernetes dependency" half of this position. Evidence that agentgateway has closed #1661 with a design different from the fallback-pool-gated fail-open pattern (e.g., permanently keeping fail-closed with no opt-out) would sharpen rather than overturn the position, since that is Position A's own stated fallback if a "real user requirement" doesn't materialize.
- **Evidence weight:** 2 directly-quoted primary-source confirmations of the Kubernetes Lease dependency (chart README's suggestive language, corroborated and made literal by `docs/operations.md`); 1 merged code diff with an explicit assertion test resolving the header-spoofing question; 2 GitHub issue/PR threads (one resolved for Envoy/llm-d-router, one still open for agentgateway) read in full on both sides of the fail-open dispute; 1 corroborating independent data point (KV-cache-indexer's own active-active-is-k8s-coupled admission) strengthening the general "coordination layer is the off-k8s gap" pattern. No source in the corpus contradicts any of these findings.

## Open questions

- Is there any design proposal (even unmerged) for a non-Kubernetes lock/coordination primitive for `--ha-enable-leader-election`, or is single-EPP-instance-only genuinely the ceiling for non-Kubernetes multi-replica HA today? Not found despite two rounds of targeted fetching.
- Is there an in-tree, shipping `PeerDiscovery` plugin implementation (Kubernetes-based or otherwise) today, or does every deployment currently have to hand-write one? `peer-discovery.md` shows only a hypothetical example; `docs/operations.md`'s Active-Active discussion doesn't name one either.
- What Envoy `failure_mode_allow` value does the no-Kubernetes reference `envoy.yaml` rely on for the ext_proc filter when the EPP process itself is down (not just returning no header)? Not set explicitly in the fetched config; Envoy's documented default for `ext_proc.failure_mode_allow` is `false` (fail closed), but this was not independently re-verified against current Envoy proto docs in this pass.
- Does ZMQ KV-event transport (Centralized or Pod-discovery mode) have any authentication or encryption option (CURVE, TLS) anywhere in the llm-d-kv-cache codebase that the fetched docs simply didn't mention? Both fetched docs (architecture.md, configuration.md) are silent on this — a real absence or an under-documented feature; worth a targeted code search if another investigator has budget.
- Is the coordinator-service architecture ([[llm-d-routerdocscoordinator_architecturemd-at-main-llm-dllm-d-router-github]]) — explicitly stateless, "any instance can serve any request... no coordination between them" — a viable alternative to EPP-replica HA for non-Kubernetes backends specifically? It still calls out to an EPP behind an Inference Gateway per phase, so it likely doesn't eliminate the underlying EPP HA question, but this wasn't tested against the file-discovery/non-k8s path in any fetched source.
