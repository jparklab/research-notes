# Don't Customize the Router: The Case for Keeping llm-d Kubernetes-Native and Changing What "Backend" Means

**Direct answer: do not customize the llm-d router to support non-pod backends. Customizing the router is the option that *minimizes* llm-d reuse, not the one that maximizes it — because the moment you compile your own endpoint-picker binary around a bespoke discovery plugin, you leave behind the layer where llm-d's value is actually operational rather than algorithmic.** The scheduling intelligence is portable; the product is not. llm-d's high availability runs on `coordination.k8s.io/Lease` and has no documented non-Kubernetes lock ([[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]]). Its Helm charts require a pod label selector and expose no discovery knob whatsoever ([[llm-d-routerconfigchartsreadmemd-at-main-llm-dllm-d-router-github]]). Its prefill/decode sidecar's only anti-SSRF control is an allowlist built exclusively from an `InferencePool` custom resource and the pods that resource selects — there is no static, CIDR, or flag-based alternative anywhere in the file ([[allowlistgo]]), and with the control disabled the sidecar proxies to whatever host and port a request header names ([[chat_completionsgo]], [[potential-ssrf-via-x-prefiller-url-or-x-prefiller-host-port-header-issue-242-llm]]). Its per-request priority and model-rewrite policy arrive through custom resources whose reconcilers simply do not start off-cluster ([[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]). And every conformant gateway data plane in the ecosystem — Istio, NGINX Gateway Fabric, kgateway — reaches backends only through an `InferencePool` that selects pods by label ([[istio-kubernetes-gateway-api-inference-extension]], [[gateway-api-inference-extension-nginx-documentation]], [[add-initial-gateway-api-inference-extension-support-issue-10411-kgateway-devkgat]]).

The seam you would build against is the youngest, least-precedented surface in the entire project. As of 2026-09-11, pkg.go.dev reports no known importers for `cmd/epp/runner` or the plugin and data-layer interface packages; `CONTRIBUTING.md` says nothing about third-party plugins ([[llm-d-routercontributingmd-at-main-llm-dllm-d-router-github]]); the only written statement anywhere about out-of-tree plugins is an untriaged issue with zero comments whose own proposal is to declare them "at-your-own-risk" against a framework that has no panic recovery on any plugin call path ([[framework-define-a-panic-isolation-posture-for-plugin-extension-points-issue-210]]); the watch-based discovery plugin the project itself attempted was closed unmerged ([[discovery-plugins-k8s-and-file-based-endpoint-discovery-by-ezrasilvera-pull-requ]]); and the configuration key the official documentation tells you to use — `dataLayer.discovery.endpoints.pluginRef` — landed on `main` on 2026-08-25, eight days *after* the newest release was tagged, and therefore exists in no shipped version you can pin ([[config-consolidate-discovery-plugins-under-a-single-discovery-section-follow-up]], [[releases-llm-dllm-d]]).

**What to do instead, in strict order of preference.** First, ask whether the estate can simply *be* pods: NVIDIA and SchedMD's Slinky operator runs Slurm daemons themselves as Kubernetes pods at production scale — over 1,000 worker nodes and 8,000-plus GPUs, with collective-communication performance matching non-containerized Slurm ([[running-large-scale-gpu-workloads-on-kubernetes-with-slurm-nvidia-technical-blog]], [[github-slinkyprojectslurm-operator-run-slurm-on-kubernetes-a-slinky-project-gith]]). Real pods mean the stock router works unmodified. Second, if the estate cannot be pods but its endpoints can be *enumerated* by any external script, keep the router inside Kubernetes and feed it a file: the shipped file-discovery plugin was deliberately written to survive ConfigMap-style symlink swaps, which is the update mechanic of a Kubernetes volume mount, and the charts expose raw-config and extra-volume escape hatches that make this reachable without forking anything ([[llm-d-routerpkgeppframeworkpluginsdatalayerdiscoveryfile-at-main-llm-dllm-d-rout]], [[llm-d-routerconfigchartsreadmemd-at-main-llm-dllm-d-router-github]]). This costs zero lines of Go and keeps leader-elected HA, the Helm packaging, the policy custom resources, and the operator-based metrics pipeline. Third — and only if both of those fail, meaning your backends are dynamic, non-enumerable, and cannot be pods — the honest comparison is no longer "llm-d with a plugin versus llm-d without one." It is llm-d against routers that already ship dynamic non-Kubernetes discovery as a supported, tested feature: NVIDIA Dynamo makes etcd/NATS discovery a first-class mode required specifically "for Slurm or other distributed deployments" and offers a plain `--discovery-backend file` for everything else ([[github-ai-dynamodynamo-a-datacenter-scale-distributed-inference-serving-framewor]]), and even ships a standalone endpoint picker explicitly designed to add KV-aware routing to a fleet of upstream vLLM pods without migrating them ([[kv-aware-routing-on-kubernetes-nvidia-dynamo-documentation]]).

The strongest case for the opposite position is real and is answered at full strength in Section 6. The short version of the answer: the evidence that llm-d's *routing logic* is platform-neutral is solid and I concede it completely. It simply does not establish what the customization plan needs it to establish, because the work you would own is not one plugin — it is a bundle, a binary, a proxy configuration, a metrics-discovery story, a health agent, and a network-isolation posture for the disaggregation sidecar, all compiled against interfaces that reshaped three times in four months with no compatibility promise and no crash isolation.

## 1. llm-d Component Inventory and Kubernetes Coupling

llm-d is not one program. It is a control plane assembled from separately versioned components, and the coupling question has a different answer for each. Since v0.7 the project calls the routing tier the **llm-d Router** — "the functional combination of a Proxy and an Endpoint Picker (EPP)" — a rename made deliberately because the old "inference scheduler" name "conflicted with Kubernetes scheduling concepts and was too narrowly tied to the Gateway API" ([[llm-d-v07-from-feature-introduction-to-production-hardening-llm-d]]). The Endpoint Picker, or EPP, is the gRPC service the proxy consults per request; it holds all the routing intelligence and returns a chosen backend as an `ip:port` string. In a live deployment the EPP runs as an ordinary pod — on Amazon EKS via KServe it is a two-container pod, a scheduler container running the picker plugins and a tokenizer container tracking prefix-cache state, sharing state over ZeroMQ ([[how-llm-d-routes-model-inference-traffic-on-amazon-eks-red-hat-developer]]).

The inventory below separates *algorithmic* components (which travel) from *operational* ones (which do not). This distinction is the spine of the entire argument, so it is worth stating plainly before the table: **llm-d's Kubernetes coupling is not concentrated in its routing algorithms. It is concentrated in everything that makes those algorithms deployable, highly available, governable, secure, and observable.** Anyone who audits only the scheduling path will conclude the router is portable, and will be right about the scheduling path and wrong about the router.

| Component | Kubernetes coupling | Reusable off-pods? |
|---|---|---|
| Scheduling plugins (filters, scorers, pickers) | None. Pure functions over endpoint metadata and scraped metrics | Yes, unchanged |
| Precise prefix-cache producer | None at code level: per-endpoint KV-event subscribers are installed by a generic endpoint-notification extractor and keyed on literal `Address:Port` ([[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcacheex]]) | Yes, for single-rank engines |
| KV-cache indexer | Optional. Ships a "Static Endpoint Mode" that binds a local ZeroMQ socket with no API access, alongside a pod-reconciler auto-discovery mode requiring `get/list/watch` on pods ([[llm-d-kv-cachedocsconfigurationmd-at-main-llm-dllm-d-kv-cache-github]]) | Yes, with caveats |
| Flow control (priority bands, fairness, saturation) | Band topology is plain YAML read once at startup, not reconciled ([[configuration-llm-d]]); per-request priority resolution is CRD-bound | Partially |
| `InferenceObjective` / `InferenceModelRewrite` | Hard. Reconcilers do not start off-cluster; lookups return nil for every request ([[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]) | No |
| Endpoint discovery | Pluggable interface; default path is a controller-runtime pod reconciler ([[pod_reconcilergo]]); only shipped non-Kubernetes implementation is file-based ([[llm-d-router-module-githubcomllm-dllm-d-router-go-packages]]) | Yes, one implementation |

Two entries deserve emphasis because they are routinely underweighted. First, high availability. The charts auto-inject `--ha-enable-leader-election` whenever replicas exceed one, which silently forces Active-Passive mode, in which only the leader passes its readiness probe and standbys answer `NOT_SERVING` on purpose ([[llm-d-routerconfigchartsreadmemd-at-main-llm-dllm-d-router-github]]). Active-Passive also delivers *zero* throughput scaling — the sizing guidance is explicit that "scaling the replica count does not increase the overall EPP throughput capacity" — while Active-Active scales near-linearly at 2.0x, 2.7x, and 3.5x for two, three, and four replicas ([[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]]). All three documented HA shapes bind a Kubernetes primitive: a Lease object, a StatefulSet with a headless Service, or an as-yet-unbuilt cross-replica syncer whose peer-discovery layer has no merged implementation ([[llm-d-routerdocspeer-discoverymd-at-main-llm-dllm-d-router-github]]).

Second, the disaggregation sidecar. This component matters because prefill/decode disaggregation is one of llm-d's two founding pillars ([[llm-d-distributed-inference-serving-on-kubernetes-kgateway]]). The sidecar routes a request's prefill leg to whatever host and port the `x-prefiller-host-port` header names. Its SSRF protection is off by default, and reading the option definitions confirms that `--inference-pool` is required only when protection is switched on, with no other population path for the allowlist anywhere in the flag set ([[optionsgo]]). When protection is off, the allowlist check unconditionally returns true and the reverse proxy dials whatever it is handed, with no host validation, no rebinding protection, and no network-layer restriction at that layer ([[proxygo]]). This is not hypothetical: the original disclosure demonstrated an external caller forcing the sidecar to forward a prefill body to an arbitrary internal address, returning 200 OK ([[potential-ssrf-via-x-prefiller-url-or-x-prefiller-host-port-header-issue-242-llm]]).

The interpretive conclusion the sources do not draw for you: **llm-d has been converging on Kubernetes-native operations even while its routing layer diverged from them.** The single most recent merged change in the router repository as of this writing is a Helm feature — structured plugin configuration layered across values files, eight changed files, all chart templates and verification scripts, zero Go files touched ([[feathelm-support-structured-plugin-config-by-hugosmoreira-pull-request-2620-llm]]). The project is investing its configuration ergonomics budget in Helm, which is to say in Kubernetes packaging. A strategy that routes around Helm routes around where the project is spending its effort.

## 2. How the llm-d Router Discovers and Tracks Backends Today

The default discovery path is a controller-runtime reconciler that watches pod objects directly. Its admission filter is pure label-selector match on create, update, delete, and generic events; at reconcile time an endpoint is admitted only if the pod is not terminating, carries the `PodReady` condition, and matches the pool labels, and the datastore then consumes `pod.Status.PodIP` verbatim with no emptiness or format validation ([[pod_reconcilergo]]). This is worth stating precisely because it forecloses a popular shim: the endpoint picker never reads Services or EndpointSlices. The `InferencePool` custom resource selects pods by label and target port — it is "similar to a Service with a selector" but is not one ([[beyond-gateway-inference-traffic-control-practice-with]], [[inferencepool-kubernetes-gateway-api-inference-extension]]).

That makes the selectorless-Service-plus-manual-EndpointSlice trick a category error rather than a hard-but-viable path. It aims at kube-proxy's Service routing, a layer the picker never consults. And even where it *is* applicable, it is fragile: a documented Kubernetes issue shows a hand-authored EndpointSlice with a named port against an unnamed Service port producing a silent kube-proxy REJECT while `kubectl get endpointslice` displayed the backend correctly, and `kubectl describe service` continues to print `Endpoints: <none>` indefinitely because the legacy object is never populated in that direction ([[both-endpoints-and-endpointslices-not-working-with-service-abstraction-for-exter]]). A shim whose failures are invisible to standard tooling is not a foundation for production routing.

Once an endpoint is in the datastore, everything downstream keys off two portable strings. The proxy contract is `ip:port` — the picker returns a destination endpoint header and the proxy forwards there, with no Kubernetes object reference on the wire ([[gateway-api-inference-extensiondocsproposals004-endpoint-picker-protocol-at-main]]). In a gateway deployment this separation is sharp: the Envoy pod itself has no Kubernetes API access at all; the control plane compiles the `InferencePool` into gateway configuration and the proxy only calls the picker over the compiled external-processing endpoint, while the `InferencePool` auto-creates a headless backing Service purely so the gateway has a stable address ([[how-llm-d-routes-model-inference-traffic-on-amazon-eks-red-hat-developer]]). The precise prefix-cache producer likewise keys its index and scoring lookups on a literal `Address:Port` string, using the Kubernetes-shaped namespaced name only as bookkeeping for subscriber lifecycle ([[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcacheex]]).

This is the strongest fact in the corpus *for* the customization thesis, and I will not soften it. But notice what it does not include: **lifecycle**. On Kubernetes, an endpoint disappears from the datastore because kubelet flipped a readiness condition and a reconciler noticed. Off Kubernetes, nothing supplies that signal. The discovery interface has no liveness field in its metadata and no framework-level health gate; a plugin is solely responsible for calling upsert only on endpoints it deems healthy, and `Ready()` — a channel closed once after the first successful sync — gates request serving but says nothing about any individual endpoint ([[filediscovery-plugin-44-wiring-into-the-runner-by-ezrasilvera-pull-request-1218]]). Worse, file reload failures are logged without terminating the plugin and the datastore retains its previous state, so the failure mode is stale-but-present endpoints rather than evicted ones ([[llm-d-routerpkgeppframeworkpluginsdatalayerdiscoveryfile-at-main-llm-dllm-d-rout]]). Because the precise prefix producer installs a subscriber on add and tears it down only on delete, a backend that dies without anyone calling delete keeps its live subscriber and its cache-index entries — so the scorer will keep *preferring* a dead machine ([[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcacheex]]). No source states this failure outright; it follows directly from the extractor's add/delete lifecycle and the documented statement that removal is the surrounding orchestrator's job off-cluster ([[llm-ddocsinfrastructureno-kubernetes-deploymentmd-at-main-llm-dllm-d-github]]).

There is a second-order tax here that only shows up at scale. The picker's idle CPU grows with the number of model-serving pods because of continuous metric scraping — roughly 7.5 cores idle at 100 pods — and memory runs 4 to 6 GiB at 50 to 100 requests per second with 1k output tokens, reaching 20-plus GiB with 5k output tokens ([[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]]). On Kubernetes those numbers are a `resources:` block the chart writes for you. Off it, they are a capacity-planning exercise you own, on a process whose failure takes the entire data path down.

## 3. Extension Seams in the Router for Non-Pod Backends

There is a genuine seam, and I will describe it accurately before explaining why building on it is the wrong call.

The router defines an `EndpointDiscovery` plugin interface with `Start` and `Ready` methods, pushing upsert and delete calls into a notifier that writes to the shared datastore; implementations are expected to enumerate all known endpoints before entering a watch loop so the datastore is never served empty, with a carve-out for mechanisms whose watch guarantees no missed events ([[llm-d-routerpkgeppframeworkinterfacedatalayerdiscoverygo-at-main-llm-dllm-d-rout]]). The notifier is explicitly not goroutine-safe; all calls must be sequential from a single goroutine, and an upsert followed by a delete must arrive in that order or the endpoint is left in the datastore incorrectly. The interface's author was explicit about intent — the split existed so that "K8s, file, Slurm, and Ray discovery" could all be plugins without contaminating the data layer with infrastructure-specific code ([[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]]). The documentation includes a "writing a custom discovery plugin" section that teaches registering a factory before calling `Run` ([[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]). The registry is an exported package-level map with an exported register function ([[registrygo]]), the runner is an importable builder ([[runnergo]]), the shipped `main` is a thin wrapper over it ([[maingo]]), and nothing sits under an `internal/` path that would structurally block an out-of-tree import ([[main]]).

So: the mechanism works. Now the five facts that make it a bad place to stake production infrastructure.

**It has no ratified support policy.** The only plugin-authoring tutorial the project ships for hooking a plugin into a running picker instructs you to edit the runner's unexported in-tree registration function ([[llm-d-routerdocscreate_new_filtermd-at-main-llm-dllm-d-router-github]]). The contributing guide is sixteen lines and mentions third-party plugins nowhere ([[llm-d-routercontributingmd-at-main-llm-dllm-d-router-github]]). A repository-wide issue search for "out-of-tree" returns exactly two hits, one of them incidental ([[issues-llm-dllm-d-router-github]]). The single substantive hit is an issue opened 2026-07-21 that remains needs-triage with zero comments, and whose second proposed option reads: in-tree plugins are the supported surface, out-of-tree plugins that panic take the process down ([[framework-define-a-panic-isolation-posture-for-plugin-extension-points-issue-210]]). That an unrebutted proposal to classify your integration as unsupported has sat untriaged for almost two months is information, not noise.

**It has no crash isolation.** The same issue establishes that nothing recovers plugin invocations anywhere in the framework, from any extension point ([[framework-define-a-panic-isolation-posture-for-plugin-extension-points-issue-210]]). A nil dereference in a discovery loop written against an unfamiliar registry API takes down the endpoint picker, and in a non-Kubernetes deployment the endpoint picker *is* the data path — there is no `InferencePool` endpoint set for the proxy to fall back to.

**It has no duplicate-registration guard.** The register function unconditionally overwrites the map entry for a plugin type; whichever initializer runs last wins, silently, with no panic, warning, or log line ([[registrygo]]).

**It churns.** The discovery surface has been reshaped three times in roughly four months: the interface was renamed and moved packages during review of the original proposal ([[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]]), the configuration key moved under the data-layer section, and then moved again into a nested endpoints/peers split ([[config-consolidate-discovery-plugins-under-a-single-discovery-sectio-llm-dllm-d]]). Configuration changes shipped migration shims; the Go-level interface and factory signature have no such shim.

**Its documented configuration key ships in no release.** This is the sharpest single fact in this section. The nested key `dataLayer.discovery.endpoints.pluginRef` merged to `main` on 2026-08-25 ([[config-consolidate-discovery-plugins-under-a-single-discovery-section-follow-up]]); the newest router tag, v0.10.0, was cut 2026-08-17 and is still newest as of 2026-09-11 ([[releases-llm-dllm-d]], [[github-llm-dllm-d-achieve-state-of-the-art-inference-performance-with-modern-acc]]). A deployment pinned to a release must therefore use the legacy flat key, while the canonical documentation teaches the nested one. The documentation and the shippable artifact disagree about the exact field your entire strategy hinges on. That is a leading indicator of interface immaturity, not a cosmetic lag.

Set against those five, notice what the seam does *not* give you even when it works. The charts have no values key for it — the model-server label selector is required whenever the pool is created, and the only route in is hand-authoring the picker configuration and mounting it through the raw-config and extra-volume escape hatches ([[llm-d-routerconfigchartsreadmemd-at-main-llm-dllm-d-router-github]]). And the seam solves discovery only. Priority resolution, model rewriting, peer discovery, metrics-target discovery, and sidecar allowlisting each need their own answer.

## 4. Upstream State: Proposals and Work on Non-Pod and External Endpoints

The upstream record is genuinely two-sided, and reading only one side is how teams talk themselves into this project.

**The affirmative record.** The v0.8 release shipped the file-discovery plugin under the explicit heading "Beyond Kubernetes: RL, Slurm, and File Discovery," stating that every previous release assumed Kubernetes and this one breaks that assumption, motivated by reinforcement-learning rollout workloads that run on Slurm ([[llm-d-v08-from-platform-to-control-plane-llm-d]]). The release notes list "Non-Kubernetes mode (RL/Slurm)" as a new capability of the router ([[releases-llm-dllm-d]]), and the v0.7 roadmap had named it in advance ([[llm-d-v07-from-feature-introduction-to-production-hardening-llm-d]]). The upstream Gateway API Inference Extension introduced standalone endpoint-picker mode at v1.3.0 as an experimental single-pod proxy-plus-picker shape built for batch inference ([[release-v130-kubernetes-sigsgateway-api-inference-extension-github]]), and the design debate that produced it records a maintainer confirming real customer demand: gateway provisioning "adds friction in the cases where the proxy is literally part of the lifecycle of a batch job," and the wire protocol does not change between modes ([[inference-support-agentgateway-as-a-standalone-provider-issue-620-agentgatewayag]]). The zero-Kubernetes design discussion explicitly contemplated static endpoint configuration with no Kubernetes dependency ([[standalone-epp-issue-1838-kubernetes-sigsgateway-api-inference-extension]]).

**The record that the affirmative reading omits.** Standalone mode is not non-Kubernetes mode. The chart work that delivered it was retitled during review from "standalone mode with Envoy Proxy" to "sidecar injection in EPP," and its author stated the scope plainly: this stage still uses `InferencePool`; a standalone picker "without any k8s crd" would be a later refactor into a distinct chart ([[helm-support-for-sidecar-injection-in-epp-by-capri-xiyue-pull-request-1821-kuber]]). Two years of chart evolution later, the agentgateway standalone path still generates a Kubernetes Service for the model backend ([[add-standalone-agentgateway-proxy-support-by-danehans-pull-request-2882-kubernet]]). llm-d's own predicted-latency guide, one of its flagship routing capabilities, is entirely `kubectl` and `helm` from end to end, and "standalone" there means no Gateway object rather than no Kubernetes ([[llm-dguidespredicted-latency-routing-at-main-llm-dllm-d-github]]). An agentgateway maintainer put the architectural objection bluntly during the design debate: "Two things make sense: All Kubernetes - No Kubernetes. A hybrid of those seems very very odd" ([[inference-support-agentgateway-as-a-standalone-provider-issue-620-agentgatewayag]]).

**The record on dynamic non-Kubernetes discovery specifically is an audited absence.** Every discovery contribution in the repository targets either flat files or Kubernetes primitives. The one attempt to ship watch-based discovery plugins was closed unmerged and replaced by the file-discovery chain ([[discovery-plugins-k8s-and-file-based-endpoint-discovery-by-ezrasilvera-pull-requ]]). The published roadmap puts an orchestrator-native `SlurmDiscovery` or `RayDiscovery` plugin explicitly in the future-work bucket; the three strategies that are *not* future work — static file, generator script writing a static file, and generator script plus file watching — are all the same shipped plugin ([[no-kubernetes-no-problem-llm-d-now-runs-anywhere-llm-d]]). Peer discovery repeats the pattern one layer up: the infrastructure merged one day before the v0.10.0 tag and therefore ships ([[feat-epp-peer-discovery-infrastructure-by-evacchi-pull-request-2341-llm-dllm-d-r]]), but the only peer-discovery plugin in existence is a Kubernetes pod-watch implementation still open and marked Alpha ([[feat-pod-watch-peer-discovery-plugin-by-evacchi-pull-request-2501-llm-dllm-d-rou]]).

**The gateway tier is moving the wrong direction for this use case.** Istio's integration requires the extension custom resource definitions, control-plane environment flags, a pod label selector, and a destination rule to secure the picker channel ([[istio-kubernetes-gateway-api-inference-extension]]). NGINX Gateway Fabric selects "from a pool of ready pods designated by the assigned `InferencePool`'s Selector field" and warns that certificate verification toward the third-party picker is disabled by default ([[gateway-api-inference-extension-nginx-documentation]]). kgateway's support is auto-enabled only when the custom resource definitions exist in-cluster, and it abandoned a planned Envoy override-host load-balancer refactor — not on technical merit but because "the community decided to deprecate the Envoy-based data plane in favor of agentgateway for AI-related features" ([[add-initial-gateway-api-inference-extension-support-issue-10411-kgateway-devkgat]], [[inference-refactor-plugin-to-use-override_host-lb-issue-11824-kgateway-devkgatew]]). llm-d followed: its own gateway-provider refresh deprecates kgateway and makes agentgateway first-class ([[refresh-support-for-kgateway-agentgateway-gie-and-gw-api-by-danehans-pull-reques]]). Yet agentgateway's standalone passthrough is deliberately fail-closed, with fail-open still an open issue, because in passthrough there is no configured backend set to fail open *to* ([[support-fail-open-fallback-for-standalone-epp-inference-routing-issue-1661-agent]], [[trust-standalone-epp-selected-destinations-by-danehans-pull-request-1658-agentga]]). Meanwhile the upstream default for `InferencePool` moved to FailOpen at v1.4.0 ([[release-v140-kubernetes-sigsgateway-api-inference-extension-github]]) — a resilience posture available precisely because the proxy holds its own endpoint set.

The synthesis: **upstream is committed to platform-neutral routing and Kubernetes-first operations simultaneously, and has been consistent about both.** The customization plan requires betting that the second half will follow the first. Nothing in the record supports that bet; the newest merged work points the other way ([[feathelm-support-structured-plugin-config-by-hugosmoreira-pull-request-2620-llm]]).

## 5. Non-Pod Backend Types and What Each Requires from the Router

"Backends other than Kubernetes pods" is not one category, and the contrarian recommendation differs sharply by type. What every type needs from the router is identical and modest: a reachable `ip:port`, an OpenAI-compatible HTTP surface, and a Prometheus metrics endpoint exposing queue depth, running requests, and KV-cache utilization. What differs is everything around routing.

| Backend type | Marginal requirement | Honest verdict |
|---|---|---|
| Slurm/HPC allocation | Dynamic, churning endpoint set; inbound reachability from the router's network | Convert with Slinky, or accept file discovery regenerated per job |
| Bare-metal / VM fleet | Stable addresses; external health signal; manual metrics scrape config | File discovery through a ConfigMap; no plugin needed |
| Docker/Podman/Nomad | Orchestrator-specific enumeration; frequent churn | The only genuine plugin case — and the weakest against alternatives |
| Remote Kubernetes clusters | Cross-cluster addressing | Use the multi-cluster variant or import mechanisms; not this problem |
| Managed/external OpenAI-compatible APIs | Auth, quotas, no metrics endpoint, no KV visibility | Out of scope for the picker; belongs at an AI-gateway tier |
| Serverless GPU providers | Cold starts, ephemeral addresses, no stable identity | Poor fit for cache-affinity routing regardless of router |

Three of these rows carry load-bearing evidence.

**Slurm.** The default framing treats Slurm as the hard case requiring router surgery. It is the easiest case requiring none, because the integration already exists in the opposite direction. Slinky's operator represents each Slurm daemon as a custom resource and manages them as pods, surfacing Slurm node states as native pod conditions, supporting scale-to-zero and horizontal autoscaling with drain-before-terminate, and running in production at NVIDIA on clusters exceeding 1,000 worker nodes and 8,000 GPUs with collective-communication performance matching non-containerized Slurm ([[running-large-scale-gpu-workloads-on-kubernetes-with-slurm-nvidia-technical-blog]], [[github-slinkyprojectslurm-operator-run-slurm-on-kubernetes-a-slinky-project-gith]]). Slurm workers that are real pods carry real pod IPs and match a label selector; the stock router routes to them with zero customization. The objection — that this hands scheduling custody of the fleet to Kubernetes — is real and is the correct axis on which to decide. It is not an objection to feasibility.

**Virtual pods.** The opposite direction fails, and it fails for a reason worth stating exactly. Architecturally, a virtual-kubelet-backed pod would pass the picker's admission path unchanged, since that path checks only label match, non-terminating status, and the ready condition, and consumes the reported pod IP without validation ([[pod_reconcilergo]], [[github-virtual-kubeletvirtual-kubelet-virtual-kubelet-is-an-open-source-kubernet]]). The blocker is networking, not admission. interLink, the production HPC provider, states in its own documentation that long-running services are explicitly "NOT a target" — it is "optimized for tasks that have a defined start and end, rather than persistent services exposing intra-cluster communication endpoints" ([[introduction-interlink]]) — and its Slurm plugin's networking is an SSH-tunnelled egress proxy to a login node, "your window to the external world," which is outward-facing by construction ([[github-interlink-hqinterlink-slurm-plugin-github]]). An inference gateway must open connections *into* the backend. The shim is architecturally admissible and operationally dead.

**Disaggregated prefill/decode, anywhere off Kubernetes.** This is the requirement that changes a deployment plan and is easiest to miss. The sidecar's allowlist takes its inputs from exactly two sources — the named `InferencePool` resource and the pods its selector matches, watched through shared informers with a 30-second resync — and there is no static file, CIDR range, or flag alternative in the implementation ([[allowlistgo]]). Enabling it additionally requires cluster-level role bindings for pool and pod watches ([[featsidecar-implement-ssrf-protection-with-inferencepool-host-port-allowlist-by]]). Off Kubernetes you must therefore run the sidecar with protection disabled, in which case the request handler proxies the prefill leg — and the KV-cache-source and encoder targets — to whatever the headers name ([[chat_completionsgo]]). The upstream threat model does place the primary control upstream: the picker clears any client-supplied prefill header before setting its own, a fix whose author noted the extension protocol supports only set-header mutations, so clearing was the best available ([[clear-prefill-target-header-if-set-in-incoming-request-by-elevran-pull-request-2]]). That control is portable. But it protects only the path through the picker; it does nothing for a caller with direct network reach to the sidecar port. And the allowlist is a weaker net than it appears even when enabled: an open issue demonstrates, with a captured reproduction, that it stores bare pod IPs and names without ports while the check strips the port from its input, so an allowlisted address with an attacker-chosen port passes ([[pd-sidecar-allowlist-stores-only-pod-ip-not-hostport-issue-979-llm-dllm-d-router]]). The honest off-Kubernetes requirement is therefore a network-isolation obligation you own — firewall or security-group rules making the sidecar port reachable only from the trusted gateway path — plus transport security, which is genuinely portable since the TLS flags are ordinary `net/tls` settings with no Kubernetes dependency ([[optionsgo]]).

## 6. Candidate Strategies Compared

Here is the steel-man of the position I am arguing against, stated as strongly as the evidence permits, followed by the answer.

**The strongest case for building a custom discovery plugin.** The interface was designed for exactly this; its author named Slurm and Ray as target backends in the design review ([[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]]). The project shipped file discovery as a headline capability and framed itself as a control plane that runs anywhere ([[llm-d-v08-from-platform-to-control-plane-llm-d]]). Registering a custom discovery plugin is documented upstream, not merely tolerated ([[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]). The reuse above the seam is genuinely total: the runner supplies the external-processing server, configuration loading, draining, and health wiring, so you inherit the scheduler, flow control, and metrics unchanged ([[runnergo]]). The flagship scorer survives the move at the code level ([[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcacheex]]), and the performance stakes are large — precise prefix-cache scheduling has been reported at roughly 57 times faster p90 time-to-first-token than approximate scheduling on a shared-prefix workload ([[kv-cache-wins-you-can-see-from-prefix-caching-in-vllm-to-distributed-scheduling]]), with time-to-first-token falling from 35 seconds to 120 milliseconds and throughput up 151 percent versus cache-blind routing ([[intelligent-inference-scheduling-with-llm-d-on-red-hat-ai-red-hat-developer]]). The proxy contract is an `ip:port` header, so the investment is reversible ([[gateway-api-inference-extensiondocsproposals004-endpoint-picker-protocol-at-main]]). Nothing structurally blocks the import ([[gomod]]). And a benchmark issue suggests multi-replica Active-Active behavior with precise prefix routing actually *improves* with scale, failures falling from an unusable baseline to 18 at four replicas while median time-to-first-token dropped from 165 to 30 milliseconds at 500 queries per second ([[evaluate-llm-d-router-both-epp-and-the-standalone-proxy-scale-limits-issue-1290]]).

**The answer.** Every one of those claims is true. Together they establish that llm-d's *scheduling algorithms* are portable. They do not establish that customizing the router is the right strategy, for four reasons.

First, **the unit of work is a bundle, not a plugin.** Discovery is one component. Health gating is a second, because nothing in the framework supplies it ([[filediscovery-plugin-44-wiring-into-the-runner-by-ezrasilvera-pull-request-1218]]). Per-request priority is a third, because the objective lookup returns nil for every request off-cluster and there is no file-mode equivalent ([[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]) — and any such plugin registers at Alpha stability, requiring an experimental-plugins flag to start ([[llm-d-routerpkgeppframeworkpluginsreadmemd-at-main-llm-dllm-d-router-github]]). Peer discovery is a potential fourth, since the only implementation is unmerged ([[feat-pod-watch-peer-discovery-plugin-by-evacchi-pull-request-2501-llm-dllm-d-rou]]). Coordination is a potential fifth if you need multi-replica HA off-cluster ([[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]]). Non-Go work rounds it out: a hand-authored Envoy configuration, static or file-based Prometheus service discovery replacing PodMonitor ([[metrics-llm-d]]), and network isolation for the sidecar. Each component multiplies exposure to a Go interface with no compatibility promise and no panic isolation.

Second, **you would be the first known user.** Precedent absence here is established, not assumed: no known importers on the package index as of 2026-09-11, nothing in the contributing guide, and a repository-wide search returning nothing ([[llm-d-routercontributingmd-at-main-llm-dllm-d-router-github]], [[issues-llm-dllm-d-router-github]]). Being first is survivable when the project has a support policy. Here the only written statement is an untriaged proposal to classify your pattern as unsupported ([[framework-define-a-panic-isolation-posture-for-plugin-extension-points-issue-210]]).

Third, **the alternatives are not strawmen.** Dynamo makes discovery backend a first-class configuration choice, with etcd or NATS JetStream required only for Slurm-class distributed deployments and a file backend available otherwise ([[github-ai-dynamodynamo-a-datacenter-scale-distributed-inference-serving-framewor]]); its discovery consumer separates a full instance listing from the incremental event stream, the same list-then-watch shape ([[watcherrs]]); and it ships a standalone endpoint picker specifically to add KV-aware routing to upstream vLLM fleets without migrating them ([[kv-aware-routing-on-kubernetes-nvidia-dynamo-documentation]]). vLLM production-stack's discovery abstraction requires one method and ships a static implementation that pairs a fixed topology with a background health-check thread filtering unhealthy URLs — precisely the health gate llm-d asks you to write ([[service_discoverypy]]). vLLM Router ships static worker URLs by default ([[github-vllm-projectrouter-a-high-performance-and-light-weight-router-for-vllm-la]]).

Fourth, **the HA counterargument cuts both ways.** The benchmark data is real, but its own operational context undermines the off-cluster reading: the chart auto-injects leader election above one replica, silently forcing Active-Passive unless disabled ([[llm-d-routerconfigchartsreadmemd-at-main-llm-dllm-d-router-github]]); flow-control state remains per replica, so priority and fairness are enforced only within each replica's share ([[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]]); and the benchmark used independent synthetic requests, so it says nothing about session-pinned workloads ([[evaluate-llm-d-router-both-epp-and-the-standalone-proxy-scale-limits-issue-1290]]). No source states that cross-replica session affinity is safe off-cluster; the benchmark's method and the per-replica flow-control statement jointly imply it is untested.

| Strategy | llm-d reuse | Maintenance burden | Feature parity | Ops complexity | Verdict |
|---|---|---|---|---|---|
| **A. Convert estate to pods (Slinky)** | Total — stock router, stock charts | Operator upgrades only | Full, including CRD policy and sidecar allowlist | Low for routing; high for fleet custody transfer | **Best where acceptable** |
| **B. Router in Kubernetes + file discovery via ConfigMap** | Very high — all charts, HA, proxy tier retained | An endpoint-generator script | Loses per-request priority and model rewrite; keeps everything else | Moderate; generator must be health-gated | **Default recommendation** |
| **C. Out-of-tree discovery plugin, custom binary** | High above the seam; zero below it | Bundle of plugins against a churning, unratified interface; no crash isolation | As B, plus whatever you rebuild | High — HA, packaging, metrics, isolation all yours | **Only after B fails** |
| **D. In-tree fork** | Same as C | Same as C plus rebase against a surface reshaped three times in four months | Same as C | Same as C | **Strictly dominated by C** |
| **E. Embed libraries in a hand-built router** | Low — you reimplement the server, config, health, draining | Dozens of interfaces instead of one or two | You own parity | Highest | **Reject** |
| **F. Kubernetes object shims (EndpointSlice, virtual pods)** | N/A | N/A | Picker never reads EndpointSlices; no HPC virtual-kubelet provider offers inbound reachability | N/A | **Reject as category error** |

## 7. Recommended Strategy and Implementation Roadmap

**Recommendation: keep the router in Kubernetes. Move the endpoint inventory, not the router.** Concretely, adopt a three-gate decision ladder and stop at the first gate that clears.

**Gate 1 — Can the compute become pods?** If the estate is Slurm and the organization can accept Kubernetes as the primary scheduler, run Slinky and stop. You then operate stock llm-d with zero customization: stock charts, leader-elected HA, `InferenceObjective` priority, `InferenceModelRewrite` canaries, PodMonitor scraping, and a sidecar allowlist that actually functions because a real `InferencePool` exists ([[github-slinkyprojectslurm-operator-run-slurm-on-kubernetes-a-slinky-project-gith]], [[allowlistgo]]). The cost is custody of the fleet's scheduling, which is a governance decision, not an engineering one. Decide it explicitly rather than defaulting past it.

**Gate 2 — Can the endpoint set be enumerated by a script?** If yes — and for bare-metal fleets, VM pools, static Slurm allocations, and per-job reservations it almost always is — run the endpoint picker as an ordinary Kubernetes Deployment targeting external addresses, with file discovery reading a mounted ConfigMap. The published patterns for Ray and Slurm are exactly this: a cron job or webhook that calls the orchestrator's own listing command and rewrites the endpoints file, which the plugin's file watcher picks up ([[no-kubernetes-no-problem-llm-d-now-runs-anywhere-llm-d]]). The plugin was written to handle atomic renames and symlink swaps, which is how a ConfigMap volume updates ([[llm-d-routerpkgeppframeworkpluginsdatalayerdiscoveryfile-at-main-llm-dllm-d-rout]]), and the chart's raw-config and extra-volume keys make the wiring reachable without a fork ([[llm-d-routerconfigchartsreadmemd-at-main-llm-dllm-d-router-github]]). This is the recommendation for most readers. It writes zero Go, keeps leader-elected HA and the entire packaging surface, and surrenders only the two CRD-driven policy inputs.

**Gate 3 — Only if both gates fail.** If backends are dynamic, non-enumerable, and cannot be pods, do not start with the plugin. Start with a bake-off against a router that ships this natively, budgeted at two weeks. If llm-d's scheduling depth wins that bake-off on your workload, then and only then build the plugin — with a hard budget and named exit criteria.

**Roadmap.**

*Phase 0 (week 1) — Kill the question cheaply.* Decide Gates 1 and 2 in writing. Pin llm-d-router at v0.9.0 or later, the floor at which the endpoint-metadata notification fix that precise-prefix subscribers depend on is present ([[endpoint-metadata-updates-do-not-trigger-endpoint-notification-events-issue-1403]]). Confirm your pinned release's discovery key: on v0.10.0 it is the legacy flat form, because the nested form ships in no release ([[config-consolidate-discovery-plugins-under-a-single-discovery-section-follow-up]], [[releases-llm-dllm-d]]).

*Phase 1 (weeks 2-3) — Stand up Gate 2 end to end.* Endpoint picker as a Deployment, file discovery from a ConfigMap, one generator writing only endpoints that pass a live health probe and deleting on the first failed probe. Health gating is the non-negotiable requirement, above any poll-versus-watch consideration, because a dead backend otherwise retains its datastore entry, its KV-event subscriber, and its index entries ([[filediscovery-plugin-44-wiring-into-the-runner-by-ezrasilvera-pull-request-1218]]). Copy production-stack's shape: fixed topology, background health thread, unhealthy addresses filtered from what discovery returns ([[service_discoverypy]]).

*Phase 2 (week 4) — Validate the claim nobody has published.* No source in the record pairs precise prefix-cache routing with file discovery in a running deployment; llm-d's own no-Kubernetes reference configuration uses the approximate scorer ([[llm-dguidesno-kubernetes-deployment-at-main-llm-dllm-d-github]]). The code says it works ([[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcacheex]]). Prove it on your hardware before depending on it. Verify that engines bind their KV-event publisher socket where the picker expects and that the picker can reach it ([[llm-dguidesprecise-prefix-cache-routingreadmemd-at-main-llm-dllm-d-github]]). For data-parallel multi-rank engines, note that the file schema carries no rank field, so every file-discovered endpoint sits at rank zero — fine for single-rank, wrong for multi-rank.

*Phase 3 (week 5) — Close the policy and security gaps.* Replace PodMonitor with static or file-based Prometheus scrape configuration against the picker's metrics port and each engine's metrics endpoint ([[metrics-llm-d]]). For model selection, use the per-request model-rewrite header, which the API reference documents as the alternative to the server-side rewrite resource ([[epp-http-headers-reference-llm-d]]); push weighted canary decisions to the gateway tier. Defer the static-priority plugin until priority tiers are actually in use, since tenant fairness already works as a bare header string and missing objectives simply default to priority zero ([[llm-d-flow-control-priority-queuing-for-shared-gpu-inference-red-hat-developer]]). If you run disaggregation, treat sidecar reachability as a firewall problem and enable prefill TLS, which is pure flags ([[optionsgo]]).

*Phase 4 (only if Gate 3) — The bundle, budgeted.* Namespace your plugin type string to avoid silent overwrite ([[registrygo]]). Wrap your own start goroutine in recovery, because the framework provides none ([[framework-define-a-panic-isolation-posture-for-plugin-extension-points-issue-210]]). Default to poll-and-diff rather than a persistent watch: the project's own watch-based discovery attempt was abandoned as too large to review ([[discovery-plugins-k8s-and-file-based-endpoint-discovery-by-ezrasilvera-pull-requ]]). Run scheduled continuous integration compiling your plugin against upstream `main`. Open an upstreaming conversation immediately — the maintainers have said in writing they want this class of plugin ([[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]]) — and set a review date at which an unmerged contribution plus unresolved panic-isolation policy triggers migration to a router that ships discovery natively ([[github-ai-dynamodynamo-a-datacenter-scale-distributed-inference-serving-framewor]]).

*Proxy decision, cutting across phases.* Choose Envoy with llm-d's reference standalone configuration, not agentgateway passthrough. llm-d's Envoy path ships scoped fail-open during the lease-transition window, defaulted on, forwarding to already-known backends ([[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]]); agentgateway passthrough is fail-closed with fail-open unresolved ([[support-fail-open-fallback-for-standalone-epp-inference-routing-issue-1661-agent]]). Be honest that outside Kubernetes the lease window does not exist, so fail-open is meaningful only if you deliberately configure a fallback cluster. Client-supplied destination headers are not a spoofing risk: the picker's header generation skips system-owned keys, with a test asserting that a client-injected destination value is replaced by the picker's own computed target ([[fix-harden-header-sanitization-and-handling-logic-by-lukeavandrie-pull-request-2]]).

## 8. Risks, Trade-offs, and Open Questions

**The risk of following this recommendation.** Gate 2 concedes per-request priority and rule-based model rewriting, which matters for multi-tenant platforms selling differentiated latency tiers. It also concedes the operator-managed metrics pipeline, which is a real ergonomic loss for teams standardized on Prometheus Operator. And it accepts a moving part — the endpoint generator — with no off-the-shelf component behind it. These are genuine costs, and if your organization needs CRD-driven priority governance today, Gate 1 rather than Gate 2 is your answer.

**The risk of ignoring it.** Concentrated in one place: you become the sole maintainer of an integration the upstream project has not agreed to support, against an interface that reshaped three times in roughly four months, whose documented configuration key ships in no release, whose registration path has no duplicate guard, whose invocation path has no panic recovery, and whose watch-based precedent was abandoned by its own author. Each fact alone is tolerable. Together they describe a surface not yet ready to carry production weight.

**Where I could be wrong, stated as falsification conditions.** If the panic-isolation issue is triaged toward a documented out-of-tree posture and that text lands in the plugin developer documentation, the precedent objection weakens materially. If a merged pull request adds a pluggable coordination primitive with a file, etcd, or Consul lock, the availability objection substantially collapses. If any orchestrator-native discovery plugin merges, the audited absence closes and the seam acquires the in-repo precedent it currently lacks. If the charts grow a first-class discovery key, the packaging objection disappears outright. These are not hedges; they are the specific commits that should reverse the recommendation, and each is plausible within two release cycles.

**Open questions the record does not answer.** Nobody has published a deployment running the endpoint picker inside Kubernetes with discovery pointed at out-of-cluster addresses; it is an inference from chart mechanics and the plugin's deliberate handling of symlink-swap updates, not an observed pattern. Nobody has published precise prefix-cache routing paired with file discovery end to end. The Envoy external-processing failure-mode setting in the no-Kubernetes reference configuration is unverified, and the proxy's documented default is fail-closed, so no one should claim fail-open off-cluster by default. Repeated-upsert idempotency on file reload is unconfirmed, which bears directly on whether a regenerating endpoint file churns KV-event subscribers. Cross-replica session affinity under Active-Active was never evaluated. And the pull request that most recently touched the sidecar allowlist was closed rather than merged, so the provenance of the current implementation deserves direct verification against the tree before anyone relies on its behavior ([[featsidecar-implement-ssrf-protection-with-inferencepool-host-port-allowlist-by]]).

**Looking eighteen months out, the decisive variable is not technical but organizational: whether the endpoint-picker protocol becomes the industry's routing seam, or whether each stack keeps its own picker.** The evidence currently points at the former, and it is the best reason to be relaxed about this decision. Dynamo implements the same picker protocol behind the same gateway extension and offers it as an on-ramp for fleets running plain upstream vLLM ([[kv-aware-routing-on-kubernetes-nvidia-dynamo-documentation]]); llm-d has moved from building its own engine images to consuming upstream ones and describing itself as a control plane rather than a distribution ([[llm-d-v08-from-platform-to-control-plane-llm-d]]); and the protocol identifies backends as `ip:port`, not as Kubernetes objects ([[gateway-api-inference-extensiondocsproposals004-endpoint-picker-protocol-at-main]]). That convergence has a direct consequence for strategy: because the proxy talks to any picker over the same wire contract, swapping picker implementations later is a configuration change, while a bespoke discovery plugin compiled into a bespoke binary is a code asset that does not transfer. The cheap, reversible move is to keep the routing decision behind a standard protocol and keep the endpoint inventory in a boring, inspectable file. The expensive, sticky move is to become the first out-of-tree importer of a three-month-old Go interface. If upstream ships orchestrator-native discovery — and its own roadmap says it intends to ([[no-kubernetes-no-problem-llm-d-now-runs-anywhere-llm-d]]) — teams that waited will adopt it as configuration, while teams that built early will spend that release migrating off their own plugin. The whole recommendation reduces to one sentence: **keep the customization in a file, not in a fork, until upstream tells you in writing that the fork is supported.**
