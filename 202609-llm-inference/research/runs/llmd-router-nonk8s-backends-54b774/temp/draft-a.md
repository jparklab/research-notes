# Customize One Seam: Running the llm-d Router Against Non-Pod Backends

Customize llm-d at exactly one place — the `EndpointDiscovery` plugin interface — and reuse everything above it unchanged. That is the answer, and the code supports it more strongly than the project's own marketing does. The llm-d router's endpoint picker (EPP — the service that decides which model server each request goes to) was deliberately refactored so that "what endpoints exist" is a plugin and "how to route across them" is not: the maintainer who built the interface wrote, in the merge review, that "we want K8s, file, Slurm, and Ray discovery all as plugins" precisely so the shared data layer never gets "contaminated with infrastructure-specific code (`ctrl.Manager`, fsnotify, etc.)" [[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]]. When a discovery plugin is configured, the EPP "does not call `ctrl.GetConfig()` or start a controller manager," "does not require an `InferencePool` CRD or any K8s RBAC," and "all scheduling, request control, and metrics collection behaviour is unchanged" [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]].

Ship it in three phases. **Phase 0 (zero Go):** point the shipped `file-discovery` plugin at an endpoints file that an external generator — a cron job, a Slurm epilog, a Ray callback, a Consul-watching script — rewrites atomically; the plugin re-attaches its `fsnotify` watcher across atomic renames and ConfigMap-style symlink swaps, and deletes endpoints that vanish from the file [[readmemd]] [[file-discovery-34-add-filediscovery-plugin-with-yamljson-file-loading-and-fsnoti]]. **Phase 1 (one Go file plus a `main`):** when a flat file stops expressing your topology, write a custom `EndpointDiscovery` implementation, register it with the exported package-level registry, and run it from a thin downstream `main()` that imports `cmd/epp/runner` and calls `runner.NewRunner().Run(ctx)` — the registry is a plain exported map (`Registry[pluginType] = factory`) with no `internal/` barrier anywhere on the import path [[registrygo]] [[main]]. **Phase 2 (in parallel):** upstream the plugin, because the maintainers have said in writing they want exactly this class of contribution, and because upstreaming is the only way to convert an unratified extension pattern into a supported one.

The affirmative case is strongest where the skeptics expect it to be weakest: the flagship precise prefix-cache scorer. Reading `extractor.go` at HEAD settles it — the precise producer implements the generic `fwkdl.EndpointExtractor` interface, its subscriber lifecycle is driven by "endpoint lifecycle events emitted by the endpoint-notification-source," and its index and score lookups key on a literal `fmt.Sprintf("%s:%s", meta.Address, meta.Port)` string, never on a Kubernetes object identity [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcacheex]] [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcachepr]]. Whatever populates `EndpointMetadata.Address` and `.Port` — a pod watch, a YAML file, your Consul plugin — feeds the same path. The same neutrality holds one layer down at the wire: the proxy protocol carries "at least one endpoint in `<ip:port>` format," not a pod reference [[gateway-api-inference-extensiondocsproposals004-endpoint-picker-protocol-at-main]].

What you do *not* get for free is narrow and nameable: per-request priority via `InferenceObjective` and model rewriting via `InferenceModelRewrite` go dark because their reconcilers never start [[readmemd]]; endpoint health and eviction become your plugin's job, because kubelet readiness gating disappears with the pod watch [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]; multi-replica router failover in its default Active-Passive form uses a Kubernetes `coordination.k8s.io/Lease` [[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]]; and the prefill/decode sidecar's anti-SSRF allowlist is built from an `InferencePool`'s pods, so off-cluster prefill/decode needs network isolation plus `--enable-tls=prefill` rather than that allowlist [[github-llm-dllm-d-routing-sidecar-incubating-pd-sidecar-for-llm-d-github]]. Each of those has a concrete, bounded answer below. None of them touches the scheduling stack, which is the part you actually wanted.

Two version facts govern the build from day one. Pin `llm-d-router` at **v0.9.0 or newer** — `FileDiscovery` shipped in v0.9.0 (2026-06-23) and the endpoint-metadata notification fix that precise-prefix subscribers depend on landed in the same release [[releases-llm-dllm-d-router]] [[endpoint-metadata-updates-do-not-trigger-endpoint-notification-events-issue-1403]]. And write the **legacy** config key if you pin the current release: the nested `dataLayer.discovery.endpoints.pluginRef` was merged on 2026-08-25, eight days *after* the v0.10.0 tag of 2026-08-17, and v0.10.0 is still the newest release as of 2026-09-11 — so a pinned v0.10.0 binary reads `dataLayer.discovery.pluginRef`, and the nested form applies only to `main` builds and whatever release follows [[config-consolidate-discovery-plugins-under-a-single-discovery-sectio-llm-dllm-d]] [[releases-llm-dllm-d-router]] [[runnergo]].

## 1. llm-d Component Inventory and Kubernetes Coupling

### A. The stack, sorted by what it actually depends on

llm-d is not one binary. It is a control plane wrapped around unmodified inference engines — a framing the project made explicit when it dropped its custom vLLM images in favour of upstream ones [[llm-d-v08-from-platform-to-control-plane-llm-d]]. That matters here because it means the Kubernetes coupling is not diffused through the system; it is concentrated in a handful of named components, and one of them is the only one you have to replace.

| Component | What it does | Kubernetes coupling | Reusable off-pod? |
|---|---|---|---|
| EPP scheduling framework (filters, scorers, pickers, profile handlers) | Scores and selects an endpoint per request | None — operates on `EndpointMetadata` from the datastore | **Yes, unchanged** [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]] |
| Data layer sources/extractors (metric scraping) | Polls each endpoint's Prometheus `/metrics` for queue depth, KV utilisation | None — plain HTTP to `address:port` | **Yes, unchanged** [[distributed-llm-inference-with-llm-d-moncef-abboud]] |
| `precise-prefix-cache-producer` + KV index | Subscribes to engine KV-events over ZMQ, indexes blocks, scores cache locality | None — driven by generic endpoint events, keyed on `Address:Port` | **Yes, unchanged** (rank-0 backends) [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcacheex]] |
| Flow control (priority bands, fairness, saturation) | Central queue, sheds or queues under load | Config is plain YAML read at startup, not reconciled | **Yes**, minus objective lookup [[configuration-llm-d]] |
| Endpoint discovery | Enumerates endpoints into the datastore | **This is the seam** — default path is a pod watch | **Replace this** [[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]] |
| `InferenceObjective` / `InferenceModelRewrite` reconcilers | Per-request priority; model-name rewriting and canary splits | Custom resources watched by controller-runtime | **No** — inactive off-cluster [[readmemd]] |
| EPP high availability (Active-Passive) | Leader election across router replicas | `coordination.k8s.io/Lease` | **No** — substitute Active-Active or keep a small cluster [[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]] |
| Peer discovery (for future cross-replica sync) | Tracks live router replicas | Only shipped implementation watches Pods, and is still unmerged | **Not yet** [[feat-pod-watch-peer-discovery-plugin-by-evacchi-pull-request-2501-llm-dllm-d-rou]] |
| Helm charts (`llm-d-router-gateway`, `-standalone`) | Packaging | Pod-label-driven; `router.modelServers.matchLabels` required when creating a pool | **Partially** — via raw-config escape hatches [[llm-d-routerconfigchartsreadmemd-at-main-llm-dllm-d-router-github]] |
| Envoy / proxy data plane | Forwards to the EPP's chosen `ip:port` | None in standalone form — static `envoy.yaml` with `ORIGINAL_DST` | **Yes** [[llm-ddocsinfrastructureno-kubernetes-deploymentmd-at-main-llm-dllm-d-github]] |
| Gateway-mode proxies (Istio, kgateway, NGINX, GKE) | Ingress with `InferencePool` integration | Fully CRD-driven | **No** — use standalone Envoy instead |
| P/D disaggregation sidecar | Coordinates prefill→decode KV transfer | SSRF allowlist watches an `InferencePool`; off by default | **Yes, with network isolation** [[github-llm-dllm-d-routing-sidecar-incubating-pd-sidecar-for-llm-d-github]] |
| `InferencePool` (Gateway API Inference Extension) | Declares the backend set | A Kubernetes custom resource, selects Pods by label | **Bypassed entirely** [[inferencepool-kubernetes-gateway-api-inference-extension]] |

### B. The interpretive point the table makes

Count the rows. Eleven of fourteen components are either fully portable or portable with a named, small mitigation. The three that are not — the two CRD-driven policy reconcilers and Lease-based leader election — are all *control-plane conveniences*, not routing logic. Every "lost" capability traces to a controller-runtime reconciler or to kubelet semantics; none of them traces to the scheduler. That asymmetry is not an accident of implementation, it is the shape the refactor was designed to produce, and it is why the one-seam strategy is available at all.

There is also a second-order signal worth reading: llm-d's own module index at v0.10.0 lists exactly one exported discovery-backend package, `.../datalayer/discovery/file`, described as "a file-based `EndpointDiscovery` implementation that reads a YAML (or JSON) file listing inference endpoints" [[llm-d-router-module-githubcomllm-dllm-d-router-go-packages]]. The Kubernetes pod watch never moved behind the interface. That is simultaneously the corpus's biggest gap (no watch-based reference implementation to copy) and its most useful clue: the interface was defined *for* the non-Kubernetes case first, which is why the non-Kubernetes case is the one that works cleanly today.

## 2. How the llm-d Router Discovers and Tracks Backends Today

### A. The default path, at code level

By default the EPP watches an `InferencePool` object and the Pods its label selector matches [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]. The admission logic in the pod reconciler is startlingly thin: the event filters admit a Pod when `Datastore.PoolLabelsMatch(pod.GetLabels())` is true, and the reconcile-time gate deletes it unless the pod is Ready and still label-matching — where "Ready" is only a non-zero deletion timestamp check plus a scan for the aggregate `PodReady == ConditionTrue` condition [[pod_reconcilergo]]. Downstream, `pod.Status.PodIP` is consumed verbatim, with no emptiness or format validation. There is no check on `Spec.NodeName` and none on `Status.Phase`.

That detail is load-bearing for the argument, so state the inference explicitly: sources establish (a) that the admission path checks only label match plus aggregate readiness [[pod_reconcilergo]], and (b) that the datastore entry a discovery source produces is an `EndpointMetadata` carrying `ID`, `Address`, `Port`, `MetricsHost` and `Labels` [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]. Taken together, these imply that nothing downstream of admission can tell a pod-sourced endpoint from a file-sourced one — the Kubernetes-ness of a backend is erased at the datastore boundary. No single source says that sentence; the two together entail it.

### B. Where exactly the Kubernetes assumption is baked in

Four places, and only four:

1. **Runner startup.** `Run()` calls `ctrl.GetConfig()` and stands up a controller-runtime manager on the default path; the file-discovery path is a separate branch that skips manager setup entirely [[discovery-plugins-k8s-and-file-based-endpoint-discovery-by-ezrasilvera-pull-requ]] [[filediscovery-plugin-44-wiring-into-the-runner-by-ezrasilvera-pull-request-1218]].
2. **Pool identity.** The `InferencePool` custom resource declares the selector and target ports; `--pool-name` / `--pool-namespace` name it. In file-discovery mode those flags are demoted to labels: the no-Kubernetes guide states they "are not Kubernetes references in file-discovery mode; they are only used as labels in the EPP's metrics and log lines" [[llm-dguidesno-kubernetes-deployment-at-main-llm-dllm-d-github]].
3. **Health gating.** Aggregate pod readiness, including custom readiness gates, is what keeps unready workers out of the pool — a mechanism a custom backend "must replicate itself" [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]].
4. **CRD-driven policy.** The `InferenceObjective` and `InferenceModelRewrite` reconcilers, and any `k8s-notification-source` data-layer plugin, simply do not bind; the runner logs a startup line naming the inactive features [[readmemd]].

Notice what is *not* on that list: scoring, filtering, picking, metric scraping, KV indexing, flow control, the ext_proc server, draining, or the wire protocol.

### C. The wire is already pod-free

The proxy never learns about pods. The Endpoint Picker Protocol — status "Implemented," versioned v1.0.0 as of 2025-07-29 — specifies that the EPP returns its choice in the `x-gateway-destination-endpoint` header and a matching `envoy.lb` dynamic-metadata entry, and that "the value of the header or metadata entry MUST contain at least one endpoint in `<ip:port>` format or multiple endpoints in `<ip:port>,<ip:port>,...` format" [[gateway-api-inference-extensiondocsproposals004-endpoint-picker-protocol-at-main]]. Off Kubernetes the flow is exactly the same, wired statically: client → Envoy listener `:8081` → ext_proc gRPC `:9002` → `ORIGINAL_DST` cluster → the worker's `<address>:<port>` [[llm-ddocsinfrastructureno-kubernetes-deploymentmd-at-main-llm-dllm-d-github]]. A practitioner write-up of the request path describes the same loop from the outside: Envoy streams headers and body to the EPP's `Process` handler, the director runs admission, flow control, data producers and the scheduler, and the EPP answers with a header naming an IP and port [[distributed-llm-inference-with-llm-d-moncef-abboud]].

Because the protocol is the seam between proxy and picker, your investment in llm-d is reversible at the architecture level and irreversible only at the plugin level — a point NVIDIA independently demonstrates by shipping its own endpoint picker behind the same protocol, including a topology explicitly aimed at "upstream vLLM pods" with "direct vLLM worker discovery" rather than its own worker stack [[kv-aware-routing-on-kubernetes-nvidia-dynamo-documentation]].

### D. The replacement interface

The `EndpointDiscovery` contract is five lines of Go plus two obligations. `Start(ctx, notifier)` blocks, enumerating known endpoints via `notifier.Upsert` before entering its watch loop so the datastore is not empty at first request; `Ready()` returns a channel closed exactly once after a successful initial sync [[no-kubernetes-no-problem-llm-d-now-runs-anywhere-llm-d]] [[filediscovery-plugin-44-wiring-into-the-runner-by-ezrasilvera-pull-request-1218]]. The notifier is explicitly **not** goroutine-safe: "an `Upsert` followed by a `Delete` for the same endpoint must arrive in that order or the endpoint will be incorrectly left in the datastore," so all calls must come from one goroutine [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]. The runner gates the ext_proc server and the health service on `Ready()` closing, but deliberately does not gate `/metrics`, so a slow startup stays observable [[filediscovery-plugin-44-wiring-into-the-runner-by-ezrasilvera-pull-request-1218]].

One residual Kubernetes-ism survives in the type system: endpoint identity is `types.NamespacedName`. A reviewer flagged it during the interface's merge — "I wonder if this is not too k8s centric and we should include an explicit `UniqueID`" — and the author agreed while deferring the change [[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]]. For a non-pod backend this is a naming tax, not a blocker: mint a stable two-part identity (job name plus partition, service ID plus datacenter) and move on. It is also why identity and addressing must not be conflated — see the next section.

## 3. Extension Seams in the Router for Non-Pod Backends

### A. The primary seam and its documented authoring path

`docs/discovery.md` contains a section titled "Writing a custom discovery plugin" that gives a complete skeleton: implement `fwkdl.EndpointDiscovery`, declare a `PluginType` constant, expose a `Factory(name string, params *json.Decoder, _ fwkplugin.Handle)`, and "register the factory in the runner before calling `Run`" via `fwkplugin.Register(myplugin.PluginType, myplugin.Factory)`, then point the discovery config at the plugin's instance name [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]. That is upstream documentation for the exact mechanism this report recommends. The only part that is an inference rather than a documented instruction is the *packaging* — putting that `Register` call in your own `main()` instead of editing the repo's runner — and `cmd/epp/main.go` is a fifteen-line wrapper around `runner.NewRunner().Run(ctx)`, which makes the substitution mechanical [[maingo]].

The registry makes it work. `registry.go` declares `var Registry = map[string]FactoryFunc{}` at package scope and mutates it through exported `Register`, `RegisterAsDefaultProducer`, `RegisterWithPluginDependencies` and `RegisterDeprecated` functions, with no "internal use only" disclaimer and no duplicate-key guard [[registrygo]]. Because Go runs every package's `init()` before `main()` begins, a blank import of your plugin package lands your factory in that map before `Run()` calls its own unexported `registerInTreePlugins()` [[runnergo]]. A recursive listing of the repository tree confirms the structural precondition: `cmd/epp/runner`, `pkg/epp/framework/interface/plugin` and `pkg/epp/framework/interface/datalayer` are all outside any `internal/` path [[main]].

### B. The precedent that proves non-pod endpoints are a first-class shape

The strongest single piece of evidence that "endpoint" does not mean "pod" in this codebase is shipped, in-tree, and documented: the multi-cluster plugin family, "for a cluster-scoped EPP whose candidate endpoints are clusters." It includes `multicluster-file-discovery`, and the plugins index states flatly that its `clusters.yaml` "follows the same format as the pod file discovery, except an `address` may be a hostname" [[llm-d-routerpkgeppframeworkpluginsreadmemd-at-main-llm-dllm-d-router-github]]. The variant is implemented by injecting a different address validator into the same plugin, and a peer's metrics may be scraped from a different host and port via `metricsAddress` / `metricsPort` labels [[readmemd]]. So upstream has already shipped a discovery plugin whose endpoints are not pods, whose addresses are not pod IPs, and whose metrics do not live at the serving port — through the same configuration field you will use.

### C. The other seams, and why you should not need them

- **Data-layer sources and extractors.** Metric scraping is a `DataSource`/`Extractor` pair over plain HTTP; the shipped engine configs key off Prometheus metric names such as `vllm:num_requests_waiting` and `sglang:num_queue_reqs` [[distributed-llm-inference-with-llm-d-moncef-abboud]]. Any OpenAI-compatible backend exposing those metric families needs no code.
- **`EndpointExtractor`.** This is how the KV-event path attaches to discovery — see Section 5 — and you consume it rather than implement it.
- **Request-control producers and admitters.** These are where a static priority plugin would live if you need priority tiers (Section 8).
- **Peer discovery.** A structurally identical plugin interface (`Start`, `Ready`, a non-goroutine-safe `PeerNotifier`) for the *router's own replicas*, whose doc comment records that "the k8s reconciler and any file-based discovery feed the same sink" [[peergo]] [[llm-d-routerdocspeer-discoverymd-at-main-llm-dllm-d-router-github]]. It exists to feed "a future cross-replica syncer," and no implementation has merged.
- **`CrossReplicaSyncer`.** A separate opt-in surface: a plugin that implements `CrossReplicaContributor` gets its per-endpoint attribute aggregated across replicas transparently [[cross_replica_syncergo]]. Note which plugin pointedly does *not* implement it — the precise prefix producer — and why that matters in Section 7.
- **Helm escape hatches.** The charts expose no discovery knob (`router.modelServers.matchLabels` is required when a pool is created), but `router.epp.pluginsConfig` accepts a structured endpoint-picker configuration and `router.epp.pluginsCustomConfig` passes raw files through, with `router.epp.volumes`/`volumeMounts` for mounting the endpoints file [[llm-d-routerconfigchartsreadmemd-at-main-llm-dllm-d-router-github]]. That is what makes the hybrid topology (router in a cluster, backends outside it) reachable without forking the chart.

### D. The gate you must remember

Every plugin carries a stability level assigned at registration; Alpha plugins require the `--allow-experimental-plugins` flag or the EPP refuses to start, and as of now "all in-tree plugins are classified as **Alpha** or **Beta**" [[llm-d-routerpkgeppframeworkpluginsreadmemd-at-main-llm-dllm-d-router-github]]. Since your plugin declares its own stability at registration, this gate is self-administered — but if you register as Alpha (the honest choice for new code), remember to set the flag.

## 4. Upstream State: Proposals and Work on Non-Pod and External Endpoints

### A. The chain that already landed

Non-Kubernetes operation is not a rumour; it is a tracked, completed release goal. llm-d's v0.8 goals issue lists, under the reinforcement-learning working group, "Non-Kubernetes deployment mode" with a named owner and a design proposal, followed by the exact merged-PR chain: the pluggable discovery interface (#908), the notifier plumbing (#1080, #1081), the `FileDiscovery` plugin itself (#1135), the runner wiring (#1218), and follow-ups that wired flow control into file-discovery mode (#1368) and fixed endpoint-update notification dispatch (#1404) [[v08-release-goals-mid-june-issue-1520-llm-dllm-d]]. A contributor's summary in the same thread is unambiguous about motive: "Non-K8s mode — Enables llm-d in Slurm/research labs without Kubernetes (file-based discovery)."

The release record confirms delivery and dates. `FileDiscovery` shipped as a key feature of llm-d-router v0.9.0 on 2026-06-23; v0.10.0 followed on 2026-08-17 and remains the newest tag as of 2026-09-11 [[releases-llm-dllm-d-router]]. On the umbrella project's side, a "New Capabilities" table lists "Non-Kubernetes mode (RL/Slurm) | llm-d-router (FileDiscovery plugin) | New" [[releases-llm-dllm-d]].

### B. What did *not* land, and why it is the decisive fact

PR #1007 would have delivered two Kubernetes-native discovery plugins — `inference-pool-discovery` and `static-selector-discovery` — migrating the existing pod-watching logic into the new framework [[discovery-plugins-k8s-and-file-based-endpoint-discovery-by-ezrasilvera-pull-requ]]. It was **closed unmerged** on 2026-05-25 after a maintainer asked for it to be broken up, with the author's own closing note: "Replace with teh file discovery PRs." No `discovery/k8s/` directory exists at HEAD; only `discovery/file/` does [[main]]. Two consequences follow. First, describe Kubernetes discovery through `pod_reconciler.go`, not through that PR. Second — and this is the honest cost of the strategy — there is no watch-based `EndpointDiscovery` implementation anywhere in the repository to copy. The reference implementation you will copy is a poll-and-diff plugin, which conveniently is also what you should build first.

### C. Peer discovery: the newest work is going the other way

The base infrastructure for peer discovery merged on 2026-08-16, one day before the v0.10.0 tag, so that release does contain the pre-consolidation `dataLayer.peerDiscovery.pluginRef` field — with, by design, "no concrete discovery mechanism," a Kubernetes implementation deferred [[feat-epp-peer-discovery-infrastructure-by-evacchi-pull-request-2341-llm-dllm-d-r]]. The follow-up that supplies one, a controller-runtime reconciler watching the router deployment's own Pods, was opened 2026-08-21 and is still open and unmerged at Alpha stability [[feat-pod-watch-peer-discovery-plugin-by-evacchi-pull-request-2501-llm-dllm-d-rou]]. So the newest discovery-adjacent work in the repository is Kubernetes-native, and off-cluster cross-replica state sharing would be a second custom plugin if you ever needed it.

### D. Audited absence, stated plainly

Across the PR history examined here, **no Consul, etcd, Slurm, Ray, or cloud service-discovery plugin has been proposed or merged**. Every discovery PR targets either a flat file or a Kubernetes primitive. The project's own blog ranks four discovery strategies and puts the dynamic one squarely in the future: static file, generator script plus static file, generator plus `watchFile: true`, and — as future work — "a dedicated `SlurmDiscovery` or `RayDiscovery` plugin against the same `EndpointDiscovery` interface, talking to the orchestrator directly with no file in the loop" [[no-kubernetes-no-problem-llm-d-now-runs-anywhere-llm-d]]. Read that correctly: it is not evidence the plugin is unwelcome, it is evidence that the first three tiers cover enough cases that nobody has needed the fourth yet. It also tells you there is no upstream branch to wait for. If you need dynamic non-Kubernetes discovery, you are writing it — which is precisely why the phased plan starts with the tier that needs no code.

The broader ecosystem has been converging on the same split. A maintainer debate in the Gateway API Inference Extension over a zero-Kubernetes standalone mode resolved toward "add a discovery layer... similar to scheduler pluggability," which is literally what shipped [[standalone-epp-issue-1838-kubernetes-sigsgateway-api-inference-extension]]. And integrators are demonstrating the reuse posture this report recommends: KAITO consumes the `llm-d-router-gateway` chart pinned at v0.9.0 with a matching endpoint-picker image, writing only its own controller and deployment wiring — wrap, do not fork [[gateway-api-inference-extension-with-llm-d-router-kaito]].

## 5. Non-Pod Backend Types and What Each Requires from the Router

### A. The universal contract

Whatever the backend is, it must satisfy four things, all of which are protocol-level rather than platform-level: an OpenAI-compatible HTTP endpoint at a routable `address:port`; a Prometheus `/metrics` endpoint the router can scrape; something that tells the router when it appears and disappears; and network reachability from the proxy (for traffic) and from the router (for metrics and, optionally, KV events).

Two shipped constraints bite immediately. The stock `file-discovery` plugin requires a **literal IPv4 address** — "hostnames are not resolved; IPv6 is not supported" — caps the file at 1 MiB, and scrapes "metrics from `address:port` (same host and port that serves inference); separate metrics endpoints are not supported" [[readmemd]]. A commit in the implementing PR is titled "file-discovery: validate IPv4 only and reject IPv6 addresses" [[file-discovery-34-add-filediscovery-plugin-with-yamljson-file-loading-and-fsnoti]]. A custom plugin escapes all three: it populates `EndpointMetadata` directly, and `MetricsHost` is a first-class field that "defaults to `address:port` if empty" — meaning a custom plugin can point metrics at a different port even though the file schema cannot [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]. That is the cleanest single argument for graduating from Phase 0 to Phase 1.

### B. Per-backend requirements

| Backend type | Discovery source | Extra requirements | Verdict |
|---|---|---|---|
| **VMs / bare metal** (vLLM, SGLang) | Generated `endpoints.yaml`, or config-management inventory | Static IPs or an IP-resolving generator; reachable `/metrics` | Phase 0 works today; this is the reference case [[llm-dguidesno-kubernetes-deployment-at-main-llm-dllm-d-github]] |
| **Docker / Podman / Nomad** | Runtime API poll → file, or a custom plugin | Stable published ports; container IP reachable from proxy | Phase 0 or 1 |
| **Slurm jobs** | Epilog/prolog script running `scontrol show hostnames` → file; later a `SlurmDiscovery` plugin | Job-lifetime churn; prompt deletion on job end | Phase 0 now, Phase 1 when churn hurts [[no-kubernetes-no-problem-llm-d-now-runs-anywhere-llm-d]] |
| **Ray actors** | `ray.nodes()` callback → file, or a plugin polling the Ray API | Actor restarts change addresses | Phase 0 now, Phase 1 for rollout workloads |
| **Remote Kubernetes clusters** | `multicluster-file-discovery` (hostnames allowed) | Cluster gateway reachable; aggregate metrics per cluster | Shipped precedent [[llm-d-routerpkgeppframeworkpluginsreadmemd-at-main-llm-dllm-d-router-github]] |
| **Managed / external OpenAI-compatible APIs** | None — do not model these as pool endpoints | Auth, rate limits, no queue/KV metrics, no KV events | Route at the gateway tier above the router, not inside the pool |
| **Serverless GPU providers** | Provider API poll → plugin | Cold starts; addresses that appear and vanish; flow control's `noEndpointRequestTTL` matters | Phase 1, with health gating as the hard requirement |

The managed-API row deserves its committed reading rather than a hedge: an external provider endpoint exposes none of the state the scheduler exists to exploit — no queue depth, no KV-cache utilisation, no KV events — so putting it in the pool converts every scorer into a constant and every routing decision into noise. Route those at an AI-gateway layer beside or above the inference gateway and keep the pool homogeneous.

### C. The KV-event path, which is where the thesis is won

The precise prefix-cache scorer is llm-d's flagship capability and the natural place for a skeptic to expect Kubernetes coupling, because the Kubernetes guide describes pod discovery: each vLLM or SGLang pod launches with `--kv-events-config` publishing over ZMQ with `KV_EVENTS_ENDPOINT=tcp://*:5556` and topic `kv@$(POD_IP):$(POD_PORT)@<model>`, binding its own publisher socket; the GPU backend additionally binds a replay socket on port 5559 retaining the last 10,000 batches so a restarted router can rebuild its index [[llm-dguidesprecise-prefix-cache-routingreadmemd-at-main-llm-dllm-d-github]]. The same guide says pod discovery "registers the precise-prefix-cache-producer as an extractor on the data-layer `endpoint-notification-source`."

The code shows that sentence is precise engineering, not gloss. `extractor.go` opens with `var _ fwkdl.EndpointExtractor = &Producer{}` and an `Extract` method whose doc comment reads: "processes endpoint lifecycle events emitted by the endpoint-notification-source: add/update installs a per-pod ZMQ KV-events subscriber, delete tears one down" [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcacheex]]. Inside, the dial target is built arithmetically from metadata — `port := p.kvEventsConfig.PodDiscoveryConfig.SocketPort + meta.GetRankIndex()`, then `"tcp://" + net.JoinHostPort(meta.Address, ...)` — and the index key is a separate literal string, `sourceEndpoint := fmt.Sprintf("%s:%s", meta.Address, meta.Port)`. The same `Address:Port` construction appears again on delete, clearing index entries, and again in the scoring path in `producer.go` [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcachepr]]. The `NamespacedName` is used only as the subscriber-manager's bookkeeping key.

So there are two identity spaces, not one that must reconcile. Routing correctness rides on `Address:Port`, which every discovery plugin populates identically. `PodDiscoveryConfig` in this path is a config carrier for two integers, not a Kubernetes client. And the producer's plugin README lists the same split of responsibilities — "(`EndpointExtractor`) Per-pod ZMQ subscriber lifecycle on add/delete" — from the documentation side [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcachere]]. A bug report written for an entirely different purpose corroborates it from a third angle, describing precise-prefix components that "install/refresh per-endpoint KV-events (ZMQ) subscribers keyed on endpoint address/port" through that same notification source [[endpoint-metadata-updates-do-not-trigger-endpoint-notification-events-issue-1403]].

One narrow, honest exception: `RankIndex` — the per-endpoint offset that gives each data-parallel rank its own ZMQ port — has no field in the file-discovery schema, so every file-discovered endpoint keeps rank 0 [[readmemd]]. For single-rank backends that is exactly right. For multi-rank data-parallel engines it is a real gap, and it is a second reason to write the custom plugin, which can set `RankIndex` directly.

There is also a simpler mode when per-endpoint subscription is not wanted: the producer's constructor eagerly installs one `"local-subscriber"` when a global ZMQ endpoint is configured, with `remoteSocket=false` — the centralised pattern the standalone KV-cache library documents as "Static Endpoint Mode," requiring no cluster API at all [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcachepr]] [[llm-d-kv-cachedocsconfigurationmd-at-main-llm-dllm-d-kv-cache-github]].

## 6. Candidate Strategies Compared

### A. The field

| # | Strategy | llm-d reuse | Maintenance burden | Feature parity | Ops complexity | Verdict |
|---|---|---|---|---|---|---|
| **a** | Model backends as Kubernetes objects (selectorless Service + EndpointSlice, virtual pods) | n/a | n/a | n/a | High | **Reject** — wrong layer |
| **b** | Convert the estate to real pods (Slinky-style Slurm operator) | Total | None on the router | Full | Very high (hand the fleet to Kubernetes) | Different question, not this one |
| **c** | File discovery fed by an external generator | Total above the seam | Near zero Go | Full minus CRD policy | Low | **Phase 0 — do this first** |
| **d** | Custom `EndpointDiscovery` plugin, out-of-tree, thin downstream `main()` | Total above the seam | One plugin + a version pin | Full minus CRD policy; fixes `MetricsHost`, `RankIndex` | Low-moderate | **Phase 1 — the recommendation** |
| **e** | In-tree fork of llm-d-router | Total | Plugin **plus** perpetual rebase | Same as (d) | Moderate | Strictly dominated by (d) |
| **f** | Custom router embedding llm-d libraries (scheduler, KV indexer) | Partial | Reimplement ext_proc server, config loader, health, draining | Degrades over time | High | Reject as default |
| **g** | Upstream the discovery plugin | Total | Review cycles, timing not yours | Full | Low | **Do in parallel, not instead** |

### B. Why (a) is not a weaker option but a category error

Making a non-pod backend *look* like a Kubernetes endpoint targets the wrong machinery. Selectorless Services and hand-authored EndpointSlices feed `kube-proxy`'s Service routing path [[endpointslices-kubernetes]]. The router's pool membership never consults Services or EndpointSlices; it lists Pods by label selector [[pod_reconcilergo]] [[inferencepool-kubernetes-gateway-api-inference-extension]]. You can author perfect EndpointSlices all day and the endpoint picker will never see them. Virtual-kubelet is architecturally different — it produces genuine Pod objects, and since admission is only label match plus aggregate readiness with `PodIP` consumed unvalidated, a correctly-labelled virtual pod would be admitted [[pod_reconcilergo]]. But the binding constraint is network: the production HPC integration in this space is egress-only by design [[github-interlink-hqinterlink-slurm-plugin-github]], so keep virtual-kubelet only as a narrow exception for cross-cluster pod-networking providers. Building a provider from scratch means implementing the full pod lifecycle and node heartbeat contract to accomplish what a five-method interface accomplishes directly.

### C. Steel-manning the strongest objection

The strongest case against this report's recommendation is not (a). It is this: *"You are proposing to be the first person ever to import `cmd/epp/runner` from outside the repository, against a three-month-old interface whose configuration shape has changed three times in four months, in a framework that has no panic recovery anywhere in the plugin path. Use a router that ships non-Kubernetes discovery natively — vLLM Router, vLLM production-stack, NVIDIA Dynamo all do — and stop paying for llm-d's Kubernetes-shaped assumptions."*

Every clause of that is true. The config surface moved from a top-level `discovery.pluginRef` under `dataLayer`, then to `dataLayer.discovery.endpoints.pluginRef` [[config-consolidate-discovery-plugins-under-a-single-discovery-sectio-llm-dllm-d]]. An open, untriaged issue proposes recording that "in-tree plugins are the supported surface; out-of-tree plugins that panic take the process down," and confirms nothing recovers plugin invocations anywhere in the framework [[framework-define-a-panic-isolation-posture-for-plugin-extension-points-issue-210]]. The scheduling-filter tutorial teaches in-tree registration by editing the runner [[llm-d-routerdocscreate_new_filtermd-at-main-llm-dllm-d-router-github]]. And the module's published package index reports no known importers of the runner package.

Here is the answer, in four moves.

**First, the fork alternative does not dodge any of it.** A fork inherits the same interface churn, the same missing panic recovery, the same absence of precedent for what you are doing — and adds rebase conflicts against the exact subsystem that is moving. Out-of-tree strictly dominates.

**Second, the risks are mitigable at the plugin level.** Namespace your `PluginType` string, because `Register` overwrites silently with no duplicate guard [[registrygo]]. Wrap your `Start()` goroutine in your own `recover()`, because the framework provides none [[framework-define-a-panic-isolation-posture-for-plugin-extension-points-issue-210]]. Pin a tagged release and run a scheduled build against upstream `main` so interface drift surfaces in CI rather than in production.

**Third, the "just use a simpler router" argument concedes the wrong thing.** Non-pod support is table stakes in those routers; llm-d's plugin depth is the asset you are buying — precise prefix-cache routing, predicted-latency scoring, priority-band flow control, prefill/decode profile handling. Vendor benchmarks on both sides are unreproduced, so treat the throughput claims as unsettled; the reproducible fact is that the entire scheduling stack survives the move, because the only thing you replace is enumeration. And because the proxy speaks the same picker protocol to any implementation [[gateway-api-inference-extensiondocsproposals004-endpoint-picker-protocol-at-main]] [[kv-aware-routing-on-kubernetes-nvidia-dynamo-documentation]], swapping routers later costs you one plugin, not your architecture. That is the reversibility argument, and it is why "customize one seam" is not just cheapest but also safest.

**Fourth, the documentation objection is narrower than it looks.** Two different documents were being conflated. The in-tree instruction lives in the *scheduling filter* tutorial; `docs/discovery.md` has its own "Writing a custom discovery plugin" section that teaches `fwkplugin.Register(PluginType, Factory)` before `Run()` without saying where that call must live [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]. Registering a custom discovery plugin is documented upstream. Only the packaging is inferred.

## 7. Recommended Strategy and Implementation Roadmap

**Recommendation: customize the `EndpointDiscovery` seam and nothing else. Reach it in phases, keep the custom Go surface to one plugin, and pursue upstreaming in parallel.**

### Phase 0 — Prove the stack on your hardware with zero Go (days 1-5)

Stand up the reference no-Kubernetes topology: the endpoint picker binary or container, a static Envoy config, and your existing engines. The exact invocation is published — `./bin/epp --config-file=/etc/epp/config.yaml --pool-name=<label> --pool-namespace=<label> --grpc-port=9002 --grpc-health-port=9003 --metrics-port=9090 --secure-serving=false` — and the pool flags are labels only in this mode [[llm-dguidesno-kubernetes-deployment-at-main-llm-dllm-d-github]]. Configure `file-discovery` with `watchFile: true`, and write the endpoints file from whatever already knows your topology.

Pin the release and match the config key to it. On v0.10.0, write the legacy form:

```yaml
plugins:
  - name: my-endpoints
    type: file-discovery
    parameters: { path: /etc/epp/endpoints.yaml, watchFile: true }
dataLayer:
  discovery:
    pluginRef: my-endpoints        # v0.10.0 and earlier
    # endpoints: { pluginRef: my-endpoints }   # main builds, post-v0.10.0 releases
```

The nested form is what `resolveDiscovery` reads at HEAD [[runnergo]], and the loader keeps the legacy key working through a migration shim with a deprecation warning [[config-consolidate-discovery-plugins-under-a-single-discovery-sectio-llm-dllm-d]] — but it is absent from every tagged release today [[releases-llm-dllm-d-router]].

Make the generator do the work a kubelet used to do: write only healthy endpoints, rewrite atomically (`mv` a temp file over the target — the watcher re-attaches after atomic renames and symlink swaps), and remove entries the moment a backend is gone, since deletion is what tears down its subscriber and clears its index entries [[readmemd]] [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcacheex]]. Carry `llm-d.ai/role` labels if you plan on prefill/decode.

**Exit criterion:** requests route end-to-end, per-endpoint metrics appear, and adding or removing a line in the file changes routing without a restart.

### Phase 1 — Turn on the intelligence you came for (days 5-12)

Enable the precise prefix-cache producer with per-endpoint discovery and pair it with the prefix-cache scorer by name (`prefixMatchInfoProducerName`), which is required or the scorer silently falls back to the approximate producer [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcachere]]. Confirm your engines publish KV events on the base socket port, plus the replay socket if you want index recovery after a restart [[llm-dguidesprecise-prefix-cache-routingreadmemd-at-main-llm-dllm-d-github]]. Then run the validation nobody has published: precise prefix-cache routing on top of file-sourced endpoints, end to end. The mechanism is code-verified; the demonstration is an audited absence in the public record, so make it a test you own rather than an assumption you inherit.

Two gates to check while you are here. Keep the router at **one replica** unless you have decided the HA question below — and note that the standalone chart silently injects `--ha-enable-leader-election` whenever replicas exceed one, which turns a four-replica deployment into one-replica throughput [[evaluate-llm-d-router-both-epp-and-the-standalone-proxy-scale-limits-issue-1290]]. And decide the proxy's failure behaviour deliberately: for non-pod backends the proxy has no endpoint list of its own, so the data path is fail-closed unless you configure an explicit fallback cluster.

### Phase 2 — Write the plugin, out of tree (1-3 weeks)

Graduate when the file stops expressing your world: churn faster than your regeneration interval, hostnames rather than IPv4 literals, metrics on a different port, non-zero `RankIndex`, or richer labels.

Structure: one package implementing `TypedName()`, `Start(ctx, notifier)` and `Ready()`, with an `init()` that calls `fwkplugin.Register("<yourorg>-<source>-discovery", stability, Factory)`; one `main.go` that blank-imports it and calls `runner.NewRunner().Run(ctx)`. Budget the full controller-runtime dependency tree, which `runner.go` imports unconditionally alongside the entire in-tree plugin catalog even when you never touch a cluster [[runnergo]] [[main]].

Design rules, in priority order:

1. **Only `Upsert` healthy endpoints; `Delete` on the first failed health signal.** This matters more than poll-versus-watch. Off-cluster nothing expires a stale entry, so a dead backend keeps its datastore row, its ZMQ subscriber and its index entries until discovery says otherwise [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]] [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcacheex]].
2. **Start with poll-and-diff.** Snapshot the source, `Upsert` everything present, `Delete` everything in the prior snapshot and absent now — the shipped file plugin's `load()` generalised [[plugingo]]. Use a long-poll if your registry offers one; reserve a persistent watch for cases where staleness has a named, measured cost, remembering the repository's only attempt at a watch-based plugin was abandoned as too large to review [[discovery-plugins-k8s-and-file-based-endpoint-discovery-by-ezrasilvera-pull-requ]].
3. **One goroutine drives the notifier.** Non-negotiable, per the ordering contract [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]].
4. **Close `Ready()` exactly once, after the first successful sync — and never gate it on a non-empty endpoint set** [[filediscovery-plugin-44-wiring-into-the-runner-by-ezrasilvera-pull-request-1218]].
5. **Namespace the plugin type; add your own `recover()`.**
6. **Enumerate before watching**, so the first request does not meet an empty datastore.
7. **Pin a release; CI against `main` weekly.**

### Phase 3 — Decide availability, deliberately (parallel)

Here is the decision rule, and it inverts the usual framing that router placement is merely organisational. If you need multi-replica router availability, availability drives topology. The default Active-Passive mode elects a leader through a `coordination.k8s.io/Lease`, and standby replicas answer `NOT_SERVING` on purpose; a second documented mode substitutes a StatefulSet with a headless Service and Envoy outlier detection — relocating the Kubernetes dependency rather than removing it [[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]] [[llm-d-routerconfigchartsreadmemd-at-main-llm-dllm-d-router-github]].

But Active-Active needs no lock at all, and the benchmark evidence says it is the right mode for precise routing specifically. Measured on real GPUs, precise prefix-cache failures at 500 QPS fall monotonically as replicas rise — one replica broken with 3,148 failures, then 57, 31, and 18 at four replicas, with median time-to-first-token dropping from 165 ms to 30 ms [[evaluate-llm-d-router-both-epp-and-the-standalone-proxy-scale-limits-issue-1290]]. The mechanism is visible in code: the precise extractor implements only `EndpointExtractor`, pointedly *not* `CrossReplicaContributor`, so each replica converges independently by subscribing to every endpoint's event stream rather than by synchronising with peers [[cross_replica_syncergo]] [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcacheex]]. The documented Active-Active warning is scoped to *approximate* prefix routing, where replicas genuinely do not share state [[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]].

So: **N routers behind a plain layer-4 load balancer, leader election off, precise prefix routing on.** Two cautions travel with it — flow-control state stays per replica, so priority and fairness are enforced only within each replica's share of traffic, and cross-replica session affinity was never evaluated (the benchmark used independent synthetic requests), so session-pinned workloads should not assume it [[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]] [[evaluate-llm-d-router-both-epp-and-the-standalone-proxy-scale-limits-issue-1290]]. If you need leader-elected failover specifically, run the routers on a small Kubernetes control plane while the backends stay outside it — mechanically supported through the chart's raw-config and volume escape hatches [[llm-d-routerconfigchartsreadmemd-at-main-llm-dllm-d-router-github]], though no production deployment of that exact shape appears in the public record.

### Phase 4 — Upstream (continuous)

Open an issue describing your discovery backend and reference the maintainer's stated intent to support Slurm- and Ray-class plugins [[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]]. Follow the file-discovery chain's shape: interface change, plumbing, plugin, wiring — four small PRs, not one large one, which is the lesson of the abandoned attempt [[v08-release-goals-mid-june-issue-1520-llm-dllm-d]] [[discovery-plugins-k8s-and-file-based-endpoint-discovery-by-ezrasilvera-pull-requ]]. Do not block Phase 2 on it. Merge timing is not yours, and most real discovery backends carry proprietary details that cannot go upstream wholesale.

## 8. Risks, Trade-offs, and Open Questions

**The extension pattern is sound but unratified.** The mechanism is verified in source: an exported registry map, exported `Register`, `init()`-before-`main()` ordering, no `internal/` barrier, no replace directives [[registrygo]] [[main]]. What is missing is a project statement blessing it, and the one open issue that names "out-of-tree plugins" as a category proposes framing them as at-your-own-risk — untriaged, uncommented, one of three competing options, not policy [[framework-define-a-panic-isolation-posture-for-plugin-extension-points-issue-210]]. Treat that as a cost priced in, not a veto: the same issue confirms no plugin invocation anywhere has panic recovery, in-tree or out, which means the mitigation is the same either way.

**Interface churn is the real maintenance line item.** Discovery's configuration shape changed three times in roughly four months, and the data layer's typed-attribute machinery was still being reworked on 2026-09-11 [[config-consolidate-discovery-plugins-under-a-single-discovery-sectio-llm-dllm-d]] [[llm-d-routerpkgeppframeworkinterfacedatalayer-at-main-llm-dllm-d-router-github]]. Config changes ship migration shims; the Go interface has no such guarantee. Budget a day per release cycle for re-verification and read the data-layer and discovery release notes every time.

**Documentation trails code by weeks.** Three separate published artifacts state the discovery config path differently, and the newest one is not in any release [[readmemd]] [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]] [[no-kubernetes-no-problem-llm-d-now-runs-anywhere-llm-d]]. Use the shipped file plugin's source as the template of record, not the prose.

**Lost policy inputs, and their substitutes.** Per-request priority via `InferenceObjective` resolves to nil off-cluster, so every request lands in the default band — the one genuine gap needing new code, best filled by a small file-backed priority plugin if and only if you actually run priority tiers [[readmemd]] [[llm-d-flow-control-priority-queuing-for-shared-gpu-inference-red-hat-developer]]. Tenant fairness needs nothing: the fairness identifier is a bare header defaulting to a standard flow [[epp-http-headers-reference-llm-d]]. Explicit model selection is already solved by a shipped header documented as the alternative to the rewrite resource; only weighted canary splitting needs logic, and it belongs at the gateway tier where something can make the weighted choice and set that header [[epp-http-headers-reference-llm-d]]. Scrape-target discovery is a non-issue — the no-Kubernetes guide ships a plain static Prometheus config pointed at the router's metrics port and each worker's `/metrics` [[llm-dguidesno-kubernetes-deployment-at-main-llm-dllm-d-github]].

**Prefill/decode needs network isolation, not a Kubernetes allowlist.** The disaggregation sidecar's SSRF protection is opt-in and, when enabled, "watches a specific `InferencePool` resource and maintains an allowlist of valid prefill targets based on pods matching the InferencePool selectors," returning 403 to anything else [[github-llm-dllm-d-routing-sidecar-incubating-pd-sidecar-for-llm-d-github]] [[allowlistgo]]. There is no static or CIDR equivalent, and with protection off the sidecar proxies to whatever the prefiller-host header names. Off Kubernetes, replace that control with network isolation — the sidecar's port reachable only from the trusted gateway path via firewall, security group or mesh policy — and enable sidecar TLS for the prefill leg, which is plain flags and fully portable. The upstream threat model already puts the primary control in the gateway stripping client-supplied routing headers on ingress, and that hardening is in the codebase: system-owned headers are excluded from the passthrough loop, with a test proving a client-injected destination endpoint is discarded in favour of the router's own decision [[2025diff]] [[fix-harden-header-sanitization-and-handling-logic-by-lukeavandrie-pull-request-2]].

**Smaller constraints to design around.** IPv4-literal-only addressing and single-port metrics in the stock file plugin (both fixed by a custom plugin); the 1 MiB file cap; `RankIndex` stuck at zero for data-parallel engines until a custom plugin sets it [[readmemd]]; and Alpha plugins requiring `--allow-experimental-plugins` [[llm-d-routerpkgeppframeworkpluginsreadmemd-at-main-llm-dllm-d-router-github]].

**Open questions worth tracking.** Whether the panic-isolation issue resolves toward tolerating out-of-tree plugins or restricting them; whether a fourth reshaping of the discovery config lands; whether repeated `Upsert` calls for an unchanged endpoint churn KV subscribers on file reload; whether anyone runs routers-in-cluster-with-external-backends in production; and whether cross-replica session affinity holds under Active-Active.

**Forward look, next six to twelve months.** Three trajectories converge on making this strategy cheaper rather than obsolete. First, the discovery abstraction is still mid-migration: the pod watch was always meant to move behind the interface so that pool discovery becomes "just another plugin alongside file, DNS, and service-registry discovery" [[no-kubernetes-no-problem-llm-d-now-runs-anywhere-llm-d]]. When that lands, the Kubernetes path and your path become peers, and the residual `NamespacedName` identity type is the natural thing to fix alongside it — which would remove the last cosmetic Kubernetes-ism from a custom plugin. Second, cross-replica state sharing is being built in the open, with a peer-discovery interface whose own doc comment already names file-based discovery as a first-class feeder [[peergo]] and an opt-in syncer surface waiting for contributors [[cross_replica_syncergo]]; if you ever need shared scorer state off-cluster, the sanctioned shape already exists even though no implementation does. Third, the protocol layer keeps hardening as the industry seam — a competing vendor ships its own picker behind it, and the protocol itself has grown ordered fallback endpoint lists [[kv-aware-routing-on-kubernetes-nvidia-dynamo-documentation]] [[gateway-api-inference-extensiondocsproposals004-endpoint-picker-protocol-at-main]]. The compounding implication is that the discovery plugin is the only artifact you own that is exposed to llm-d's internal churn; everything else you depend on is either a stable wire protocol or a configuration file. Keeping the custom surface to one plugin is therefore not just the cheapest way to start — it is the only structure that stays cheap as the project moves under you.

**What is not recommended.** Do not fork to get a plugin. Do not shim non-pod backends into Kubernetes objects that the picker never reads. Do not rebuild a router around llm-d's libraries to avoid one interface. Do not put managed provider endpoints in the pool. And do not wait for `SlurmDiscovery` or `RayDiscovery` to appear upstream — the generator-plus-file tier is production-viable today, and the custom plugin is a week of work, not a quarter.
