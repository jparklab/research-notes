# Interim report: extension-mechanism

**Locus question:** Which extension mechanism maximizes llm-d reuse for non-pod backends: file-discovery fed by an external generator (no Go), an out-of-tree EndpointDiscovery plugin in a thin downstream EPP build (exported registry, undocumented, no precedent), an in-tree fork (documented, merge burden), embedding llm-d scheduling/kv-cache packages in a custom router, or upstreaming the plugin — and what does each cost across llm-d's ~monthly release cadence?
**Flavor:** dialectical

## What the corpus already said

The width sweep already established the core architectural fact: llm-d-router's discovery subsystem was deliberately redesigned around a pluggable `EndpointDiscovery` interface so the EPP can run without Kubernetes at all — no `ctrl.GetConfig()`, no controller manager, no `InferencePool` CRD, no K8s RBAC ([[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]). The contradiction graph's `out-of-tree-plugin-registration` cluster (`research/runs/llmd-router-nonk8s-backends-54b774/temp/contradiction-graph.json`) had already framed the live tension precisely: side A says the registry is an exported package-level map with an exported `Register()` ([[registrygo]], [[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]]), side B says the only *documented* path is editing `runner.go`'s unexported `registerInTreePlugins()` ([[llm-d-routerdocscreate_new_filtermd-at-main-llm-dllm-d-router-github]], [[runnergo]]), and the graph's own `scope_overlap` note already concluded "both right: technically sound but undocumented, unprecedented, and exposed to internal-API drift." My job was to resolve whether that residual undocumented/unprecedented risk is disqualifying or just a cost to price in — and to rank all five mechanisms named in the locus, not just the two the contradiction graph captured.

## What the new sources say

I did not need new web fetches to resolve the core technical question — the corpus already contained the full source of `registry.go`, `runner.go`, `main.go`, `plugin.go` (file-discovery), the PR #908 review thread, PR #1007, PR #2434, and the `releases-llm-d/llm-d` timeline. I read all of these in full rather than from summaries; the load-bearing lines are quoted below. I also dispatched one fetcher sub-task (still running as of this note; see Open Questions) to search specifically for downstream precedent and any maintainer statement on out-of-tree registration, since the locus rationale flags "no downstream precedent exists" as a specific, checkable claim rather than an assumption.

**`cmd/epp/runner/runner.go`** ([[runnergo]]) settles the mechanics precisely. `Runner` is a builder-pattern struct (`NewRunner()`, `WithExecutableName`, `WithRequestControlConfig`, `WithSchedulerConfig`, `WithCustomCollectors`, `Run(ctx)`) — a normal, importable Go type, not gated behind `internal/`. Plugin registration happens via `r.registerInTreePlugins()`, called from inside `parseConfigurationPhaseOne`, which itself is called at the top of `Run()` — i.e., **after** any external package's `init()` has already run (Go guarantees all `init()` functions across the whole program complete before `main()` begins, and `Run()` executes after `main()` starts). This ordering means a separate binary that blank-imports a plugin package (which calls `plugin.Register()` in its own `init()`) will already have its plugin type sitting in the shared `Registry` map by the time `registerInTreePlugins()` runs and starts adding the ~90 in-tree registrations I counted in that function body. There is no exported `WithPlugins(...)` or `RegisterPlugin(...)` method on `Runner` — the only injection seam is the package-level global.

**`registry.go`** ([[registrygo]]) confirms the seam is functionally complete, not a crippled subset: `Register`, `RegisterAsDefaultProducer`, `RegisterWithPluginDependencies`, and `RegisterDeprecated` all funnel through the same exported map writes (`Registry[pluginType] = factory`). Critically, **there is no duplicate-key guard** — `Register` unconditionally overwrites `Registry[pluginType]`. Whichever `init()` runs last for a given `pluginType` string wins silently, with no panic, warning, or log line. This is a real, if narrow, risk: it is quiet under Go's largely-deterministic-but-not-contractually-ordered same-package `init()` sequencing, and it means a downstream author who is not careful about picking a distinctive plugin-type string (e.g., naming it `file-discovery` instead of something namespaced like `acmecorp-slurm-discovery`) could silently shadow or be shadowed by an in-tree plugin.

**PR #908** ([[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]]) is the single most decisive piece of evidence for *intent*. Author Ezra Silvera, explaining why discovery had to be split out of the datalayer package: *"We aim to also support non k8s in the future so we need to keep the datalayer clean: we want K8s, file, Slurm, and Ray discovery all as plugins. If discovery lives inside the datalayer, the datalayer gets contaminated with infrastructure-specific code (ctrl.Manager, fsnotify, etc.), which defeats the whole point of the abstraction."* This confirms the interface was purpose-built for exactly the user's scenario (non-pod, non-k8s backends), and confirms K8s-specific machinery is confined to the K8s discovery plugin implementation, not the shared `DiscoveryNotifier`/datastore path — a from-scratch discovery plugin for a Slurm- or Ray-like backend needs zero Kubernetes client-library imports. The same PR also surfaces an unresolved design debt: the endpoint identifier is `types.NamespacedName` (a Kubernetes type), which a reviewer flagged as "too k8s centric," and the author agreed but deferred fixing it. A non-k8s plugin must still mint synthetic `Namespace`/`Name` strings to satisfy this type — a minor friction cost, not a blocker.

**`discovery.md`**'s "Writing a custom discovery plugin" section ([[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]) is the one piece of documentation that is *not* unambiguously in-tree-only. It gives a complete, compiling code skeleton for a from-scratch `EndpointDiscovery` implementation and instructs: *"Register the factory in the runner before calling `Run`: `fwkplugin.Register(myplugin.PluginType, myplugin.Factory)`."* Unlike `create_new_filter.md`, this does not say "edit runner.go" — it is agnostic about where that `Register()` call lives, which is technically consistent with calling it from a separate `main.go`. But it is also not an endorsement of the out-of-tree pattern; it simply doesn't foreclose it, and it is written from the assumption that you're building the same `epp` binary the repo already builds via `go build -o epp ./cmd/epp`.

**`create_new_filter.md`** ([[llm-d-routerdocscreate_new_filtermd-at-main-llm-dllm-d-router-github]]) is unambiguous the other way, for a different plugin category (scheduling filters): step 1 of "Hooking the filter into the scheduling flow" is *"Add an import and a `plugin.Register` call in `runner.go`"* inside `registerInTreePlugins()`. There is no out-of-tree alternative offered, even though the exact same `Register()` function is being called. This is a genuine internal documentation inconsistency across the two tutorials, not a resolved position — the discovery tutorial and the filter tutorial were evidently written independently and never reconciled on whether out-of-tree registration is a sanctioned pattern.

**Release/config-churn evidence** ([[releases-llm-dllm-d]], [[discovery-plugins-k8s-and-file-based-endpoint-discovery-by-ezrasilvera-pull-requ]], [[config-consolidate-discovery-plugins-under-a-single-discovery-sectio-llm-dllm-d]]) lets me answer the locus's explicit cadence question with real dates rather than an estimate. `llm-d/llm-d` shipped v0.3.0 (10 Oct 2025) through v0.9.0 (17 Aug 2026) — 9 minor releases in roughly 10 months, i.e., close to but slightly slower than monthly (a new minor roughly every 5-6 weeks). More important than the top-line cadence is that the discovery subsystem specifically has changed shape three times in about four months: (1) the interface itself was renamed `DiscoveryPlugin` → `EndpointDiscovery` and *moved packages* (`interface/discovery` → `interface/datalayer`) during PR #908's review (Apr 28 – May 3, 2026); (2) PR #1007 (merged May 25, 2026) moved the config key `discovery.pluginRef` from a top-level `EndpointPickerConfig` field to nested under `dataLayer`; (3) PR #2434 (merged Aug 25, 2026, explicitly a "follow up #2341") nested it *again*, from `dataLayer.discovery.pluginRef` to `dataLayer.discovery.endpoints.pluginRef`, splitting `discovery` into `endpoints`/`peers` subsections. That's three breaking or near-breaking reshapings of the exact surface a custom discovery plugin must target, landing roughly every 6-8 weeks — faster than the project's own overall release cadence, because this specific subsystem is still under active design churn (each change did ship a backward-compatibility shim, per [[runnergo]]'s `migrateDiscoveryConfig`-style handling, but the *Go-level* `EndpointDiscovery` interface and factory signature are a separate surface with no such shim).

**`pkg/epp/framework/plugins/README.md`** ([[llm-d-routerpkgeppframeworkpluginsreadmemd-at-main-llm-dllm-d-router-github]]) adds two facts directly useful for weighing the mechanisms: first, every plugin — in-tree or not — is Alpha/Beta/Stable, with "none Stable pre-1.0," and Alpha plugins require `--allow-experimental-plugins` or the EPP refuses to start; a custom out-of-tree plugin registers itself with whatever `StabilityLevel` its own author chooses via `Register(pluginType, stability, factory)`, so this gate is self-administered, not a barrier. Second, and this is a genuine shipped precedent for the *shape* of the user's ask even though it's not an out-of-tree example: the "multi-cluster" plugin variants are a documented case of the EPP's candidate endpoints being **clusters, not pods** — `multicluster-file-discovery` reads `clusters.yaml`, "the same format as the pod file discovery, except an address may be a hostname," proving the endpoint model already treats non-pod, non-IP-literal addressing as a first-class case reachable purely through `dataLayer.discovery.endpoints.pluginRef` configuration.

## Evidence synthesis

Two things are true simultaneously and neither is in serious doubt after reading the source directly: (1) out-of-tree registration works today, by construction of Go's `init()` ordering and the package-level `Registry` map — this is not a hack that depends on an implementation accident, it is the same mechanism every in-tree plugin uses, just invoked from a different `main()`; and (2) the project has never said so in writing, has one tutorial (`create_new_filter.md`) that actively models the *opposite* workflow, and has zero downstream examples in the corpus of anyone actually doing it. The dialectical question is what to do with that gap between "technically sound" and "documented and precedented."

### Position A: out-of-tree plugin + thin downstream `main()` importing `cmd/epp/runner` is the right default

The case for this is that it is genuinely lightweight in the one dimension that matters for a discovery-only integration: you write one Go file implementing a ~3-method interface (`TypedName`, `Start`, optionally `Ready`), one `init()` call, and a `main.go` that is nearly identical to the upstream's own 15-line `main.go` ([[maingo]]) — `runner.NewRunner().Run(ctx)` — plus a blank import of your plugin package. You get the entire scheduler, kv-cache scoring, flow control, HA/leader-election, ext_proc gRPC server, and Prometheus metrics stack for free, unmodified, because you are running the *same* `Run()` code path upstream runs, not a copy of it. Nothing about your integration lives inside the vendored/forked copy of llm-d-router's source, so there is nothing to rebase on every release — you bump a `go.mod` version pin and recompile. PR #908's own design rationale (Slurm/Ray named explicitly as target backends) shows this is squarely inside what the interface was built for, and the multi-cluster precedent shows non-pod addressing is already a first-class, shipped configuration shape.

### Position B: without a documented, maintainer-endorsed path or any existing example, out-of-tree registration is an unsupported technique dressed as a stable API, and a fork (or upstreaming) is the defensible choice

The case for this is that "the registry happens to be exported" is a description of Go visibility rules, not a support contract. `create_new_filter.md` is the *only* plugin-authoring tutorial the project ships that talks about hooking a plugin into a running EPP, and it tells every reader to edit `runner.go`. There is no CONTRIBUTING.md guidance, issue, or discussion in the corpus where a maintainer says "you can also do this from your own module" — the closest thing, PR #908's Slurm/Ray comment, is Ezra Silvera describing plugins *he* expects to land in-tree (file, Slurm, Ray "all as plugins" — read in context as a roadmap for what llm-d-router itself will ship, alongside the actual in-tree file-discovery series #1080/#1081/#1218 that followed it), not a statement that third parties should import `cmd/epp/runner` from outside the module. Given the demonstrated churn (interface renamed/moved once, discovery's config key reshaped twice, in ~4 months) and the missing duplicate-key guard, a team betting production infrastructure on an unendorsed technique with zero precedent is accepting silent-collision and silent-drift risk with no compatibility promise and no one to ask when it breaks.

Both positions are consistent with the same source code; they disagree about how much weight "no maintainer statement either way" and "no precedent" should carry against "it works and was designed to support exactly this."

## Committed position

The evidence adds up to a staged recommendation, not a single winner-take-all mechanism, because the five options in the locus solve different sub-problems and are not mutually exclusive. First: if the non-pod backend can be reduced to a periodically-refreshed list of `address:port` + labels, use **file-discovery fed by an external (non-Go) generator** — it is already shipped, stable enough to be listed as a "New Capability" in llm-d v0.8/v0.9 release notes, requires writing zero Go code, and carries none of the registry or interface-churn risk because you never touch `pkg/epp/framework/interface/plugin` at all. Second, only when the backend genuinely needs push-based updates, richer per-endpoint metadata, or logic a flat file can't express: use the **out-of-tree `EndpointDiscovery` plugin in a thin downstream `main()`** (Position A) over an in-tree fork, because the mechanism is not a trick — it is Go's ordinary `init()`-before-`main()` guarantee applied to a package-level registry that every in-tree plugin already uses, PR #908's own design rationale explicitly names Slurm/Ray-shaped non-k8s backends as the intended audience, and the multicluster precedent proves non-pod addressing is a first-class, already-shipped path through the same config surface. The in-tree fork buys you nothing an out-of-tree plugin doesn't already get for free (same dependency graph, same interface, same config surface) while adding a rebase-conflict obligation against a subsystem whose config shape has changed twice and whose Go interface has been renamed once in the last four months — a cost with no corresponding benefit once you've confirmed your plugin-type string doesn't collide with any of the ~90 names `registerInTreePlugins()` registers. Third, reject embedding llm-d's scheduling/kv-cache packages into a hand-built custom router as a default: it is not lighter-weight than the plugin approach — you inherit the identical transitive dependency graph (`runner.go` imports the full plugin catalog unconditionally regardless of which plugins you configure) — while forcing you to reimplement the ext_proc gRPC server, config loader, HA/draining, and health-check wiring that `Run()` already gives you, and it multiplies your exposure to breaking changes from a handful of interfaces (`EndpointDiscovery`, `DiscoveryNotifier`) to dozens (`SchedulerConfig`, `Director`, `Endpoint`, the whole `requestcontrol` package). Fourth, pursue **upstreaming** in parallel, not instead: the maintainers have said in writing they want Slurm/Ray-class discovery plugins, and the four-PR file-discovery chain (#1080/#1081/#1218 plus #908/#1007) is a working template for how such a contribution gets reviewed and merged — but this does not replace shipping now, since merge timing isn't yours to control and most real non-pod backends will have proprietary elements that can't go upstream wholesale.

- **Position:** For a backend that needs more than a static/semi-dynamic endpoint list, build a thin downstream `main()` that imports `github.com/llm-d/llm-d-router/cmd/epp/runner`, blank-imports a custom `EndpointDiscovery` plugin package that registers itself via `init()` + `fwkplugin.Register()` under a distinctive, non-colliding plugin-type string, and calls `runner.NewRunner().Run(ctx)` unmodified — this maximizes reuse at lower ongoing cost than an in-tree fork or a from-scratch router, and should be paired with a file-discovery-only fallback for the subset of the deployment that is expressible as a static list, plus a parallel upstreaming conversation for the discovery backend itself.
- **Confidence:** medium-high on the technical soundness (source-code-verified: exported registry, `init()`-ordering, no `internal/` barrier, tagged/importable module per pkg.go.dev v0.10.0); medium on the "recommended default" ranking specifically, because the one thing that would most directly settle Position A vs. B — an explicit maintainer statement or an existing downstream example — was not found in the corpus, and my supplementary search for that evidence had not returned by the time this note was finalized (see Open Questions).
- **Boundary conditions:** This holds for discovery-only integration (getting non-pod endpoints into the datastore). It does NOT extend to replacing scheduling/scoring logic itself with non-router code — `create_new_filter.md`'s in-tree-only instructions govern that surface, and I found no equivalent "write it as a separate package" doc language for scorers/filters/pickers the way `discovery.md` provides for discovery. It also assumes the backend's identity model can be shoehorned into `types.NamespacedName` (namespace+name strings) and IPv4-or-hostname-style addressing; backends needing richer identity (e.g., multi-homed nodes, non-network addressing) are outside what I verified.
- **What would change this position:** (a) discovery of a GitHub issue/discussion or CONTRIBUTING.md statement saying out-of-tree plugin registration is unsupported or discouraged would flip the recommendation toward "fork, and upstream your registration mechanism request" rather than out-of-tree; (b) discovery that `registerInTreePlugins()` has ever silently overwritten a community-chosen plugin-type string (a real collision incident) would elevate the duplicate-key-guard risk from theoretical to demonstrated and argue for a fork (where a collision is a visible compile/lint-time diff, not a silent runtime overwrite); (c) if a fourth config-schema reshaping of `dataLayer.discovery.*` occurs within weeks of this note, that would push the interface's "still churning" characterization from "recent history" to "ongoing pattern," strengthening the case for pinning tightly and re-testing every release regardless of which mechanism is chosen.
- **Evidence weight:** Technical viability of out-of-tree registration: source-code-certain (registry.go, runner.go, main.go all read in full). Design intent (Slurm/Ray as first-class targets): one maintainer PR-review quote, high confidence. Documentation posture: mixed/contradictory between two official tutorials (create_new_filter.md vs. discovery.md), not resolved by any third source found. Precedent: none found in the corpus as of this note; one fetcher sub-task dispatched specifically to audit this absence was still in flight at write time.
