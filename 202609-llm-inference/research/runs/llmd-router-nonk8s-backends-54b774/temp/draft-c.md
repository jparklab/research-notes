# Customizing the llm-d Router for Non-Pod Backends: A Decision-Rule Strategy

**Bottom line: do not customize the router. Customize exactly one plugin inside it — the endpoint-discovery plugin — and reuse everything above that seam unchanged.** llm-d's own maintainers already carved this seam and shipped it: since llm-d-router v0.9.0 the Endpoint Picker (EPP — the process that decides which backend serves each request) can obtain its entire backend inventory from a pluggable `EndpointDiscovery` implementation instead of watching Kubernetes Pods, and when one is configured "the EPP **does not** call `ctrl.GetConfig()` or start a controller manager… **does not** require an `InferencePool` CRD or any K8s RBAC" while "all scheduling, request control, and metrics collection behaviour is unchanged" [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]. The interface author's stated design intent names your exact case: "We aim to also support non k8s in the future so we need to keep the datalayer clean: we want K8s, file, Slurm, and Ray discovery all as plugins" [[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]].

The genuine question is therefore not *whether* to customize but *which rung of a four-rung ladder your estate lands on* — a static endpoints file, a file rewritten by an external generator, a custom discovery plugin compiled into your own thin binary, or a different product entirely — and *where the router process itself should run*. Those are not matters of taste. Five measurable properties of a backend estate decide them: **churn rate** (how often the endpoint set changes), **availability requirement** (is a single router replica tolerable?), **security boundary** (who can reach the prefill hop and the metrics ports?), **addressing and scale** (IPv4 literals under a 1 MiB file, or hostnames and thousands of endpoints?), and **team capability** (can you own roughly 200 lines of Go against an interface whose configuration shape moved three times in four months?).

This report argues one thesis throughout: **the two prevailing readings of llm-d's non-Kubernetes story — "it already works, just point it at a file" and "the operations layer is still Kubernetes-first, so you will be building real infrastructure" — are both true, at different layers, and the boundary between them is drawable with precision.** The routing *logic* is platform-neutral and reusable essentially in full. The routing *inputs* (CRD-driven per-request priority), the endpoint *lifecycle* (readiness gating and eviction), the *coordination* layer (leader election), and the *observability* plumbing (PodMonitor) are not. Every decision rule below is an attempt to place a given estate on the correct side of that line, and to name the operational obligations that come attached.

Three facts anchor the version-specific advice, verified against the record as of 11 September 2026. First, the nested configuration key `dataLayer.discovery.endpoints.pluginRef` was merged on 2026-08-25, eight days *after* the newest tagged router release (v0.10.0, 2026-08-17), so it exists only on unreleased `main`; a pinned v0.10.0 build must use the legacy `dataLayer.discovery.pluginRef`, which the migration shim keeps working thereafter [[config-consolidate-discovery-plugins-under-a-single-discovery-sectio-llm-dllm-d]] [[config-consolidate-discovery-plugins-under-a-single-discovery-section-follow-up]]. Second, llm-d-router **v0.9.0 is a hard floor**: FileDiscovery shipped there, and so did the fix for endpoint-metadata updates failing to dispatch notification events, which every per-endpoint subscriber depends on [[endpoint-metadata-updates-do-not-trigger-endpoint-notification-events-issue-1403]]. Third, the prefill/decode sidecar's SSRF protection is bound to an InferencePool and is **off by default**, which makes network isolation plus `--enable-tls=prefill` the mandatory off-Kubernetes posture rather than an optional hardening step [[optionsgo]] [[github-llm-dllm-d-routing-sidecar-incubating-pd-sidecar-for-llm-d-github]].

## 1. llm-d Component Inventory and Kubernetes Coupling

llm-d is best understood as a control plane wrapped around unmodified inference engines, and it says so itself: as of v0.8 the project dropped its custom vLLM images in favour of upstream `vllm/vllm-openai`, framing the change as "not just a packaging simplification — it is a statement about what llm-d is. The project is a control plane that wraps inference engines, not a distribution that replaces them" [[llm-d-v08-from-platform-to-control-plane-llm-d]]. That framing is load-bearing for this strategy: a control plane's coupling to Kubernetes lives in how it *learns about* and *governs* backends, not in how it talks to them.

The components sort into three coupling classes.

| Component | What it does | Kubernetes coupling | Reusable off-cluster? |
|---|---|---|---|
| Endpoint Picker (EPP) scheduling framework — filters, scorers, pickers, profile handlers | Chooses the endpoint per request | None once a discovery plugin is configured [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]] | Yes, unchanged |
| ext_proc wire protocol | Returns the choice to the proxy | Endpoints are `<ip:port>` strings, not object references [[gateway-api-inference-extensiondocsproposals004-endpoint-picker-protocol-at-main]] | Yes |
| Data layer: polling metrics sources + extractors | Scrapes `/metrics`, feeds scorers | `PollingDataSource` is generic; `NotificationSource` is "an event-driven DataSource for a single k8s GVK" [[datalayer-package-sigsk8siogateway-api-inference-extensionpkgeppframeworkinterfa]] | Yes (drop `k8s-notification-source`) |
| Endpoint discovery | Populates the datastore | Default path is a controller-runtime Pod reconciler [[pod_reconcilergo]]; pluggable since v0.9.0 | Yes, via plugin — **this is the seam** |
| KV-cache indexer + precise prefix producer | Tracks real KV blocks per endpoint | Driven by generic endpoint events, keyed on `Address:Port` [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcacheex]] | Yes, single-rank |
| Flow control (priority bands, fairness, saturation) | Admission before scheduling | Bands and policies are static YAML read once at startup [[configuration-llm-d]]; only the objective *lookup* is CRD-backed | Partly — see §5 |
| P/D routing sidecar | Coordinates prefill→decode | TLS flags portable [[tlsgo]]; SSRF allowlist requires an InferencePool watch [[optionsgo]] | Yes, with network isolation |
| Latency predictor | XGBoost TTFT/TPOT prediction | FastAPI services on ports 8000/8001, no API-server dependency [[github-llm-dllm-d-latency-predictor-latency-prediction-service-for-ml-model-base]] | Yes |
| InferencePool / InferenceObjective / InferenceModelRewrite CRDs | Pool identity, priority, model rewriting | Kubernetes API objects by definition [[inferencepool-kubernetes-gateway-api-inference-extension]] | No |
| Helm charts, HA leader election, PodMonitor/ServiceMonitor | Packaging, coordination, scrape discovery | Lease objects, StatefulSets, Prometheus-Operator CRDs [[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]] [[metrics-llm-d]] | No — replace |

The interpretive point the table makes that no single source states: **coupling tracks the control plane's *governance* surface, not its *data* surface.** Everything on the request path — parse, admit, filter, score, pick, emit a header — is Kubernetes-free by construction, because the protocol it terminates in was specified in terms of addresses. Everything that tells the router *what exists*, *what matters*, and *who is in charge* was built on controller-runtime reconcilers, because that was the cheapest correct implementation on Kubernetes. A migration off Kubernetes is therefore not a port; it is a substitution of four specific inputs.

One nuance matters for expectations. The router's own repository landing page is silent on all of this: a digest of the README and commit history at v0.10.0 found zero mentions of discovery, `EndpointDiscovery`, or non-Kubernetes standalone operation, and "Standalone Mode" there means a self-managed Envoy without Gateway API, still Helm-deployed [[source-analysis-llm-d-router-github-repo-readme-commit-history]]. The capability is real and documented in `docs/discovery.md`; it is simply not yet marketed at the front door. Teams evaluating llm-d from its README alone will conclude, wrongly, that this strategy is impossible.

## 2. How the llm-d Router Discovers and Tracks Backends Today

The default path is a plain Pod watch. A controller-runtime reconciler admits a Pod on exactly two conditions — the label selector matches, and the aggregate `Ready` condition is true — and then uses `pod.Status.PodIP` verbatim with no validation of emptiness or format [[pod_reconcilergo]]. The EPP's RBAC is correspondingly narrow: get/list/watch on pods and endpoints plus the inference CRDs, no write access [[how-llm-d-routes-model-inference-traffic-on-amazon-eks-red-hat-developer]]. `InferencePool` selects Pods by label and target ports — not Services, not EndpointSlices [[inferencepool-kubernetes-gateway-api-inference-extension]].

That last fact kills an entire family of shims before it starts. Manually authoring a selectorless Service plus EndpointSlice is the officially documented way to expose external endpoints to *kube-proxy* [[endpointslices-kubernetes]], but the EPP never reads EndpointSlices, so the shim routes nothing through the scheduler you came for. This is a category error, not a weaker option — drop it from consideration entirely.

Downstream of admission, the datastore is genuinely backend-shaped. `EndpointMetadata` carries `ID types.NamespacedName`, `Name`, `Address`, `Port`, `MetricsHost` (defaulting to `address:port`), and free-form `Labels` [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]. The godoc still describes the struct as "the relevant Kubernetes Pod state of an inference server" and retains `NamespacedName`/`PodName` fields [[datalayer-package-sigsk8siogateway-api-inference-extensionpkgeppframeworkinterfa]], and a reviewer on the discovery PR flagged `Delete(id types.NamespacedName)` as "too k8s centric" with a `UniqueID` replacement agreed in principle and deferred [[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]]. A non-Kubernetes plugin must therefore mint a synthetic two-part identity. That is a naming tax, not a design obstacle.

The decisive detail for feature parity is that **identity and addressing are two separate spaces, and only addressing is load-bearing for routing**. The precise prefix-cache producer uses `meta.ID.String()` purely as a bookkeeping key for its per-endpoint ZeroMQ subscriber lifecycle, while every scoring and index operation keys on the literal string `fmt.Sprintf("%s:%s", meta.Address, meta.Port)` [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcacheex]] [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcachepr]]. The vLLM KV-event topic format `kv@<ip>:<port>@<model>` and `NamespacedName` were never meant to be string-equal and do not need to be. This is why llm-d's flagship scorer survives the move off Kubernetes intact — a conclusion that follows from the code, not from marketing.

At the wire, the EPP sets `x-gateway-destination-endpoint` and Envoy's `ORIGINAL_DST` cluster reads it (`use_http_header: true`, `http_header_name: x-gateway-destination-endpoint`), giving the flow: client → Envoy listener → ext_proc gRPC on 9002 → header → chosen `<address>:<port>` [[llm-ddocsinfrastructureno-kubernetes-deploymentmd-at-main-llm-dllm-d-github]] [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]. Client spoofing of that header is closed: the sanitization fix drops system-owned headers from the passthrough loop, with a test asserting an injected `1.1.1.1:666` is replaced by the EPP's own `1.2.3.4:8080` [[fix-harden-header-sanitization-and-handling-logic-by-lukeavandrie-pull-request-2]] [[2025diff]].

## 3. Extension Seams in the Router for Non-Pod Backends

The `EndpointDiscovery` contract is three methods and two calls: `Start(ctx, notifier)`, `Ready() <-chan struct{}`, and `TypedName()`, with the plugin pushing `notifier.Upsert(*EndpointMetadata)` and `notifier.Delete(types.NamespacedName)` [[llm-d-routerpkgeppframeworkinterfacedatalayerdiscoverygo-at-main-llm-dllm-d-rout]]. Three contract details are non-negotiable and are the most common source of subtle bugs:

1. **Enumerate before watching.** Implementations "SHOULD enumerate all currently known endpoints via `notifier.Upsert` before entering the watch loop, to avoid serving an empty datastore at startup," with a carve-out only for watch mechanisms that guarantee no missed events [[llm-d-routerpkgeppframeworkinterfacedatalayerdiscoverygo-at-main-llm-dllm-d-rout]].
2. **`Ready()` closes once, after the first successful sync, and zero endpoints is a valid outcome** — never gate readiness on a non-empty set. The runner gates request serving (but not `/metrics`) on that channel [[filediscovery-plugin-44-wiring-into-the-runner-by-ezrasilvera-pull-request-1218]].
3. **`DiscoveryNotifier` is not goroutine-safe.** All calls must be sequential from one goroutine in causal order, or "an `Upsert` followed by a `Delete` for the same endpoint" arriving out of order leaves a dead endpoint in the datastore permanently [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]].

The one shipped non-Kubernetes implementation, `file-discovery`, is also the reference design. It reads a YAML or JSON file, validates each entry, upserts it, and — with `watchFile: true` — reattaches its fsnotify watcher after an atomic rename or a ConfigMap-style symlink swap, deleting endpoints absent from the new load [[llm-d-routerpkgeppframeworkpluginsdatalayerdiscoveryfile-at-main-llm-dllm-d-rout]] [[readmemd]] [[plugingo]]. Its limits are the thresholds your estate must be measured against: **the file is capped at 1 MiB; `address` must be a literal IPv4 (no hostnames, no IPv6); metrics are scraped from the same `address:port` that serves inference; duplicate names within a namespace resolve last-write-wins; a single bad entry is skipped but an unparseable file aborts startup; and reload failures are logged non-fatally, leaving the previous datastore state in place** [[llm-d-routerpkgeppframeworkpluginsdatalayerdiscoveryfile-at-main-llm-dllm-d-rout]] [[readmemd]].

Two shipped precedents prove the endpoint model already tolerates non-pod shapes. `multicluster-file-discovery` treats whole *clusters* as candidate endpoints, "follows the same format as the pod file discovery, except an address may be a hostname," and supports per-entry `metricsAddress`/`metricsPort` labels for out-of-band scraping [[llm-d-routerpkgeppframeworkpluginsreadmemd-at-main-llm-dllm-d-router-github]]. And `plugin.go` injects its address validator at construction specifically "so a variant can loosen it" [[plugingo]]. The inference those two facts jointly license: a custom plugin that emits hostnames, separate metrics hosts, or synthetic identities is not fighting the framework — it is walking a path the framework was already widened for.

Registration is where the only genuine controversy lives. The registry is an exported package-level map mutated by an exported `Register()`, under `pkg/` with no `internal/` barrier and no "not a public API" disclaimer [[registrygo]] [[llm-d-routerpkgeppframeworkinterfacepluginregistrygo-at-main-llm-dllm-d-router-g]]; `main.go` is a thin wrapper over an importable runner [[maingo]]; and `docs/discovery.md` tells you to "register the factory in the runner before calling `Run`" [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]. **Steel-manning the objection**: the only plugin-authoring *tutorial* the project ships instructs you to edit `runner.go`'s unexported `registerInTreePlugins()` [[llm-d-routerdocscreate_new_filtermd-at-main-llm-dllm-d-router-github]]; the `Runner` exposes no `WithPlugins` hook [[runnergo]]; `Register()` has no duplicate-key guard, so a colliding type name silently overwrites [[registrygo]]; there is no panic recovery anywhere in the plugin-invocation path, and the one open issue that even names "out-of-tree plugins" proposes classifying them as at-your-own-risk [[framework-define-a-panic-isolation-posture-for-plugin-extension-points-issue-210]]; `CONTRIBUTING.md` is silent [[llm-d-routercontributingmd-at-main-llm-dllm-d-router-github]]; and a repository-wide issue search for the term returns essentially nothing [[issues-llm-dllm-d-router-github]].

The objection is answerable, and the answer is a scoping distinction: the in-tree tutorial governs *scheduling filters*; `docs/discovery.md` has its own "Writing a custom discovery plugin" section that teaches exactly the `Register`-before-`Run` pattern for *discovery* [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]]. Registering a custom discovery plugin is documented upstream. Only the packaging choice — doing it from your own `main()` rather than editing the repository — is an inference, and nothing blocks it: no `internal/` path, no replace directives, at the cost of a `go 1.26.6` floor and the full controller-runtime dependency tree even in no-Kubernetes mode [[main]] [[gomod]]  [[maingo]]. The residual risks are real and identical under a fork: namespace your plugin type, wrap `Start()` in your own `recover()`, pin a release, and run CI against upstream `main`. Note also that a custom plugin declares its own stability level, and Alpha plugins refuse to start without `--allow-experimental-plugins` [[llm-d-routerpkgeppframeworkpluginsreadmemd-at-main-llm-dllm-d-router-github]].

## 4. Upstream State: Proposals and Work on Non-Pod and External Endpoints

The non-Kubernetes path is not speculative; it is a completed, dated, ten-PR delivery chain tracked as a release goal. Issue #1520 lists it under `sig-rl` with the design proposal and the merged sequence: the pluggable interface (#908), the store plumbing (#1080, #1081), the FileDiscovery plugin itself (#1135), a rename (#1154), runner wiring (#1218), documentation corrections (#1338), a gRPC-parameter fix (#1362), flow control wired into file-discovery mode (#1368), and the endpoint-notification fix (#1404) [[v08-release-goals-mid-june-issue-1520-llm-dllm-d]]. The v0.8 release notes list "Non-Kubernetes mode (RL/Slurm) | llm-d-router (FileDiscovery plugin) | New" as a shipped capability [[releases-llm-dllm-d]], and v0.7 had already made standalone (generic-proxy, no Gateway API) the *default* deployment because full gateway configuration was too hard for adopters [[llm-d-v07-from-feature-introduction-to-production-hardening-llm-d]] [[releases-llm-dllm-d]].

The upstream debate that produced this is worth reading because it bounds what will and will not arrive next. The Gateway API Inference Extension issue proposing a zero-Kubernetes mode was motivated by batch and reinforcement-learning customers, and the winning counter-proposal was precisely "add a discovery layer… similar to scheduler pluggability" [[standalone-epp-issue-1838-kubernetes-sigsgateway-api-inference-extension]]. In the parallel agentgateway thread, a maintainer's initial dismissal ("made up use case") was withdrawn once the batch-inference rationale landed, with the decisive point being that "the protocol is not changing (the ext-proc and EPP protocol on how the endpoint is communicated back to the proxy)" [[inference-support-agentgateway-as-a-standalone-provider-issue-620-agentgatewayag]].

**But the same threads bound the commitment.** The zero-Kubernetes issue states "the end goal is to land users on k8s and the gateway api," and a maintainer objected that a hybrid of Kubernetes and non-Kubernetes "seems very very odd" [[standalone-epp-issue-1838-kubernetes-sigsgateway-api-inference-extension]] [[inference-support-agentgateway-as-a-standalone-provider-issue-620-agentgatewayag]]. The Gateway API standalone guide's flag-only mode still selects Kubernetes pods by label, and the guide itself was deleted in a June 2026 documentation cleanup with no replacement page [[gateway-api-inference-extensionsite-srcguidesstandalonemd-at-91ad0da44f64d41642d]]. The standalone chart that added agentgateway as a sidecar proxy still generates a Kubernetes Service as the addressing anchor [[add-standalone-agentgateway-proxy-support-by-danehans-pull-request-2882-kubernet]]. Every gateway-mode proxy — Istio, kgateway, NGINX Gateway Fabric, GKE — implements the extension only through `InferencePool` and cannot target non-pod endpoints directly.

The honest synthesis, and the one this report builds on: **bet on the discovery seam, and do not bet on upstream soon supplying non-Kubernetes coordination, packaging, or observability.** Orchestrator-native discovery plugins are explicitly future work — the project's own roadmap language puts "a dedicated `SlurmDiscovery` or `RayDiscovery` plugin against the same `EndpointDiscovery` interface" in the future bucket, listing three shipped strategies that are all variants of the one file plugin [[no-kubernetes-no-problem-llm-d-now-runs-anywhere-llm-d]]. There are, at the pull-request level, zero Consul, etcd, Slurm, or Ray discovery implementations anywhere in the repository's history; every discovery PR targets flat files or Kubernetes primitives. A dynamic non-Kubernetes discovery plugin is greenfield work with no upstream branch to track — which is a cost, and also an opportunity to contribute.

Peer discovery sharpens the same point. The infrastructure merged for v0.10.0 (`dataLayer.peerDiscovery.pluginRef`, later consolidated under `discovery.peers`) [[feat-epp-peer-discovery-infrastructure-by-evacchi-pull-request-2341-llm-dllm-d-r]], but the only peer-discovery implementation is a Kubernetes Pod-watch plugin that remains open and unmerged at Alpha [[feat-pod-watch-peer-discovery-plugin-by-evacchi-pull-request-2501-llm-dllm-d-rou]], and the documentation describes the cross-replica syncer it would feed as "future" [[llm-d-routerdocspeer-discoverymd-at-main-llm-dllm-d-router-github]]. Off-cluster peer discovery would be a *second* custom plugin — which is exactly why the recommended design avoids needing it (§7).

## 5. Non-Pod Backend Types and What Each Requires from the Router

Different estates impose genuinely different obligations. The following mapping is the operational core of this report.

| Backend estate | Discovery rung | Health source | KV-event path | Notable obligation |
|---|---|---|---|---|
| Fixed bare-metal / VM rack | Static file | External health agent rewrites file | Router dials each host's ZMQ PUB | Firewall must allow EPP → host:5556 and :8000 |
| Docker / Podman / Nomad | File + generator | Runtime health checks feed generator | Same | Host networking or explicit port maps |
| Slurm allocation | File + generator (`scontrol show hostnames`) or custom plugin | Job state | Same, job-scoped | Router lifecycle tied to the job; `--pool-namespace` must be set explicitly |
| Ray cluster | File + generator (`ray.nodes()`) or custom plugin | Actor liveness | Same | Actor churn drives the poll interval |
| Service registry (Consul, etcd, cloud SD) | Custom plugin | Registry-native (`?passing=true`) | Same | Poll/long-poll loop plus identity synthesis |
| Remote Kubernetes clusters | `multicluster-file-discovery` | Peer cluster gateway health | Cluster-aggregate metrics | Hostnames allowed; separate metrics host supported |
| Managed APIs (OpenAI, Bedrock, Gemini) | **Not the EPP's job** | Provider SLA | None | Route at the AI-gateway tier instead |
| Serverless GPU providers | Custom plugin, high churn | Provider API | Often unavailable | Cold starts break saturation assumptions |

Four cross-cutting requirements apply to every row.

**The model-server contract is portable; nothing in it mentions Kubernetes.** A backend must speak OpenAI-compatible HTTP and expose Prometheus metrics the extractors understand — queue depth, running requests, KV-cache utilization — with engine-specific metric names selected by a label key [[gateway-api-inference-extensionsite-srcguidesepp-configurationconfig-textmd-at-9]]. The no-Kubernetes guide's monitoring section is a plain static `scrape_configs` block pointed at the EPP's `:9090` and each worker's `/metrics` [[llm-dguidesno-kubernetes-deployment-at-main-llm-dllm-d-github]]; PodMonitor is a Prometheus-Operator convenience, not a routing input [[metrics-llm-d]]. This is the cheapest of the four substitutions and should not be described as a loss.

**Prefix-cache routing is what you are buying, and it survives.** Under round-robin across eight replicas, a shared system prompt is seen by any given replica only ~12.5% of the time, so per-replica hit rates approach zero and get *worse* as you scale [[gke-inference-gateway-kv-cache-aware-llm-routing-explained-spheron-blog]]. Upstream benchmarks on 8 vLLM replicas across 16 H100s (Qwen3-32B, 60 RPS, shared prefixes) report P90 TTFT falling from ~35 s to ~120 ms and throughput up 151% [[intelligent-inference-scheduling-with-llm-d-on-red-hat-ai-red-hat-developer]], with precise scheduling at 8,730 output tokens/sec and 0.542 s P90 TTFT versus 4,429 tok/s and ~93 s for cache-blind [[kv-cache-wins-you-can-see-from-prefix-caching-in-vllm-to-distributed-scheduling]]. These are vendor-reported and not independently reproduced [[best-of-both-worlds-cloud-native-ai-inference-at-scale-using-kserve-and-llm-d-ks]], so treat the magnitudes as indicative — but the mechanism is sound and the direction is corroborated across sources. Operationally, each backend binds its own ZMQ publisher (`KV_EVENTS_ENDPOINT=tcp://*:5556`, topic `kv@<ip>:<port>@<model>`) and the router dials *out* to it, with newer vLLM additionally binding a replay socket on 5559 retaining the last 10,000 batches so a restarted router rebuilds its index without waiting for traffic [[llm-dguidesprecise-prefix-cache-routingreadmemd-at-main-llm-dllm-d-github]]. **Obligation: the router must have inbound-to-outbound reachability to every backend's event port, not merely its serving port.** The one genuine gap is data-parallel multi-rank engines: the dial port is `SocketPort + RankIndex`, and the file schema has no rank field, so every file-discovered endpoint stays at rank 0 — a custom plugin can set it directly [[readmemd]].

**Prefill/decode disaggregation works, but its security model does not travel.** Pairing is decentralized by design — "the first time D sees an unknown P engine it performs a background handshake… with no centralized service-discovery plane required" — with leases and heartbeats freeing blocks if the decoder dies [[networking-for-distributed-inference-in-llm-d-llm-d]]. Role selection is just labels (`llm-d.ai/role: prefill|decode`), which file discovery sets natively [[pd-disaggregation-llm-d]] [[llm-dguidesno-kubernetes-deployment-at-main-llm-dllm-d-github]]. But the sidecar's SSRF allowlist requires a Kubernetes client watching a named InferencePool, has no static or CIDR alternative, and defaults to off; when off, the proxy forwards to whatever `x-prefiller-host-port` names [[optionsgo]] [[github-llm-dllm-d-routing-sidecar-incubating-pd-sidecar-for-llm-d-github]]. **Obligation: treat this as a network-isolation requirement — the sidecar port reachable only from the trusted gateway path via firewall, security group, or mesh ACL — and enable `--enable-tls=prefill`, which is plain Go TLS with no Kubernetes CA dependency [[tlsgo]] [[optionsgo]].**

**Per-request priority is the one real functional loss.** The objective header names a Kubernetes resource; off-cluster the reconciler never starts and lookups return nil, so every request lands in the default band [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]] [[epp-http-headers-reference-llm-d]]. Everything around it is fine: bands, fairness policies, ordering policies and the saturation detector are static YAML read once at startup [[configuration-llm-d]]; tenant fairness is a bare string header defaulting to `default-flow`; missing objectives default to priority 0 and only sub-zero priorities are sheddable [[llm-d-flow-control-priority-queuing-for-shared-gpu-inference-red-hat-developer]]; and model aliasing has a shipped header alternative, `x-llm-d-model-name-rewrite` [[epp-http-headers-reference-llm-d]]. If you need priority tiers, the fix is a small static or file-backed admitter/data-producer plugin, auto-wired by interface [[configuration-llm-d]]. If you do not, skip it — this is the single most effective way to keep your custom surface to one plugin.

## 6. Candidate Strategies Compared

| Strategy | llm-d reuse | Maintenance burden | Feature parity | Ops complexity | Choose when |
|---|---|---|---|---|---|
| **A. Static endpoints file** | Total | Near zero | Full minus CRD inputs | Lowest | Fixed rack; churn near zero; ≤ a few thousand IPv4 endpoints |
| **B. File + external generator (`watchFile`)** | Total | Owns one script | Same as A | Low | Slurm/Ray/VM fleets where an orchestrator can emit the list |
| **C. Custom `EndpointDiscovery` plugin, out-of-tree `main()`** | Total (same `Run()` path) | One Go file + release-pin CI | Same as A, plus `RankIndex`, hostnames, separate metrics hosts | Moderate | Registry-backed or high-churn estates; DP-rank engines |
| **D. In-tree fork** | Total | C **plus** rebase against a fast-moving config surface | Same as C | Moderate-high | Only if you must also change scheduling internals |
| **E. Embed llm-d libraries in a custom router** | Partial | Highest | You reimplement ext_proc, config, draining, health | High | Essentially never for discovery-only needs |
| **F. Kubernetes object shims (EndpointSlice / virtual pods)** | N/A | — | EndpointSlice reaches the EPP not at all | — | Never, except Liqo-class cross-cluster pod networking |
| **G. Slinky (Slurm workers as real pods)** | Total, zero router code | Operates a Slurm-on-Kubernetes operator | Full | High (fleet custody moves) | Building a fleet fresh and content for Kubernetes to schedule it |
| **H. Different router (vLLM Router, production-stack, Dynamo)** | None | Theirs | Loses llm-d's plugin depth | Low | No shared prefixes, no P/D, no flow control needs |
| **I. Upstream the plugin** | Total | Shared | Same as C | Low, eventually | In parallel with C, never instead of it |

Three comparisons deserve argument rather than a table row.

**C beats D, decisively.** A fork buys nothing a downstream `main()` does not already get — the same dependency graph, the same interfaces, the same absence of panic recovery — while adding a rebase obligation against a subsystem whose configuration shape changed three times in about four months: the interface was renamed and moved packages during review of #908; the key moved under `dataLayer`; then it nested again into `dataLayer.discovery.endpoints` [[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]] [[config-consolidate-discovery-plugins-under-a-single-discovery-sectio-llm-dllm-d]]. Each change shipped a compatibility shim for the *config*, but the Go interface has no such shim.

**C beats E on the very axis E is usually chosen for.** Embedding looks lighter until you notice that the runner imports the full plugin catalogue unconditionally, so you inherit the identical transitive dependency tree while giving up the ext_proc server, configuration loader, draining, and health wiring that `Run()` hands you free [[runnergo]] [[gomod]]. It also multiplies your breaking-change exposure from two interfaces to dozens. The one-line version: **embedding trades a small, versioned contract for a large, unversioned one.**

**H is a live option, and its existence is what makes C safe.** Simpler routers ship static discovery natively [[github-vllm-projectrouter-a-high-performance-and-light-weight-router-for-vllm-la]] [[router-configuration-vllm-projectproduction-stack-deepwiki]] [[github-ai-dynamodynamo-a-datacenter-scale-distributed-inference-serving-framewor]], and competing throughput claims exist on both sides without published harnesses [[vllm-router-a-high-performance-and-prefilldecode-aware-load-balancer-for-large-s]]. The decisive consideration is not the benchmark: because every proxy reaches every picker through the same ext_proc protocol, and NVIDIA's own stack ships a different picker behind that same protocol [[gateway-api-inference-extensiondocsproposals004-endpoint-picker-protocol-at-main]] [[kv-aware-routing-on-kubernetes-nvidia-dynamo-documentation]], **the choice of llm-d is reversible and the discovery plugin is the only picker-specific investment you make.** Keeping that logic in one isolated plugin means switching pickers later costs one file, not an architecture. That is an argument for C that no benchmark can overturn.

Finally, managed APIs are not a router problem at all. Every credible pattern puts external providers at a gateway tier above or beside the inference gateway — an `ai:` backend block alongside a self-hosted pool reached through `inferenceRouting` [[routing-agent-traffic-is-really-three-decisions-aks-engineering-blog]], a LiteLLM proxy with a static `model_list` [[centralized-routing-for-external-and-self-hosted-llms-on-openshift-ai-red-hat-de]]. The reason is mechanical: the EPP's entire value is per-replica queue depth and KV-cache pressure, and a managed endpoint exposes neither.

## 7. Recommended Strategy and Implementation Roadmap

**The recommendation, stated as a decision procedure.**

*Rule 1 — availability selects topology, and this is the first branch.* If a single router instance is acceptable (job-scoped serving, RL rollouts, batch, development, an HPC allocation whose lifetime equals the job's), run the router entirely outside Kubernetes: `epp` plus Envoy as host processes or containers, with the documented flags `--config-file`, `--pool-name`, `--pool-namespace`, `--grpc-port=9002`, `--grpc-health-port=9003`, `--metrics-port=9090` [[llm-dguidesno-kubernetes-deployment-at-main-llm-dllm-d-github]]. If you need multi-replica availability, you have two paths, and the tie-breaker is whether a small Kubernetes control plane is acceptable. If it is, run the EPP in-cluster under the Helm chart — leader election over a `coordination.k8s.io/Lease` works normally — while the backend inventory points off-cluster, using the chart's documented `pluginsCustomConfig` plus `volumes`/`volumeMounts` escape hatches to inject configuration and mount the endpoints file [[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]] [[llm-d-routerconfigchartsreadmemd-at-main-llm-dllm-d-router-github]]. If Kubernetes is unavailable anywhere, run N EPPs Active-Active behind a plain L4 load balancer with leader election *explicitly disabled* and **precise** (not approximate) prefix routing, because each replica subscribes independently to every backend's KV-event stream and converges without coordination; the scaling evidence runs in favour of this, with failures at 500 QPS falling from a broken single replica (3,148 failures) to 18 at four replicas while P50 TTFT dropped 165 ms → 30 ms [[evaluate-llm-d-router-both-epp-and-the-standalone-proxy-scale-limits-issue-1290]] [[llm-d-v09-hardened-for-scale-llm-d]]. Two cautions attach: the chart silently injects `--ha-enable-leader-election` whenever replicas exceed one [[llm-d-routerconfigchartsreadmemd-at-main-llm-dllm-d-router-github]], and flow control state is per replica, so priority and fairness are enforced only within each replica's share of traffic [[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]].

*Rule 2 — churn and addressing select the discovery rung.* Start at the lowest rung your estate tolerates. A static file if the set is fixed. A generator plus `watchFile: true` if an orchestrator can emit the list — this is the documented Slurm and Ray pattern and requires zero Go [[no-kubernetes-no-problem-llm-d-now-runs-anywhere-llm-d]] [[llm-dguidesno-kubernetes-deployment-at-main-llm-dllm-d-github]]. Escalate to a custom plugin when any of four gates trips: endpoints are addressed by hostname rather than IPv4 literal; the inventory exceeds the 1 MiB file budget; backends are data-parallel and need non-zero `RankIndex`; or churn is fast enough that a regenerate-and-rewrite loop leaves a measurable window of routing to dead workers. Within the plugin, default to an interval poll plus snapshot diff — a near-mechanical transliteration of the file plugin's load loop — use a long-poll primitive where the registry offers one (a blocking query with the last-seen index, plus `?passing=true` for server-side health filtering [[blocking-queries-consul-hashicorp-developer]] [[health-http-api-consul-hashicorp-developer]]), and reserve a genuine persistent watch for cases where staleness has a named cost, because the project's own attempt at a watch-based plugin under this interface was abandoned as too large to review [[discovery-plugins-k8s-and-file-based-endpoint-discovery-by-ezrasilvera-pull-requ]].

*Rule 3 — health gating outranks the poll-versus-watch question.* Kubernetes readiness is gone and nothing replaces it; the datastore will route to a dead backend forever if discovery never calls `Delete`, and the stale entry keeps its ZMQ subscriber and its KV-index entries alive too [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]] [[llm-d-routerpkgeppframeworkpluginsrequestcontroldataproducerpreciseprefixcacheex]]. Therefore: **only Upsert endpoints you believe healthy, Delete on the first failed health signal, and pin llm-d-router ≥ v0.9.0 so metadata changes actually dispatch notifications** [[endpoint-metadata-updates-do-not-trigger-endpoint-notification-events-issue-1403]]. A useful calibration from a comparable project: a shipped static-discovery implementation layers a background health-check thread under a fixed topology and filters unhealthy URLs out of its returned set without mutating the list [[service_discoverypy]]. Copy that shape.

*Rule 4 — the proxy choice silently decides your failure mode.* Use Envoy with llm-d's reference configuration for any off-Kubernetes deployment. It is the documented path, and it is the one where you can deliberately add a fallback cluster and set ext_proc's `failure_mode_allow` [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]] [[external-processing-envoy-1400-dev-13b0a8-documentation]]. Agentgateway's standalone passthrough is fail-closed and its fail-open design is still an open issue [[support-fail-open-fallback-for-standalone-epp-inference-routing-issue-1661-agent]] [[trust-standalone-epp-selected-destinations-by-danehans-pull-request-1658-agentga]]. Do not assume fail-open off Kubernetes: llm-d's scoped fail-open is tied to the lease-transition window that does not exist without a Lease [[llm-d-routerdocsoperationsmd-at-main-llm-dllm-d-router-github]], and with a header-driven `ORIGINAL_DST` cluster the proxy has no endpoint list of its own to fall back to. The protocol's ordered fallback-endpoint list is worth enabling because it gives per-request retry resilience that does not depend on router availability at all [[amend-the-endpoint-picker-protocol-to-support-multiple-fallback-endpoints-by-wbp]].

**Roadmap, with gates rather than dates.**

*Phase 0 (days) — prove parity before writing code.* Stand up the shipped no-Kubernetes reference on two workers: file discovery, the optimized-baseline plugin mix (prefix-cache-scorer at weight 3; queue, KV-utilization and no-hit-LRU scorers at weight 2; max-score picker), Envoy with `ORIGINAL_DST`, static Prometheus scrape targets [[llm-dguidesno-kubernetes-deployment-at-main-llm-dllm-d-github]]. Pin llm-d-router to a tagged release and use the legacy `dataLayer.discovery.pluginRef` on v0.10.0; adopt `dataLayer.discovery.endpoints.pluginRef` only on `main` builds or the release that follows [[config-consolidate-discovery-plugins-under-a-single-discovery-section-follow-up]]. Set `--pool-namespace` explicitly, since the fallback is the literal string `default` — a Kubernetes-flavoured label that is meaningless in a Slurm or Ray context [[llm-d-routerdocsdiscoverymd-at-main-llm-dllm-d-router-github]].

*Phase 1 (days) — validate the flagship scorer end-to-end.* Enable precise prefix-cache routing against file-discovered endpoints and confirm subscribers attach and index hits register. **This is the single highest-value experiment in the plan, because the code path is verified but no published report pairs precise routing with file discovery in a running deployment** — an absence worth closing with your own test rather than with caution [[llm-dguidesprecise-prefix-cache-routingreadmemd-at-main-llm-dllm-d-github]].

*Phase 2 (days) — automate the inventory.* Write the generator that regenerates `endpoints.yaml` from your orchestrator and rewrites it by atomic rename; verify the reload log line fires [[llm-dguidesno-kubernetes-deployment-at-main-llm-dllm-d-github]]. Add health filtering here, not later. Many estates stop at this phase permanently, and should.

*Phase 3 (1–2 weeks, only if a Rule-2 gate tripped) — the plugin.* Implement `EndpointDiscovery` against your registry, copying the file plugin's structure [[plugingo]]; register it via `init()` under a namespaced type string from a downstream `main()` that calls `runner.NewRunner().Run(ctx)` [[registrygo]] [[maingo]]; wrap `Start()` in your own `recover()`; add a scheduled CI job that compiles against upstream `main` so interface drift surfaces as a build failure rather than a production one.

*Phase 4 (ongoing) — harden and contribute.* Isolate the prefill hop at the network layer and turn on sidecar TLS [[optionsgo]]; enable metrics-endpoint authentication [[2061]]; add priority only if tiers are genuinely needed; and open an upstream issue offering the plugin, since maintainers have said in writing they want exactly this class of discovery backend [[feat-add-pluggable-discoveryplugin-interface-by-ezrasilvera-pull-request-908-llm]].

**Looking forward.** Three trajectories will matter over the next six to twelve months, and each one argues for the same posture. First, the router's roadmap names "a standardized model server interface… independent of whether the engine underneath is vLLM, SGLang, or TensorRT-LLM" [[llm-d-v09-hardened-for-scale-llm-d]] — a further decoupling of the router from any particular backend shape, which strengthens the bet that discovery is the last Kubernetes-shaped seam left. Second, the data plane is consolidating: llm-d deprecated its kgateway path in favour of agentgateway [[refresh-support-for-kgateway-agentgateway-gie-and-gw-api-by-danehans-pull-reques]] [[inference-serving-with-superpowers-agentgateway-agent-connectivity-solved]], and kgateway abandoned an Envoy load-balancer refactor because it was deprecating its Envoy data plane entirely for AI features [[inference-refactor-plugin-to-use-override_host-lb-issue-11824-kgateway-devkgatew]]. A deployment that stays on plain Envoy with the reference configuration is insulated from that churn; one that couples tightly to a specific gateway's behaviour is not. Third, the design direction across the field converges on backend-agnostic global schedulers addressed over REST/gRPC with opaque instance identity rather than orchestrator objects [[rfc-mooncake-conductor-design-and-implementation-of-a-global-scheduler-module-fo]]. The prediction this licenses — stated as inference, not as a sourced fact — is that orchestrator-native discovery plugins will eventually land upstream, and that a team who wrote one against today's interface will be positioned to upstream it rather than to rewrite. The cost of being early is the interface drift you must absorb; the cost of waiting is running someone else's roadmap.

## 8. Risks, Trade-offs, and Open Questions

**The interface is young and moves faster than its documentation.** Three independent documentation artifacts are already wrong about the exact configuration key this strategy depends on, and the authoritative nested form ships in no release yet [[config-consolidate-discovery-plugins-under-a-single-discovery-section-follow-up]] [[llm-d-routerpkgeppframeworkinterfacedatalayerdiscoverygo-at-main-llm-dllm-d-rout]]. Mitigation is process, not code: pin a tagged release, treat the shipped file plugin's source as the real template rather than the documentation skeleton, and read release notes for data-layer changes every cycle.

**You will be the first.** Package indexing reports no known importers for the runner or the framework interface packages as of 11 September 2026, and the project's only written position on out-of-tree plugins is an untriaged issue with zero comments [[runner-package-importedby-githubcomllm-dllm-d-routercmdepprunner-go-packages]] [[plugin-package-importedby-githubcomllm-dllm-d-routerpkgeppframeworkinterfaceplug]] [[framework-define-a-panic-isolation-posture-for-plugin-extension-points-issue-210]]. This is a support risk, not a technical blocker — but it means no one will have hit your bug before you.

**No panic isolation exists anywhere in the plugin path.** A panicking plugin takes down the whole process, in-tree or out [[framework-define-a-panic-isolation-posture-for-plugin-extension-points-issue-210]]. Your own `recover()` in `Start()` is not optional.

**Custom surface has a tendency to grow.** The recommendation costs one plugin only if you decline the others. Priority tiers add an admitter [[configuration-llm-d]]; off-cluster multi-replica coordination would add a peer-discovery plugin, since the only one in flight is Kubernetes Pod-watch and still unmerged [[feat-pod-watch-peer-discovery-plugin-by-evacchi-pull-request-2501-llm-dllm-d-rou]]. **Treat "keep the bundle to one plugin" as an explicit design constraint with a named owner**, because each addition multiplies exposure to a framework with no stability guarantees pre-1.0 [[llm-d-routerpkgeppframeworkpluginsreadmemd-at-main-llm-dllm-d-router-github]].

**Genuine unknowns, stated as such.** Nobody has published an end-to-end account of precise prefix-cache routing running against file discovery — the mechanism is verified in code but the deployment is undemonstrated. Nobody has published the hybrid shape either (router in Kubernetes, backends outside); it is reachable through documented chart escape hatches, but it is a capability inference rather than an observed pattern. Cross-replica *session affinity* under Active-Active was never evaluated — the scaling benchmark used independent synthetic requests — so session-pinned workloads must not assume correctness there [[evaluate-llm-d-router-both-epp-and-the-standalone-proxy-scale-limits-issue-1290]]. The `failure_mode_allow` setting in the shipped no-Kubernetes Envoy configuration is unverified, so no one should claim fail-open by default off-cluster [[envoyyaml]]. And repeated-`Upsert` idempotency on file reload — whether re-upserting an unchanged endpoint churns its subscriber — is untested [[file-discovery-34-add-filediscovery-plugin-with-yamljson-file-loading-and-fsnoti]]. Each of these is a test to write, not a reason to hedge the strategy.

**The trade-off you are actually making.** Choosing llm-d for non-pod backends means accepting a discovery seam you must maintain, in exchange for a scheduling stack — precise prefix affinity, load and queue awareness, saturation-gated admission, priority and fairness queuing, prefill/decode profiles, predicted-latency scoring — that simpler routers do not have. If your workload has no shared prefixes, no disaggregation, and no multi-tenant contention, that exchange is a bad deal and a router with native static discovery is the right answer. If it does, the exchange is strongly favourable, and it is made smaller still by the protocol boundary: the proxy talks to whatever picker you point it at, so the plugin is the only thing you would have to rewrite if you ever changed your mind.
